# SuperUser แจกงานอย่างไร

หัวหน้าทีม (agent ที่คุยกับผู้ใช้) ตัดสินใจแจกงานตามลำดับตายตัว 6 ขั้น คือจัดขนาด วางกราฟงาน เลือกระดับ model เขียนใบสั่งงาน ส่งผ่านด่าน แล้วตรวจจนผ่าน ขั้นที่หัวหน้าลืมได้ง่ายมี hook คอยกันไว้ 3 ด่าน หัวหน้าส่งงานที่ไม่ครบไม่ได้ ต้องแก้แล้วส่งใหม่

กฎทั้งหมดในหน้านี้สรุปจากต้นฉบับที่ model อ่านจริง ถ้าต้นฉบับเปลี่ยน ให้ถือต้นฉบับเป็นหลัก:
[`SKILL.md`](../../../plugins/superuser/skills/superuser/SKILL.md) หัวข้อ 2 และ 5 · [`sizing.md`](../../../plugins/superuser/skills/superuser/references/sizing.md) · [`dispatch.md`](../../../plugins/superuser/skills/superuser/references/dispatch.md) · [`brief-template.md`](../../../plugins/superuser/skills/superuser/references/brief-template.md) · ด่านอยู่ใน [`superuser-hook.mjs`](../../../plugins/superuser/hooks/superuser-hook.mjs)

## ภาพรวมเป็น algorithm

```text
แจกงาน(งาน):
  เขียน 3 บรรทัด: เป้า · เสร็จเมื่อ · เสี่ยง
  ขนาด = จัดขนาด(งาน)                                  # ขั้น 1
  ถ้า ขนาด = เล็ก:
      หัวหน้าทำเอง → ตรวจผล → ตอบ                     # ไม่แตกงาน ไม่เปิด playbook
      จบ
  ถ้า ขนาด = XL (หลายวัน · มีคนจริงร่วมทีม):
      ใช้ playbook team-project แทน แล้วจบ
  ถ้า ขนาด = ใหญ่หรือไม่ชัด:
      brainstormer เสนอ 2–3 ทาง → หัวหน้าเลือก 1 ทาง
  กราฟ = วางกราฟงาน(งาน)                               # ขั้น 2
  จด "คาด: ขนาด · ลูกทีม · รอบตรวจ · ระดับ" ในตารางการตัดสินใจ

  ทำซ้ำจนทุกชิ้นเสร็จ:
      พร้อม = ชิ้นที่ไม่ต้องรอชิ้นอื่นแล้ว เรียงตาม rank
      คลื่นนี้ = พร้อม[: min(จำนวนชิ้นที่พร้อม, 8)]
      สำหรับแต่ละ ชิ้น ใน คลื่นนี้:
          ระดับ = เลือกระดับ(ชิ้น, งาน)                  # ขั้น 3
          ใบ = เขียนใบสั่งงาน(ชิ้น)                       # ขั้น 4
      ส่งทุกชิ้นในคลื่นพร้อมกันใน 1 ข้อความ             # ขั้น 5 · ผ่านด่านของ hook
      รอข้อความแจ้งว่าลูกทีมเสร็จ (ไม่วนเปิดไฟล์ดู)
      สำหรับแต่ละ ผลที่กลับมา:
          ให้คะแนน ผ่าน · แก้ · ทำใหม่ เทียบกับ "เสร็จเมื่อ"
          ถ้า ชิ้นเดียวกันตอบ ขาดบริบท หรือ ติด 2 ครั้งติด: หยุดส่งชิ้นนั้น
          ถ้า ไม่ผ่าน: ขึ้น effort ก่อน แล้วค่อยขึ้น model (haiku → sonnet → opus → fable)
                     ส่งให้ลูกทีมตัวใหม่ พร้อมรายงานรอบก่อน
  รวมผล → ตรวจจนผ่าน(งาน)                             # ขั้น 6
  สรุป แล้วเทียบ "คาด" กับที่เกิดจริง
```

## ขั้น 1 · จัดขนาด

หัวหน้าดูจำนวนชิ้นที่ทำได้โดยไม่ต้องรอกัน และขนาดโค้ดรวมที่คาดไว้ ถ้าไม่แน่ใจให้ปัดขึ้น 1 ขนาด

| ขนาด | ดูจาก | ทำอย่างไร |
|---|---|---|
| เล็ก | 1 ชิ้น · โค้ดรวมไม่ถึง 200 บรรทัด · token ไม่เกินราว 50k | หัวหน้าทำเอง |
| กลาง | 2–8 ชิ้น · โค้ดรวมตั้งแต่ 200 บรรทัด | เปิด playbook ที่ตรงที่สุด แตกงานตามกราฟ |
| ใหญ่หรือไม่ชัด | เกิน 8 ชิ้น · ทางเดินยาวเกิน 4 ชิ้น · มีหลายทางให้เลือก | ให้ brainstormer เสนอทางก่อน แล้วค่อยวางกราฟ |
| XL | หลายวัน · มีคนจริงร่วมทีม | playbook `team-project` |

เกณฑ์ 200 บรรทัดมาจาก bench 2026-11-11 ต่ำกว่านี้แตกงานแล้วแพงขึ้นแต่ไม่เร็วขึ้น ส่วนตัวเลขอื่นในตารางเป็นค่าตั้งต้นที่ยังไม่ได้วัด

## ขั้น 2 · วางกราฟงาน

หัวหน้าเขียนตาราง `ชิ้น | ไฟล์ที่แตะ | ขนาด | ต้องรอชิ้นไหน | ลูกทีม · ระดับ` ให้ครบทั้งงานก่อนส่งชิ้นแรก

- **1 หน่วยของงาน = 1 ลูกทีม** เช่น 1 โมดูลพร้อม test ของมัน ห้ามแยกโค้ดกับ test ไปให้ 2 ตัว
- **จำนวนลูกทีมเท่ากับความกว้างของกราฟ** คือจำนวนชิ้นที่ทำพร้อมกันได้ คลื่นแรกส่งไม่เกิน 8 ตัว
- **กราฟกว้าง 1** แปลว่าทุกชิ้นต้องรอชิ้นก่อนหน้า ให้ลูกทีมตัวเดียวทำทั้งสาย เพราะงานที่ต่อกันเป็นทอดถ้าแตกให้หลายตัวทำ ผลแย่ลง 39–70% (Kim et al. 2025 arXiv 2512.08296)
- **2 ชิ้นแตะไฟล์เดียวกัน** ห้ามส่งพร้อมกัน ให้ชิ้นหนึ่งรออีกชิ้น

## ขั้น 3 · เลือกระดับ model และ effort

ทุกชิ้นต้องระบุทั้ง `model` และ `effort` หัวหน้าไล่จากบนลงล่าง แล้วใช้ข้อแรกที่ตรง

| ลำดับ | เงื่อนไข | ระดับ |
|---|---|---|
| 0 | ทั้งงานเสี่ยง (เงิน ภาษี กฎหมาย สุขภาพ ย้อนไม่ได้) | ทุกชิ้น `opus` + `medium` |
| 1 | ชิ้นนั้นแตะเงิน กฎหมาย สุขภาพ สิทธิ์ ข้อความถึงคนนอก หรือโครงสร้างระบบ | `opus` + `medium` |
| 2 | งานตามแบบที่ใบสั่งงานให้ไว้ ตรวจได้ทันที ไม่ถึงคนนอก ไม่ต้องตัดสินใจเอง | `haiku` + `low` |
| 3 | ที่เหลือทั้งหมด | `sonnet` + `medium` |

`opus` + `high` ใช้กับผู้ตรวจรอบสุดท้ายของงานเสี่ยงเท่านั้น ผู้ใช้ตัดสินใจไว้ 2026-11-18 ว่า effort สูงควรอยู่ที่ขั้นตรวจ ไม่ใช่ขั้นสร้าง

## ขั้น 4 · เขียนใบสั่งงาน

ใบสั่งงานยาวไม่เกินราว 15 บรรทัด อ้าง spec เป็นชื่อไฟล์กับหัวข้อ ห้ามคัดลอกเนื้อ spec ลงไป เพราะ bench t5 2026-11-11 พบว่าหัวหน้าใช้ output 50–64% ไปกับการคัดลอก spec ใส่ใบสั่งงาน

```text
เป้า: <ชิ้นนี้ทำอะไร> — ชิ้นที่ 1 จาก <N> ของ <งาน>
ขอบเขต: เขียน <path> · ห้ามแตะ <ชิ้นอื่น> · spec = <ไฟล์> หัวข้อ <N>
เสร็จเมื่อ: `<คำสั่ง test>` ผ่านครบ
กติกา: <ช่องว่างของ spec → ทางที่เลือก เหมือนกันทุกใบ> · ห้ามเพิ่มการตรวจ error หรือเปลี่ยนรูปค่าที่คืน (เช่น object ไม่มี prototype · class) ที่ spec ไม่ได้สั่ง ยกเว้นตรวจ input ที่ขอบระบบ
ขนาด: <N>k
ส่งกลับ: บรรทัดแรกเป็น เสร็จ | เสร็จ มีข้อกังวล | ขาดบริบท | ติด · ไม่เกิน 15 บรรทัด
```

- **ช่องว่างของ spec** คือสิ่งที่ spec ไม่ได้บอก เช่นชนิดข้อมูล ค่าว่าง รูปแบบ หัวหน้าต้องหาให้เจอก่อนแตกงาน เลือกทางที่รับค่าได้กว้างที่สุด แล้วเขียนทางเดียวกันลงทุกใบ
- **ประโยคห้ามตรวจเกิน** ต้องอยู่ทุกใบแบบคำต่อคำ เพราะ t5 เคยตกซ้ำจากลูกทีมที่เพิ่มการตรวจเอง
- **ใบของ reviewer และ brainstormer** ไม่ต้องมี 5 หัวข้อ แต่ยังต้องมี `model` + `effort` และบรรทัด `ขนาด:`

## ขั้น 5 · ส่งผ่านด่านของ hook

hook มี 3 ด่าน: 2 ด่านตรวจคำสั่งเรียก Agent ก่อนทำงาน และ 1 ด่านตรวจตอนหัวหน้าเขียนไฟล์โค้ดเอง ถ้าไม่ผ่าน hook จะตีกลับพร้อมบอกว่าขาดอะไร แล้วหัวหน้าต้องแก้และส่งใหม่

| ด่าน | ตรวจอะไร | ไม่ผ่านเมื่อ |
|---|---|---|
| ด่านแตกงาน (`split_gate`) | ตอนหัวหน้าเขียนไฟล์โค้ด: เขียนเองไปเท่าไรแล้ว | เขียนโค้ดรวมตั้งแต่ 200 บรรทัดแล้วยังไม่ได้ส่งลูกทีมเลย จะถูกกันตอนเริ่มไฟล์โค้ดที่ 2 |
| ด่านส่งงาน (`dispatch_gate`) | คำสั่งเรียก Agent | ไม่มี `model` หรือ `effort` · ใบสั่งงานขาดหัวข้อไทยที่ขึ้นต้นบรรทัด (เป้า · ขอบเขต · เสร็จเมื่อ · กติกา · ส่งกลับ) · ไม่มีประโยคห้ามตรวจเกิน (ใบของ reviewer และ brainstormer ไม่ตรวจหัวข้อและประโยคนี้) |
| ด่านโควตา | บรรทัด `ขนาด: Nk` เทียบกับโควตาที่เหลือของบัญชี | ไม่มีบรรทัด `ขนาด:` · หรือขนาด × 1.2 เกินโควตาที่เหลือ |

ด่านโควตาทำงานเฉพาะตอนที่เครื่องมีข้อมูลโควตาที่อายุไม่เกิน 1 ชั่วโมง (status line จดไว้ และมีขนาดถังใน `accounts.json`) ถ้าไม่มีข้อมูล ด่านนี้จะปล่อยผ่าน

ปิดด่านส่งงานได้ใน `.claude/superuser/config.json` ด้วย `{"modules": {"dispatch_gate": false}}`

## ขั้น 6 · ตรวจจนผ่าน

| งาน | ผู้ตรวจ | รอบสูงสุด |
|---|---|---|
| โค้ดที่มี test และไม่เสี่ยง | หัวหน้ารัน test ให้เห็นว่าตกก่อนแก้และผ่านหลังแก้ แล้วส่ง `reviewer` ตัวใหม่ 1 รอบ ตรวจแค่ diff | รอบ 2 เฉพาะเมื่อรอบแรกเจอข้อระดับสูง |
| งานกลางที่ไม่เข้าแถวบน | `reviewer` ตัวใหม่ทุกรอบ (`sonnet` + `medium`) | 3 |
| งานใหญ่หรือเสี่ยง | `reviewer` ตัวใหม่ทุกรอบ รอบสุดท้ายของงานเสี่ยงใช้ `opus` + `high` | 5 |

ใบสั่งงานถึง `reviewer` มีแค่ผลงานกับเกณฑ์ ไม่ใส่ความเห็นของหัวหน้า ถ้าครบรอบแล้วยังไม่ผ่าน หัวหน้าหยุดแล้วรายงาน ไม่วนต่อเอง

## วัดผลการแจกงาน

[`scripts/evals/speed/`](../../../scripts/evals/speed/README.md) รันงานชุดเดียวกันทั้งแบบมีและไม่มี superuser แล้วตรวจด้วย test ที่ agent มองไม่เห็น ตาราง **ทีมรายรอบ** บอก model/effort ของลูกทีมทุกตัว และคอลัมน์ **เรียก Agent** บอกว่าด่านตีกลับกี่ครั้ง

| วันที่ | งาน | รุ่น | เรียก Agent ต่อรอบ | ตีกลับ | test ที่ซ่อนไว้ |
|---|---|---|---|---|---|
| 2026-11-18 | t5 | 3.50.1 | 19 (1 รอบแตกงานน้อยกว่า ได้ 7) | 12 (รอบนั้น 3) | 32/32 ทั้ง 6 รอบ |
| 2026-11-18 | t5 | 3.50.2 | 7 | 0 | 32 · 32 · 28 (3 รอบ) |
| 2026-11-19 | t5 | 3.50.2 + แก้การตรวจเกิน spec | 7 | 0 | 32/32 ทั้ง 5 รอบ |

ข้อควรระวังเวลาอ่านตัวเลข: ตัวเลขการตีกลับเชื่อได้ เพราะด่านให้ผลเหมือนเดิมทุกครั้ง ส่วนอัตราผ่าน test ยังเชื่อได้น้อย เพราะวัดแค่ t5 งานเดียว รอบละ 3–5 ครั้ง
