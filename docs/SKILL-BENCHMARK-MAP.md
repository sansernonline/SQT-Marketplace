# การตัดสินใน skill ที่วัดเป็นตัวเลขได้ ของทั้ง 286 skill

_ตรวจ 2026-11-08 ที่ main `2d922f5` · ไม่ได้รันอะไรที่เสียเงิน · ตารางเต็มทีละแถวอยู่ใน [`skill-benchmark/`](skill-benchmark/)_

**ข้อสรุป:** จาก 286 skill (และ agent `reviewer` อีก 1 ตัว) มี 87 ตัวที่วัดเป็นตัวเลขได้ทันทีด้วยของที่มีอยู่แล้ว และอีก 120 ตัวมีกลไกแล้ว ขาดแค่ชุดเคสที่รู้คำตอบ · ส่วนที่ผู้ใช้ถามถึงคือการแจกงานของ superuser แยกได้ 18 การตัดสิน แต่วัดได้ทันทีแค่ 3 เรื่อง เพราะ log งานจริงไม่จด token ที่คาด effort และจำนวนข้อที่ผู้ตรวจเจอ · งานแรกที่ถูกที่สุดจึงเป็นการให้ hook จดค่าเหล่านี้ ไม่ใช่การเขียนชุดทดสอบใหม่

เอกสารนี้ต่างจาก [`SKILL-SCORECARD.md`](SKILL-SCORECARD.md) ตรงที่ scorecard วัดว่า skill **เปิดถูกจังหวะไหม และช่วยให้งานผ่านมากขึ้นไหม** ส่วนเอกสารนี้ไล่ดู **ข้างใน** skill ว่าตัดสินอะไรบ้าง (จัดขนาด · เลือก model · จัดระดับความรุนแรง · คิดเงิน · ตรวจผ่านหรือไม่ผ่าน) แล้วแต่ละเรื่องเทียบกับคำตอบที่ถูกได้อย่างไร

## 5 · ข้อจำกัดของแผนที่นี้

- ลูกทีมอ่าน SKILL.md เฉพาะช่วงที่มีตัวเลขและเกณฑ์ ไม่ได้อ่านทุกไฟล์เต็ม · skill แบบดัชนี 9 ตัวใน software-company (เช่น `fintech-payments` `healthcare-systems`) ได้ระดับ `ไม่คุ้ม` เพราะไม่ได้เปิด `references/` ที่เก็บเกณฑ์จริง ระดับจริงอาจสูงกว่านี้
- ตัวเลขเกณฑ์ที่คัดมาจาก SKILL.md (เบี้ย ภาษี เงินช่วยเหลือ ค่าธรรมเนียมแพลตฟอร์ม) ยังไม่ได้เทียบกับแหล่งทางการรอบนี้ ใช้วันหมดอายุใน `scripts/check/expiry.json` ตามเดิม
- self-test ส่วนใหญ่เทียบกับค่าที่ผู้เขียนสคริปต์คิดเอง ยกเว้น CRC ของ PromptPay และหลักตรวจเลขบัตรประชาชน · "test ผ่าน" จึงบอกว่าโค้ดตรงกับความเข้าใจของผู้เขียน ยังไม่ได้บอกว่าตรงกับกฎจริง
- path ที่ขึ้นต้น `L/` ในตาราง superuser ชี้ไป `.claude/superuser/` ในโฟลเดอร์หลัก ซึ่งไม่อยู่ใน git
- ขนาดชุดเคสที่เสนอในตาราง (เช่น 20 เคส 10 บิล) เป็นข้อเสนอ ไม่ใช่ของที่มีอยู่
