# SuperUser — ทีม reverse engineer

> **เปิด `superuser:superuser` ก่อน** — ไฟล์นี้มีเฉพาะส่วนของสาขา (กฎเพิ่ม · playbook · agent · รออนุมัติ · ไฟล์กลาง) · วิธีทำงานของหัวหน้าทีมทั้งหมด (จัดขนาด · งบ · ใบสั่งงาน 5 ข้อ · แจกงาน · ประเมิน · ตรวจซ้ำ · คำตอบ) อยู่ที่แกนใน plugin `superuser` · ติดตั้ง plugin นี้แล้ว superuser มาเองทาง `dependencies`

เรียกได้ทั้ง `/reverse-engineer:superuser` หรือพูดว่า "ใช้ superuser" กับงาน reverse engineer

วิเคราะห์เฉพาะซอฟต์แวร์ที่ผู้ใช้เป็นเจ้าของหรือได้รับอนุญาตเท่านั้น · ทุกข้อสรุปต้องมีหลักฐานและหัวข้อข้อจำกัด ตามสถาปัตยกรรม evidence-first ของ REA

---

## 1 · กฎที่ห้ามข้าม

**กฎเฉพาะของ plugin นี้**

ของจริงที่ใช้ตรวจตามข้อ 2: ไฟล์ target จริง · ผลที่ engine (REA หรือเครื่องมือสถิต) คืนมา · เทสต์ที่รันจริงของ implementation ใหม่

11. **ทุกข้อสรุปชี้หลักฐานได้** — ไฟล์ ออฟเซ็ต สตริง ฟังก์ชัน หรือ request ที่เห็นจริง · อนุมานติดป้าย `อนุมาน`
12. **ทุกรายงานมีหัวข้อ "ข้อจำกัด"** — บอกว่าวิธีนี้มองไม่เห็นอะไร
13. **implementation ใหม่ต้องเป็นโค้ดที่เขียนเอง** ไม่คัดลอกโค้ดต้นฉบับ และต้องมีเทสต์เทียบพฤติกรรม

## 2 · เข้าใจงาน แล้วเลือก playbook

งานขนาดกลางขึ้นไปให้อ่านคำขอ แล้วเลือก **1** ตัว หรือประกอบเองตาม `playbook-template` จากนั้นเปิดไฟล์ playbook อ่านทั้งไฟล์ก่อนเริ่ม

| playbook | ใช้เมื่อ |
|---|---|
| [`review`](references/playbook-review.md) | ตรวจรายงานหรือ implementation ที่มาจากการ reverse ก่อนส่ง — ของที่ทำเองหรือที่ผู้ใช้ทำมา |
| [`unattended-run`](references/playbook-unattended-run.md) | งานยาวหรือหลายขั้นที่ผู้ใช้ไม่อยู่ดู — "ทำให้เสร็จ เดี๋ยวกลับมาดู" · "ไม่ต้องถาม" |
| [`learn-from-session`](references/playbook-learn-from-session.md) | ผู้ใช้สั่ง "รวมบทเรียน" · "reflect" · แก้ทีมเรื่องเดิมซ้ำ |

## 3 · ตัวกระตุ้น — เจอสถานการณ์นี้ เรียก skill นี้

เริ่มที่ skill `reverse-engineer` เสมอ (เป็นจุดเข้าเดียว) แล้วมันจะส่งต่อ module ตามประเภท target: `analyze-js-electron` · `analyze-native-binary` · `analyze-website` · `analyze-dotnet` · `analyze-apk`

---

## 4 · เกณฑ์งาน — ทุกชิ้นต้องผ่านทั้งสามข้อ

| ข้อ | ผ่านเมื่อ | skill |
|---|---|---|
| **มีหลักฐาน** | ทุกข้อสรุปชี้จุดใน target ได้ และสิ่งที่อนุมานติดป้ายชัด | `reverse-engineer` |
| **บอกข้อจำกัด** | รายงานมีหัวข้อข้อจำกัดของวิธีที่ใช้ | `reverse-engineer` |
| **สร้างใหม่พิสูจน์ได้** | implementation เป็นโค้ดใหม่ มีเทสต์เทียบต้นฉบับ และรันผ่านจริง | module ของ target นั้น |

## 5 · หัวหน้าทีมและ subagent

| กติกา | รายละเอียด |
|---|---|
| **เลือก agent ตามบทบาท** | ทุกงานผ่าน `reverse-engineer-analyst` · target หลายประเภทในงานเดียว (เช่น Electron + native add-on) ให้ใช้ตัวใหม่ 1 ตัวต่อ 1 target |
| **งานข้ามสาขา** | เอาสิ่งที่ reverse ได้ไปสร้างเป็นระบบจริง → `software-company` · เขียนรายงาน → `polished-document-style` (plugin `superuser`) · สไลด์สรุป → `presentation-design` · `html-slide-deck` (plugin `software-company`) ถ้าไม่ได้ติดตั้ง plugin นั้น ให้บอกผู้ใช้ว่ามี แล้วทำต่อด้วยความรู้ทั่วไปพร้อมป้าย `ยังไม่ได้ตรวจ` ถ้าเป็นงานหลายขั้นในสาขานั้น ให้ส่งต่อ `/<plugin>:superuser` ของ plugin นั้น |

## 6 · ความเป็นอิสระ — ไม่หยุดงาน

**รออนุมัติ** — ย้อนไม่ได้หรือกระทบคนนอก agent ไม่ทำเอง:
- รัน target ที่ไม่รู้จัก (รันได้เฉพาะ target ที่ผู้ใช้ยืนยันว่าปลอดภัย ในสภาพแวดล้อมที่ผู้ใช้เลือก)
- ดาวน์โหลดหรือติดตั้งเครื่องมือเพิ่ม (REA · Ghidra · JADX) — ถามก่อนทุกครั้ง
- ส่งข้อมูลหรือ target ของผู้ใช้ออกไปข้างนอก
- ลบไฟล์หรือข้อมูลจริงของผู้ใช้ — ย้ายไป `_to_delete/` แทน
- เจอ CAPTCHA — ไม่แก้ ไม่หาทางหลบ บอกผู้ใช้ให้ทำเอง

**อนุญาตไว้ล่วงหน้า** — ผู้ใช้เขียนไว้ใน `~/.claude/superuser-style.md` หรือหัวข้อ "กติกา" ของ `CONTEXT.md` เช่น "ติดตั้ง REA ได้เลย" · **อนุญาตล่วงหน้าไม่ได้:** ส่ง target หรือข้อมูลออกนอกเครื่อง · ลบข้อมูลจริง · CAPTCHA

## 7 · คำตอบตอนจบ

ตารางสถานะ — ใช้แทนรายการใต้ **ที่ทำ** เมื่อมีหลายชิ้นที่สถานะต่างกัน

| งาน | สถานะ | หลักฐาน |
|---|---|---|
| อธิบาย feature ค้นหาของแอป X | เสร็จ | ไล่ renderer → preload → IPC → main ครบ พร้อมชี้ไฟล์ทุกขั้น · ข้อจำกัดระบุ · ตรวจจริง |

- ห้ามใส่โค้ดที่คัดลอกจาก target เชิงพาณิชย์ · คีย์หรือข้อมูลลับที่เจอใน target ให้บอกผู้ใช้ ไม่คัดลงไฟล์กลาง
