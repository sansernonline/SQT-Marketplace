# agent-patterns — 6 รูปแบบการทำงานของทีม agent

ใช้คู่กับ `superuser` ทุก plugin หัวหน้าทีมเลือกรูปแบบตอนวางแผน แล้วบอกในรายงานตอนจบว่าใช้แบบไหน
ไฟล์นี้เหมือนกันทุก plugin ใน SQT-Marketplace ต้นฉบับอยู่ที่ plugin `superuser` ให้แก้ที่นั่นแล้วรัน `node scripts/sync/sync-superuser.mjs`

---

## 1 · เลือกแบบไหน

| รูปแบบ | ทำอย่างไร | ใช้เมื่อ | ไม่ต้องใช้เมื่อ |
|---|---|---|---|
| **Planning** | วางแผนทั้งหมดก่อน → ทำทีละข้อ | งานเกิน 3 ขั้น · งานที่ผู้ใช้ไม่อยู่ดู | คำถามเดียว · แก้จุดเดียว |
| **ReAct** | คิด → ทำ → ดูผล → วนจนเสร็จ | ทุกขั้นที่ลงมือจริง (รันโค้ด · ค้นข้อมูล · คำนวณ) | — ใช้เสมอ |
| **Reflection** | ทำเสร็จ → อีกตัวตรวจ → แก้ | ก่อนส่งงานที่คนอื่นจะใช้ · งานที่พลาดแล้วเสียหาย | ร่างที่ผู้ใช้จะแก้เองต่อทันที |
| **Multi-Agent** | หลาย agent คนละงาน ส่งต่อเป็นสาย | งานที่ต้องใช้หลายความถนัด · ชิ้นงานแยกกันได้ | งานเล็กที่ agent เดียวทำจบ |
| **Mixture-of-Agents (MoA)** | หลาย agent ทำงานเดียวกันคนละมุม → รวม | ตัดสินใจสำคัญ · ทางแรกอาจผิด · ต้องการมุมที่ขัดกัน | งานที่มีคำตอบถูกข้อเดียวและตรวจได้ |
| **Reranker** | ให้คะแนนหลายชิ้น → เลือกชิ้นที่ตรงที่สุด | มีแหล่ง ไฟล์ หรือตัวเลือกมากเกินอ่านหมด | มีไม่เกิน 3 ชิ้น |

**สูตรปกติของงานหนึ่งชิ้น:** Planning → (ReAct ทุกขั้น) → Reflection ก่อนส่ง ถ้างานใหญ่ให้เพิ่ม Multi-Agent ถ้ามีทางเลือกสำคัญให้เพิ่ม MoA และถ้าข้อมูลเยอะให้เพิ่ม Reranker

## 2 · Planning — วางแผนก่อน แล้วทำทีละข้อ

1. playbook ที่เลือกคือแผน ให้คัดขั้นตอนลง todo ตรงตัว ถ้าไม่มี playbook ที่ตรง ให้เขียนแผนตามโครง เข้าใจ → วางแผน → ลงมือ → พิสูจน์ → รายงาน
2. ทุกข้อในแผนมี "เสร็จเมื่อ" ที่ตรวจได้ ข้อไหนเขียนเงื่อนไขไม่ได้ให้แตกให้เล็กลง
3. ทำทีละข้อตามลำดับ ถ้าระหว่างทางเจอว่าแผนผิด ให้แก้แผนก่อน แล้วจดเหตุผลในบันทึกการตัดสินใจ ห้ามทำนอกแผนเงียบ ๆ
4. ถ้างานยาวหรือหลายวัน ให้เขียนแผนลงไฟล์ (`docs/BUILD-PLAN.md` หรือ `CONTEXT.md`) ไม่เก็บไว้ในแชต

กับดัก: แผนละเอียดเกินจนไม่ได้ลงมือ ทั้งที่แผน 3 ข้อก็พอสำหรับงานครึ่งชั่วโมง

## 3 · ReAct — คิด → ทำ → ดูผล วนจนเสร็จ

1. **คิด** — ขั้นนี้จะทำอะไร คาดว่าจะเห็นผลอะไร (เขียน 1 บรรทัด)
2. **ทำ** — ลงมือ 1 การกระทำ: รันคำสั่ง · ค้นเว็บ · อ่านไฟล์ · คำนวณ
3. **ดูผล** — อ่านผลจริงแล้วเทียบกับที่คาด ถ้าตรงก็ไปขั้นถัดไป ถ้าไม่ตรงให้กลับไปคิดใหม่จากผลที่เห็น
4. ถ้าวนด้วยวิธีเดิม 3 รอบแล้วไม่ผ่าน ให้หยุด แล้วเปลี่ยนวิธี หรือใส่สถานะ "ติด" แล้วไปข้ออื่น

กับดัก: ทำหลายอย่างรวดเดียวแล้วค่อยดูผล พอพังก็ไม่รู้ว่าพังที่ไหน · เชื่อผลที่ "น่าจะ" ได้ โดยไม่เปิดดูผลจริง

## 4 · Reflection — ทำเสร็จ → อีกตัวตรวจ → แก้

1. คนทำส่งงานพร้อมเกณฑ์ตรวจ (เกณฑ์ 3 ข้อในหัวข้อ 4 ของ `superuser` ของ plugin นั้น)
2. **คนตรวจต้องเป็น subagent ตัวใหม่ที่ไม่เห็นงานมาก่อน** เพราะการตรวจตัวเองในบริบทเดิมจะเห็นแต่สิ่งที่ตั้งใจทำ ไม่เห็นสิ่งที่ทำจริง
3. คนตรวจส่งกลับเป็นรายการ: ปัญหา · ชี้จุดในงานได้ · หลักฐาน · ระดับ (ต้องแก้ · ควรแก้)
4. หัวหน้าทีมยืนยันทุกข้อก่อนสั่งแก้ ข้อที่ยืนยันไม่ได้ให้ทิ้ง
5. แก้แล้วตรวจซ้ำได้อีกไม่เกิน 1 รอบ ถ้ายังไม่ผ่านให้ใส่ใน "ค้างอยู่" พร้อมเหตุผล

ระดับโมเดลของคนตรวจ: เท่าคนทำหรือสูงกว่า 1 ระดับ ไม่ใช้ตัวเล็กตรวจงานของตัวใหญ่

## 5 · Multi-Agent — หลาย agent คนละงาน ส่งต่อเป็นสาย

1. หัวหน้าทีมแบ่งงานเป็นชิ้น 1 ชิ้นต่อ 1 agent ตามบทบาท แล้วบอกว่าชิ้นนี้รับอะไรจากชิ้นก่อน และส่งอะไรให้ชิ้นถัดไป
2. ส่งต่อด้วยไฟล์ ไม่ส่งต่อด้วยความจำ: agent A เขียนผลลงไฟล์ → agent B อ่านไฟล์นั้น
3. ชิ้นที่ไม่พึ่งกันให้ส่งพร้อมกัน ส่วนชิ้นที่พึ่งกันให้เรียงตามสาย
4. หัวหน้าทีมตรวจผลของทุกชิ้นก่อนส่งต่อ เพราะถ้าชิ้นก่อนผิด ชิ้นหลังจะผิดตามทั้งสาย
5. ห้ามให้ 2 agent เขียนไฟล์เดียวกันพร้อมกัน

กับดัก: แบ่งงานละเอียดเกินจนเสียเวลาส่งต่อมากกว่าทำ · agent ตัวหลังเดาว่าตัวก่อนทำอะไร แทนที่จะอ่านไฟล์

## 6 · Mixture-of-Agents (MoA) — งานเดียวกัน คนละมุม แล้วรวม

1. ตั้งโจทย์เดียวกันให้ 3 ตัว (งานแพงไม่เกิน 4) และต้องตั้งใจใส่ความต่าง: มุมมองต่างกัน หรือข้อจำกัดต่างกัน หรือระดับโมเดลต่างกัน
2. เขียนเกณฑ์ตัดสินก่อนปล่อย เกณฑ์อยู่กับหัวหน้าทีม ไม่ส่งให้ตัวที่ทำงาน
3. ส่งทุกตัวพร้อมกัน แต่ละตัวเขียนผลลงที่ของตัวเอง
4. **รวม (aggregate)** — ตัวรวมเป็น agent ใหม่ที่อ่านทุกคำตอบ ให้คะแนนตามเกณฑ์ เลือกฐาน 1 ตัว แล้วยืมข้อดีของตัวอื่นมาเสริม ทุกจุดที่ขัดกันต้องบอกว่าเลือกฝั่งไหนเพราะอะไร
5. ผลรวมผ่าน Reflection อีกรอบก่อนส่ง

ต้นทุน: ใช้แรง 3–5 เท่าของทำครั้งเดียว จึงใช้เฉพาะเรื่องที่เลือกผิดแล้วแพง

## 7 · Reranker — ให้คะแนน แล้วเลือกชิ้นที่ตรงที่สุด

1. **รวบรวมกว้าง** — ค้นหรือ list มาก่อน 10–30 ชิ้น (แหล่งข้อมูล · ไฟล์ · ตัวเลือก · ประกาศงาน · สินค้า)
2. **ตั้งเกณฑ์ 3–4 ข้อ** ให้คะแนนข้อละ 0–3 เช่น ตรงคำถาม · น่าเชื่อถือ (ทางการ > มาตรฐาน > ผู้ดูแลเครื่องมือ > อื่น ๆ) · ใหม่พอ · ครบ
3. **ให้คะแนนทีละชิ้น** — ถ้าชิ้นเยอะ ให้ subagent ระดับเล็กให้คะแนนรอบแรก พอรอบท้ายเหลือ 5–8 ชิ้น ให้ระดับกลางหรือใหญ่ให้คะแนนซ้ำ
4. **เลือก top-k** (ปกติ 3–5) แล้วอ่านเต็มเฉพาะชิ้นที่เลือก ชิ้นที่ทิ้งไม่ต้องอ่าน
5. แสดงตารางคะแนนในรายงานหรือภาคผนวก: ชิ้น · คะแนนแต่ละเกณฑ์ · รวม · เลือกหรือไม่ เพื่อให้คนอ่านเห็นว่าทำไมเลือกชิ้นนี้

ใช้คู่กับกฎ "≥ 3 แหล่งยืนยันตรงกัน" ของ `superuser` โดย Reranker เลือกแหล่ง ส่วนกฎ 3 แหล่งตัดสินว่าเชื่อได้ไหม
ถ้าเป็นระบบที่ผู้ใช้สร้าง (RAG ในแอปจริง) ให้ใช้ reranker แบบโมเดลจริงตาม `llm-engineering` ของ software-company เพราะไฟล์นี้พูดถึงวิธีทำงานของทีม agent เท่านั้น
