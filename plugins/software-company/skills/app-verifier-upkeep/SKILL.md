# app-verifier-upkeep — ดูแลมือและตาให้ตรงกับแอป

> verify skill ที่บอกขั้นตอนผิด อันตรายกว่าไม่มี เพราะ agent จะเชื่อแล้วรายงานว่าผ่าน

ใช้กับ skill ที่สร้างจาก [`app-verifier-setup`](../app-verifier-setup/SKILL.md)

## ขั้นตอน

1. **ทำรายการฟีเจอร์จริง** — จาก route · เมนู · command list · SRS ล่าสุด เทียบกับ `features/README.md` แล้วแยกเป็น ตรงกัน · หายจากแผนที่ · ไม่มีในแอปแล้ว
2. **อ่านโค้ดแบบขนาน** — ส่ง agent `qa-tester` ตัวใหม่หนึ่งตัวต่อกลุ่มฟีเจอร์ (ไม่เกิน 5 ฟีเจอร์ต่อตัว) อ่านอย่างเดียว ให้รายงานว่าขั้นตอนในไฟล์ `features/*.md` ยังตรงกับโค้ดหรือไม่ พร้อมไฟล์:บรรทัด · ใช้ [`parallel-split-and-merge`](../parallel-split-and-merge/SKILL.md)
3. **ขับแอปจริงรอบเดียว** — agent ตัวเดียว เปิดแอปด้วย `scripts/start` แล้วทำทุกฟีเจอร์ตามไฟล์ บันทึก ผ่าน · ล้ม · ภาพหน้าจอ · ขั้นที่ล้ม
4. **แก้เฉพาะสิ่งที่พิสูจน์แล้ว** — ทุกการแก้ต้องมีหลักฐานจากข้อ 2 หรือ 3 · ฟีเจอร์ที่ล้มเพราะแอปพังจริง ไม่ใช่เพราะขั้นตอนผิด → แยกเป็นรายงานบั๊ก (`bug-report-template`) อย่าแก้ขั้นตอนให้ผ่าน
5. **เพิ่มฟีเจอร์ที่หายจากแผนที่** ตามรูปแบบเดิม และรันจริงอย่างน้อยหนึ่งครั้งก่อนบันทึก
6. **รวมการแก้เป็นชุดเดียว** — commit เดียวหรือ PR เดียว ข้อความบอกจำนวน ตรงกัน · แก้ · เพิ่ม · ลบ · บั๊กที่พบ
7. `status-report` ประเภท `ตรวจ`

## สิ่งที่ห้ามทำ

- แก้ขั้นตอนให้ผ่านทั้งที่แอปทำงานผิด — ซ่อนบั๊กไว้ในเครื่องมือตรวจ
- ลบฟีเจอร์ออกจากแผนที่เพราะทดสอบยาก
- แตก PR เป็นหลายชิ้นเล็ก ๆ — คนรีวิวต้องเห็นภาพรวมของการเปลี่ยนในรอบเดียว
