# principle · data shape first — ได้รูปข้อมูลก่อน โค้ดจะตามมาเอง

> โค้ดที่ยุ่งส่วนใหญ่ไม่ได้มาจาก logic ยาก แต่มาจากรูปข้อมูลที่ผิดตั้งแต่ต้น
> ได้ type และโครงข้อมูลที่ถูก if ส่วนใหญ่จะหายไปเอง

## ก่อนเขียนบรรทัดแรก ตอบให้ได้ 4 ข้อ

| ถาม | ได้อะไร |
|---|---|
| ข้อมูลหลักของงานนี้คืออะไร มี field อะไร | type หรือ schema ที่เขียนออกมาจริง ไม่ใช่อยู่ในหัว |
| สถานะที่เป็นไปได้มีกี่แบบ | union หรือ enum ตัวเดียว แทน boolean หลายตัวที่ขัดกันได้ |
| ข้อมูลเข้ามาจากนอกระบบตรงไหน | จุดเดียวที่แปลง (parse) และตรวจ แล้วข้างในเชื่อ type |
| ใครเขียนข้อมูลนี้พร้อมกันบ้าง | แยกให้ไม่ต้องแชร์ก่อน · ใช้ล็อกหรือคิวเฉพาะเมื่อต้องมีผู้เขียนคนเดียวจริง ๆ |

## กฎ

- **สถานะที่ผิดต้องสร้างไม่ได้** — `{ status: 'paid', paidAt }` ไม่ใช่ `isPaid` + `paidAt?` ที่ขัดกันได้
- **ค่าที่มีความหมายมี type ของมัน** — `OrderId` ไม่ใช่ `string` เปล่า · เงินเก็บเป็นจำนวนเต็มหน่วยเล็กสุด (สตางค์)
- **กฎธุรกิจอยู่ในโครงสร้าง ไม่กระจายเป็น if** — ตาราง map · state machine · lookup แทน `if (type === ...)` ซ้ำหลายไฟล์
- **ตรวจที่ขอบ เชื่อข้างใน** — CLI · config · request · ไฟล์ · API ภายนอก แปลงด้วย schema ที่ขอบ ข้างในไม่ต้องเช็ก null ซ้ำ
- **ไม่โกหก compiler** — ไม่ใช้ `any` · `as` · `!` เพื่อให้ผ่าน · `switch` ต้องครบทุกกรณีโดยมีตัวตรวจ (exhaustive check)
- **type มาจากแหล่งเดียว** — สร้างจาก schema ฐานข้อมูลหรือ OpenAPI ไม่เขียนซ้ำด้วยมือ
- **ความต้องการใหม่ขัดกับรูปเดิม** — ออกแบบใหม่เหมือนรู้ตั้งแต่วันแรก ไม่แปะ flag เพิ่ม

## ในงาน

playbook `feature` และ `new-project` เขียนรูปข้อมูลลง todo ก่อนขั้นลงมือ · ตารางใหม่ใช้ `database-design` · API ใช้ `api-conventions`

## ไม่ต้องทำเมื่อ

สคริปต์ใช้ครั้งเดียว หรือแก้ภายในฟังก์ชันเดียวที่ไม่เปลี่ยนรูปข้อมูล
