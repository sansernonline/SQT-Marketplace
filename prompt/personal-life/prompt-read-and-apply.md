# prompt-read-and-apply — อ่านแล้วใช้ให้เป็น: paper เอกสารอังกฤษ เล่าให้ทีมฟัง

ยังไม่ได้ทดสอบจริง

ใช้คู่กับ plugin `personal-life` (หมวดเรียนรู้) · ไฟล์นี้รวม prompt 3 ฉบับ · 1 ฉบับ = 1 งาน

## วิธีใช้

1. เปิด Claude Code, Codex CLI หรือ Gemini CLI ที่**โฟลเดอร์เรียนรู้** (โฟลเดอร์เดียวใช้ได้ทุกฉบับ)
2. กรอกช่อง "ผู้ใช้กรอก" ของฉบับที่จะทำ · ไม่รู้ปล่อยว่างได้
3. วางทั้งไฟล์ แล้วพิมพ์ต่อท้ายว่าจะทำฉบับไหน เช่น `ทำข้อ 1`

**กฎการทำงาน (agent ต้องทำตาม):** เปิด skill `superuser` ของ plugin `personal-life` ก่อนเริ่ม แล้วทำตาม playbook ที่ฉบับนั้นระบุทุกขั้น · กฎร่วม (อ่าน `.claude/superuser/CONTEXT.md` ก่อนเริ่ม · ถามแบบเลือกคำตอบตอนเริ่มและตอนจบ ไม่หยุดถามกลางทาง · บันทึกการตัดสินใจ · รายการ "รออนุมัติ" · รอบเรียนรู้ · สรุปงานตอนจบ) อยู่ในแกนของ plugin `superuser` ที่ skill นั้นใช้ร่วม ไม่เขียนซ้ำที่นี่ · ช่อง "ผู้ใช้กรอก" ที่ยังว่างและจุดที่ต้องเลือก → ถามรวมครั้งเดียวก่อนเริ่ม แบบเลือกคำตอบ ทุกตัวเลือกมีหลักฐาน ไม่ได้คำตอบ → ใส่ `(รอยืนยัน)` แล้วทำต่อ · เปิดผ่านคำสั่ง skill ไม่ได้ → อ่าน `skills/<ชื่อ>/SKILL.md` ในโฟลเดอร์ plugin แทน · ไม่มี agent ที่อ้าง → ใช้ agent ทั่วไปพร้อมเปิด `agents/<ชื่อ>.md` · หาไม่เจอทั้ง 2 ทาง → ข้ามชิ้นนั้น ทำส่วนอื่นให้จบ แล้วรายงานว่าติด

**วนจนเสร็จ (agent loop):** ทุกฉบับวน ทำ → ตรวจ → แก้ → ตรวจซ้ำ จนผ่านทุกข้อที่ฉบับนั้นต้องมี · ตรวจด้วยหลักฐานจริง (เปิดไฟล์ · รันคำสั่ง · เทียบแหล่ง) ไม่ใช่คำบอกของตัวที่ทำ · รอบตรวจใช้ `reviewer` ตัวใหม่ทุกรอบ · ไม่ผ่าน → แก้ที่ต้นเหตุแล้วตรวจซ้ำทั้งข้อเดิมและจุดที่แก้ · เหลือแค่ข้อระดับต่ำ → ปิดได้แล้วลงรายงาน · ครบเพดานรอบ (งานกลาง 3 · งานใหญ่หรืองานเสี่ยง 5) ยังไม่ผ่าน → ติดป้าย `ติด` ทำส่วนอื่นให้จบ แล้วรายงานข้อที่เหลือ · รายละเอียดอยู่ใน skill `superuser` กฎข้อ 3

**ขอบเขต:** ข้อมูลเวอร์ชัน การเปลี่ยนแปลง และหลักสูตรสอบ อ่านจากแหล่งทางการ (release notes · changelog · exam guide) รอบนี้ ติดวันที่ตรวจ · โค้ดตัวอย่างต้องรันผ่านจริงก่อนส่ง · การสมัครสอบ ซื้อคอร์ส หรือจ่ายเงิน อยู่ใน "รออนุมัติ"

**ภาษาและไฟล์:** เขียนตาม `human-writing` · ชื่อไฟล์ตามที่ skill กำหนด (เช่น `radar/reports/YYYY-Www.md` · `cert/<exam-code>-plan.md` · `notes/<short-title>.md`) ไม่กำหนด → ใช้ชื่อในตาราง

| 2 | อ่านเอกสารอังกฤษยาก ๆ ให้เข้าใจ | — (เล็ก ทำเลย) | ตอบในแชต · บันทึกลง `notes/` ถ้าขอ |

## 1. จาก paper หรือบทความ สู่โค้ดที่รันได้

playbook `paper-to-practice` · agent `tech-mentor` · skill `paper-to-practice` · `english-tech-reading`
**ผลลัพธ์:** `notes/<short-title>.md` · `examples/<short-title>/` (โค้ดขั้นต่ำที่รันได้)

### ข้อมูล (ผู้ใช้กรอก)

- paper / RFC / บทความ (ลิงก์ หรือ path PDF):
- อยากเข้าใจเพื่อทำอะไร:
- ภาษาโปรแกรมที่อยากให้เขียนตัวอย่าง:

### ต้องมีในผลงาน

1. สรุปภาษาคน 1 หน้า: ปัญหา → วิธีของเขา → ผลที่อ้าง → ข้อจำกัด
2. คำศัพท์ / สมการสำคัญ อธิบายเป็นภาษาไทย
3. ตัวอย่างโค้ดเล็กที่สุดที่แสดงแนวคิดหลัก รันผ่านจริง พร้อมคำสั่งรัน
4. ส่วนที่ตัวอย่างไม่ได้ทำ (ต่างจาก paper ตรงไหน)
5. นำไปใช้กับงานของผู้ใช้ได้ไหม อย่างไร

## 2. อ่านเอกสารอังกฤษยาก ๆ ให้เข้าใจ

skill `english-tech-reading` · งานเล็ก ทำเลยไม่ต้องเปิด playbook
**ผลลัพธ์:** คำอธิบายในแชต · ผู้ใช้ขอเก็บ → `notes/<short-title>.md`

### ข้อมูล (ผู้ใช้กรอก)

- ข้อความ (error message · ย่อหน้าเอกสาร · ส่วนของ RFC):
- ทำอะไรอยู่ตอนเจอ:

### ต้องมีในผลงาน

1. แปลความหมายเป็นภาษาไทยที่อ่านรู้เรื่อง
2. แยกโครงประโยคหรือส่วนของ error (ตรงไหนบอกอะไร)
3. คำบังคับ MUST / SHOULD / MAY แปลว่าบังคับแค่ไหน (ถ้ามี)
4. ต้องทำอะไรต่อ 1–3 ข้อ

## 3. สรุปเรื่องที่เรียนไปเล่าให้ทีมฟัง

playbook `paper-to-practice` (ขั้น 1–4 ตามเดิม · ขั้น 5 เขียนเป็นโครงเล่าแทนบันทึก) · agent `tech-mentor` · skill `paper-to-practice` · `answer-shape`
**ผลลัพธ์:** `talks/<short-title>/outline.md` (โครงเล่า + คำถามที่น่าจะโดนถาม) · `talks/<short-title>/demo/` (โค้ด demo ที่รันได้) · **รออนุมัติ:** ส่งเข้ากลุ่มทีม · โพสต์ในช่องทางของบริษัท

### ข้อมูล (ผู้ใช้กรอก)

- เรื่องที่จะเล่า (ลิงก์ · หรือโน้ตเดิมใน `notes/`):
- คนฟังเป็นใคร รู้เรื่องนี้แค่ไหน:
- เวลาที่ได้ (เช่น 15 หรือ 30 นาที):
- รูปแบบ (สไลด์ · เปิดโค้ดสด · เอกสารให้อ่านเอง):

### ต้องมีในผลงาน

1. ประเด็นเดียวที่อยากให้คนฟังจำได้ เขียน 1 ประโยค
2. โครงเล่าตามเวลา: นาที · หัวข้อ · สิ่งที่โชว์
3. demo เล็กที่รันผ่านจริง พร้อมคำสั่งรัน และแผนสำรองถ้า demo พังตอนเล่า (ภาพหน้าจอผลรัน)
4. คำถามที่น่าจะโดนถาม 3–5 ข้อ พร้อมคำตอบสั้น · ข้อที่ยังตอบไม่ได้เขียนว่ายังไม่รู้
5. ข้อสรุป "ทีมเราควรใช้ไหม" แยกข้อเท็จจริงออกจากความเห็น

### กฎเฉพาะฉบับนี้

- ไม่ใส่โค้ด ข้อมูลลูกค้า หรือค่าลับของบริษัทลงในไฟล์ที่จะแชร์ · ต้องยกตัวอย่างจากงานจริง → ใช้ข้อมูลสมมติ
