# prompt-keep-up — ตามเทคโนโลยีให้ทัน: เรดาร์ เวอร์ชันใหญ่ ของใหม่ตามกระแส

ใช้คู่กับ plugin `personal-life` (หมวดเรียนรู้) · ไฟล์นี้รวม prompt 3 ฉบับ · 1 ฉบับ = 1 งาน

## วิธีใช้

1. เปิด Claude Code, Codex CLI หรือ Gemini CLI ที่**โฟลเดอร์เรียนรู้** (โฟลเดอร์เดียวใช้ได้ทุกฉบับ)
2. กรอกช่อง "ผู้ใช้กรอก" ของฉบับที่จะทำ · ไม่รู้ปล่อยว่างได้
3. วางทั้งไฟล์ แล้วพิมพ์ต่อท้ายว่าจะทำฉบับไหน เช่น `ทำข้อ 1`

**กฎการทำงาน (agent ต้องทำตาม):** เปิด skill `superuser` ของ plugin `personal-life` ก่อนเริ่ม แล้วทำตาม playbook ที่ฉบับนั้นระบุทุกขั้น · กฎร่วม (อ่าน `.claude/superuser/CONTEXT.md` ก่อนเริ่ม · ถามแบบเลือกคำตอบตอนเริ่มและตอนจบ ไม่หยุดถามกลางทาง · บันทึกการตัดสินใจ · รายการ "รออนุมัติ" · รอบเรียนรู้ · สรุปงานตอนจบ) อยู่ใน skill นั้นที่เดียว ไม่เขียนซ้ำที่นี่ · ช่อง "ผู้ใช้กรอก" ที่ยังว่างและจุดที่ต้องเลือก → ถามรวมครั้งเดียวก่อนเริ่ม แบบเลือกคำตอบ ทุกตัวเลือกมีหลักฐาน ไม่ได้คำตอบ → ใส่ `(รอยืนยัน)` แล้วทำต่อ · เปิดผ่านคำสั่ง skill ไม่ได้ → อ่าน `skills/<ชื่อ>/SKILL.md` ในโฟลเดอร์ plugin แทน · ไม่มี agent ที่อ้าง → ใช้ agent ทั่วไปพร้อมเปิด `agents/<ชื่อ>.md` · หาไม่เจอทั้ง 2 ทาง → ข้ามชิ้นนั้น ทำส่วนอื่นให้จบ แล้วรายงานว่าติด

**วนจนเสร็จ (agent loop):** ทุกฉบับวน ทำ → ตรวจ → แก้ → ตรวจซ้ำ จนผ่านทุกข้อที่ฉบับนั้นต้องมี · ตรวจด้วยหลักฐานจริง (เปิดไฟล์ · รันคำสั่ง · เทียบแหล่ง) ไม่ใช่คำบอกของตัวที่ทำ · รอบตรวจใช้ `reviewer` ตัวใหม่ทุกรอบ · ไม่ผ่าน → แก้ที่ต้นเหตุแล้วตรวจซ้ำทั้งข้อเดิมและจุดที่แก้ · เหลือแค่ข้อระดับต่ำ → ปิดได้แล้วลงรายงาน · ครบเพดานรอบ (งานกลาง 3 · งานใหญ่หรืองานเสี่ยง 5) ยังไม่ผ่าน → ติดป้าย `ติด` ทำส่วนอื่นให้จบ แล้วรายงานข้อที่เหลือ · รายละเอียดอยู่ใน skill `superuser` กฎข้อ 2

**ขอบเขต:** ข้อมูลเวอร์ชัน การเปลี่ยนแปลง และหลักสูตรสอบ อ่านจากแหล่งทางการ (release notes · changelog · exam guide) รอบนี้ ติดวันที่ตรวจ · โค้ดตัวอย่างต้องรันผ่านจริงก่อนส่ง · การสมัครสอบ ซื้อคอร์ส หรือจ่ายเงิน อยู่ใน "รออนุมัติ"

**ภาษาและไฟล์:** เขียนตาม `human-writing` · ชื่อไฟล์ตามที่ skill กำหนด (เช่น `radar/reports/YYYY-Www.md` · `cert/<exam-code>-plan.md` · `notes/<short-title>.md`) ไม่กำหนด → ใช้ชื่อในตาราง

| # | งาน | playbook | ได้ไฟล์ |
|---|---|---|---|
| 1 | เรดาร์เทคโนโลยีประจำสัปดาห์ | `tech-radar` | `radar/reports/YYYY-Www.md` |
| 2 | ไลบรารีหลักออกเวอร์ชันใหญ่หรือเลิกสนับสนุน ต้องอัปเกรดไหม | `tech-radar` (ขั้น 2–5 กับไลบรารีเดียว) | `radar/deep-dives/<library>-<version>.md` |
| 3 | ของใหม่ที่ทุกคนพูดถึง ควรลงแรงเรียนไหม | `tech-radar` (ขั้น 2–5 กับเรื่องเดียว) | `radar/evaluations/<ชื่อ>.md` + `examples/<ชื่อ>-trial/` |

ใช้ต่อกัน: เรดาร์เจอเรื่อง "ต้องทำ" ที่เป็นเวอร์ชันใหญ่ → 1 → 2 · เรดาร์เจอของใหม่ที่น่าสนใจ → 1 → 3 แล้วคำตัดสิน "เรียนตอนนี้" → `prompt-start-learning.md` ฉบับ 1 · ตรวจก่อนใช้ → `prompt-start-learning.md` ฉบับ 4

## 1. เรดาร์เทคโนโลยีประจำสัปดาห์

playbook `tech-radar` · agent `tech-mentor` · skill `tech-radar`
**ผลลัพธ์:** `radar/reports/YYYY-Www.md` · อัปเดต `radar.md` (รายการที่ติดตาม)

### ข้อมูล (ผู้ใช้กรอก)

- ไลบรารี / framework / เครื่องมือที่ติดตาม (หรือให้อ่านจาก `radar.md` / ไฟล์ dependency ของโปรเจกต์):
- โปรเจกต์ที่ใช้ของเหล่านี้ (path):
- เจาะลึกโปรเจกต์ไหนเป็นพิเศษไหม:

### ต้องมีในผลงาน

1. ตาราง 3 กลุ่ม: **ต้องทำ** (กระทบโปรเจกต์ · มีช่องโหว่ · เลิกสนับสนุน) · **ควรรู้** · **ข้ามได้**

## 2. ไลบรารีหลักออกเวอร์ชันใหญ่หรือเลิกสนับสนุน ต้องอัปเกรดไหม

playbook `tech-radar` (ขั้น 2–5 ทำกับไลบรารีเดียวแบบเจาะลึก) · agent `tech-mentor` · skill `tech-radar` · `english-tech-reading`
**ผลลัพธ์:** `radar/deep-dives/<library>-<version>.md` · **ไม่แก้โค้ดในโปรเจกต์จริง** · งานอัปเกรดจริงส่งต่อ plugin `software-company` (`prompt-existing-dev.md` ฉบับ 3)

- [ ] อนุญาตให้ลองอัปเกรดในสำเนาแยก (git worktree หรือสำเนาใน `_to_delete/`) แล้วรัน test · ไม่แตะโค้ดจริง ไม่ commit

### ข้อมูล (ผู้ใช้กรอก)

- ไลบรารี / framework และเวอร์ชันที่ใช้อยู่:
- เวอร์ชันใหม่หรือประกาศที่เห็น (ลิงก์):
- โปรเจกต์ที่ใช้ (path):
- มี test อัตโนมัติไหม / คำสั่งรัน test:

### ต้องมีในผลงาน

1. วันหมดการสนับสนุนของเวอร์ชันที่ใช้อยู่ จากหน้า release หรือ lifecycle ทางการ ติดวันที่ตรวจ
2. breaking change ที่กระทบโค้ดของผู้ใช้จริง — ค้นในโปรเจกต์แล้วบอกจำนวนจุดและไฟล์ · แยก "เจอในโค้ดแล้ว" ออกจาก "อาจกระทบ"
3. ทางเลือก 3 ทาง: อัปเกรดตอนนี้ · รอรุ่นย่อยถัดไป · ยังไม่อัปเกรด พร้อมความเสี่ยงของแต่ละทาง และแนะนำ 1 ทาง
4. ติ๊กอนุญาตไว้ → ผลลองอัปเกรดในสำเนาแยก: รัน test จริง ผ่านกี่ข้อ ไม่ผ่านกี่ข้อ · ไม่ติ๊ก → เขียนว่ายังไม่ได้ลอง
5. ขั้นแรกที่ลงมือได้เลย

### กฎเฉพาะฉบับนี้

- ไม่มี test อัตโนมัติ → บอกว่าความเสี่ยงสูงขึ้นเพราะตรวจผลไม่ได้ ห้ามสรุปว่า "อัปเกรดได้ปลอดภัย"

## 3. ของใหม่ที่ทุกคนพูดถึง ควรลงแรงเรียนไหม

playbook `tech-radar` (ขั้น 2–5 ทำกับเรื่องเดียว) · agent `tech-mentor` · skill `tech-radar` · `answer-shape`
**ผลลัพธ์:** `radar/evaluations/<ชื่อ>.md` (คำตัดสิน) · `examples/<ชื่อ>-trial/` (ทดลองเล็ก) · **รออนุมัติ:** สมัครบริการหรือแพ็กเกจที่เสียเงินเพื่อทดลอง

### ข้อมูล (ผู้ใช้กรอก)

- ชื่อเทคโนโลยี / เครื่องมือ:
- ได้ยินจากไหน (ลิงก์):
- งานที่ทำอยู่และ stack ที่ใช้:
- เวลาที่ยอมลงทดลอง:

### ต้องมีในผลงาน

1. มันแก้ปัญหาอะไร 1 ย่อหน้า จากเอกสารทางการ ไม่ใช่จากโพสต์รีวิว
2. สถานะจริง: เวอร์ชันล่าสุด · ออกมานานแค่ไหน · ใครดูแล · สัญญาอนุญาตการใช้งาน (license) — ติดวันที่ตรวจ
3. ทดลองเล็ก 1–2 ชั่วโมง: ตัวอย่างที่รันผ่านจริง เทียบกับวิธีที่ผู้ใช้ทำอยู่
4. คำตัดสิน 1 ใน 3: **เรียนตอนนี้** · **ติดตามในเรดาร์** (เพิ่มลง `radar.md`) · **ข้าม** พร้อมเหตุผลที่ผูกกับงานของผู้ใช้
5. ถ้า "เรียนตอนนี้": ขั้นถัดไปที่ชัด

### กฎเฉพาะฉบับนี้

- ตัวเลขเรื่องความเร็วหรือประสิทธิภาพที่มาจากผู้พัฒนาเอง → บอกว่าเป็นตัวเลขของผู้พัฒนา ไม่ใช่ผลวัดของเรา
