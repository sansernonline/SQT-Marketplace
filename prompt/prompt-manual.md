# prompt-manual — คู่มือผู้ใช้และคู่มือฝึกอบรม

ใช้คู่กับ plugin `software-company` · ไฟล์นี้รวม prompt 2 ฉบับ แต่ละฉบับสร้างเอกสารหนึ่งชุด · ไฟล์แยกรายฉบับอยู่ในโฟลเดอร์ `prompt-manual/`

## วิธีใช้

วางทั้งไฟล์ใน Claude Code, Codex CLI หรือ Gemini CLI ที่รากโฟลเดอร์โปรเจกต์ แล้วพิมพ์ต่อท้ายว่าจะทำฉบับไหน เช่น `ทำทั้งหมด` หรือ `ทำข้อ 3 และ 4`

**กฎการทำงานของไฟล์รวม (agent ต้องทำตาม):**

1. ทำทีละฉบับตามลำดับในตาราง ข้ามฉบับที่ผู้ใช้ไม่ได้สั่ง
2. **จบแต่ละฉบับให้หยุด** อัปเดตตารางสถานะใน `docs/BUILD-PLAN.md` ตามข้อ "รายงานสถานะ" ในกฎร่วม แล้วแสดงในคำตอบ: แถวที่เปลี่ยน · ค้างอยู่ · ฉบับถัดไป — รอผู้ใช้พิมพ์ `ต่อ` หรือสั่งแก้ **ห้ามเริ่มฉบับถัดไปเอง**
3. ช่องที่เขียนว่า "ผู้ใช้กรอก" ของฉบับไหนยังว่าง ให้ถามตอนเริ่มฉบับนั้น ไม่ต้องถามทั้งหมดตั้งแต่ต้น
4. ฉบับหลังใช้ผลของฉบับก่อนเป็นข้อมูลนำเข้า — อ่านจากดิสก์ใหม่ทุกครั้ง (ผู้ใช้อาจแก้ไปแล้ว)

| # | เอกสาร | ได้ไฟล์ |
|---|---|---|
| 1 | คู่มือผู้ใช้ปลายทาง (User Manual) แยกตามบทบาท | `docs/user-manual-<บทบาท>.md` หนึ่งไฟล์ต่อบทบาท · ภาพหน้าจอใน `docs/figures/<บทบาท>/` |
| 2 | คู่มือฝึกอบรมการใช้งาน (Training Guide) | `docs/training/` |

## กฎร่วมทุกฉบับ

- อ่าน `docs/BUILD-PLAN.md` (หัวข้อ `สถานะล่าสุด`) และ `docs/README.md` ก่อน (ถ้ามี) — สถานะงาน รหัสโปรเจกต์ ขนาดงาน ธีมสี อยู่ที่นั่น · ไม่มีให้ถามเฉพาะค่าที่ขาด
- **ที่เก็บไฟล์** (ตาม skill `project-doc-set`): `ref/` ไฟล์ที่ได้รับมา อ่านอย่างเดียว · `docs/` เอกสารที่เราเขียน (รูปใน `docs/figures/`) · `mockup/` UI mockup · `qa/` test case ผลทดสอบ รายงานบั๊ก · `assets/` โลโก้ ไอคอน · `_to_delete/` ของชั่วคราว — สร้างโฟลเดอร์เมื่อมีของจริงเท่านั้น
- อ่านไฟล์จากดิสก์ก่อนแก้ · ไฟล์ยาวเกิน 300 บรรทัดอ่านเฉพาะช่วง · ต้องเปิดเกิน 3 ไฟล์เพื่อตอบเรื่องเดียว ให้ส่ง subagent
- ข้อมูลไม่พอหรือเอกสารขัดกัน → รวมเป็นคำถามท้ายคำตอบแล้ว **หยุด** ห้ามเดา ห้ามแต่งตัวเลข/ชื่อ/วันที่
- ตัวย่อทุกตัวกางเต็มครั้งแรก เช่น Software Requirements Specification (SRS) · ของชั่วคราวลง `_to_delete/`
- ตั้งชื่อไฟล์ตาม skill `document-naming` · รูปแบบเอกสารตาม `polished-document-style`
- **รายงานสถานะทุกครั้งที่จบฉบับ** (ใช้ skill `status-report` ถ้ามี) ลง `docs/BUILD-PLAN.md` — ไม่มีไฟล์ให้สร้าง · แก้เฉพาะสองหัวข้อนี้ ไม่แตะหัวข้ออื่นในไฟล์:
  - `## สถานะล่าสุด` **เขียนทับทั้งหัวข้อ**: วันที่เวลา · ตาราง `| รายการ | ประเภท | สถานะ | ผลตรวจ | ค้าง / หมายเหตุ |` ครบทุกเอกสารและงานของโปรเจกต์ (รายการที่รอบนี้ไม่ได้แตะ คัดลอกค่าเดิม) · ตามด้วย **ค้างอยู่** (คำถามที่ต้องมีคนตอบ พร้อมบอกว่าถามใคร ไม่มีเขียน `ไม่มี`) และ **ถัดไป** (ไม่เกิน 3 อย่าง)
  - สถานะเอกสาร: `ยังไม่เริ่ม` · `DRAFT` · `REVIEW` — `APPROVED` ผู้ใช้ตั้งเองเท่านั้น · ผลตรวจ: `ผ่าน — <หลักฐาน>` · `ไม่ผ่าน — <อะไร>` · `ยังไม่ตรวจ` — **ห้ามเขียน `ผ่าน` ถ้าไม่ได้ตรวจหรือรันจริง**
  - `## ประวัติสถานะ` เพิ่มหนึ่งบรรทัดบนสุด: `วันที่ เวลา · งาน · สถานะ · ผล · ค้างกี่ข้อ`
- คำตอบตอนจบ: แสดงเฉพาะแถวที่เปลี่ยน + ค้างอยู่ + ถัดไป แล้วบอกว่าตารางเต็มอยู่ใน `docs/BUILD-PLAN.md` — ไม่คัดลอกเนื้อเอกสารกลับมา

## 1. คู่มือผู้ใช้ปลายทาง (User Manual) แยกตามบทบาท

agent `technical-writer` · skill `polished-document-style` · `i18n-and-locale` · `branded-document-design` (ตอน render) · `e2e-testing-patterns` (ถ่ายภาพหน้าจอ)
**ต้องมีก่อน:** โปรแกรมที่รันได้ (คำสั่งรันใน `docs/README.md` หรือที่ผู้ใช้ระบุ) · `docs/srs.md` (รู้ว่ามีบทบาทอะไร)
**ผลลัพธ์:** `docs/user-manual-<บทบาท>.md` หนึ่งไฟล์ต่อบทบาท · ภาพหน้าจอใน `docs/figures/<บทบาท>/`

### บทบาทที่ทำคู่มือ (ผู้ใช้กรอก หรือให้ agent เสนอจาก SRS แล้วรอยืนยัน)

- บทบาท · งานหลักที่บทบาทนี้ทำ · ภาษาของผู้อ่าน (ไทย/อังกฤษ):
- ผู้อ่านคุ้นกับคอมพิวเตอร์แค่ไหน:

### ลำดับ

1. รันแอปตามคำสั่ง — ถ้ารันไม่ได้ให้หยุดและบอก **ห้ามเขียนคู่มือจาก mockup หรือจินตนาการ**
2. เตรียมข้อมูลตัวอย่างและบัญชีทดสอบของแต่ละบทบาท (ในสภาพแวดล้อมทดสอบเท่านั้น ห้ามใช้ข้อมูลจริงของใคร)
3. ทำรายการ "งานของบทบาทนี้" จาก FR ที่บทบาทนั้นใช้ แล้วลองทำทีละงานในแอปจริง
4. เขียนคู่มือตามโครงด้านล่าง ถ่ายภาพหน้าจอด้วยเครื่องมือ (Playwright) ทุกขั้นที่ผู้อ่านอาจหลง พร้อมคำบรรยายใต้ภาพ
5. ตรวจเองรอบสอง: ทำตามคู่มือที่เขียนเองทีละข้อ จุดไหนทำแล้วไม่ตรงที่เขียน ให้แก้คู่มือ หรือลงคำถามค้างว่าเป็นบั๊ก

### โครงคู่มือ

1. **เริ่มต้นใช้งาน** — เข้าระบบอย่างไร · หน้าแรกมีอะไร (ภาพเดียวพร้อมหมายเลขชี้) · ศัพท์ที่ต้องรู้ไม่เกิน 10 คำ
2. **งานที่ทำบ่อย** — ต่อหนึ่งงาน: เป้าหมายหนึ่งบรรทัด · ก่อนเริ่มต้องมีอะไร · ขั้นตอนเลขลำดับ (หนึ่งการกระทำต่อข้อ) · ภาพ · ผลที่ควรเห็น
3. **งานที่ทำนาน ๆ ครั้ง** — รูปแบบเดียวกัน
4. **แก้ปัญหาเบื้องต้น** — ข้อความที่ผู้ใช้อาจเจอจริง (ดึงจากแอป) → ความหมาย → ทำอย่างไร → เมื่อไรต้องติดต่อใคร
5. **คำถามที่พบบ่อย** — เฉพาะที่มาจากงานจริง ไม่แต่ง
6. **ภาคผนวก** — คำศัพท์ · ทางลัด · ช่องทางขอความช่วยเหลือ (ผู้ใช้ให้ข้อมูล ไม่มีเว้นช่องให้เติม)

### กฎเฉพาะฉบับนี้

- ใช้ชื่อปุ่ม เมนู ข้อความบนจอตรงทุกตัวอักษร · ภาษาง่าย ประโยคสั้น ไม่ใช้ศัพท์เทคนิคที่ผู้ใช้ไม่ต้องรู้
- ห้ามอธิบายฟีเจอร์ที่บทบาทนี้มองไม่เห็น · สิทธิ์ที่ต่างกันเขียนแยกไฟล์ ไม่ปนกัน
- ภาพหน้าจอห้ามมีข้อมูลส่วนบุคคลจริง

## 2. คู่มือฝึกอบรมการใช้งาน (Training Guide)

agent `technical-writer` + `ux-designer` (ลำดับการเรียนรู้) · skill `polished-document-style` · `presentation-design` (ถ้าทำสไลด์) · `branded-document-design`
**ต้องมีก่อน:** `docs/user-manual-<บทบาท>.md` (ถ้ามี — ใช้เป็นแหล่งขั้นตอน ไม่คัดลอกซ้ำ ให้อ้างหัวข้อ) · โปรแกรมที่รันได้
**ผลลัพธ์:** `docs/training/` — `training-plan.md` · `facilitator-guide.md` · `exercises.md` (+ `quiz.md` ถ้าเลือก)

### ข้อมูลการอบรม (ผู้ใช้กรอก)

- ผู้เรียน (บทบาท จำนวนคน พื้นฐาน):
- เวลาที่มี (กี่ชั่วโมง / กี่ครั้ง) และรูปแบบ (ในห้อง / ออนไลน์):
- เป้าหมายหลังอบรม (ผู้เรียนต้อง "ทำอะไรได้"):
- มีสภาพแวดล้อมทดสอบ/ข้อมูลตัวอย่างให้ฝึกไหม:
- ต้องมีสไลด์ไหม: ☐ ใช่ ☐ ไม่ · ต้องมีแบบทดสอบไหม: ☐ ใช่ ☐ ไม่

### เอกสารที่ได้

| ไฟล์ | เนื้อหา |
|---|---|
| `training-plan.md` | วัตถุประสงค์ที่วัดได้ ("ผู้เรียนสร้าง … ได้ภายใน … นาที") · กลุ่มเป้าหมายและความรู้ก่อนเรียน · ตารางเวลาเป็นช่วง (หัวข้อ · วิธี บรรยาย/สาธิต/ลงมือ · นาที) · สิ่งที่ต้องเตรียม (บัญชีทดสอบ เครื่อง ข้อมูลตัวอย่าง) · เกณฑ์ว่า "ผ่านการอบรม" |
| `facilitator-guide.md` | ต่อหนึ่งช่วง: เป้าหมาย · สิ่งที่ผู้สอนพูด/สาธิต (ทีละขั้น) · จุดที่ผู้เรียนมักพลาดและวิธีช่วย · คำถามชวนคิด · เวลา · ข้อควรระวังตอนสาธิต (เช่น ห้ามใช้ข้อมูลจริง) |
| `exercises.md` | แบบฝึกหัดเรียงจากง่ายไปยาก: โจทย์เป็นสถานการณ์จริงของผู้เรียน · ข้อมูลที่ให้ · ผลที่ควรได้ · แนวเฉลยสั้น ๆ · เวลา |
| `quiz.md` (เลือก) | ข้อสอบวัดตามวัตถุประสงค์ทีละข้อ เฉลย เกณฑ์ผ่าน — ข้อสอบต้องทำได้จากสิ่งที่สอนจริงเท่านั้น |

### วิธีทำ

1. ตั้งวัตถุประสงค์จากงานจริงของบทบาท (จากคู่มือ/FR) — ทุกหัวข้อที่สอนต้องผูกกับวัตถุประสงค์อย่างน้อยหนึ่งข้อ ไม่มีผูก = ตัดทิ้ง
2. ลำดับ: งานที่ใช้ทุกวันก่อน → ขยายไปงานที่ซับซ้อน · แต่ละช่วงไม่เกิน 45 นาทีต่อก้อน และมีช่วงลงมือทำอย่างน้อยครึ่งหนึ่ง
3. ลองทำแบบฝึกหัดทุกข้อในแอปจริงก่อนเขียน — ข้อที่ทำไม่ได้หรือผลต่างจากที่เขียน → แก้หรือลงคำถามค้าง
4. ถ้าเลือกสไลด์: ทำตาม `presentation-design` หนึ่งสไลด์หนึ่งข้อความ (ไฟล์สไลด์เป็นงานแยก ขอผู้ใช้ก่อน)

### กฎเฉพาะฉบับนี้

- ไม่แต่งตัวเลขเวลา/จำนวนคนที่ผู้ใช้ไม่ได้ให้ → `(รอยืนยัน)`
- ข้อมูลตัวอย่างต้องเป็นข้อมูลสมมติเท่านั้น
