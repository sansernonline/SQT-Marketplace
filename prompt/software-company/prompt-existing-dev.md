# prompt-existing-dev — รับแอปที่มีอยู่แล้วมาพัฒนาต่อ

ใช้คู่กับ plugin `software-company` · ไฟล์นี้รวม prompt 4 ฉบับ · ใช้เมื่อได้รับแอปที่ใช้งานอยู่แล้ว (เขียนเองหรือรับช่วงจากทีมอื่น) แล้วต้องเพิ่มฟีเจอร์ อัปเกรด หรือทำให้เร็วขึ้น · ต้องการแค่เอกสาร → `prompt-existing-code.md` · ต้องการแค่ test → `prompt-test-automation.md`

## วิธีใช้

วางทั้งไฟล์ใน Claude Code, Codex CLI หรือ Gemini CLI ที่รากโฟลเดอร์โปรเจกต์ แล้วพิมพ์ต่อท้ายว่าจะทำฉบับไหน เช่น `ทำข้อ 1 และ 2`

<!-- rules:begin -->
**กฎการทำงาน (agent ต้องทำตาม):** เปิด skill `superuser` ก่อนเริ่ม แล้วทำตาม playbook ที่ฉบับนั้นระบุ (ไม่ระบุ → `project-docs`) · กฎร่วม (ถามครั้งเดียว · ทำจบรอบเดียว · ตัดสินใจเอง · รายงานสถานะ) อยู่ใน skill `superuser` และ playbook ที่เดียว · ตัดสินใจเองและสถานะลง `docs/BUILD-PLAN.md` (ยังไม่มี → สร้าง) · ไฟล์ทำงานของ SuperUser (`CONTEXT.md` · `IMPROVEMENTS.md` · log) อยู่ใต้ `.claude/superuser/` ตาม `project-doc-set` ข้อ 1 ไม่วางที่รากโปรเจกต์ · ใช้ skill และ agent ของ plugin `software-company` เท่านั้น (ไม่ใช้ตัวชื่อซ้ำของ plugin อื่น) · เปิด skill ไม่ได้ → อ่าน `skills/<ชื่อ>/SKILL.md` ของ plugin · ไม่มี agent → ใช้ agent ทั่วไปพร้อมเปิด `agents/<ชื่อ>.md` · หาไม่เจอทั้ง 2 ทาง → ข้ามชิ้นนั้น ทำส่วนอื่นให้จบ แล้วรายงานว่าติด · ไม่มี `learning-reviewer` → ข้ามรอบเรียนรู้แล้วจดไว้
<!-- rules:end -->

**ภาษาและรูป:** ทุกเอกสารเขียนตาม skill `human-writing` · รูปในเอกสารส่งมอบใช้ `diagram-figures` · Mermaid (`software-diagrams`) ใช้ได้เฉพาะเอกสารภายในทีม

**แอปที่มีอยู่แล้ว (ใช้ทุกฉบับ):** `docs/` และ `qa/` อยู่ที่รากโปรเจกต์ · README และ CHANGELOG อยู่ใน repo ของแอป · รากโปรเจกต์เป็น repo เดียวกับแอป → เอกสารเข้า branch เดียวกับโค้ด · ก่อนรันแอปหรือ seed ให้ชี้ที่เก็บข้อมูล (เช่น `DATA_DIR` · connection string) ไปที่ `_to_delete/` ห้ามรันกับข้อมูลจริง · คำสั่ง test ที่ repo ประกาศไว้พัง → รายงานผลของคำสั่งนั้นตรงตัว แล้วบอกคำสั่งที่ใช้แทนแยกบรรทัด · ห้ามมีรหัสผ่านหรือค่าลับในเอกสารและภาพ แม้เป็นบัญชีทดสอบ · ไม่มี `stack-*` ที่ตรงภาษา → ข้ามแล้วบอกในรายงาน

### ข้อมูลแอป (ผู้ใช้กรอก ใช้ร่วมทุกฉบับ)

- แอปนี้ทำอะไรโดยย่อ:
- path ของ repo · branch ที่ใช้เป็นฐาน:
- วิธีรันที่รู้อยู่ (เว้นว่างได้):
- เอกสารที่มี: ☐ SRS/FSD ☐ `docs/as-is/` ☐ README ☐ ไม่มีเลย
- ผู้ที่ตอบคำถามเรื่องระบบได้ (บทบาท ไม่ต้องใส่ชื่อ):

**ทุกฉบับที่แก้โค้ด:** ทำบน branch ใหม่ชื่อตามฉบับ (`feature/…` · `upgrade/…` · `perf/…`) · commit บนเครื่องเท่านั้น · ไม่ push · ไม่ merge เข้า branch หลัก · รัน test ทั้งชุดก่อนและหลังแก้ แล้วรายงานตัวเลขจริงทั้ง 2 รอบ · สั่งหลายฉบับ → ทำฉบับ 1 ก่อนบน branch ฐานโดยไม่ commit · ฉบับที่แก้โค้ดแต่ละฉบับแตก branch จาก branch ฐาน ไม่ต่อกัน และ commit สคริปต์ตรวจแอปจากฉบับ 1 เป็นก้อนแรก · รายงานว่า branch รวมกันได้ไหม

## 1. รับช่วงโค้ด: รันได้บนเครื่อง และรู้ว่าแก้ตรงไหน

agent `solution-architect` (อ่านอย่างเดียว) + `developer` · skill `code-orientation` · `app-verifier-setup` · `context-budget` · `/software-company:legacy-onboard` (เมื่อไม่มีเอกสารเลยและต้องรับ change request ต่อ)
**ผลลัพธ์:** `docs/ONBOARDING-NOTES.md` — **ไม่แก้โค้ดของแอป** (ไฟล์ตั้งค่าบนเครื่องที่ไม่เข้า git แก้ได้ · สคริปต์ตรวจแอปและ skill ที่ `app-verifier-setup` สร้าง เพิ่มได้แต่ยังไม่ commit · ตรวจว่า test runner ของ repo ไม่เก็บสคริปต์นั้นไปรันด้วย)

### หัวข้อที่ต้องมี

1. **วิธีรันที่ลองแล้วได้จริง** — คำสั่งทีละบรรทัด · สิ่งที่ต้องติดตั้งพร้อมเวอร์ชัน · ตัวแปรสภาพแวดล้อม (ชื่ออย่างเดียว ไม่ใส่ค่า) · รันไม่ขึ้น → เขียนว่าติดตรงไหน พร้อมข้อความ error
2. **ผลรัน test เดิม** — จำนวนผ่าน/ไม่ผ่าน/ข้าม · ไม่มี test → เขียนว่าไม่มี
3. **แผนที่โค้ด** ไม่เกิน 10 บรรทัดตาม `code-orientation` — จุดเริ่มโปรแกรม · โฟลเดอร์หลัก · ชั้นข้อมูล · ระบบภายนอก
4. **ถ้าจะแก้เรื่อง X ไปที่ไหน** — ตาราง 5–10 แถวของงานที่น่าจะได้รับบ่อย
5. **จุดเสี่ยง** — ส่วนที่ไม่มี test · โค้ดที่หลายส่วนใช้ร่วมกัน · ค่าลับที่ฝังในโค้ด (ชี้ไฟล์:บรรทัด ไม่คัดค่า)
6. คำถามถึงผู้ที่รู้ระบบ

### กฎเฉพาะฉบับนี้

- ยังไม่มีวิธีให้ agent รันแอปแล้วดูผลเอง → ทำ `app-verifier-setup` ก่อนเขียนหัวข้อ 1 (รวมขั้นให้ agent ตัวใหม่ลองใช้ skill ตรวจแอป 1 ครั้ง)
- ทุกคำสั่งในหัวข้อ 1 ต้องรันจริงแล้ว · ที่ยังไม่ได้รัน → ติดป้าย `ยังไม่ได้ลอง`

## 2. เพิ่มหรือเปลี่ยนฟีเจอร์ในแอปเดิม

agent `system-analyst` + `developer` + `qa-tester` · skill `blast-radius` · `targeted-fix` · `testing-standards` · `stack-*` ตามภาษา · `principle-secure-by-default`
**ต้องมีก่อน:** `docs/ONBOARDING-NOTES.md` (ฉบับ 1) · คำขอที่อนุมัติแล้วใน `docs/change/CR-*.md` (`prompt-change.md` ฉบับ 1) หรือคำอธิบายในช่องข้างล่าง
**ผลลัพธ์:** โค้ด + test · เอกสารที่ถูกแตะแก้ครบในรอบเดียว (SRS · FSD · `docs/as-is/` · คู่มือ ที่มีอยู่)

- [ ] อนุญาตให้แก้โค้ดตามแผน (commit บนเครื่องเท่านั้น บน branch แยก `feature/…` · ไม่ push · ไม่ merge เข้า branch หลัก)

### ฟีเจอร์ (ผู้ใช้กรอก · มี CR แล้วใส่แค่เลข CR)

- เลข CR หรือคำอธิบาย:
- เกณฑ์ว่าเสร็จ (ผู้ใช้ทำอะไรได้ที่ตอนนี้ทำไม่ได้):
- ข้อจำกัดที่ยังไม่แน่ใจ เช่น ค่าสูงสุด (เว้นว่าง = agent เลือกเองแล้วติด `(รอยืนยัน)`):

### ลำดับ

1. หาจุดที่ต้องแก้ แล้วทำ `blast-radius` — ส่วนอื่นที่ได้รับผลกระทบทั้งหมด
2. เขียน test ของพฤติกรรมใหม่ให้แดงก่อน · ส่วนที่กระทบแต่ยังไม่มี test → เขียน test จับพฤติกรรมเดิมไว้ก่อนแก้ · พฤติกรรมเดิมที่ดูเป็นบั๊ก → ไม่ล็อกด้วย test จดเป็นคำถามถึงผู้รู้ระบบ และไม่แก้ในงานนี้
3. แก้โค้ดน้อยที่สุดที่ทำให้ test เขียว โดยใช้แบบเดียวกับโค้ดรอบข้าง ไม่จัดโครงใหม่ระหว่างทาง
4. รัน test ทั้งชุด · เปิดแอปลองตามเกณฑ์ว่าเสร็จ
5. แก้เอกสารที่ถูกแตะ · เขียนสรุปการเปลี่ยนลง `CHANGELOG.md` ใน repo หัวข้อ "ยังไม่ปล่อย" ตามรูปแบบใน `project-bootstrap` ข้อ 3 (ไม่มีไฟล์ → สร้าง)

### กฎเฉพาะฉบับนี้

- ไม่ติ๊กอนุญาต → ทำแค่ขั้น 1 และร่างแผนแก้ไว้ใน `docs/change/` แล้วหยุด
- CR ยังเป็น `เสนอ` → ทำแค่ขั้นวิเคราะห์และแผน แล้วหยุดเฉพาะฉบับนี้ ลงคำถามค้าง
- เจอสิ่งที่อยากจัดโครงใหม่ → จดไว้เสนอเป็นฉบับ 3 ไม่ทำรวมในงานนี้

## 3. ปรับโครงหรืออัปเกรดเวอร์ชัน

agent `solution-architect` + `developer` · skill `blast-radius` · `principle-small-verifiable-steps` · `principle-replace-then-delete` · `stack-*` ตามภาษา · `adr-writer`
**ต้องมีก่อน:** `docs/ONBOARDING-NOTES.md` (ฉบับ 1) · test เดิมรันได้ (ไม่มี test → เขียน test จับพฤติกรรมของ flow หลักก่อน ตาม `prompt-test-automation.md` ฉบับ 3 · skill `testing-standards` · `e2e-testing-patterns`)
**ผลลัพธ์:** `docs/upgrade-<เรื่อง>.md` (แผน + ผล) · ADR 1 ฉบับที่ `docs/decisions/ADR-NNNN-<เรื่อง>.md` · โค้ด

- [ ] อนุญาตให้แก้โค้ดตามแผน (commit บนเครื่องเท่านั้น บน branch แยก `upgrade/…` · ไม่ push · ไม่ merge เข้า branch หลัก)

### เรื่องที่จะทำ (ผู้ใช้กรอก)

- จากอะไรไปอะไร (เช่น .NET Framework 4.8 → .NET 8 · Angular 12 → 18):
- เหตุผล (หมดอายุการสนับสนุน · ช่องโหว่ · ต้องใช้ความสามารถใหม่):
- ส่วนที่ห้ามแตะ:

### หัวข้อใน `docs/upgrade-<เรื่อง>.md`

1. สภาพก่อนทำ — เวอร์ชัน · ผลรัน test · ตัวเลขที่ต้องไม่แย่ลง (เวลา build · ไม่มีขั้น build ใช้เวลาเปิดแอปจนตอบได้ · เวลาตอบสนองหลัก) วัดแบบฉบับ 4 ข้อ 1 และบอกช่วงแกว่ง
2. สิ่งที่เปลี่ยนแบบใช้ร่วมไม่ได้ (breaking change) ที่กระทบ repo นี้ พร้อมไฟล์ที่โดน · อ้างเอกสารทางการของผู้ผลิต
3. ขั้นตอนเป็นก้อนเล็ก แต่ละก้อนรันผ่านและย้อนกลับได้
4. ผลหลังทำ — ตัวเลขเดียวกับหัวข้อ 1 · สิ่งที่ยังค้าง

### กฎเฉพาะฉบับนี้

- พฤติกรรมต้องเท่าเดิม · test เดิมแดงหลังแก้ → แก้โค้ด ห้ามแก้ test ให้ผ่าน เว้นแต่ test นั้นผูกกับรายละเอียดของเวอร์ชันเก่า (เขียนเหตุผลทุกข้อ)
- ทำทีละก้อน commit ทีละก้อน · ก้อนไหนไม่ผ่านแล้วแก้ไม่ได้ใน 3 รอบ → ย้อนก้อนนั้นแล้วรายงาน
- งานอัปเกรดไม่ทำขั้น 3 ของ playbook `refactor` (ลบโค้ดที่ไม่ถูกเรียก) จดไว้เสนอแยก · ไม่ใช้เกณฑ์ "diff ลดลง" · breaking change อ้างเอกสารทางการของผู้ผลิต 1 แหล่งพอ

## 4. ทำให้เร็วขึ้นหรือกินเครื่องน้อยลง

agent `developer` + `devops-engineer` · skill `observability-basics` · `stack-*` ตามภาษา · `stack-sql` (เมื่อช้าที่ฐานข้อมูล)
**ต้องมีก่อน:** `docs/ONBOARDING-NOTES.md` (ฉบับ 1)
**ผลลัพธ์:** `docs/perf-<เรื่อง>.md` ตัวเลขก่อน-หลัง · โค้ด

- [ ] อนุญาตให้แก้โค้ดตามแผน (commit บนเครื่องเท่านั้น บน branch แยก `perf/…` · ไม่ push · ไม่ merge เข้า branch หลัก)

### ปัญหา (ผู้ใช้กรอก)

- ช้าหรือกินเครื่องตรงไหน (หน้าจอ · API · งานเบื้องหลัง):
- ตอนนี้ประมาณเท่าไร · เป้าที่ต้องการ (ตัวเลข):
- ข้อมูลขนาดไหนที่ทำให้เกิด:

### ลำดับ

1. วัดก่อนแก้ด้วยวิธีที่ทำซ้ำได้ (คำสั่งวัด + ขนาดข้อมูล) · วัด 3 รอบ ใช้ค่ากลาง · เพิ่มรอบเฉพาะเมื่อผลแกว่งมากกว่าส่วนต่างที่ต้องการเห็น
2. หาจุดที่กินเวลาจริงด้วยเครื่องมือ profile หรือ query plan · ห้ามแก้จากการเดา
3. แก้ทีละจุด วัดซ้ำทุกครั้ง · จุดที่แก้แล้วไม่ดีขึ้น → ย้อนกลับ
4. ถึงเป้าหรือแก้ครบ 5 จุดแล้ว → หยุดและรายงาน

### กฎเฉพาะฉบับนี้

- ตัวเลขทุกตัวในรายงานมาจากการตรวจจริงพร้อมคำสั่งที่ใช้ · ไม่ได้วัด → ไม่เขียน
- test ทั้งชุดต้องเขียวหลังทุกจุดที่แก้
