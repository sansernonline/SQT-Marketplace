# prompt-product — งานผลิตภัณฑ์: ตั้งชื่อ roadmap แผน sprint deck นำเสนอ

ยังไม่ได้ทดสอบจริง

ใช้คู่กับ plugin `software-company` · ไฟล์นี้รวม prompt 4 ฉบับ · ใช้ก่อนหรือระหว่างพัฒนา เมื่อต้องตัดสินใจเชิงผลิตภัณฑ์หรือนำเสนอ · ยังไม่มีโปรเจกต์เลย → `prompt-new-project.md` ก่อน

## วิธีใช้

วางทั้งไฟล์ใน Claude Code, Codex CLI หรือ Gemini CLI ที่รากโฟลเดอร์โปรเจกต์ แล้วพิมพ์ต่อท้ายว่าจะทำฉบับไหน เช่น `ทำข้อ 2 และ 3`

<!-- rules:begin -->
**กฎการทำงาน (agent ต้องทำตาม):** เปิด skill `superuser` ก่อนเริ่ม แล้วทำตาม playbook ที่ฉบับนั้นระบุ (ไม่ระบุ → `project-docs`) · กฎร่วม (ถามแบบเลือกคำตอบครั้งเดียว ทุกตัวเลือกมีหลักฐาน · ทำจบรอบเดียว · ตัดสินใจเอง · รายงานสถานะ) อยู่ใน skill `superuser` และ playbook ที่เดียว · ข้อที่ต้องตัดสิน: ใช้ค่าตั้งต้นของเจ้าของใน `~/.claude/superuser-style.md` ก่อน ไม่มี → ค้นแล้วโหวต 3 agent ตาม skill `superuser` หัวข้อ 6 · ถามผู้ใช้เฉพาะข้อที่โหวตแทนไม่ได้ และตัวแนะนำบอกผลโหวต · ตัดสินใจเอง (พร้อมผลโหวต) และสถานะลง `docs/BUILD-PLAN.md` (ยังไม่มี → สร้าง) · ไฟล์ทำงานของ SuperUser (`CONTEXT.md` · `IMPROVEMENTS.md` · log) อยู่ใต้ `.claude/superuser/` ตาม `project-doc-set` ข้อ 1 ไม่วางที่รากโปรเจกต์ · ใช้ skill และ agent ของ plugin `software-company` เท่านั้น (ไม่ใช้ตัวชื่อซ้ำของ plugin อื่น) · เปิด skill ไม่ได้ → อ่าน `skills/<ชื่อ>/SKILL.md` ของ plugin · ไม่มี agent → ใช้ agent ทั่วไปพร้อมเปิด `agents/<ชื่อ>.md` · หาไม่เจอทั้ง 2 ทาง → ข้ามชิ้นนั้น ทำส่วนอื่นให้จบ แล้วรายงานว่าติด · ไม่มี `reviewer` หรือ `brainstormer` (plugin เวอร์ชันเก่า) → `general-purpose` ตัวใหม่ทำหน้าที่เดียวกัน (ตรวจอย่างเดียว ไม่แก้ · เสนอ 2–3 ทาง) · ไม่มี `learning-reviewer` → ข้ามรอบเรียนรู้แล้วจดไว้

**วนจนเสร็จ (agent loop):** ทุกฉบับวน ทำ → ตรวจ → แก้ → ตรวจซ้ำ จนผ่านทุกข้อที่ฉบับนั้นต้องมี · ตรวจด้วยหลักฐานจริง (เปิดไฟล์ · รันคำสั่ง · เทียบแหล่ง) ไม่ใช่คำบอกของตัวที่ทำ · รอบตรวจใช้ `reviewer` ตัวใหม่ทุกรอบ · ไม่ผ่าน → แก้ที่ต้นเหตุแล้วตรวจซ้ำทั้งข้อเดิมและจุดที่แก้ · เหลือแค่ข้อระดับต่ำ → ปิดได้แล้วลงรายงาน · ครบเพดานรอบ (งานกลาง 3 · งานใหญ่หรืองานเสี่ยง 5) ยังไม่ผ่าน → ติดป้าย `ติด` ทำส่วนอื่นให้จบ แล้วรายงานข้อที่เหลือ · รายละเอียดอยู่ใน skill `superuser` กฎข้อ 3

## 1. ตั้งชื่อผลิตภัณฑ์

agent `product-manager` · skill `product-naming`
**ผลลัพธ์:** `docs/naming.md` · **รออนุมัติ:** จดโดเมน · จดเครื่องหมายการค้า · สร้างบัญชีโซเชียล

### โจทย์ (ผู้ใช้กรอก)

- ตั้งชื่ออะไร (ผลิตภัณฑ์ · แอป · โมดูล · code name ภายใน):
- ทำอะไร ให้ใคร 1 ประโยค:
- ชื่อในตระกูลเดียวกันที่มีอยู่แล้ว (ชื่อแบรนด์แม่ · ผลิตภัณฑ์อื่น):
- ตลาด (ไทย · ต่างประเทศ · ทั้งสอง):
- คำที่ชอบ / ไม่เอา:

### หัวข้อที่ต้องมี

1. ชื่อเสนอ 10–20 ชื่อจากหลายสูตร แล้วตัดด้วย kill test ของ skill จนเหลือ 3–5
2. ชื่อที่เหลือ: ความหมาย · คนไทยออกเสียงอย่างไร · เข้าตระกูลชื่อเดิมไหม
3. ตรวจกับของจริง: โดเมน (.com · .co.th) · ชื่อบนร้านแอป · ชื่อซ้ำในสายเดียวกัน · ฐานข้อมูลเครื่องหมายการค้าของกรมทรัพย์สินทางปัญญา — ทุกผลติดวันที่
4. แนะนำ 1 ชื่อพร้อมเหตุผล

## 2. roadmap ผลิตภัณฑ์

skill `product-roadmap` · agent `product-manager` · skill `user-story-writer` · `simplicity-first`
**ผลลัพธ์:** `docs/roadmap.md` · **ไม่แก้** SRS · ไม่เพิ่มแถวงานใน BUILD-PLAN (สถานะและตัดสินใจเองยังลงได้)

### โจทย์ (ผู้ใช้กรอก)

- ช่วงเวลา (เช่น 6 เดือนข้างหน้า · Q1–Q4 2027):
- เป้าธุรกิจ (รายได้ · ผู้ใช้ · ลูกค้าองค์กรรายแรก):
- ไอเดียฟีเจอร์ที่มี (หรือให้อ่านจาก `docs/srs.md` · `docs/research/`):
- ทีม / เวลาที่มีต่อสัปดาห์:
- คำขอจากลูกค้าที่ได้ยินบ่อย:

### หัวข้อที่ต้องมี

1. เป้าของช่วงนี้ 1–3 ข้อ วัดได้ด้วยตัวเลข
2. ตารางให้คะแนน RICE (Reach · Impact · Confidence · Effort) ต่อฟีเจอร์ ตัวเลขที่เดา → ติด `(รอยืนยัน)`
3. roadmap แบ่ง ตอนนี้ / ถัดไป / ภายหลัง (ไม่ผูกวันที่แน่นอนในช่วงไกล)
4. สิ่งที่**ไม่ทำ**ในช่วงนี้ พร้อมเหตุผล
5. ตัวชี้วัดความสำเร็จต่อช่วง

## 3. แผน sprint

skill `sprint-plan` · agent `project-manager` · skill `user-story-writer` · `status-report`
**ผลลัพธ์:** `docs/sprints/sprint-<เลข>.md` · แถวงานใหม่ใน `docs/BUILD-PLAN.md` (รูปแบบเดียวกับตารางงานใน BUILD-PLAN (`prompt-new-project.md` ฉบับ 11 ข้อ 4) · สถานะเริ่ม `รอทำ`) · คอลัมน์ Points · สถานะ · Sprint ใน `docs/USER-STORIES.md`

### ลำดับ

1. อ่าน `docs/USER-STORIES.md` · หยิบเฉพาะ story สถานะ Ready · story ที่ยังเป็น Draft ไม่เข้า sprint → บอกในรายงานว่าต้องทำ `prompt-user-story.md` ฉบับ 3 ก่อน
2. เลือก story ตามเป้าและความจุทีม (หัวข้อข้างล่าง)
3. เขียนกลับลง `docs/USER-STORIES.md` เฉพาะ story ที่เลือก ทั้งตารางสารบัญและเนื้อหา story: Points (ทีมประเมินใหม่ → ใส่ค่าใหม่) · คอลัมน์ Sprint = เลข sprint นี้ · สถานะ `In sprint`

### โจทย์ (ผู้ใช้กรอก)

- sprint ที่ / วันเริ่ม-จบ:
- เป้าของ sprint 1 ประโยค:
- คนในทีมและเวลาที่มี (วันลา · งานอื่น):
- งานค้างจาก sprint ก่อน:
- ความเร็วทีมที่ผ่านมา (ถ้ามี):

### หัวข้อที่ต้องมี

1. งานที่เลือก: user story · เกณฑ์รับงาน · ขนาด · ใครทำ · อ้าง FR ใน SRS
2. ความจุทีมเทียบงานที่เลือก (ไม่เกิน 80% ของเวลาที่มี)
3. งานที่ตัดออกและไปอยู่ sprint ไหน
4. ความเสี่ยงและสิ่งที่ต้องรอคนอื่น
5. เกณฑ์ "เสร็จ" ของ sprint ที่ตรวจได้

## 4. deck นำเสนอ

agent `product-manager` (เนื้อหา) + `graphic-designer` (หน้าตา) · skill `presentation-design` · `branded-document-design`
**ผลลัพธ์:** `docs/deck/<ชื่อ>.md` (เนื้อหาแต่ละสไลด์ + บทพูด) · `docs/deck/<ชื่อ>.pptx`

### โจทย์ (ผู้ใช้กรอก)

- นำเสนอให้ใคร / เขาต้องตัดสินใจอะไรหลังฟัง:
- เวลาพูด (นาที) / จำนวนสไลด์ไม่เกิน:
- เนื้อหาที่มี (อ่านจาก `docs/` · ตัวเลข · ภาพหน้าจอ · mockup):
- โลโก้และสีแบรนด์ (path):
- ภาษา:

### หัวข้อที่ต้องมี

1. ลำดับเรื่อง (ปัญหา → ทางแก้ → หลักฐาน → สิ่งที่ขอ) เป็นหัวสไลด์ที่อ่านแล้วได้ข้อสรุป
2. สไลด์ละ 1 ประเด็น · ตัวเลขทุกตัวมีที่มา · ภาพหน้าจอจริงจาก `mockup/` หรือแอป
3. บทพูดต่อสไลด์ใน `.md` ตามเวลาที่ได้
4. `.pptx` เปิดได้จริง ฟอนต์ไทยแสดงถูก (render เป็นภาพแล้วตรวจทุกหน้า)
5. สไลด์สุดท้ายบอกสิ่งที่ขอให้ผู้ฟังทำ
