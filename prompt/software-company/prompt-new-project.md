# prompt-new-project — สร้างเอกสารโปรเจกต์ใหม่ (spec + mockup)

ใช้คู่กับ plugin `software-company` · ไฟล์นี้รวม prompt 16 ฉบับ (0–15) แต่ละฉบับสร้างเอกสาร 1 ชุด · ฉบับ 4–6 (user story · ออกแบบหน้าตาและ mockup) และ 12 (คู่มือ) เนื้อหาอยู่ในไฟล์แยก · ฉบับ 0 research แอปต้นแบบ ใช้เมื่ออยากได้แอปแบบเดียวกับที่มีอยู่แล้ว · ฉบับ 11 สร้าง prompt agent-loop (prompt ที่สั่ง agent เขียนโปรแกรมของโปรเจกต์นี้ต่อทีละข้อกำหนด)

## วิธีใช้

วางทั้งไฟล์ใน Claude Code, Codex CLI หรือ Gemini CLI ที่รากโฟลเดอร์โปรเจกต์ แล้วพิมพ์ต่อท้ายว่าจะทำฉบับไหน เช่น `ทำทั้งหมด` หรือ `ทำข้อ 3 และ 4` · อยากได้หน้าตาเหมือนแอปไหน พิมพ์ต่อท้ายได้เลย เช่น `หน้าตาแบบ C:\...\Telex` หรือ `แบบ Linear มืด ๆ`

**กฎการทำงาน (agent ต้องทำตาม):** เปิด skill `superuser` ก่อนเริ่ม แล้วทำตาม playbook ที่ฉบับนั้นระบุ (ไม่ระบุ → `project-docs`) · กฎร่วม (ถามแบบเลือกคำตอบครั้งเดียว ทุกตัวเลือกมีหลักฐาน · ทำจบรอบเดียว · ตัดสินใจเอง · รายงานสถานะ) อยู่ใน skill `superuser` และ playbook ที่เดียว · ข้อที่ต้องตัดสิน: ใช้ค่าตั้งต้นของเจ้าของใน `~/.claude/superuser-style.md` ก่อน ไม่มี → ค้นแล้วโหวต 3 agent ตาม skill `superuser` หัวข้อ 6 · ถามผู้ใช้เฉพาะข้อที่โหวตแทนไม่ได้ และตัวแนะนำบอกผลโหวต · ตัดสินใจเอง (พร้อมผลโหวต) และสถานะลง `docs/BUILD-PLAN.md` (ยังไม่มี → สร้าง) · ไฟล์ทำงานของ SuperUser (`CONTEXT.md` · `IMPROVEMENTS.md` · log) อยู่ใต้ `.claude/superuser/` ตาม `project-doc-set` ข้อ 1 ไม่วางที่รากโปรเจกต์ · ใช้ skill และ agent ของ plugin `software-company` เท่านั้น (ไม่ใช้ตัวชื่อซ้ำของ plugin อื่น) · เปิด skill ไม่ได้ → อ่าน `skills/<ชื่อ>/SKILL.md` ของ plugin · ไม่มี agent → ใช้ agent ทั่วไปพร้อมเปิด `agents/<ชื่อ>.md` · หาไม่เจอทั้ง 2 ทาง → ข้ามชิ้นนั้น ทำส่วนอื่นให้จบ แล้วรายงานว่าติด · ไม่มี `reviewer` หรือ `brainstormer` (plugin เวอร์ชันเก่า) → `general-purpose` ตัวใหม่ทำหน้าที่เดียวกัน (ตรวจอย่างเดียว ไม่แก้ · เสนอ 2–3 ทาง) · ไม่มี `learning-reviewer` → ข้ามรอบเรียนรู้แล้วจดไว้

**วนจนเสร็จ (agent loop):** ทุกฉบับวน ทำ → ตรวจ → แก้ → ตรวจซ้ำ จนผ่านทุกข้อที่ฉบับนั้นต้องมี · ตรวจด้วยหลักฐานจริง (เปิดไฟล์ · รันคำสั่ง · เทียบแหล่ง) ไม่ใช่คำบอกของตัวที่ทำ · รอบตรวจใช้ `reviewer` ตัวใหม่ทุกรอบ · ไม่ผ่าน → แก้ที่ต้นเหตุแล้วตรวจซ้ำทั้งข้อเดิมและจุดที่แก้ · เหลือแค่ข้อระดับต่ำ → ปิดได้แล้วลงรายงาน · ครบเพดานรอบ (งานกลาง 3 · งานใหญ่หรืองานเสี่ยง 5) ยังไม่ผ่าน → ติดป้าย `ติด` ทำส่วนอื่นให้จบ แล้วรายงานข้อที่เหลือ · รายละเอียดอยู่ใน skill `superuser` กฎข้อ 3

**ภาษาและรูป:** ทุกเอกสารเขียนตาม skill `human-writing` · รูปในเอกสารส่งมอบใช้แบบเดียวกันทั้งชุด: ผังระบบ · flow · ผังคลาวด์ → `diagram-figures` · Mermaid (`software-diagrams`) ใช้ได้เฉพาะเอกสารภายในทีม · **Mermaid ทุกบล็อกขึ้นต้นด้วยบรรทัด `%%{init`** ของ `software-diagrams` — ฉบับที่เขียน Mermaid (3 · 7 · 8 · 10 · 11 และฉบับ 13 ตอนตรวจ) ต้องรัน `node <ที่ติดตั้ง plugin>/skills/software-diagrams/scripts/check-mermaid-theme.mjs <ไฟล์ .md ที่เขียน>` ได้ exit 0 ก่อนส่ง

## กฎเฉพาะไฟล์นี้

- ไม่มี `docs/BUILD-PLAN.md` และ `docs/README.md` → ถามผู้ใช้ครั้งเดียว 5 ค่า: รหัสโปรเจกต์ · ขนาดงาน · แพลตฟอร์ม (web · mobile · windows) · **แอปหรือโปรเจกต์ที่ชอบหน้าตา** (ลิงก์ · ชื่อแอป · path โปรเจกต์ในเครื่อง · หรือคำบรรยาย เช่น "มืด หรู แบบ Linear" — ไม่มี → ฉบับ 5 เสนอ 3 แนว) · **เลือกแนวภาพเองไหม** (ใช่ → ฉบับ 5 หยุดให้เลือก · ไม่ → ผู้ตรวจเลือกให้) · สีแบรนด์ใช้ถ้าผู้ใช้ให้มา ไม่มี → ฉบับ 5 เสนอพร้อมแนวภาพ + `(รอยืนยัน)` ไม่หยุดถาม — เขียนค่าทั้งหมด (รวมสีแบรนด์) ลง `docs/README.md` (mockup อ่านแพลตฟอร์มและแอปอ้างอิงจากที่นี่)
- มี `docs/BUILD-PLAN.md` แล้วแต่ผู้ใช้สั่ง `ทำใหม่` → ถามครั้งเดียวรวมกัน: ฉบับไหน · ไฟล์เดิมเก็บหรือย้าย · **หน้าตาเดิมคงไว้หรือออกแบบใหม่** (สั่งทำ mockup ใหม่ = ออกแบบใหม่ เว้นแต่ผู้ใช้บอกให้คง)
- **งานเฉพาะสาขา** → agent และ skill ของสาขาเข้าทีมทุกฉบับที่เกี่ยว (ระบุสาขาใน `docs/README.md` · ไม่ระบุ → อ่านจากโจทย์แล้วลง `## ตัดสินใจเอง`) · AI / LLM → `ai-engineer` + `llm-engineering` (+ `prompt-ai-feature.md`) · IoT · firmware → `iot-engineer` + `iot-systems` · แอปมือถือ → `mobile-engineer` + `mobile-engineering` · สุขภาพ → `healthcare-engineer` + `hipaa-officer` + `healthcare-systems` · รับเงิน · การเงิน → `fintech-engineer` + `fintech-compliance-officer` + `fintech-payments` · ร้านค้าออนไลน์ → `ecommerce-engineer` + `ecommerce-patterns` · B2B SaaS → `revops-analyst` + `saas-platform` · เกม → `game-designer` + `game-developer` + `game-development` · บล็อกเชน → `blockchain-engineer` + `smart-contracts` · ประกันภัย → `insurance-engineer` + `insurance-analyst` + `insurance-systems` · กฎหมาย · สัญญา → `legaltech-engineer` + `legal-compliance-officer` + `legal-document-systems` · ระบบเทรด · Expert Advisor (EA) → `quant-analyst` + `stack-mql` (ใช้ `prompt-trading-system.md` แทนไฟล์นี้)
- มี `docs/research/` (จากฉบับ 0) → BRD · SRS · mockup ใช้เป็นข้อมูลตั้งต้น · ทุกครั้งที่หยิบข้อเสนอหรือ feature จากแอปต้นแบบมาใช้ ให้อ้างรหัส `IMP-xx` / เลขแหล่ง
- หยุดก่อนทำครบได้อีก 2 กรณี: ฉบับ 12 เมื่อยังรันแอปไม่ได้ · ฉบับ 5 ขั้น A เมื่อผู้ใช้ตอบว่าจะเลือกแนวภาพเอง (ทำฉบับอื่นที่ไม่พึ่ง mockup ต่อระหว่างรอ)
- ฉบับที่ชี้ไปไฟล์แยก (4 · 5 · 6 · 12) → สั่ง `ทำทั้งหมด` ให้วางไฟล์นั้นต่อท้ายไฟล์นี้ในข้อความเดียวกัน · ไม่ได้วางมา → อ่านจากโฟลเดอร์ `prompt/software-company/` ถ้าเข้าถึงได้ · ไม่ได้ทั้ง 2 ทาง → ทำตาม skill ที่ระบุในฉบับนั้น (user story → `user-story-writer` · mockup → ทำตามขั้นสั้นในฉบับ 5–6 ของไฟล์นี้ + `ui-craft` ข้อ 0.1 และ 9 + skill ตามแพลตฟอร์ม · คู่มือ → `technical-writer` + `branded-document-design`) · **ห้ามข้ามขั้นออกแบบเพราะหาไฟล์ไม่เจอ** แล้วลงใน `## ตัดสินใจเอง`
- โปรเจกต์แบบ ecosystem (หลาย sub-project แต่ละตัวมีเอกสารของตัวเอง) → เอกสารของ sub-project อยู่ใน `ecosystem/<รหัส>-<SUB>/` (`docs/` · `mockup/` · `qa/`) ส่วนแผนโครงการ · BRD · BUILD-PLAN อยู่ใน `docs/` ที่ราก · path ในตารางข้างบนให้อ่านโดยมี `ecosystem/<รหัส>-<SUB>/` นำหน้า · ชื่อโฟลเดอร์ต้องเป็น `ecosystem/` ห้ามใช้ `projects/` (skill `project-doc-set` ข้อ 1)

## 3. เขียน Software Requirements Specification (SRS)

agent `business-analyst` หรือ `system-analyst` · skill `srs-writing` · `user-story-writer` · `software-diagrams` · `polished-document-style`
**ต้องมีก่อน:** `docs/README.md` · `docs/<รหัส>-BRD-*.docx` (ถ้าขนาดงานมี BRD)
**ผลลัพธ์:** `docs/<รหัส>-SRS-v<M.m>-<สถานะ>.docx` (ร่าง `_to_delete/drafts/srs.md` → render ตามฉบับ 14)

### หัวข้อที่ต้องมี

ตามโครงของ skill `srs-writing` (อ้างอิง ISO/IEC/IEEE 29148) อย่างน้อย:

1. ภาพรวมระบบ ผู้ใช้ และบริบท (ไดอะแกรมบริบท 1 ภาพ)
2. ข้อกำหนดเชิงหน้าที่ (Functional Requirement — FR) รหัส `FR-001…` **1 ข้อ = 1 ประโยค = ผู้กระทำ 1 ราย** พร้อมเกณฑ์ยอมรับแบบ Given-When-Then และอ้าง `BR-xxx` ที่ข้อนั้นตอบ
3. ข้อกำหนดที่ไม่ใช่หน้าที่ (Non-Functional Requirement — NFR) `NFR-001…` ใส่ตัวเลขทุกข้อ (เวลาตอบ จำนวนผู้ใช้พร้อมกัน ความพร้อมใช้งาน) ไม่ใช้คำคุณศัพท์
4. ข้อมูลและกฎธุรกิจ — รายการข้อมูลหลักและกฎการคำนวณ/ตรวจสอบ
5. อินเทอร์เฟซภายนอก (ระบบอื่น/อุปกรณ์) · ข้อจำกัด · ข้อสมมติ
6. ตารางสืบย้อน `BR → FR → (ภายหลัง) test`

### กฎเฉพาะฉบับนี้

- ไม่ใส่วิธีทำ (solution) ลงในข้อกำหนด · ข้อกำหนดที่ตรวจไม่ได้ให้เขียนใหม่หรือย้ายไปคำถามค้าง
- ข้อกำหนดที่ทำให้ต้องเก็บข้อมูลส่วนบุคคล ทำเครื่องหมาย `[PDPA]` (Personal Data Protection Act)
- **ข้อเท็จจริงจากภายนอก** (คีย์ลัดของแอปอื่น · รุ่นหรือบิลด์ของระบบปฏิบัติการ · ขีดจำกัดของ API · ราคา · กฎหมาย) **ตรวจกับเอกสารทางการก่อนจบฉบับนี้** — ใส่ลิงก์ + วันที่เข้าถึงในตารางหรือหมายเหตุ · ตรวจไม่ได้ → `(รอยืนยัน)` + คำถามค้าง · ห้ามใส่ค่าจากความจำ เพราะเอกสารปลายน้ำทุกฉบับจะลอกค่าไปต่อ (subagent ไม่มีเครื่องมือค้นเว็บ → หัวหน้าทีมส่ง `general-purpose` ตรวจแยก)
- จบงานแล้วรายงานจำนวน FR / NFR และข้อที่ยังกำกวม
- ร่างมี Mermaid → รัน `check-mermaid-theme.mjs` กับร่างก่อน render (ข้อ "ภาษาและรูป")

## 11. สร้าง prompt agent-loop ของโปรเจกต์นี้

agent `solution-architect` + `project-manager` · skill `superuser` (อ่าน playbook `unattended-run` `feature` `bug-fix` `visual-parity` `pickup-and-pause` ก่อนเขียน) · `spec-to-code-loop` · `app-verifier-setup` · `testing-standards` · `simplicity-first`
**ต้องมีก่อน:** `docs/<รหัส>-SRS-*.docx` · `mockup/<รหัส>-mockup.html` (ถ้ามีหน้าจอ) · `docs/<รหัส>-ARCH-*.docx` · `docs/<รหัส>-FSD-*.docx` · `docs/<รหัส>-TESTPLAN-*.docx` (เท่าที่ขนาดงานมี) — ชื่อไฟล์จริงดูจากสารบัญ `docs/README.md` ถ้าโปรเจกต์ตั้งชื่อต่างจากนี้ · **render .docx ที่อ้างให้มีจริงก่อนเริ่มฉบับนี้**
**ผลลัพธ์:** `docs/AGENT-LOOP.md` ไฟล์เดียว — prompt สำเร็จรูปที่ผู้ใช้จะเอาไปสั่งให้ agent เขียนโปรแกรมของโปรเจกต์นี้ทีละข้อกำหนด · **ฉบับนี้เขียน prompt อย่างเดียว ห้ามเริ่มเขียนโค้ด ห้ามรัน loop**

### ข้อมูลที่ต้องดึงจากเอกสารของโปรเจกต์ใส่ลงใน prompt (ห้ามเว้นเป็นตัวแปรลอย ๆ)

1. ชื่อโปรเจกต์ · เป้าหมาย 1 ประโยค · path จริงของเอกสารนำเข้าทุกไฟล์ (ชื่อ `.docx` เต็มพร้อมเวอร์ชัน) · บอกให้ agent อ่าน `.docx` ด้วย `anthropic-skills:docx` หรือ python-docx
2. เทคโนโลยี/เฟรมเวิร์กจาก `docs/<รหัส>-ARCH-*.docx` · โครงโฟลเดอร์โค้ดที่ตั้งใจ
3. คำสั่ง install · test · smoke · รันแอป และ URL — จาก `docs/<รหัส>-TESTPLAN-*.docx` / `docs/README.md` · ถ้ายังไม่มี ให้กำหนดว่า "ข้อแรกของแผนคือตั้งโครงโปรเจกต์และคำสั่งเหล่านี้" ห้ามแต่งคำสั่ง
4. รายการรหัสข้อกำหนด (`FR-…`) ทั้งหมดจาก SRS พร้อมลำดับการพึ่งพาที่แนะนำ · FR ไหนมีหน้าจอ ให้ระบุ section ใน `mockup/<รหัส>-mockup.html` ที่ต้องเทียบ (`#s-<หน้าจอ>`)
5. test case ที่ต้องผ่านต่อ FR (อ้างรหัสจาก test plan ถ้ามี)
6. ข้อห้ามเฉพาะโปรเจกต์ (เช่น ห้ามต่อระบบจริง ห้ามใช้ข้อมูลส่วนบุคคลจริง) จาก NFR/สถาปัตยกรรม
7. skill ตรวจแอปของโปรเจกต์ (สร้างด้วย `app-verifier-setup`) — path และคำสั่งเริ่ม · ถ้ายังไม่มี ให้กำหนดว่า "ข้อที่สองของแผนคือสร้าง verify skill" ต่อจากการตั้งโครงโปรเจกต์

### โครงของ `docs/AGENT-LOOP.md` ที่ต้องเขียน

1. **วิธีใช้** (สำหรับผู้ใช้ อ่านใน 30 วินาที): รันที่รากโปรเจกต์ (ที่มี `docs/` และ `.claude/` · โค้ดอยู่ใน `<project-name>/`) — ไม่รันในโฟลเดอร์โค้ด เพราะ `docs/AGENT-LOOP.md` และ verify skill ใน `.claude/skills/` จะหาไม่เจอ · ยังไม่มี git หรือยังไม่อยู่บน branch งาน `build/loop` → รอบแรกตั้งให้เอง (ข้อ 6) · ใช้ได้ 2 แบบ — วางทีละรอบในหน้าต่างใหม่ (context สะอาด) หรือสั่ง `/loop อ่านและทำตาม docs/AGENT-LOOP.md` ให้วนเอง (`/loop` มีเฉพาะ Claude Code — เครื่องมืออื่นใช้แบบวางทีละรอบ) · สั่งหยุดด้วยไฟล์ `_to_delete/STOP` (เจ้าของลบเองก่อนรันใหม่) · เขียนให้ชัดว่า **การสั่งรัน loop = อนุญาตให้ `git init` · สร้างและสลับไป branch `build/loop` · `git commit` บน branch นี้เท่านั้น** ห้าม commit/merge ลง branch หลัก ห้าม push (ไม่เขียน → agent หยุดถามทุก commit ตามกฎ "หยุดถามเสมอ" ของ `superuser`)
2. **บริบทโปรเจกต์**: ข้อมูลข้อ 1–7 ข้างบน
3. **SuperUser ทุกรอบ** — เปิด skill `superuser` ก่อนทำอย่างอื่น · `unattended-run` คือกรอบของทั้ง loop · ทุกรอบมี **playbook หลัก 1 ตัว** จากตารางนี้ (`pickup-and-pause` คือขั้นเปิด/ปิดรอบ · `visual-parity` คือขั้นพิสูจน์ของแถวหน้าจอ ไม่นับเป็น playbook หลัก) แล้วคัดขั้นตอนของ playbook หลักลง todo ตรงตัว:

   | สถานการณ์ของรอบ | playbook |
   |---|---|
   | เริ่มทุกรอบ — อ่านสถานะ ตรวจ `git status` · `git log` · `git worktree list` ว่าตรงกับแถวที่ `เสร็จ` · ของที่ยังไม่ commit: ของแถว `กำลังทำ` ใช้ต่อ · ไม่ใช่ บันทึกเป็น `_to_delete/pause-<วันที่>.patch` แล้ว `git stash` | `pickup-and-pause` (pickup) |
   | ยังไม่มีโค้ด — แถวตั้งโครงโปรเจกต์และคำสั่ง | `new-project` |
   | แถวข้อกำหนดทั่วไป | `feature` |
   | แถวที่มีหน้าจอ | `feature` แล้วต่อด้วย `visual-parity` เทียบ mockup |
   | รอบแก้ (test/smoke แดง) | `bug-fix` |
   | รอบปิดงาน | `review` + skill `security-gate` |
   | รอบถูกตัดกลางทาง หรือ context ใกล้เต็ม | `pickup-and-pause` (pause) |

   **บทบาท** ตามกฎใน `superuser` หัวข้อ 5 (อ้างชื่อ ไม่คัดลอก): agent หลักเขียน `docs/BUILD-PLAN.md` คนเดียวและไม่เขียนโค้ด · โค้ดแถวละ `developer` ตัวใหม่ · test อัตโนมัติและขับแอป → `qa-tester` · ก่อน commit มีผู้ตรวจตัวใหม่ (ข้ามโมดูลหรือแตะความปลอดภัย → `adversarial-review-panel`) · เพิ่ม dependency หรือแตะ login · สิทธิ์ · ไฟล์ · ข้อมูลส่วนบุคคล → `security-gate` · แถวขนานที่ไม่แตะไฟล์เดียวกัน → `parallel-split-and-merge` (commit แถวละ 1 ครั้ง)
4. **ไฟล์สถานะ `docs/BUILD-PLAN.md`** — ทุกรอบอ่านไฟล์นี้ก่อน สถานะอยู่ในไฟล์ ไม่อยู่ในหัว agent:
   - ตารางค่าคงที่ `| รายการ | ค่า |` แถว `install` `test` `smoke` `รันแอป` `URL แอป` (ค่าอยู่ใน backtick)
   - ตารางงาน — ถ้ามีอยู่แล้วจากการวางแผน ใช้หัวตารางเดิมได้ แต่ต้องมีคอลัมน์ `milestone` `พึ่งแถว` `เกณฑ์เสร็จ` `สถานะ` `commit` · ถ้ายังไม่มี ใช้ `| # | รหัส | milestone | ข้อกำหนด | ไฟล์อ้างอิง | พึ่งแถว | เกณฑ์เสร็จ | สถานะ | commit |` · ช่อง `milestone` ใส่รหัส `M…` จากแผนโครงการ (ฉบับ 1) · ไม่มีแผน → ว่างได้ · 1 แถว = งาน 1 ก้อนที่ commit ได้ในครั้งเดียว (FR เดียว หรือกลุ่ม FR ที่แยกไม่ได้) · สถานะใช้แค่ `รอทำ` `กำลังทำ` `เสร็จ` `ติด` (ชุดคำสำหรับโค้ดและ build ของ `status-report`)
   - ยังไม่มี verify skill → ต้องมีแถว "สร้าง verify skill (`app-verifier-setup`)" ต่อจากแถวตั้งโครง — **เขียนลงตารางจริง** ไม่ใช่แค่บอกใน prompt
   - หัวข้อ `## คำถามค้าง` (คอลัมน์ `คำตอบ · วันที่ · ใครตอบ`) และ `## ผลปิดงาน`
   - หัวข้อ `## สถานะล่าสุด` `## ประวัติสถานะ` และ `## ตัดสินใจเอง` (มีอยู่แล้วจากตอนทำเอกสาร) — **เก็บไว้ ห้ามลบ**
5. **ด่านก่อนแถวโค้ดแรก**: การตัดสินใจที่ผูกทั้งโปรเจกต์และย้อนยาก (ภาษา เฟรมเวิร์ก ฐานข้อมูล — ADR ที่ยังเป็น "เสนอ") ต้องยืนยันแล้ว · ยังไม่ยืนยัน → ไม่เริ่มแถวโค้ด จบรอบด้วย `BLOCKED` พร้อมคำถามใน `## คำถามค้าง` · ระบุชื่อ ADR ที่ต้องยืนยันลงใน prompt · งานที่ ADR ต้องใช้ตัดสิน (spike) ทำก่อนด่านได้ แต่ระบุให้ชัด
6. **1 รอบทำอะไร** — 1 รอบ = 1 แถว · ตัดสินจากไฟล์ ตามลำดับนี้:
   - มีไฟล์ `_to_delete/STOP` → ไม่ทำงาน · เพิ่มบรรทัด `หยุดตามไฟล์ STOP` ใน `## ประวัติสถานะ` อย่างเดียว → `BLOCKED`
   - **ตั้ง git** (ทำบนเครื่องเท่านั้น ไม่แตะ remote): โฟลเดอร์โค้ดตามข้อ 2 ยังไม่มี git → `git init` · ยังไม่ได้ตั้ง `user.name`/`user.email` → ลงคำถามค้าง → `BLOCKED` · ยังไม่มีไฟล์ `.gitignore` → สร้างตามเทคโนโลยีของโปรเจกต์ (ไม่เก็บ build output · dependency · `.env` · `_to_delete/`) · ยังไม่อยู่บน `build/loop` → สร้างหรือสลับไป branch นั้น · ยังไม่มี commit เลย → commit แรก `chore: เริ่มโปรเจกต์` · อยู่ branch อื่นและมีไฟล์ที่ยังไม่ commit → ไม่สลับ branch ลงคำถามค้าง → `BLOCKED` · เพิ่มบรรทัดใน `## ประวัติสถานะ` ว่าตั้งอะไรไป แล้วตรวจข้อถัดไปในรอบเดียวกัน · ไฟล์ที่อยู่นอกโฟลเดอร์โค้ด (เช่น verify skill ใน `.claude/skills/`) ไม่อยู่ใน commit — บอกให้ชัด
   - ด่านข้อ 5 ยังไม่ผ่าน → `BLOCKED` · ผ่านแล้วแต่คำถามของด่านยังเปิด → ย้ายไป "ข้อที่ปิดแล้ว" แล้วตรวจข้อถัดไปในรอบเดียวกัน
   - `BUILD-PLAN.md` ยังไม่มีตารางงาน → **รอบวางแผน**: เพิ่มตารางค่าคงที่และตารางงานจาก FR ข้อ 4 แล้ว**ทำแถวแรกต่อในรอบเดียวกัน** · หยุดที่แผนเฉพาะเมื่อผู้ใช้สั่ง `วางแผนอย่างเดียว`
   - มีแถว `กำลังทำ` ค้างจากรอบก่อน → อ่าน diff ที่ค้างแล้วทำต่อจากของเดิม (นับเป็นอีก 1 ครั้งของแถวนั้น · เริ่มครบ 3 ครั้งแล้ว → ตั้ง `ติด` ห้ามเริ่มครั้งที่ 4)
   - มีแถว `รอทำ` ที่ **ทุกแถวที่มันพึ่ง `เสร็จ` แล้ว** และไม่มีคำถามค้างที่ระบุเลขแถวนั้น → ทำแถวแรก: ตั้ง `กำลังทำ` และเพิ่มบรรทัด `แถว N · ครั้งที่ k · เริ่ม` ใน `## ประวัติสถานะ` ทันที → เขียน test ของแถวก่อน และเห็น test แดงด้วยเหตุผลที่ถูก → เขียนโค้ดน้อยที่สุดให้ test เขียว → test ทั้งชุดเขียว → แถวที่มีหน้าจอ ขับแอปจริงด้วย verify skill เทียบ mockup → ผู้ตรวจผ่าน → `git commit` ครั้งเดียว `feat(<โมดูล>): … [FR-xxx]` → ตั้ง `เสร็จ` + เลข commit
   - ยังมีแถวไม่เสร็จ แต่ไม่มีแถวไหนทำได้ (ที่เหลือ `ติด` · พึ่งแถวที่ยังไม่เสร็จ · หรือติดคำถามค้าง) → สรุปว่าแต่ละแถวรออะไร → `BLOCKED`
   - ทุกแถว `เสร็จ` → **รัน test และ smoke จริงก่อน** · แดง → **รอบแก้** (เพิ่มบรรทัด `รอบแก้ · ครั้งที่ k · เริ่ม`): หาต้นเหตุ 1 ข้อ แก้เฉพาะจุด commit `fix(<โมดูล>): …`
   - ทุกแถว `เสร็จ` และ test กับ smoke คืนค่า 0 → **รอบปิดงาน**: ตรวจตาม `review` + `security-gate` แล้วเขียนตารางสืบย้อน FR → test → commit ใน `## ผลปิดงาน` → `DONE`
   - **นิยามที่ prompt ต้องเขียนให้ชัด:** "พึ่ง" ดูจากอะไร (คอลัมน์พึ่งแถว · ช่องว่างหมายถึงอะไร · `—` หมายถึงอะไร) · คำถามค้างบล็อกแถวเฉพาะเมื่อระบุเลขแถว · ใครปิดคำถามค้างได้ (ข้อเท็จจริง → agent ปิดด้วยผลตรวจจริง · ด่าน ADR → เจ้าของเท่านั้น) · เจ้าของตอบคำถามที่ทำให้แถว `ติด` แล้ว → กลับเป็น `รอทำ` พร้อมบรรทัดประวัติ · path ในตารางนับจากโฟลเดอร์ไหน · เกณฑ์ที่พิสูจน์ได้เฉพาะหลัง push (เช่น CI) ผ่านอย่างไรในรอบ loop · แถวที่ไม่มีโค้ด (ตัดสินใจ/ยืนยันถ้อยคำ/spike) ปิดอย่างไรโดยไม่ commit · แถวที่ไม่อยู่ในกลุ่มใดพึ่งอะไร · test case ที่ Blocked หรือต้องทำมือ จัดการอย่างไร
7. **เงื่อนไขจบที่ตรวจด้วยเครื่องได้**: ทุกแถว `เสร็จ` **และ** คำสั่ง test คืนค่า 0 **และ** คำสั่ง smoke คืนค่า 0 — agent ต้องรันคำสั่งเองแล้วรายงานผลจริง ห้ามสรุปว่าผ่านจากการอ่านโค้ด
8. **เพดาน**: นับครั้งจากบรรทัด `แถว N · ครั้งที่ k · เริ่ม` (เขียนตอนเริ่ม ไม่ใช่ตอนจบ — รอบที่พังกลางทางจึงถูกนับ) · หยุดแบบตั้งใจ (`pickup-and-pause` pause) → เขียน `แถว N · พัก` และไม่นับครั้ง · แถวเดิมไม่จบในครั้งที่ 3 → ตั้ง `ติด` พร้อมเหตุผล 1 บรรทัด แล้วไปแถวถัดไปที่ไม่พึ่งแถวนี้ (ตาม `unattended-run`) · รอบแก้ไม่ผ่าน 3 ครั้งติดกัน (นับจากบรรทัด `รอบแก้ · ครั้งที่ k · เริ่ม`) → `BLOCKED`
9. **ท้ายทุกรอบ** (ยกเว้นรอบที่หยุดตามไฟล์ STOP): skill `status-report` เขียนทับ `## สถานะล่าสุด` — แถวโค้ดรวมเป็นช่วงรหัสตามสถานะ (`FR-001 ถึง FR-012 · เสร็จ · ผ่าน — test 48/48`) แถวเอกสารคงค่าเดิม · มีคอลัมน์ `milestone` → เพิ่มบรรทัดละ milestone (`M3 · เสร็จ 5/8 แถว`) · ผลตรวจเอาจากคำสั่งที่รันจริงในรอบนั้น · ค้างอยู่ = แถว `ติด` และคำถามค้าง · แล้วเพิ่ม 1 บรรทัดใน `## ประวัติสถานะ` · ตัดสินใจเองลง `## ตัดสินใจเอง` ตาม `decision-log` · ติดป้าย `ตรวจจริง` / `จากแหล่ง` / `อนุมาน` / `ยังไม่ได้ตรวจ` ตาม `superuser` ข้อ 7
10. **บรรทัดสุดท้ายของทุกรอบ** ต้องเป็นหนึ่งใน `LOOP-STATUS: CONTINUE` · `LOOP-STATUS: PLAN-READY` (เฉพาะสั่ง `วางแผนอย่างเดียว`) · `LOOP-STATUS: BLOCKED` · `LOOP-STATUS: DONE` (ใช้กับ `/loop`: เมื่อเป็น `BLOCKED` `PLAN-READY` หรือ `DONE` ให้หยุดวน)
11. **ข้อห้าม**: ห้ามแก้ SRS/FSD/mockup/ไฟล์ test case (เจอจุดผิดให้ลงคำถามค้าง) · ห้ามลบหรือผ่อน test ให้ผ่าน · ห้าม commit โค้ดที่ test แดง · subagent ห้ามเขียน `docs/BUILD-PLAN.md` · ห้ามรอคำตอบกลางรอบ — คำถามข้อเท็จจริงลง `## คำถามค้าง` แล้วทำแถวถัดไปที่ไม่ติดคำถามนั้น · คำถามที่เป็นการตัดสินใจให้เลือกทางผลกระทบน้อยสุดเองแล้วลง `## ตัดสินใจเอง` ไม่ตั้ง `ติด` · ของชั่วคราวลง `_to_delete/`

### กฎเฉพาะฉบับนี้

- prompt ที่ได้ต้องใช้ได้ทันทีโดยไม่ต้องแก้ — ทุกค่าเป็นของจริงของโปรเจกต์ ค่าที่ยังไม่รู้เขียนว่า `(รอยืนยัน)` ต่อท้ายด้วย "ข้อแรกของแผนต้องตั้ง" ไม่ใช่ `<ใส่ค่า>`

- **ตรวจก่อนส่ง:** ให้ subagent ตัวใหม่อ่าน prompt ที่ได้แบบ agent ที่ไม่เคยเห็นโปรเจกต์ แล้วไล่สถานการณ์ 7 แบบ — เริ่มครั้งแรกในโฟลเดอร์ที่ยังไม่มี git · เริ่มครั้งแรก · แถวค้าง `กำลังทำ` · แถว `ติด` · test แดงหลังทุกแถวเสร็จ · ADR ยังไม่ยืนยัน · มีไฟล์ STOP — ทุกแบบต้องรู้ว่าทำอะไรและจบด้วย LOOP-STATUS ใด โดยไม่ต้องถามคน · ไม่ผ่าน → แก้แล้วไล่ซ้ำ
