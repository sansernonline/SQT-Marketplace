# prompt-rebuild — รื้อแอปเดิม สร้างรุ่นใหม่ ออกแบบใหม่ทั้งหมด

ยังไม่ได้ทดสอบจริง

ใช้คู่กับ plugin `software-company` · ไฟล์นี้รวม prompt 6 ฉบับ · ใช้เมื่อแอปเดิมแก้ต่อไม่คุ้มแล้ว ต้องสร้างใหม่ทั้งโครง หน้าตา และ stack โดย**เก็บบางส่วนของเดิมไว้ใช้** (กฎธุรกิจ ข้อมูล สูตรคำนวณ ข้อความ ไฟล์ asset) · แค่อัปเกรด framework แต่พฤติกรรมเท่าเดิม → `prompt-existing-dev.md` ฉบับ 3 · แค่ต้องการเอกสารของแอปเดิม → `prompt-existing-code.md`

## วิธีใช้

วางทั้งไฟล์ใน Claude Code, Codex CLI หรือ Gemini CLI ที่รากโฟลเดอร์โปรเจกต์ แล้วพิมพ์ต่อท้ายว่าจะทำฉบับไหน เช่น `ทำทั้งหมด` หรือ `ทำข้อ 1 ถึง 3`

<!-- rules:begin -->
**กฎการทำงาน (agent ต้องทำตาม):** เปิด skill `superuser` ก่อนเริ่ม แล้วทำตาม playbook ที่ฉบับนั้นระบุ (ไม่ระบุ → `project-docs`) · กฎร่วม (ถามแบบเลือกคำตอบครั้งเดียว ทุกตัวเลือกมีหลักฐาน · ทำจบรอบเดียว · ตัดสินใจเอง · รายงานสถานะ) อยู่ใน skill `superuser` และ playbook ที่เดียว · ข้อที่ต้องตัดสิน: ใช้ค่าตั้งต้นของเจ้าของใน `~/.claude/superuser-style.md` ก่อน ไม่มี → ค้นแล้วโหวต 3 agent ตาม skill `superuser` หัวข้อ 6 · ถามผู้ใช้เฉพาะข้อที่โหวตแทนไม่ได้ และตัวแนะนำบอกผลโหวต · ตัดสินใจเอง (พร้อมผลโหวต) และสถานะลง `docs/BUILD-PLAN.md` (ยังไม่มี → สร้าง) · ไฟล์ทำงานของ SuperUser (`CONTEXT.md` · `IMPROVEMENTS.md` · log) อยู่ใต้ `.claude/superuser/` ตาม `project-doc-set` ข้อ 1 ไม่วางที่รากโปรเจกต์ · ใช้ skill และ agent ของ plugin `software-company` เท่านั้น (ไม่ใช้ตัวชื่อซ้ำของ plugin อื่น) · เปิด skill ไม่ได้ → อ่าน `skills/<ชื่อ>/SKILL.md` ของ plugin · ไม่มี agent → ใช้ agent ทั่วไปพร้อมเปิด `agents/<ชื่อ>.md` · หาไม่เจอทั้ง 2 ทาง → ข้ามชิ้นนั้น ทำส่วนอื่นให้จบ แล้วรายงานว่าติด · ไม่มี `reviewer` หรือ `brainstormer` (plugin เวอร์ชันเก่า) → `general-purpose` ตัวใหม่ทำหน้าที่เดียวกัน (ตรวจอย่างเดียว ไม่แก้ · เสนอ 2–3 ทาง) · ไม่มี `learning-reviewer` → ข้ามรอบเรียนรู้แล้วจดไว้

**วนจนเสร็จ (agent loop):** ทุกฉบับวน ทำ → ตรวจ → แก้ → ตรวจซ้ำ จนผ่านทุกข้อที่ฉบับนั้นต้องมี · ตรวจด้วยหลักฐานจริง (เปิดไฟล์ · รันคำสั่ง · เทียบแหล่ง) ไม่ใช่คำบอกของตัวที่ทำ · รอบตรวจใช้ `reviewer` ตัวใหม่ทุกรอบ · ไม่ผ่าน → แก้ที่ต้นเหตุแล้วตรวจซ้ำทั้งข้อเดิมและจุดที่แก้ · เหลือแค่ข้อระดับต่ำ → ปิดได้แล้วลงรายงาน · ครบเพดานรอบ (งานกลาง 3 · งานใหญ่หรืองานเสี่ยง 5) ยังไม่ผ่าน → ติดป้าย `ติด` ทำส่วนอื่นให้จบ แล้วรายงานข้อที่เหลือ · รายละเอียดอยู่ใน skill `superuser` กฎข้อ 3

**ภาษาและรูป:** ทุกเอกสารเขียนตาม skill `human-writing` · รูปในเอกสารส่งมอบใช้ `diagram-figures` · Mermaid (`software-diagrams`) ใช้ได้เฉพาะเอกสารภายในทีม

**รุ่นเดิมกับรุ่นใหม่ (ใช้ทุกฉบับ):**

- **รุ่นเดิมอ่านอย่างเดียว** — ไม่แก้ ไม่ลบ ไม่ย้ายโฟลเดอร์โค้ดเดิม · ของที่จะเอามาใช้ให้**คัดลอก**ไปรุ่นใหม่ แล้วจดที่มา (`ไฟล์:บรรทัด` ของเดิม) ไว้ใน `docs/rebuild/INVENTORY.md`
- **รุ่นใหม่อยู่โฟลเดอร์ใหม่ที่ราก** ชื่อตามโปรเจกต์ตัวเล็กคั่น `-` · ชื่อชนกับโฟลเดอร์เดิม → ต่อท้าย `-v2` · git แยกจากของเดิม (`git init` · branch `build/rebuild`) · commit บนเครื่องเท่านั้น ไม่ push
- เอกสารของงานรื้ออยู่ `docs/rebuild/` · สเปกรุ่นเดิมอยู่ `docs/as-is/` · mockup รุ่นใหม่อยู่ `mockup/`
- ก่อนรันแอปเดิมหรือรุ่นใหม่ ให้ชี้ที่เก็บข้อมูล (`DATA_DIR` · connection string) ไปที่สำเนาใน `_to_delete/` ห้ามรันกับข้อมูลจริง · ห้ามมีรหัสผ่านหรือค่าลับในเอกสารและภาพ
- **ออกแบบใหม่ทั้งหมด = ไม่ลอกหน้าตาเดิม** — ใช้ `ui-craft` ข้อ 0.1 (ทิศทางภาพใหม่) ไม่ใช้ข้อ 0 (ลอกหน้าพี่น้อง) · css และ component ของเดิมไม่ยกมา
- **ทำเหมือนเดิมได้ไม่ใช่เป้า แต่ห้ามหายโดยไม่ตั้งใจ** — ความสามารถทุกข้อของรุ่นเดิมต้องมีสถานะใน `docs/rebuild/PARITY.md`: `เก็บ` · `เปลี่ยน` · `ตัด (ผู้ใช้อนุมัติ)` · ข้อที่ยังไม่ได้ตัดสิน → `เก็บ` ไว้ก่อนแล้วติด `(รอยืนยัน)`

## 1. สำรวจของเดิม: มีอะไร อะไรเก็บ อะไรทิ้ง

agent `solution-architect` (อ่านอย่างเดียว) + `system-analyst` + `developer` · skill `legacy-spec-recovery` · `code-orientation` · `app-verifier-setup` · `context-budget`
**ผลลัพธ์:** `docs/as-is/` (ตาม `legacy-spec-recovery` ทุกข้อมีหลักฐาน `ไฟล์:บรรทัด`) · `docs/rebuild/INVENTORY.md` · `docs/rebuild/PARITY.md` ร่างแรก — **ไม่แก้โค้ดเดิม**

### หัวข้อใน `INVENTORY.md`

ตาราง 1 แถวต่อ 1 ชิ้นของเดิม · คอลัมน์: ชิ้น · ที่อยู่ (`ไฟล์:บรรทัด`) · ประเภท · คุณภาพ (มี test ไหม · ขึ้นกับ framework เดิมแค่ไหน) · ข้อเสนอ · เหตุผล 1 บรรทัด

| ข้อเสนอ | ใช้เมื่อ |
|---|---|
| `ยกมาทั้งชิ้น` | กฎธุรกิจหรือสูตรที่ไม่ผูกกับหน้าจอและ framework · มี test หรือเขียน test ล็อกได้ |
| `ยกแนวคิด เขียนใหม่` | logic ถูกแต่ผูกกับ framework เดิม |
| `ยกข้อมูล` | ตารางข้อมูล ค่าตั้งต้น ข้อความ คำแปล รูป โลโก้ |
| `ทิ้ง` | โค้ดตาย · ของที่ framework ใหม่มีให้แล้ว · ฟีเจอร์ที่ไม่มีใครใช้ (ต้องมีหลักฐานว่าไม่มีคนใช้ ไม่มี → `(รอยืนยัน)`) |

### หัวข้อใน `PARITY.md` (ร่างแรก)

ความสามารถทุกข้อของรุ่นเดิมจาก `docs/as-is/` · คอลัมน์: รหัส · ความสามารถ · บทบาทผู้ใช้ · สถานะ (`เก็บ` ตั้งต้นทุกข้อ) · หมายเหตุ

### กฎเฉพาะฉบับนี้

- รันแอปเดิมให้ได้ก่อนถ้าทำได้ แล้วลองใช้ flow หลักจริง · รันไม่ขึ้น → เขียนว่าติดตรงไหน แล้วสำรวจจากโค้ดอย่างเดียว ติดป้าย `ยังไม่ได้ตรวจ (ไม่ได้รัน)`
- พฤติกรรมเดิมที่ดูเป็นบั๊ก → จดเป็นคำถามถึงผู้รู้ระบบ ไม่ตัดสินเองว่าเก็บหรือแก้
- ค่าลับที่ฝังในโค้ดเดิม → ชี้ `ไฟล์:บรรทัด` ไม่คัดค่า และใส่ในรายการต้องเปลี่ยนค่าก่อนขึ้นรุ่นใหม่

## 2. เป้าหมายรุ่นใหม่ + แนวทางรื้อ + stack

agent `product-manager` + `solution-architect` + `brainstormer` · skill `architecture-patterns` · `adr-writer` · `prior-art-review` · `simplicity-first` · `reference-app-research` (เมื่อผู้ใช้บอกว่า "อยากได้แบบแอป X")
**ต้องมีก่อน:** `INVENTORY.md` และ `PARITY.md` (ฉบับ 1)
**ผลลัพธ์:** `docs/rebuild/VISION.md` · ADR ที่ `docs/decisions/ADR-NNNN-<เรื่อง>.md`

### หัวข้อใน `VISION.md`

1. ทำไมรื้อ — ปัญหาของรุ่นเดิม พร้อมหลักฐานจากฉบับ 1
2. รุ่นใหม่ต้องดีกว่าเดิมตรงไหน — 3–5 ข้อ วัดได้ (เวลาทำงานหลัก · จำนวนขั้น · รองรับมือถือ ฯลฯ)
3. ของใหม่ที่เพิ่ม · ของเดิมที่ตัด (ต้องตรงกับ `PARITY.md`)
4. สิ่งที่ไม่ทำในรุ่นนี้

### ADR ที่ต้องมี

- **แนวทางรื้อ** — เขียนใหม่แล้วสลับทีเดียว (big-bang) หรือแทนทีละส่วนโดยรุ่นเดิมยังทำงาน (strangler) · เทียบในตาราง: ความเสี่ยง · เวลา · ผู้ใช้เจออะไรระหว่างทาง · ข้อมูลต้องซิงก์ 2 ทางไหม
- **stack รุ่นใหม่** — ทางเลือก 2–3 ทางจาก `brainstormer` · เลือกของที่ทีมดูแลได้และยังได้รับการสนับสนุน · อ้างหน้าทางการของผู้ผลิตพร้อมวันที่ตรวจ
- **โครงข้อมูลใหม่** (เมื่อเปลี่ยนโครงตาราง) — อะไรคงเดิม อะไรแตก อะไรรวม

### กฎเฉพาะฉบับนี้

- ผู้ใช้ระบุ stack มาแล้ว → ไม่ต้องเสนอทางเลือก เขียน ADR บันทึกเหตุผลและความเสี่ยงอย่างเดียว
- ยังไม่มีหลักฐานว่า stack ใหม่ทำสิ่งที่ยากที่สุดของระบบได้ → เสนอ `prompt-poc.md` ก่อนฉบับ 5 ลงคำถามค้าง

## 3. ออกแบบหน้าตาใหม่: 3 ทิศทาง โหวตเลือก แล้วทำ mockup

agent `ux-designer` + `graphic-designer` (เมื่อต้องทำโลโก้หรือสีแบรนด์ใหม่) · skill `ui-craft` ข้อ 0.1 · `parallel-attempts-pick-best` · `web-app-design` / `mobile-app-design` / `windows-app-design` ตามแพลตฟอร์ม · `principle-user-experience-first`
**ต้องมีก่อน:** `VISION.md` (ฉบับ 2) · flow หลักจาก `docs/as-is/`
**ผลลัพธ์:** `docs/rebuild/DESIGN-DIRECTION.md` · `mockup/` รุ่นใหม่ (.html กดได้จริง)

### ลำดับ

1. เลือก 3 หน้าที่บอกตัวตนของแอปได้มากที่สุด (เช่น หน้าแรก · หน้าทำงานหลัก · หน้ารายงาน)
2. `ux-designer` ตัวใหม่ 3 ตัว แยกกันทำ 1 ทิศทางต่อตัว ตาม `parallel-attempts-pick-best` · แต่ละทิศทางมี: อารมณ์ 1 บรรทัด · สี · ตัวอักษร · ความหนาแน่น · 3 หน้านั้น
3. `reviewer` ตัวใหม่ 3 ตัวให้คะแนนแยกกัน · ชนะ 2 ใน 3 · เสมอ → หัวหน้าทีมเลือกตาม `VISION.md` ข้อ 2 แล้วลง `decision-log`
4. ขยาย mockup ของทิศทางที่ชนะให้ครบ flow ใน `PARITY.md` ตาม `prompt-mockup.md` ฉบับ 1 และตรวจตามฉบับ 2

### กฎเฉพาะฉบับนี้

- ไม่เปิดดูหน้าจอเดิมระหว่างออกแบบ ยกเว้นเพื่อนับว่าหน้านั้นต้องแสดงข้อมูลอะไรบ้าง
- ข้อความ คำศัพท์ทางธุรกิจ และลำดับขั้นที่ผู้ใช้คุ้น → เก็บไว้ได้ แม้หน้าตาเปลี่ยน · เปลี่ยนลำดับขั้นของงานหลัก → เขียนเหตุผลใน `DESIGN-DIRECTION.md`
- ทิศทางที่แพ้เก็บไว้ใน `mockup/_alternatives/` ไม่ลบ
