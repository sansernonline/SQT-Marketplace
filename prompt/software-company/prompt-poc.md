# prompt-poc — พิสูจน์แนวคิด (Proof of Concept — POC) ให้ลูกค้าหรือผู้บริหารเห็นว่าทำได้จริง

ใช้คู่กับ plugin `software-company` · ไฟล์นี้มี prompt 4 ฉบับ ทำเรียงกัน 1 → 2 → 3 → 4 · ใช้เมื่อต้องพิสูจน์ว่าทำได้จริงก่อนลงเงินหรือเซ็นสัญญา เช่น ลูกค้าขอ POC ก่อนตัดสินใจ · TOR กำหนดให้ทำ POC · ผู้บริหารขอดูของจริงก่อนอนุมัติงบ

ต่างจาก `prompt-explore.md` ฉบับ 3 (ทดลองหลายแบบ): ฉบับนั้นทีมเทียบทางเลือกกันเองแล้วทิ้งโค้ด · ไฟล์นี้ทำของ 1 ชิ้นที่รันได้ตั้งแต่ต้นจนจบ ให้คนนอกทีมดู แล้วตัดสินว่าไปต่อหรือไม่

## วิธีใช้

วางทั้งไฟล์ใน Claude Code, Codex CLI หรือ Gemini CLI ที่รากโฟลเดอร์โปรเจกต์ แล้วพิมพ์ต่อท้ายว่าจะทำฉบับไหน เช่น `ทำทั้งหมด` หรือ `ทำข้อ 1`

<!-- rules:begin -->
**กฎการทำงาน (agent ต้องทำตาม):** เปิด skill `superuser` ก่อนเริ่ม แล้วทำตาม playbook ที่ฉบับนั้นระบุ (ไม่ระบุ → `project-docs`) · กฎร่วม (ถามแบบเลือกคำตอบครั้งเดียว ทุกตัวเลือกมีหลักฐาน · ทำจบรอบเดียว · ตัดสินใจเอง · รายงานสถานะ) อยู่ใน skill `superuser` และ playbook ที่เดียว · ข้อที่ต้องตัดสิน: ใช้ค่าตั้งต้นของเจ้าของใน `~/.claude/superuser-style.md` ก่อน ไม่มี → ค้นแล้วโหวต 3 agent ตาม skill `superuser` หัวข้อ 6 · ถามผู้ใช้เฉพาะข้อที่โหวตแทนไม่ได้ และตัวแนะนำบอกผลโหวต · ตัดสินใจเอง (พร้อมผลโหวต) และสถานะลง `docs/BUILD-PLAN.md` (ยังไม่มี → สร้าง) · ไฟล์ทำงานของ SuperUser (`CONTEXT.md` · `IMPROVEMENTS.md` · log) อยู่ใต้ `.claude/superuser/` ตาม `project-doc-set` ข้อ 1 ไม่วางที่รากโปรเจกต์ · ใช้ skill และ agent ของ plugin `software-company` เท่านั้น (ไม่ใช้ตัวชื่อซ้ำของ plugin อื่น) · เปิด skill ไม่ได้ → อ่าน `skills/<ชื่อ>/SKILL.md` ของ plugin · ไม่มี agent → ใช้ agent ทั่วไปพร้อมเปิด `agents/<ชื่อ>.md` · หาไม่เจอทั้ง 2 ทาง → ข้ามชิ้นนั้น ทำส่วนอื่นให้จบ แล้วรายงานว่าติด · ไม่มี `reviewer` หรือ `brainstormer` (plugin เวอร์ชันเก่า) → `general-purpose` ตัวใหม่ทำหน้าที่เดียวกัน (ตรวจอย่างเดียว ไม่แก้ · เสนอ 2–3 ทาง) · ไม่มี `learning-reviewer` → ข้ามรอบเรียนรู้แล้วจดไว้

**วนจนเสร็จ (agent loop):** ทุกฉบับวน ทำ → ตรวจ → แก้ → ตรวจซ้ำ จนผ่านทุกข้อที่ฉบับนั้นต้องมี · ตรวจด้วยหลักฐานจริง (เปิดไฟล์ · รันคำสั่ง · เทียบแหล่ง) ไม่ใช่คำบอกของตัวที่ทำ · รอบตรวจใช้ `reviewer` ตัวใหม่ทุกรอบ · ไม่ผ่าน → แก้ที่ต้นเหตุแล้วตรวจซ้ำทั้งข้อเดิมและจุดที่แก้ · เหลือแค่ข้อระดับต่ำ → ปิดได้แล้วลงรายงาน · ครบ 5 รอบยังไม่ผ่าน → ติดป้าย `ติด` ทำส่วนอื่นให้จบ แล้วรายงานข้อที่เหลือ · รายละเอียดอยู่ใน skill `superuser` กฎข้อ 2

## กฎเฉพาะไฟล์นี้

- **เกณฑ์ผ่านเขียนก่อนเขียนโค้ด** และห้ามแก้หลังเห็นผล · จะแก้ → ลงเหตุผลใน `docs/BUILD-PLAN.md` และบอกในรายงานฉบับ 4
- POC ทำเฉพาะเส้นทางที่ต้องพิสูจน์ · สิ่งที่ข้ามไป (login จริง · สิทธิ์ · ข้อผิดพลาดทุกกรณี · รองรับคนจำนวนมาก) จดลงรายการ "ยังไม่ได้ทำ" ทุกข้อ ไม่ซ่อน
- ใช้ข้อมูลตัวอย่างหรือข้อมูลที่ปิดชื่อแล้ว · ข้อมูลจริงของลูกค้าใช้ได้เมื่อผู้ใช้ติ๊กอนุญาตในฉบับ 2 เท่านั้น
- ระยะเวลา (timebox) เป็นวันตามปฏิทินของคน เป็นข้อมูลของผู้ใช้ → ห้ามเดา ใส่ `(รอยืนยัน)` · ใช้ในแผนรายวันของ `poc-plan.md` เท่านั้น · **กฎหยุดของ agent:** เกณฑ์ข้อไหนลองสร้างครบ 3 ครั้งแล้วยังไม่ผ่าน → หยุดสร้าง ไปฉบับ 3 ด้วยผลที่มี
- ส่งรายงานหรือ demo ให้ลูกค้าจริง อยู่ใน "รออนุมัติ" เสมอ

## 1. วางแผน POC และเกณฑ์ผ่าน

playbook `project-docs` · agent `solution-architect` + `project-manager` · skill `simplicity-first` · `principle-small-verifiable-steps` · `architecture-patterns`
**ผลลัพธ์:** `docs/poc/poc-plan.md`

### โจทย์ (ผู้ใช้กรอก)

- ชื่อลูกค้าและชื่องาน:
- สิ่งที่ลูกค้ายังไม่เชื่อว่าทำได้ (เขียนเป็นคำถาม เช่น "อ่านใบแจ้งหนี้ภาษาไทยได้ถูกเกิน 95% ไหม"):
- ใครเป็นคนตัดสินว่าผ่าน:
- ระยะเวลาที่ให้ (วัน):
- ข้อมูลตัวอย่างที่ได้รับ (path ใน `ref/`):
- ระบบที่ต้องเชื่อมต่อ (ถ้ามี):
- TOR หรือเอกสารที่กำหนดให้ทำ POC (ถ้ามี · path ใน `ref/`):

### หัวข้อที่ต้องมี

1. **คำถามที่ POC ต้องตอบ** — ไม่เกิน 3 ข้อ · ข้อละ 1 บรรทัด
2. **เกณฑ์ผ่าน** — ตาราง `| คำถาม | วัดอะไร | ผ่านเมื่อ | วัดอย่างไร |` · ทุกเกณฑ์เป็นตัวเลขหรือสิ่งที่เห็นได้ ไม่ใช้คำว่า "ใช้งานได้ดี"
3. **ขอบเขต** — ทำ · ไม่ทำ · ทำปลอม (mock) แทนของจริง พร้อมเหตุผลทีละข้อ
4. **แนวทางทางเทคนิค** — ผังระบบ 1 รูป · เทคโนโลยีที่ใช้และเหตุผล 1 บรรทัดต่อตัว · ถ้ายังเลือกไม่ได้ → ชี้ไป `prompt-explore.md` ฉบับ 2 หรือ 3 ก่อน
5. **ข้อมูลทดสอบ** — มาจากไหน · กี่รายการ · ปิดชื่อแล้วหรือยัง · ชุดไหนใช้วัด ชุดไหนใช้ demo
6. **แผนรายวัน** — งานย่อยละไม่เกิน 1 วัน · วันสุดท้ายเผื่อไว้วัดผลและเตรียม demo
7. **ความเสี่ยง** — สิ่งที่ถ้าเจอแล้ว POC ล้ม · สัญญาณที่บอกว่าควรหยุดก่อนกำหนด

### กฎเฉพาะฉบับนี้

- คำถามที่ตอบได้ด้วยการอ่านเอกสารหรือถามผู้ขาย ไม่ต้องทำ POC → ย้ายไป `prompt-explore.md` ฉบับ 1 หรือ 2 แล้วบอกผู้ใช้
- คำถามเรื่องรสนิยม (สวยไหม ชอบไหม) ไม่ใช่เกณฑ์ POC → ใช้ `prompt-mockup.md` แทน

## 2. สร้าง POC

playbook `new-project` (ยังไม่มีโค้ด) หรือ `feature` (ต่อจากโค้ดเดิม) · agent `developer` (+ agent เฉพาะทางตามเรื่อง เช่น `ai-engineer` · `data-engineer` · `mobile-engineer`) · skill `lazy-coding` · `readable-code` · `principle-secure-by-default` · `config-and-secrets` · `principle-prove-it-works`
**ต้องมีก่อน:** `docs/poc/poc-plan.md`
**ผลลัพธ์:** โค้ดในโฟลเดอร์โค้ดของโปรเจกต์ (ชื่อโปรเจกต์ ตัวพิมพ์เล็ก คั่นด้วย `-`) บน branch `poc/<เรื่อง>` · `docs/poc/poc-build-log.md` · **ไม่แก้โค้ด** เว้นแต่ข้างล่างติ๊ก `[x]`

- [ ] อนุญาตให้สร้างและแก้โค้ด (commit บนเครื่องเท่านั้น · ไม่ push · ไม่ merge เข้า branch หลัก) · ยังไม่มี git → `git init` ได้ (ถือว่าอนุญาตจากช่องติ๊กนี้) · อยู่ branch อื่นและมีไฟล์ค้าง → ไม่สลับ ลงคำถามค้าง
- [ ] อนุญาตให้ใช้ข้อมูลจริงของลูกค้า (ไม่ติ๊ก → ใช้ข้อมูลตัวอย่างหรือข้อมูลที่ปิดชื่อแล้วเท่านั้น)

### สิ่งที่ต้องได้

1. **รันได้ด้วยคำสั่งเดียว** — เขียนไว้ใน `README.md` ของโฟลเดอร์โค้ด พร้อมสิ่งที่ต้องติดตั้งก่อน
2. **เส้นทางหลักทำงานจริงตั้งแต่ต้นจนจบ** — ตามขอบเขต "ทำ" ใน `poc-plan.md` · ส่วน "ทำปลอม" ติดป้ายในโค้ดว่า `POC: mock`
3. **ค่าลับอยู่ใน environment variable** ไม่อยู่ในโค้ดและ git · มี `.env.example`
4. **บันทึกการสร้าง** `poc-build-log.md` — รายวัน: ทำอะไร · ติดอะไร · เปลี่ยนแผนอะไร
5. **รายการ "ยังไม่ได้ทำ"** — ทุกอย่างที่ข้ามเพื่อให้ทันเวลา · แต่ละข้อบอกว่าถ้าทำจริงต้องเพิ่มอะไร

### กฎเฉพาะฉบับนี้

- ทำทีละขั้นเล็ก รันดูผลทุกขั้น · ขั้นไหนไม่ได้เป็นไปตามเกณฑ์ใน `poc-plan.md` → จดตัวเลขที่ได้จริง ไม่ปรับเกณฑ์ให้ผ่าน
- นับครั้งที่ลองต่อเกณฑ์ลงใน `poc-build-log.md` · เกณฑ์ไหนลองครบ 3 ครั้งแล้วยังไม่ผ่าน → หยุดสร้าง ไปฉบับ 3 ด้วยผลที่มี (ไม่ใช้จำนวนวันเป็นตัวหยุด เพราะ agent วัดวันไม่ได้)
- ไม่เพิ่มของที่ไม่อยู่ในขอบเขต แม้ทำง่าย · อยากเพิ่ม → จดเป็นข้อเสนอในฉบับ 4

## 3. วัดผลและเตรียม demo

playbook `review` · agent `qa-tester` + `developer` · skill `principle-prove-it-works` · `test-case-template` · `security-gate`
**ต้องมีก่อน:** `poc-plan.md` · โค้ด POC ที่รันได้
**ผลลัพธ์:** `docs/poc/poc-results.md` · `docs/poc/poc-demo.md`

### หัวข้อที่ต้องมีใน `poc-results.md`

1. **ผลเทียบเกณฑ์** — ตาราง `| เกณฑ์ | ผ่านเมื่อ | ได้จริง | ผ่าน/ไม่ผ่าน | หลักฐาน |` · หลักฐานเป็นไฟล์ log ภาพ หรือคำสั่งที่รันซ้ำได้
2. **วิธีวัด** — เครื่อง · ข้อมูลชุดไหน · กี่รอบ · คนอื่นรันซ้ำแล้วได้ตัวเลขเดียวกัน
3. **สิ่งที่เจอระหว่างวัด** — กรณีที่ล้ม · ข้อมูลแบบไหนที่ทำไม่ได้
4. **ผลตรวจความปลอดภัยเบื้องต้น** — จาก `security-gate` · POC ไม่ต้องผ่านทุกข้อ แต่ต้องระบุว่าข้อไหนยังไม่ผ่าน

### หัวข้อที่ต้องมีใน `poc-demo.md`

1. **บท demo 10–15 นาที** — ลำดับหน้าจอ · พูดอะไร · ชี้ให้ดูตรงไหน · ตอบคำถามข้อไหนของ `poc-plan.md`
2. **ข้อมูลสำหรับ demo** — ชุดไหน · เตรียมไว้ที่ไหน · ล้างแล้วเริ่มใหม่อย่างไร
3. **แผนสำรอง** — วิดีโอบันทึกหน้าจอหรือภาพหน้าจอทุกขั้น เผื่อเครื่องหรือเน็ตมีปัญหา
4. **คำถามที่น่าจะโดนถาม** — พร้อมคำตอบ · โดยเฉพาะเรื่องที่อยู่ในรายการ "ยังไม่ได้ทำ"

### กฎเฉพาะฉบับนี้

- ไม่ผ่านก็รายงานว่าไม่ผ่าน · ห้ามเลือกเฉพาะชุดข้อมูลที่ผ่านมาแสดง
- demo ใช้ข้อมูลชุดที่ไม่ได้ใช้ระหว่างสร้าง ถ้ามี

## 4. สรุปผลและข้อเสนอไปต่อหรือไม่

playbook `project-docs` · agent `solution-architect` + `product-manager` + `technical-writer` · skill `polished-document-style` · `branded-document-design` (ตอน render) · `presentation-design` (ถ้าต้องนำเสนอ) · `adr-writer`
**ต้องมีก่อน:** `poc-plan.md` · `poc-results.md`
**ผลลัพธ์:** `docs/poc/poc-report.md` → .docx + .pdf · ADR ของเทคโนโลยีที่เลือกใน `docs/decisions/`

### หัวข้อที่ต้องมี

1. **สรุปสำหรับผู้บริหาร** — ครึ่งหน้า: คำถาม → ผล → ข้อเสนอ (ไปต่อ · ไปต่อแบบมีเงื่อนไข · ไม่ไปต่อ)
2. **ผลเทียบเกณฑ์** — จาก `poc-results.md` ตรงทุกตัวเลข
3. **สิ่งที่เรียนรู้** — สิ่งที่ง่ายหรือยากกว่าที่คิด · สมมติฐานไหนผิด
4. **ระยะห่างจาก POC ถึงระบบจริง** — ตาราง `| เรื่อง | POC ทำแค่ไหน | ระบบจริงต้องมีอะไร | ขนาดงาน (เล็ก/กลาง/ใหญ่) |` · มาจากรายการ "ยังไม่ได้ทำ" ครบทุกข้อ
5. **ความเสี่ยงที่ยังเหลือ** — และวิธีลดแต่ละข้อ
6. **ขั้นต่อไป** — ไปต่อ → ประเมินงานและราคาด้วย `prompt-proposal.md` ฉบับ 2 (ไม่มี TOR → ฉบับ 2 ใช้ `poc-plan.md` + `poc-report.md` แทน `tor-analysis.md`) · ไม่ไปต่อ → ทางเลือกอื่นที่ควรดู
7. **ภาคผนวก** — วิธีรัน POC · ลิงก์วิดีโอ demo · `poc-build-log.md`

### กฎเฉพาะฉบับนี้

- ห้ามบอกว่า "พร้อมใช้งานจริง" · POC พิสูจน์ได้แค่คำถามใน `poc-plan.md`
