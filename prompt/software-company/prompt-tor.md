# prompt-tor — เขียนขอบเขตงาน (Terms of Reference — TOR) เพื่อหาผู้รับจ้าง

ใช้คู่กับ plugin `software-company` · ไฟล์นี้มี prompt 3 ฉบับ ทำเรียงกัน 1 → 2 → 3 · ใช้เมื่อ**เราเป็นฝั่งผู้ว่าจ้าง** หรือช่วยลูกค้าร่าง TOR ก่อนประกาศหาผู้รับจ้าง

ได้รับ TOR จากลูกค้าแล้วจะทำข้อเสนอ → ใช้ `prompt-proposal.md` แทน

## วิธีใช้

วางทั้งไฟล์ใน Claude Code, Codex CLI หรือ Gemini CLI ที่รากโฟลเดอร์โปรเจกต์ แล้วพิมพ์ต่อท้ายว่าจะทำฉบับไหน เช่น `ทำทั้งหมด` หรือ `ทำข้อ 3`

## กฎเฉพาะไฟล์นี้

- ความต้องการ บันทึกประชุม ระบบเดิม และแบบฟอร์ม TOR ของหน่วยงาน (ถ้ามี) วางไว้ใน `ref/` · อ่านอย่างเดียว ไม่แก้ · มีแบบฟอร์มของหน่วยงาน → ใช้หัวข้อตามแบบฟอร์มนั้น แล้วเติมสิ่งที่ขาดจากรายการข้างล่าง
- ทุกข้อใน TOR มีเลขข้อ (เช่น `4.2`) เพื่อให้ผู้เสนออ้างถึงได้
- งบประมาณ วิธีจัดซื้อ ค่าปรับ เงื่อนไขการจ่ายเงิน และคุณสมบัติผู้เสนอเป็นข้อมูลของผู้ใช้ → ห้ามเดา ใส่ `(รอยืนยัน)`
- หน่วยงานรัฐ: ระเบียบจัดซื้อจัดจ้าง แบบฟอร์ม และเกณฑ์ตัดสินต้องตรวจกับเจ้าหน้าที่พัสดุของหน่วยงาน · agent ไม่ยืนยันข้อกฎหมายเอง ติดป้าย `ตรวจกับฝ่ายพัสดุ`
- **ไม่ล็อกสเปก** — ห้ามระบุยี่ห้อ รุ่น หรือคุณสมบัติที่มีผู้ขายรายเดียวทำได้ เว้นแต่ผู้ใช้ให้เหตุผลที่จำเป็น (เช่น ต้องเชื่อมกับระบบเดิม) และจดเหตุผลไว้ในข้อนั้น
- ประกาศหรือส่ง TOR ออกไปจริง อยู่ใน "รออนุมัติ" เสมอ

### หัวข้อที่ต้องมี

1. **ความเป็นมาและปัญหา** — สภาพปัจจุบัน · ปัญหา · ผลกระทบ
2. **วัตถุประสงค์** — ไม่เกิน 5 ข้อ · แต่ละข้อวัดได้ว่าสำเร็จหรือไม่
3. **ขอบเขตงาน** — ทำ · ไม่ทำ · ผู้ใช้แต่ละกลุ่มและสิ่งที่แต่ละกลุ่มทำได้
4. **ความต้องการด้านการใช้งาน** — แยกตามโมดูล · ทุกข้อทดสอบได้ · ใช้คำว่า "ต้อง" สำหรับข้อบังคับ "ควร" สำหรับข้อที่ให้คะแนนเพิ่ม
5. **ความต้องการด้านเทคนิค** — ความเร็ว · จำนวนผู้ใช้พร้อมกัน · ความปลอดภัย · การสำรองข้อมูล · PDPA · ที่ตั้งเซิร์ฟเวอร์ · การเชื่อมระบบเดิม
6. **การย้ายข้อมูล การอบรม และเอกสารส่งมอบ** — รายการเอกสารที่ผู้รับจ้างต้องส่ง (คู่มือผู้ใช้ · คู่มือผู้ดูแลระบบ · source code · ผังระบบ)
7. **ระยะเวลาและงวดงาน** — งวด · สิ่งที่ส่ง · เกณฑ์ตรวจรับแต่ละงวด · สัดส่วนการจ่ายเงิน `(รอยืนยัน)`
8. **การตรวจรับ** — ใครตรวจ · ทดสอบอะไร · ไม่ผ่านแล้วทำอย่างไร
9. **การรับประกันและบำรุงรักษา** — ระยะเวลา · เวลาตอบสนองแยกตามความรุนแรง
10. **ทรัพย์สินทางปัญญาและข้อมูล** — ใครเป็นเจ้าของ source code และข้อมูล · ส่งคืนข้อมูลเมื่อจบสัญญา
11. **คุณสมบัติผู้เสนอราคาและเอกสารที่ต้องยื่น** `(รอยืนยัน)`
12. **เกณฑ์พิจารณา** — ฉบับนี้ใส่หัวข้อไว้พร้อมข้อความ `(รอฉบับ 2)` · ฉบับ 2 เติมเนื้อหาหลังเขียน `evaluation.md`
13. **วงเงินงบประมาณและผู้ติดต่อ** `(รอยืนยัน)`

### กฎเฉพาะฉบับนี้

## 2. ราคากลางและเกณฑ์ให้คะแนน

agent `project-manager` + `solution-architect` · skill `simplicity-first`
**ต้องมีก่อน:** `docs/tor/tor.md`
**ผลลัพธ์:** `docs/tor/reference-price.md` · `docs/tor/reference-price.xlsx` · `docs/tor/evaluation.md` · หัวข้อ 12 ใน `tor.md` (สรุปเกณฑ์ผ่านขั้นต่ำและน้ำหนักคะแนนจาก `evaluation.md` แทนข้อความ `(รอฉบับ 2)`)

### ข้อมูลราคา (ผู้ใช้กรอก)

- เรทต่อวันอ้างอิงแยกตามบทบาท (หรือแหล่งอ้างอิงที่หน่วยงานใช้):
- ใบเสนอราคาจากผู้ขายที่สืบมาแล้ว (path ใน `ref/` ถ้ามี):
- น้ำหนักราคาต่อคุณภาพที่ต้องการ (เช่น 30:70):

### หัวข้อที่ต้องมีใน `reference-price.md`

1. **แตกงาน** — ตามโมดูลใน TOR · อ้างเลขข้อ TOR ทุกงาน
2. **ประเมินแบบ 3 ค่า** — เร็วสุด · น่าจะเป็น · ช้าสุด → ค่าที่ใช้ = (เร็ว + 4 × น่าจะเป็น + ช้า) ÷ 6
3. **ตารางราคากลาง** — วันคน × เรท + ค่าเซิร์ฟเวอร์ · license · บำรุงรักษา = ราคากลาง · คำนวณในไฟล์ .xlsx ด้วยสูตร ไม่คิดในหัว
4. **เทียบกับใบเสนอราคาที่สืบมา** (ถ้ามี) — ต่างเกิน 20% → อธิบายว่าทำไม
5. **สมมติฐาน** — ทุกข้อที่ถ้าเปลี่ยนแล้วราคาเปลี่ยน

### หัวข้อที่ต้องมีใน `evaluation.md`

1. **เกณฑ์ผ่านขั้นต่ำ** — เอกสารครบ · คุณสมบัติ · ข้อ "ต้อง" ครบทุกข้อ
2. **ตารางให้คะแนน** — `| หัวข้อ | น้ำหนัก | ได้เต็มเมื่อ | ได้ครึ่งเมื่อ | ได้ 0 เมื่อ |` · น้ำหนักรวม 100
3. **ตัวอย่างการคิดคะแนน** — ผู้เสนอสมมติ 2 ราย ให้เห็นว่าคิดอย่างไร

### กฎเฉพาะฉบับนี้

- ตัวเลขใน .md กับ .xlsx ต้องตรงกันทุกตัว · ตรวจซ้ำก่อนจบ
- เกณฑ์ให้คะแนนทุกข้อต้องให้กรรมการ 2 คนให้คะแนนแล้วได้เท่ากัน · ข้อที่ขึ้นกับความรู้สึก (เช่น "เข้าใจโจทย์ดี") ต้องแตกเป็นสิ่งที่ตรวจได้

## 3. ตรวจ TOR ก่อนประกาศ

playbook `review` · agent `business-analyst` + `solution-architect` + `security-engineer` · skill `adversarial-review-panel` · `srs-writing` · `branded-document-design` (ตอน render)
**ต้องมีก่อน:** `tor.md` · `reference-price.md` · `evaluation.md`
**ผลลัพธ์:** `docs/tor/tor-review.md` + แก้ `tor.md` ตามผลตรวจ (แก้เฉพาะข้อที่ไม่ใช่ข้อมูลของผู้ใช้) → render `tor.md` เป็น .docx + .pdf ตาม `prompt-new-project.md` ฉบับ 14 เป็นขั้นสุดท้าย

### ตรวจจากมุมผู้เสนอราคา

ให้ reviewer สวมบทผู้รับจ้างที่จะยื่นข้อเสนอ แล้วตอบ:

1. **ข้อที่ตีความได้หลายทาง** — แต่ละทางทำให้ราคาต่างกันแค่ไหน
2. **ข้อที่ขัดกันเอง** — ระหว่างหัวข้อ หรือระหว่าง TOR กับเกณฑ์ให้คะแนน
3. **ข้อที่ทดสอบไม่ได้** — ตรวจรับแล้วจะเถียงกันว่าผ่านหรือไม่
4. **ข้อกำหนดแฝง** — สิ่งที่ต้องมีจริงแต่ไม่ได้เขียน (ย้ายข้อมูล · อบรม · สำรองข้อมูล · PDPA · ใบอนุญาตซอฟต์แวร์)
5. **ข้อที่ล็อกสเปก** — ยี่ห้อ รุ่น หรือคุณสมบัติที่มีผู้ขายรายเดียวทำได้
6. **ความสมดุลของความเสี่ยง** — ค่าปรับ รับประกัน และงวดเงินที่หนักจนไม่มีใครยื่น หรือหลวมจนผู้ว่าจ้างไม่ได้รับการคุ้มครอง
7. **ราคากลางเทียบขอบเขต** — งานที่ TOR สั่งทำได้ในราคานี้จริงไหม

### รูปแบบ `tor-review.md`

ตาราง `| เลขข้อ TOR | ปัญหา | ผลถ้าไม่แก้ | เสนอแก้เป็น | แก้แล้ว/รอผู้ใช้ |` เรียงจากผลกระทบมากสุด

### กฎเฉพาะฉบับนี้

- ข้อที่แก้ได้เองโดยไม่เปลี่ยนเนื้อหา (คำกำกวม · เลขข้อผิด · ข้อซ้ำ) → แก้ใน `tor.md` เลย
- ข้อที่เปลี่ยนขอบเขต งบ หรือเงื่อนไข → ไม่แก้เอง ใส่ "รอผู้ใช้" พร้อมคำแนะนำ
