# prompt-explore — หาคำตอบเชิงเทคนิค ทดลองก่อนเลือก ทำหน้าจอให้ตรงต้นแบบ

ใช้คู่กับ plugin `software-company` · ไฟล์นี้รวม prompt 4 ฉบับ · ใช้ระหว่างพัฒนา เมื่อต้องรู้ก่อนลงมือ หรือต้องพิสูจน์ด้วยการรันแทนการเดา

## วิธีใช้

วางทั้งไฟล์ใน Claude Code, Codex CLI หรือ Gemini CLI ที่รากโฟลเดอร์โปรเจกต์ แล้วพิมพ์ต่อท้ายว่าจะทำฉบับไหน เช่น `ทำข้อ 1`

<!-- rules:begin -->
**กฎการทำงาน (agent ต้องทำตาม):** เปิด skill `superuser` ก่อนเริ่ม แล้วทำตาม playbook ที่ฉบับนั้นระบุ (ไม่ระบุ → `project-docs`) · กฎร่วม (ถามครั้งเดียว · ทำจบรอบเดียว · ตัดสินใจเอง · รายงานสถานะ) อยู่ใน skill `superuser` และ playbook ที่เดียว · ตัดสินใจเองและสถานะลง `docs/BUILD-PLAN.md` (ยังไม่มี → สร้าง) · ไฟล์ทำงานของ SuperUser (`CONTEXT.md` · `IMPROVEMENTS.md` · log) อยู่ใต้ `.claude/superuser/` ตาม `project-doc-set` ข้อ 1 ไม่วางที่รากโปรเจกต์ · ใช้ skill และ agent ของ plugin `software-company` เท่านั้น (ไม่ใช้ตัวชื่อซ้ำของ plugin อื่น) · เปิด skill ไม่ได้ → อ่าน `skills/<ชื่อ>/SKILL.md` ของ plugin · ไม่มี agent → ใช้ agent ทั่วไปพร้อมเปิด `agents/<ชื่อ>.md` · หาไม่เจอทั้ง 2 ทาง → ข้ามชิ้นนั้น ทำส่วนอื่นให้จบ แล้วรายงานว่าติด · ไม่มี `reviewer` หรือ `brainstormer` (plugin เวอร์ชันเก่า) → `general-purpose` ตัวใหม่ทำหน้าที่เดียวกัน (ตรวจอย่างเดียว ไม่แก้ · เสนอ 2–3 ทาง) · ไม่มี `learning-reviewer` → ข้ามรอบเรียนรู้แล้วจดไว้

**ภาษาและรูป:** ทุกเอกสารเขียนตาม skill `human-writing` · รูปในเอกสารส่งมอบใช้ `diagram-figures` · Mermaid (`software-diagrams`) ใช้ได้เฉพาะเอกสารภายในทีม

## 1. ตอบคำถามเชิงเทคนิค

playbook `investigation` · agent `system-analyst` (อ่านอย่างเดียว) · skill `code-orientation`
**ผลลัพธ์:** คำตอบในแชต + `docs/notes/<ปี-เดือน-วัน>-<เรื่อง>.md` · **ไม่แก้โค้ด**

### คำถาม (ผู้ใช้กรอก)

- คำถาม ("X ทำงานอย่างไร" · "ทำไมทำแบบนี้" · "ควรวางไว้ที่ไหน" · "แน่ใจไหมว่า..."):
- ส่วนของระบบที่เกี่ยว (ถ้ารู้):
- อยากให้อธิบายแบบสอน (ใช่ / ไม่):

### หัวข้อที่ต้องมี

1. คำตอบ 1 ประโยค
2. เส้นทางจากจุดเข้า (route · command · หน้าจอ) ถึงข้อมูลที่อ่าน/เขียน พร้อมไฟล์:บรรทัด
3. ข้ออ้างที่พิสูจน์ด้วยการรันได้ → รันจริง ติดป้าย `ตรวจจริง` · อ่านจากโค้ด (ไฟล์:บรรทัด) → `จากแหล่ง` · คิดต่อ → `อนุมาน`
4. ถ้าขอแบบสอน: อธิบายต่อชั้นจากสิ่งที่ผู้ใช้รู้แล้ว

### กฎเฉพาะฉบับนี้

- ต้องรันแอปเพื่อพิสูจน์ → ชี้ที่เก็บข้อมูลไปที่ `_to_delete/` ห้ามรันกับข้อมูลจริง
- ไม่มีไฟล์ในโปรเจกต์ถูกแก้ ยกเว้นโน้ตใน `docs/notes/`

## 2. ทำเองหรือใช้ของที่มีอยู่แล้ว

playbook `investigation` · agent `solution-architect` · skill `prior-art-review` · `adr-writer`
**ผลลัพธ์:** `docs/research/prior-art-<เรื่อง>.md` · ตัดสินแล้ว → บันทึกการตัดสินใจด้านสถาปัตยกรรม (ADR) ใน `docs/decisions/`

### เรื่องที่จะสร้าง (ผู้ใช้กรอก)

- จะสร้างอะไร (ไลบรารี · ฟีเจอร์ · โมเดล · บริการ):
- ข้อกำหนดที่ต้องได้ (อ่านจาก `docs/srs.md` ถ้ามี):
- ข้อจำกัด (ภาษา · license ที่รับได้ · ทำงานออฟไลน์ · งบ):
- ตัวเลือกที่รู้อยู่แล้ว:

### หัวข้อที่ต้องมี

1. ตัวเลือก 3–6 ตัว: license · ความเคลื่อนไหวล่าสุด (release · issue) · ตรงข้อกำหนดกี่ข้อ · ขนาด dependency
2. ข้อมูลทุกตัวมีลิงก์และวันที่ตรวจ
3. คำตัดสิน ใช้ตัวไหน / ห่อของที่มี / สร้างเอง พร้อมเหตุผล
4. ความเสี่ยงของตัวที่เลือก (เลิกพัฒนา · license เปลี่ยน) และทางถอย

## 3. ทดลองหลายแบบ ให้ผลรันตัดสิน

playbook `prototype` · agent `developer` · skill `parallel-attempts-pick-best` · `decision-log`
**ผลลัพธ์:** `docs/research/prototype-<เรื่อง>.md` · โค้ดทดลองใน `_to_delete/prototype-<เรื่อง>/` · **ไม่ย้ายโค้ดทดลองเข้าโปรเจกต์ตรง ๆ**

### โจทย์ (ผู้ใช้กรอก)

- คำถามที่จะให้การทดลองตอบ (ความเร็ว · หน้าตา · ใช้หน่วยความจำ · ใช้ได้จริงไหม):
- ทางเลือกที่อยากลอง (หรือให้ agent เสนอ):
- เกณฑ์ตัดสิน (ตัวเลขหรือสิ่งที่เห็นได้):
- ข้อมูลทดสอบ (path):

### หัวข้อที่ต้องมี

1. คำถามและเกณฑ์ เขียนก่อนเริ่มรัน
2. ทางเลือก 2–3 ทาง แบบเล็กที่สุดที่ตอบคำถามได้
3. ผลวัดทุกทาง ข้อมูลชุดเดียวกัน เครื่องเดียวกัน · ตารางตัวเลขหรือภาพเทียบ
4. ทางที่ชนะ · ผลก้ำกึ่ง → เลือกทางที่โค้ดน้อยกว่า
5. แถวใน decision log: เลือก · ไม่เลือก · ตัวเลข

### กฎเฉพาะฉบับนี้

- เรื่องรสนิยมหรือธุรกิจที่ทดลองไม่ได้ → ไม่ใช้ฉบับนี้ บอกผู้ใช้แล้วหยุด

## 4. หน้าจอจริงต้องตรงต้นแบบ

playbook `visual-parity` · agent `developer` + `ux-designer` · skill `app-verifier-setup` · `ui-craft` · `principle-prove-it-works`
**ผลลัพธ์:** `qa/visual-parity/<หน้าจอ>.md` + ภาพเทียบ `qa/visual-parity/img/` · **ไม่แก้โค้ด** เว้นแต่ข้างล่างติ๊ก `[x]`

- [ ] อนุญาตให้แก้โค้ดหน้าจอให้ตรงต้นแบบ (แก้ทีละกลุ่ม · ถ่ายภาพเทียบใหม่ทุกครั้ง · commit ต่อกลุ่ม) (commit บนเครื่องเท่านั้น บน branch แยก เช่น `fix/visual-parity-<หน้าจอ>` · ไม่ push · ไม่ merge เข้า branch หลัก)

### คู่ที่จะเทียบ (ผู้ใช้กรอก)

- ต้นแบบ (`mockup/<รหัส>-mockup.html` หรือภาพหน้าจอระบบเดิม):
- หน้าจอจริง (URL · หน้าจอในแอป):
- ขนาดหน้าต่างที่ใช้เทียบ (desktop · tablet · มือถือ):
- ข้อมูลทดสอบ / บัญชีทดสอบ (ใส่ใน environment variable ไม่ใช่ในไฟล์):

### หัวข้อที่ต้องมี

1. ภาพทั้งสองฝั่ง ขนาดหน้าต่างเดียวกัน ข้อมูลชุดเดียวกัน
2. ตาราง `| จุด | ต้นแบบ | ของจริง | แก้ที่ไฟล์ |` เรียงจากที่ผู้ใช้เห็นก่อน
3. จุดที่ต่างโดยตั้งใจ พร้อมเหตุผล (ต้นแบบผิดหลัก `ui-craft` · ทำจริงไม่ได้)
4. ผลกดทุกปุ่มบนหน้าจอจริง ไม่ดูแค่หน้าตา
