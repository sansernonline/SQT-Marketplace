# prompt-manual — คู่มือผู้ใช้และคู่มือฝึกอบรม

ใช้คู่กับ plugin `software-company` · ไฟล์นี้รวม prompt 2 ฉบับ แต่ละฉบับสร้างเอกสาร 1 ชุด

## วิธีใช้

วางทั้งไฟล์ใน Claude Code, Codex CLI หรือ Gemini CLI ที่รากโฟลเดอร์โปรเจกต์ แล้วพิมพ์ต่อท้ายว่าจะทำฉบับไหน เช่น `ทำทั้งหมด` หรือ `ทำข้อ 3 และ 4`

<!-- rules:begin -->
**กฎการทำงาน (agent ต้องทำตาม):** เปิด skill `superuser` ก่อนเริ่ม แล้วทำตาม playbook ที่ฉบับนั้นระบุ (ไม่ระบุ → `project-docs`) · กฎร่วม (ถามครั้งเดียว · ทำจบรอบเดียว · ตัดสินใจเอง · รายงานสถานะ) อยู่ใน skill `superuser` และ playbook ที่เดียว · ตัดสินใจเองและสถานะลง `docs/BUILD-PLAN.md` (ยังไม่มี → สร้าง) · ไฟล์ทำงานของ SuperUser (`CONTEXT.md` · `IMPROVEMENTS.md` · log) อยู่ใต้ `.claude/superuser/` ตาม `project-doc-set` ข้อ 1 ไม่วางที่รากโปรเจกต์ · ใช้ skill และ agent ของ plugin `software-company` เท่านั้น (ไม่ใช้ตัวชื่อซ้ำของ plugin อื่น) · เปิด skill ไม่ได้ → อ่าน `skills/<ชื่อ>/SKILL.md` ของ plugin · ไม่มี agent → ใช้ agent ทั่วไปพร้อมเปิด `agents/<ชื่อ>.md` · หาไม่เจอทั้ง 2 ทาง → ข้ามชิ้นนั้น ทำส่วนอื่นให้จบ แล้วรายงานว่าติด · ไม่มี `learning-reviewer` → ข้ามรอบเรียนรู้แล้วจดไว้

**แอปที่มีอยู่แล้ว (เมื่อทำคู่มือให้แอปที่มีอยู่แล้ว):** `docs/` และ `qa/` อยู่ที่รากโปรเจกต์ · README และ CHANGELOG อยู่ใน repo ของแอป · รากโปรเจกต์เป็น repo เดียวกับแอป → เอกสารเข้า branch เดียวกับโค้ด · ก่อนรันแอปหรือ seed ให้ชี้ที่เก็บข้อมูล (เช่น `DATA_DIR` · connection string) ไปที่ `_to_delete/` ห้ามรันกับข้อมูลจริง · คำสั่ง test ที่ repo ประกาศไว้พัง → รายงานผลของคำสั่งนั้นตรงตัว แล้วบอกคำสั่งที่ใช้แทนแยกบรรทัด · ห้ามมีรหัสผ่านหรือค่าลับในเอกสารและภาพ แม้เป็นบัญชีทดสอบ · ไม่มี `stack-*` ที่ตรงภาษา → ข้ามแล้วบอกในรายงาน

## 1. คู่มือผู้ใช้ปลายทาง (User Manual) แยกตามบทบาท

agent `technical-writer` · skill `polished-document-style` · `i18n-and-locale` · `branded-document-design` (ตอน render) · `e2e-testing-patterns` (ถ่ายภาพหน้าจอ)
**ต้องมีก่อน:** โปรแกรมที่รันได้ (คำสั่งรันใน `docs/README.md` · แอปที่มีอยู่แล้วใช้คำสั่งที่ลองจริงแล้วใน `docs/as-is/overview.md` · หรือที่ผู้ใช้ระบุ — README เดิมของแอปอาจไม่ตรงกับโค้ด) · `docs/<รหัส>-SRS-*.docx` (รู้ว่ามีบทบาทอะไร · อ่านด้วย `anthropic-skills:docx`) · แอปเดิมที่ไม่มี SRS ใช้ `docs/as-is/features.md` จาก `prompt-existing-code.md` ฉบับ 1 แทน
**ผลลัพธ์:** `docs/<รหัส>-MAN-<บทบาท>-v<M.m>-<สถานะ>.docx` + `.pdf` 1 ชุดต่อบทบาท (ร่าง `_to_delete/drafts/guide-<บทบาท>.md` → render ตามฉบับ 14 ของ `prompt-new-project.md`) · ภาพหน้าจอใน `docs/figures/<บทบาท>/`

### บทบาทที่ทำคู่มือ (ผู้ใช้กรอก · เว้นว่าง = agent เสนอจาก SRS แล้วติด `(รอยืนยัน)` ทำต่อได้)

- บทบาท · งานหลักที่บทบาทนี้ทำ · ภาษาของผู้อ่าน (ไทย/อังกฤษ):
- ผู้อ่านคุ้นกับคอมพิวเตอร์แค่ไหน:
- วิธีรันแอป · ชื่อตัวแปรบัญชีทดสอบแต่ละบทบาท (ใส่ใน environment variable ไม่ใช่ในไฟล์):

### ลำดับ

1. รันแอปตามคำสั่ง · รันไม่ได้ → หยุดและบอก **ห้ามเขียนคู่มือจาก mockup หรือจินตนาการ**
2. เตรียมข้อมูลตัวอย่างและบัญชีทดสอบของแต่ละบทบาท (ในสภาพแวดล้อมทดสอบเท่านั้น ห้ามใช้ข้อมูลจริงของใคร) · seed ใหม่ก่อนถ่ายภาพทุกชุด ให้ตัวเลขในภาพตรงกับคู่มือ
3. ทำรายการ "งานของบทบาทนี้" จาก FR ที่บทบาทนั้นใช้ แล้วลองทำทีละงานในแอปจริง
4. เขียนคู่มือตามโครงด้านล่าง · ถ่ายภาพหน้าจอด้วยเครื่องมือ (Playwright) ทุกขั้นที่ผู้อ่านอาจหลง พร้อมคำบรรยายใต้ภาพ · ใช้สคริปต์ตัวเดียวทั้งถ่ายภาพและเดินตามคู่มือในข้อ 5 · เก็บสคริปต์ไว้ที่ `qa/manual-shots/` เพื่อถ่ายใหม่เมื่อหน้าจอเปลี่ยน
5. ตรวจเองรอบ 2: ทำตามคู่มือที่เขียนทีละข้อ · จุดไหนทำแล้วไม่ตรงที่เขียน → แก้คู่มือ หรือลงคำถามค้างว่าเป็นบั๊ก

### โครงคู่มือ

1. **เริ่มต้นใช้งาน** — เข้าระบบอย่างไร · หน้าแรกมีอะไร (1 ภาพพร้อมหมายเลขชี้) · ศัพท์ที่ต้องรู้ไม่เกิน 10 คำ
2. **งานที่ทำบ่อย** — แต่ละงานมี: เป้าหมาย 1 บรรทัด · ก่อนเริ่มต้องมีอะไร · ขั้นตอนเรียงเลข (ข้อละ 1 การกระทำ) · ภาพ · ผลที่ควรเห็น
3. **งานที่ทำนาน ๆ ครั้ง** — รูปแบบเดียวกัน
4. **แก้ปัญหาเบื้องต้น** — ข้อความที่ผู้ใช้อาจเจอจริง (ดึงจากแอป) → ความหมาย → ทำอย่างไร → เมื่อไรต้องติดต่อใคร
5. **คำถามที่พบบ่อย** — เฉพาะที่มาจากงานจริง ไม่แต่ง
6. **ภาคผนวก** — คำศัพท์ · ทางลัด · ช่องทางขอความช่วยเหลือ (ผู้ใช้ให้ข้อมูล · ไม่มี → เว้นช่องให้เติม)

### กฎเฉพาะฉบับนี้

- ใช้ชื่อปุ่ม เมนู ข้อความบนจอตรงทุกตัวอักษร · ภาษาง่าย ประโยคสั้น ไม่ใช้ศัพท์เทคนิคที่ผู้ใช้ไม่ต้องรู้
- ห้ามอธิบายฟีเจอร์ที่บทบาทนี้มองไม่เห็น · บทบาทที่สิทธิ์ต่างกัน → เขียนแยกไฟล์ ไม่ปนกัน
- ภาพหน้าจอและคู่มือห้ามมีข้อมูลส่วนบุคคลจริง รหัสผ่าน หรือค่าลับ แม้เป็นบัญชีทดสอบ
- `<บทบาท>` ในชื่อไฟล์และโฟลเดอร์ภาพใช้ชื่อบทบาทในโค้ด ตัวพิมพ์เล็ก

## 2. คู่มือฝึกอบรมการใช้งาน (Training Guide)

agent `technical-writer` + `ux-designer` (ลำดับการเรียนรู้) · skill `polished-document-style` · `presentation-design` (ถ้าทำสไลด์) · `branded-document-design`
**ต้องมีก่อน:** `docs/<รหัส>-MAN-<บทบาท>-*.docx` (ถ้ามี · อ่านด้วย `anthropic-skills:docx` · ใช้เป็นแหล่งขั้นตอน โดยอ้างหัวข้อ ไม่คัดลอกซ้ำ) · โปรแกรมที่รันได้
**ผลลัพธ์:** `docs/training/` — `training-plan.md` · `facilitator-guide.md` · `exercises.md` (+ `quiz.md` ถ้าเลือก)

### ข้อมูลการอบรม (ผู้ใช้กรอก)

- ผู้เรียน (บทบาท จำนวนคน พื้นฐาน):
- เวลาที่มี (กี่ชั่วโมง / กี่ครั้ง) และรูปแบบ (ในห้อง / ออนไลน์):
- เป้าหมายหลังอบรม (ผู้เรียนต้อง "ทำอะไรได้"):
- มีสภาพแวดล้อมทดสอบ/ข้อมูลตัวอย่างให้ฝึกไหม:
- ต้องมีสไลด์ไหม: ☐ ใช่ ☐ ไม่ · ต้องมีแบบทดสอบไหม: ☐ ใช่ ☐ ไม่

### เอกสารที่ได้

| ไฟล์ | เนื้อหา |
|---|---|
| `training-plan.md` | วัตถุประสงค์ที่วัดได้ ("ผู้เรียนสร้าง … ได้ภายใน … นาที") · กลุ่มเป้าหมายและความรู้ก่อนเรียน · ตารางเวลาเป็นช่วง (หัวข้อ · วิธี บรรยาย/สาธิต/ลงมือ · นาที) · สิ่งที่ต้องเตรียม (บัญชีทดสอบ เครื่อง ข้อมูลตัวอย่าง) · เกณฑ์ว่า "ผ่านการอบรม" |
| `facilitator-guide.md` | แต่ละช่วงมี: เป้าหมาย · สิ่งที่ผู้สอนพูด/สาธิต (ทีละขั้น) · จุดที่ผู้เรียนมักพลาดและวิธีช่วย · คำถามชวนคิด · เวลา · ข้อควรระวังตอนสาธิต (เช่น ห้ามใช้ข้อมูลจริง) |
| `exercises.md` | แบบฝึกหัดเรียงจากง่ายไปยาก: โจทย์เป็นสถานการณ์จริงของผู้เรียน · ข้อมูลที่ให้ · ผลที่ควรได้ · แนวเฉลยสั้น ๆ · เวลา |
| `quiz.md` (เลือก) | ข้อสอบวัดตามวัตถุประสงค์ทีละข้อ · เฉลย · เกณฑ์ผ่าน · ข้อสอบต้องตอบได้จากสิ่งที่สอนจริงเท่านั้น |

### วิธีทำ

1. ตั้งวัตถุประสงค์จากงานจริงของบทบาท (จากคู่มือ/FR) · ทุกหัวข้อที่สอนต้องผูกกับวัตถุประสงค์อย่างน้อย 1 ข้อ · หัวข้อที่ไม่ผูกกับข้อไหน → ตัดทิ้ง
2. ลำดับ: งานที่ใช้ทุกวันก่อน → ขยายไปงานที่ซับซ้อน · แต่ละช่วงยาวไม่เกิน 45 นาที และเวลาอย่างน้อยครึ่งหนึ่งเป็นการลงมือทำ
3. ลองทำแบบฝึกหัดทุกข้อในแอปจริงก่อนเขียน · ข้อที่ทำไม่ได้หรือผลต่างจากที่เขียน → แก้หรือลงคำถามค้าง
4. ถ้าเลือกสไลด์: ทำตาม `presentation-design` · 1 สไลด์ 1 ประเด็น (ติ๊ก ☐ ใช่ ที่ช่องสไลด์ข้างบน = อนุมัติแล้ว ไม่ต้องถามซ้ำ · ไม่ติ๊ก → ไม่ทำสไลด์)

### กฎเฉพาะฉบับนี้

- ไม่แต่งตัวเลขเวลา/จำนวนคนที่ผู้ใช้ไม่ได้ให้ → `(รอยืนยัน)`
- ข้อมูลตัวอย่างต้องเป็นข้อมูลสมมติเท่านั้น
