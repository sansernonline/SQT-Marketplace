# prompt-proposal — เอกสารก่อนได้งาน (TOR · ประเมินงาน · proposal)

ใช้คู่กับ plugin `software-company` · ไฟล์นี้มี prompt 3 ฉบับ ทำเรียงกัน 1 → 2 → 3 · ใช้ตอนลูกค้าส่งขอบเขตงาน (Terms of Reference — TOR) หรือขอใบเสนอ ก่อนเซ็นสัญญา

เราเป็นฝั่งผู้ว่าจ้างที่ต้องเขียน TOR เอง → `prompt-tor.md` · ต้องพิสูจน์ว่าทำได้จริงก่อนยื่น → `prompt-poc.md`

## วิธีใช้

วางทั้งไฟล์ใน Claude Code, Codex CLI หรือ Gemini CLI ที่รากโฟลเดอร์โปรเจกต์ แล้วพิมพ์ต่อท้ายว่าจะทำฉบับไหน เช่น `ทำทั้งหมด` หรือ `ทำข้อ 2`

<!-- rules:begin -->
**กฎการทำงาน (agent ต้องทำตาม):** เปิด skill `superuser` ก่อนเริ่ม แล้วทำตาม playbook ที่ฉบับนั้นระบุ (ไม่ระบุ → `project-docs`) · กฎร่วม (ถามครั้งเดียว · ทำจบรอบเดียว · ตัดสินใจเอง · รายงานสถานะ) อยู่ใน skill `superuser` และ playbook ที่เดียว · ตัดสินใจเองและสถานะลง `docs/BUILD-PLAN.md` (ยังไม่มี → สร้าง) · ไฟล์ทำงานของ SuperUser (`CONTEXT.md` · `IMPROVEMENTS.md` · log) อยู่ใต้ `.claude/superuser/` ตาม `project-doc-set` ข้อ 1 ไม่วางที่รากโปรเจกต์ · ใช้ skill และ agent ของ plugin `software-company` เท่านั้น (ไม่ใช้ตัวชื่อซ้ำของ plugin อื่น) · เปิด skill ไม่ได้ → อ่าน `skills/<ชื่อ>/SKILL.md` ของ plugin · ไม่มี agent → ใช้ agent ทั่วไปพร้อมเปิด `agents/<ชื่อ>.md` · หาไม่เจอทั้ง 2 ทาง → ข้ามชิ้นนั้น ทำส่วนอื่นให้จบ แล้วรายงานว่าติด · ไม่มี `reviewer` หรือ `brainstormer` (plugin เวอร์ชันเก่า) → `general-purpose` ตัวใหม่ทำหน้าที่เดียวกัน (ตรวจอย่างเดียว ไม่แก้ · เสนอ 2–3 ทาง) · ไม่มี `learning-reviewer` → ข้ามรอบเรียนรู้แล้วจดไว้

**ภาษาและรูป:** ทุกเอกสารเขียนตาม skill `human-writing` · รูปในเอกสารส่งมอบใช้แบบเดียวกันทั้งชุด: ผังระบบ · flow · ผังคลาวด์ → `diagram-figures` · Mermaid (`software-diagrams`) ใช้ได้เฉพาะเอกสารภายในทีม

## กฎเฉพาะไฟล์นี้

- TOR และไฟล์จากลูกค้าวางไว้ใน `ref/` · อ่านอย่างเดียว ไม่แก้
- ทุกข้อในเอกสารอ้างเลขข้อของ TOR ได้ เช่น `TOR 4.2` · ข้อไหนเราเพิ่มเอง ติดป้าย `เสนอเพิ่ม`
- เรทค่าแรง กำไร และเงื่อนไขการจ่ายเงินเป็นข้อมูลของผู้ใช้ → ห้ามเดา ใส่ `(รอยืนยัน)`
- เอกสารนี้ส่งถึงลูกค้า → การส่งจริงอยู่ใน "รออนุมัติ" เสมอ

agent `business-analyst` · skill `srs-writing` · `simplicity-first`
**ผลลัพธ์:** `docs/proposal/tor-analysis.md`

### ข้อมูลงาน (ผู้ใช้กรอก)

- ชื่อลูกค้าและชื่องาน:
- ไฟล์ TOR ใน `ref/`:
- วันส่งข้อเสนอ:
- งบที่ลูกค้าบอก (ถ้ามี):

### หัวข้อที่ต้องมี

1. **สรุป 5 บรรทัด** — ลูกค้าอยากได้อะไร ใครใช้ ส่งเมื่อไร งบเท่าไร มีความเสี่ยงใหญ่อะไร
2. **ตารางข้อกำหนด** — เลขข้อ TOR · สิ่งที่ต้องทำ · ชัดแล้ว / ยังไม่ชัด / ขัดกันเอง
3. **คำถามถึงลูกค้า** — เรียงจากเรื่องที่กระทบราคามากสุด · ทุกข้อบอกว่าถ้าไม่ได้คำตอบ เราจะสมมติอะไร
4. **ข้อกำหนดแฝง** — สิ่งที่ TOR ไม่ได้เขียนแต่ต้องมีจริง เช่น ย้ายข้อมูลเดิม · อบรม · สำรองข้อมูล · PDPA
5. **เงื่อนไขที่เสี่ยง** — ค่าปรับ · ระยะรับประกัน · ทรัพย์สินทางปัญญา · การรับมอบงาน

### กฎเฉพาะฉบับนี้

- ข้อที่ตีความได้หลายทาง → เขียนทุกทาง แล้วบอกว่าเราจะสมมติทางไหนในข้อเสนอ

## 2. ประเมินงาน เวลา และราคา

agent `project-manager` + `solution-architect` · skill `architecture-patterns` · `simplicity-first`
**ต้องมีก่อน:** `docs/proposal/tor-analysis.md` · ไม่มี TOR แต่ทำ POC แล้ว (`prompt-poc.md`) → ใช้ `docs/poc/poc-plan.md` + `docs/poc/poc-report.md` แทน โดยข้ามฉบับ 1 · ทุกที่ที่ให้อ้างเลขข้อ TOR ให้อ้างหัวข้อของ POC แทน เช่น `POC-plan 3` · `POC-report 4`
**ผลลัพธ์:** `docs/proposal/estimate.md` · `docs/proposal/estimate.xlsx`

### ข้อมูลราคา (ผู้ใช้กรอก)

- เรทต่อวันแยกตามบทบาท:
- กำไรหรือเผื่อความเสี่ยงที่ต้องการ (%):
- ค่าใช้จ่ายอื่น (เซิร์ฟเวอร์ · license · เดินทาง):

### หัวข้อที่ต้องมี

1. **แนวทางที่เลือก** — ผังระบบ 1 รูป · เหตุผลที่เลือก 3 บรรทัด
2. **แตกงาน** — งานย่อยละไม่เกิน 5 วันคน · ทุกงานอ้างเลขข้อ TOR
3. **ประเมินแบบ 3 ค่า** — เร็วสุด · น่าจะเป็น · ช้าสุด → ค่าที่ใช้ = (เร็ว + 4 × น่าจะเป็น + ช้า) ÷ 6
4. **ตารางราคา** — วันคน × เรท + ค่าใช้จ่ายอื่น + เผื่อความเสี่ยง = ราคาเสนอ · คำนวณในไฟล์ .xlsx ด้วยสูตร ไม่คิดในหัว
5. **แผนเวลา** — งวดงาน · สิ่งที่ส่งแต่ละงวด · การจ่ายเงินแต่ละงวด
6. **สมมติฐาน** — ทุกข้อที่ถ้าเปลี่ยนแล้วราคาเปลี่ยน

### กฎเฉพาะฉบับนี้

- ตัวเลขใน .md กับ .xlsx ต้องตรงกันทุกตัว · ตรวจซ้ำก่อนจบ
- งานที่ยังประเมินไม่ได้ → แยกเป็นรายการ "ประเมินหลังศึกษาเพิ่ม" ไม่ใส่ตัวเลขลอย ๆ

## 3. เขียนข้อเสนอ (proposal)

agent `product-manager` + `technical-writer` · skill `polished-document-style` · `branded-document-design` (ตอน render) · `presentation-design` (ถ้าต้องนำเสนอ)
**ต้องมีก่อน:** `tor-analysis.md` (ไม่มี TOR → `poc-plan.md` + `poc-report.md` ตามฉบับ 2 · หัวข้อ 9 เป็นตารางตอบเกณฑ์ POC แทน) · `estimate.md`
**ผลลัพธ์:** `docs/proposal/proposal.md` → .docx + .pdf

### หัวข้อที่ต้องมี

1. **สรุปสำหรับผู้บริหาร** — 1 หน้า: ปัญหาของลูกค้า → สิ่งที่เราจะทำ → ได้อะไร → ราคาและเวลา
2. **ความเข้าใจโจทย์** — เล่าโจทย์ด้วยคำของลูกค้า อ้างเลขข้อ TOR
3. **แนวทางและสถาปัตยกรรม** — ผังระบบตามกฎ "ภาษาและรูป"
4. **ขอบเขต** — ทำ · ไม่ทำ · ทำถ้าตกลงเพิ่ม
5. **แผนงานและงวดส่งมอบ** — จาก `estimate.md`
6. **ทีมงาน** — บทบาทและหน้าที่ (ชื่อคนจริงผู้ใช้ใส่เอง)
7. **ราคาและเงื่อนไขการจ่าย** — จาก `estimate.md` ตรงทุกตัวเลข
8. **การรับประกันและดูแลหลังส่งมอบ**
9. **ตารางตอบ TOR ทีละข้อ** — เลขข้อ · ตอบสนองอย่างไร · อยู่หน้าไหนของข้อเสนอ

### กฎเฉพาะฉบับนี้

- ห้ามสัญญาสิ่งที่ไม่อยู่ใน `estimate.md`
- ผลงานเดิมและตัวเลขอ้างอิงต้องมาจากผู้ใช้ ห้ามแต่ง ไม่มี → ใส่ `[ผลงานอ้างอิง]`
