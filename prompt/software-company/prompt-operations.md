# prompt-operations — ดูแลระบบที่ใช้งานจริง: ระบบล่ม ทบทวนหลังเหตุ เฝ้าระวัง ภัยคุกคาม เก็บกวาด

ใช้คู่กับ plugin `software-company` · ไฟล์นี้รวม prompt 5 ฉบับ · ใช้หลังระบบขึ้นใช้งานจริงแล้ว · เตรียม deploy และ runbook → `prompt-release.md` · ตรวจโค้ดหาช่องโหว่ → `prompt-quality.md`

## วิธีใช้

วางทั้งไฟล์ใน Claude Code, Codex CLI หรือ Gemini CLI ที่รากโฟลเดอร์โปรเจกต์ แล้วพิมพ์ต่อท้ายว่าจะทำฉบับไหน เช่น `ทำข้อ 1`

## 1. รับมือระบบล่ม

playbook `investigation` · skill `incident-response` · agent `devops-engineer` (นำ) + `security-analyst` ถ้าเกี่ยวกับความปลอดภัย · skill `incident-runbook-template` · `observability-basics`
**ผลลัพธ์:** `docs/incidents/INC-<ปี-เดือน-วัน>-<เรื่อง>.md` อัปเดตตลอดเหตุ · **รออนุมัติ:** ทุกคำสั่งที่เปลี่ยนระบบจริง

### อาการ (ผู้ใช้กรอก)

- เกิดอะไร / เริ่มเมื่อไร (เวลาและเขตเวลา):
- ใครได้รับผลกระทบ / กี่คน:
- เปลี่ยนอะไรล่าสุด (deploy · config · ข้อมูล):
- log / dashboard / ข้อความ error (path หรือแปะ):
- runbook ที่มี (path):
- เข้าถึงอะไรได้บ้าง (log อย่างเดียว / server / cloud console):

### หัวข้อที่ต้องมี

1. สถานะบรรทัดเดียวบนสุด: `กำลังตรวจ / หยุดความเสียหายแล้ว / แก้แล้ว` + เวลาอัปเดตล่าสุด
2. ไทม์ไลน์ตามเวลาจริง: เห็นอะไร · ทำอะไร · ผลเป็นอย่างไร
3. สมมติฐาน แยก `ยืนยันแล้ว` กับ `กำลังตรวจ`
4. ทางหยุดความเสียหายก่อนหาสาเหตุ (rollback · ปิดฟีเจอร์ · เพิ่มเครื่อง) พร้อมคำสั่งที่รอผู้ใช้กด
5. ข้อความแจ้งผู้ใช้ระบบ / ลูกค้า (สั้น บอกผลกระทบและเวลาอัปเดตถัดไป)

### กฎเฉพาะฉบับนี้

- หยุดความเสียหายมาก่อนหาสาเหตุ
- เหตุด้านความปลอดภัย (ถูกเจาะ · ข้อมูลรั่ว) → เก็บหลักฐานก่อนแก้ ตาม `security-operations` · ข้อมูลส่วนบุคคลรั่ว → นับเวลา 72 ชั่วโมงตาม `pdpa-compliance`

## 2. ทบทวนหลังเหตุ (postmortem)

playbook `project-docs` · agent `devops-engineer` + `project-manager` · skill `postmortem-template` · `principle-fix-root-cause` · `repeated-mistakes-to-checks`
**ผลลัพธ์:** `docs/incidents/INC-<ปี-เดือน-วัน>-<เรื่อง>-postmortem.md` · แถวงานใน `docs/BUILD-PLAN.md`

### ข้อมูล (ผู้ใช้กรอก)

- เอกสารเหตุจากฉบับ 1 (path) หรือเล่าเหตุ:
- ระยะเวลาที่ระบบใช้ไม่ได้ / ผลกระทบที่วัดได้:
- คนที่เกี่ยว (ใช้บทบาท ไม่ใช้ชื่อ):

### หัวข้อที่ต้องมี

1. สรุป 3 บรรทัด: เกิดอะไร · กระทบใคร · แก้อย่างไร
2. ไทม์ไลน์ · เวลาตรวจพบ / หยุดความเสียหาย / แก้เสร็จ
3. สาเหตุเชิงระบบ (ไม่โทษคน) ถาม "ทำไม" จนถึงสิ่งที่แก้ได้
4. สิ่งที่ช่วยและสิ่งที่ถ่วง
5. งานที่ต้องทำต่อ: งาน · เจ้าของ (บทบาท) · วันครบกำหนด · ป้องกันแบบไหน (ตัวตรวจอัตโนมัติ > alert > เอกสาร)

## 3. แผนเฝ้าระวังระบบ

playbook `project-docs` (ติ๊กแก้โค้ด → ส่วนโค้ดใช้ `feature`) · agent `devops-engineer` · skill `observability-basics` · `logging-standards` · `notifications`
**ผลลัพธ์:** `docs/observability.md` · **ไม่แก้โค้ดหรือ config** เว้นแต่ข้างล่างติ๊ก `[x]`

- [ ] อนุญาตให้เพิ่ม log / metric ในโค้ดตามแผน (commit แยกต่อบริการ · test ผ่านทั้งชุด · commit บนเครื่องเท่านั้น บน branch แยก `obs/…` · ไม่ push · ไม่ merge เข้า branch หลัก)

### ระบบ (ผู้ใช้กรอก)

- บริการที่มี (อ่านจาก `docs/architecture.md` ถ้ามี):
- เครื่องมือที่ใช้หรืออยากใช้ (Grafana · Prometheus · Seq · Application Insights · CloudWatch · ยังไม่มี):
- แจ้งเตือนทางไหน (LINE · อีเมล · Teams · โทร):
- ช่วงเวลาที่ต้องมีคนรับเรื่อง:

### หัวข้อที่ต้องมี

1. 4 สัญญาณต่อบริการ (latency · traffic · errors · saturation) พร้อมชื่อ metric
2. รูปแบบ log เดียวทั้งระบบ · ระดับ log · correlation id · สิ่งที่ห้ามลง log
3. alert ที่ผู้ใช้รู้สึก (ไม่ใช่หน่วยประมวลผล (CPU) สูงอย่างเดียว) · เกณฑ์ · ส่งหาใคร · ลิงก์ runbook
4. dashboard 1 หน้าต่อบริการ: มีกราฟอะไร
5. ช่องว่างจากของที่มีตอนนี้ → ลำดับทำ

## 4. วิเคราะห์ภัยคุกคาม (threat model)

playbook `project-docs` · skill `threat-model` · agent `security-engineer` · skill `principle-secure-by-default` · `auth-implementation-patterns`
**ผลลัพธ์:** `docs/security/threat-model-<ส่วน>.md` · **ไม่แก้โค้ด**

### ขอบเขต (ผู้ใช้กรอก)

- ส่วนที่จะวิเคราะห์ (ทั้งระบบ / ฟีเจอร์ / API):
- ข้อมูลสำคัญที่ระบบเก็บ (ข้อมูลส่วนบุคคล · เงิน · ความลับทางการค้า):
- ใครเข้าถึงได้ (ผู้ใช้ทั่วไป · admin · ระบบภายนอก):
- ข้อกำหนดที่ต้องผ่าน (พ.ร.บ.คุ้มครองข้อมูลส่วนบุคคล (PDPA) · Payment Card Industry Data Security Standard (PCI-DSS) · ISO/IEC 27001 · ไม่มี):

### หัวข้อที่ต้องมี

1. ผังการไหลของข้อมูล พร้อมเส้นแบ่งความเชื่อถือ (trust boundary)
2. ตาราง STRIDE (ปลอมตัว · แก้ข้อมูล · ปฏิเสธการกระทำ · ข้อมูลรั่ว · ทำให้ใช้ไม่ได้ · ยกระดับสิทธิ์) ต่อองค์ประกอบ
3. ภัยแต่ละข้อ: โอกาส · ผลกระทบ · ป้องกันอยู่แล้วไหม (ไฟล์:บรรทัด) · ต้องเพิ่มอะไร
4. 5 เรื่องที่ต้องแก้ก่อน เรียงตามความเสี่ยง → แถวงานใน `docs/BUILD-PLAN.md`

## 5. เก็บกวาดเครื่องและโปรเจกต์

playbook `housekeeping` · agent `devops-engineer` · skill `temp-file-discipline` · `docker-sandbox`
**ผลลัพธ์:** ตาราง "รออนุมัติ" ในคำตอบ · ลบเฉพาะรายการที่ผู้ใช้อนุมัติ

### ขอบเขต (ผู้ใช้กรอก)

- เก็บกวาดอะไร (worktree · branch · Docker sandbox · image · `_to_delete/` · ทั้งหมด):
- โปรเจกต์ที่ห้ามแตะ:
- อนุมัติล่วงหน้าได้เลยไหม สำหรับกลุ่มที่ "ลบได้แน่" (ใช่ / ไม่):

### หัวข้อที่ต้องมี

1. รายการก่อนลบ: `| ของ | ขนาด | เหตุผลที่ลบได้ | ความเสี่ยง |` แยก "ลบได้แน่" กับ "ต้องถาม"
2. worktree ที่มีไฟล์ค้าง → เก็บ patch สำรองก่อนลบ
3. พื้นที่ที่ได้คืนหลังลบ
