# prompt-ai-feature — สร้างฟีเจอร์ที่ใช้ AI: เลือก model · ชุดทดสอบ · RAG · กันพัง · เฝ้าดูต้นทุน

ยังไม่ได้ทดสอบจริง

ใช้คู่กับ plugin `software-company` · ไฟล์นี้มี prompt 5 ฉบับ · ใช้เมื่อแอปจะเรียก Large Language Model (LLM) หรือ model AI อื่น เช่น แชตบอต · สรุปเอกสาร · ถอดเสียง · อ่านภาพ · ให้คะแนนหรือจัดหมวด · ยังไม่แน่ใจว่าทำได้จริง → `prompt-poc.md` ก่อน · ทั้งแอปยังไม่มีเอกสาร → `prompt-new-project.md`

## วิธีใช้

วางทั้งไฟล์ใน Claude Code, Codex CLI หรือ Gemini CLI ที่รากโฟลเดอร์โปรเจกต์ แล้วพิมพ์ต่อท้ายว่าจะทำฉบับไหน เช่น `ทำทั้งหมด` หรือ `ทำข้อ 1 และ 2`

- **ชุดทดสอบและเกณฑ์ผ่านมาก่อนเขียน prompt** · ห้ามแก้เกณฑ์หลังเห็นผล · จะแก้ → ลงเหตุผลใน `docs/BUILD-PLAN.md`

- ตัวเลขความแม่นมาจากการรันจริงเท่านั้น · ห้ามประมาณจากความรู้สึกหรือจากตัวอย่าง 2–3 ข้อ
- agent ที่ใช้: `ai-engineer` (นำ) · `product-manager` · `security-engineer` · `qa-tester` · `reviewer` ตรวจทุกฉบับ

## 1. ออกแบบฟีเจอร์ AI และเลือก model

playbook `project-docs` · agent `ai-engineer` + `product-manager` · skill `llm-engineering` · `simplicity-first` · `architecture-patterns` · `adr-writer`
**ผลลัพธ์:** `docs/ai/AI-DESIGN.md` · ADR การเลือก model ใน `docs/decisions/`

### โจทย์ (ผู้ใช้กรอก)

- ฟีเจอร์อะไร ผู้ใช้คือใคร:
- ตัวอย่างงานจริง 3–5 ชิ้น (path ใน `ref/`):
- ผิดแล้วเสียหายแค่ไหน (แค่รำคาญ · เสียเงิน · กระทบสุขภาพหรือกฎหมาย):
- ใช้ cloud ได้ไหม · ต้องรันในเครื่องหรือเซิร์ฟเวอร์ของเราเอง:
- งบต่อเดือน / ความเร็วที่รับได้ (วินาทีต่อคำตอบ):
- [ ] อนุญาตให้ส่งข้อมูลจริงไปผู้ให้บริการ AI (ไม่ติ๊ก → ใช้ข้อมูลตัวอย่างหรือที่ปิดชื่อแล้วเท่านั้น)

### หัวข้อที่ต้องมี

1. **งานที่ AI ทำ** — 1 ประโยค · input → output · ทำโดยไม่ใช้ AI ได้ไหม (กฎ · ค้นคำ · regex) → ได้ = เสนอทางนั้นก่อน
2. **ตัวเลือก model** — ตาราง `| model | cloud/เครื่องเรา | ราคาต่อ 1 ล้าน token หรือต่อครั้ง | ความเร็ว | ภาษาไทย | ข้อจำกัด | แหล่ง + วันที่ตรวจ |` อย่างน้อย 3 ตัว · ตัวที่เลือก ลง ADR
3. **ต้นทุนประมาณ** — คำขอต่อวัน × token ต่อคำขอ × ราคา = บาทต่อเดือน · แสดงวิธีคิดให้คิดซ้ำได้
4. **ผิดแล้วทำอย่างไร** — คนตรวจก่อนใช้ผลไหม · ผลที่ AI ไม่มั่นใจ → ส่งต่อคน · ปุ่มให้ผู้ใช้แจ้งว่าผิด
5. **ความเสี่ยง** — prompt injection จากข้อความผู้ใช้หรือเอกสาร · ข้อมูลรั่วข้ามผู้ใช้ · คำตอบแต่ง (hallucination) · ค่าใช้จ่ายพุ่ง · ผู้ให้บริการล่ม → ทางสำรอง

## 2. ชุดทดสอบ (eval) และเกณฑ์ผ่าน

playbook `project-docs` · agent `ai-engineer` + `qa-tester` · skill `llm-engineering` · `test-case-template` · `principle-prove-it-works`
**ต้องมีก่อน:** `docs/ai/AI-DESIGN.md`
**ผลลัพธ์:** `docs/ai/eval/eval-plan.md` · `docs/ai/eval/cases.jsonl`

### หัวข้อที่ต้องมี

1. **กรณีทดสอบ** — อย่างน้อย 30 กรณี (งานเสี่ยงสูง 100) แต่ละกรณีมี input · คำตอบที่ถูก หรือกฎตัดสินว่าถูก · ที่มาของคำตอบที่ถูก (เจ้าของงาน · เอกสาร · คนตรวจ) — ห้ามให้ model ตัวที่ทดสอบเป็นคนเฉลย
2. **ส่วนผสมของกรณี** — งานปกติ · ขอบ (ยาวมาก · ภาษาไทยปนอังกฤษ · พิมพ์ผิด · ภาพไม่ชัด) · ควรปฏิเสธ (นอกขอบเขต · ข้อมูลไม่พอ) · โจมตี (prompt injection · ขอข้อมูลคนอื่น)
3. **วิธีให้คะแนน** — ตรงตัว · ตามกฎในโค้ด · ให้ model อีกตัวตัดสินพร้อมเกณฑ์ (ต้องสุ่มให้คนตรวจซ้ำอย่างน้อย 10% ว่าตัดสินตรงคน)
4. **เกณฑ์ผ่าน** — ความถูกต้อง % · กรณีโจมตีหลุดได้ 0 · ความเร็ว · ต้นทุนต่อคำขอ · ทุกตัวเลขผู้ใช้ยืนยัน ไม่รู้ → ค่าแนะนำพร้อม `(รอยืนยัน)`
5. **วิธีรัน** — คำสั่งเดียวรันทั้งชุดแล้วได้ตาราง · รันซ้ำแล้วผลใกล้เดิม (ตั้ง temperature และ seed ถ้า model รองรับ)

### กฎเฉพาะฉบับนี้

- กรณีทดสอบใช้ข้อมูลตัวอย่างหรือที่ปิดชื่อแล้ว · ไม่มีเลขบัตรประชาชน · เบอร์โทร · ข้อมูลสุขภาพของคนจริง

## 3. ตอบจากเอกสารของเรา (RAG)

playbook `project-docs` · agent `ai-engineer` + `data-engineer` · skill `llm-engineering` · `database-design` · `principle-secure-by-default`
**ใช้เมื่อ:** AI ต้องตอบจากเอกสาร คู่มือ หรือข้อมูลของเรา — ไม่ต้อง ข้ามฉบับนี้
**ต้องมีก่อน:** `AI-DESIGN.md` · `eval-plan.md` (มีกรณีที่คำตอบอยู่ในเอกสาร และกรณีที่ไม่อยู่)
**ผลลัพธ์:** `docs/ai/RAG-DESIGN.md`

### หัวข้อที่ต้องมี

1. **แหล่งเอกสาร** — มีอะไร · กี่ไฟล์ · ใครแก้ · อัปเดตบ่อยแค่ไหน · ไฟล์ไหนห้ามให้บางคนเห็น
2. **ตัดเอกสารและเก็บ** — ตัดตามหัวข้อหรือตามความยาว · ภาษาไทยตัดคำอย่างไร · embedding model · ที่เก็บ (pgvector · ตัวอื่น) พร้อมเหตุผล
3. **ดึงและเรียง** — ค้นด้วยความหมาย + ค้นคำ · เรียงซ้ำ (rerank) ไหม · กี่ชิ้นต่อคำถาม
4. **สิทธิ์** — กรองเอกสารตามสิทธิ์ผู้ถามก่อนส่งให้ model ไม่ใช่หลังได้คำตอบ
5. **ตอบพร้อมที่มา** — ทุกคำตอบอ้างเอกสารและตำแหน่ง · ไม่เจอในเอกสาร → ตอบว่าไม่เจอ ไม่แต่ง
6. **วัดผลแยก 2 ชั้น** — ดึงถูกไหม (เอกสารที่ถูกอยู่ใน top-k กี่ %) · ตอบถูกไหม

## 4. สร้างและวัดผล

playbook `feature` (ยังไม่มีโค้ด → `new-project`) · agent `ai-engineer` + `developer` + `security-engineer` · skill `llm-engineering` · `lazy-coding` · `readable-code` · `config-and-secrets` · `error-handling-patterns` · `security-gate` · stack ตามภาษา (`stack-python` · `stack-typescript` · `stack-dotnet`)
**ต้องมีก่อน:** `AI-DESIGN.md` · `eval-plan.md` (· `RAG-DESIGN.md`)
**ผลลัพธ์:** โค้ดบน branch `ai/<ฟีเจอร์>` · `docs/ai/eval/results-<ปี-เดือน-วัน>.md` · **ไม่แก้โค้ด** เว้นแต่ข้างล่างติ๊ก `[x]`

- [ ] อนุญาตให้สร้างและแก้โค้ด (commit บนเครื่องเท่านั้น · ไม่ push · ไม่ merge เข้า branch หลัก)
- [ ] อนุญาตให้เรียก API ที่เสียเงินระหว่างทดสอบ (งบไม่เกิน ___ บาท)

### สิ่งที่ต้องได้

1. prompt อยู่ในไฟล์แยกจากโค้ด มีเลขรุ่น · ผลลัพธ์ที่โปรแกรมต้องอ่านต่อใช้ structured output แล้วตรวจ schema ทุกครั้ง
2. กันพัง: timeout · ลองใหม่แบบมีเพดาน · ผู้ให้บริการล่ม → ทางสำรองตาม `AI-DESIGN.md` หัวข้อ 5 · ข้อความจากผู้ใช้และเอกสารแยกจากคำสั่งระบบ ไม่ต่อ string ปนกัน
3. ทุกคำขอ log: เวลา · model · รุ่น prompt · token เข้า/ออก · ต้นทุน · เวลาตอบ · ไม่ log ข้อความเต็มที่มีข้อมูลส่วนบุคคล
4. ผลรันชุดทดสอบเทียบเกณฑ์ `| เกณฑ์ | ผ่านเมื่อ | ได้จริง | ผ่าน/ไม่ผ่าน |` · กรณีที่ล้มทุกข้อพร้อม input และคำตอบที่ได้
5. ต้นทุนจริงต่อคำขอจาก log เทียบกับที่ประมาณในฉบับ 1

### กฎเฉพาะฉบับนี้

- แก้ prompt ทีละอย่าง แล้วรันชุดทดสอบทั้งชุดทุกครั้ง · จดใน results ว่าแก้อะไร ผลเปลี่ยนเท่าไร
- ห้ามเพิ่มกรณีทดสอบที่ผ่านแล้วลบกรณีที่ล้มเพื่อให้ตัวเลขดีขึ้น

## 5. ขึ้นใช้งานจริงและเฝ้าดู

playbook `ship` · agent `ai-engineer` + `devops-engineer` · skill `llm-engineering` · `observability-basics` · `incident-runbook-template` · `logging-standards`
**ต้องมีก่อน:** ผลฉบับ 4 ผ่านเกณฑ์
**ผลลัพธ์:** `docs/ai/AI-OPS.md` · **รออนุมัติ:** เปิดให้ผู้ใช้จริง · ตั้งงบรายเดือนที่ผู้ให้บริการ

### หัวข้อที่ต้องมี

1. **เปิดทีละน้อย** — เริ่มกับผู้ใช้กลุ่มเล็ก หรือเปิดให้คนตรวจก่อนส่งผล · เกณฑ์ขยาย
2. **เฝ้าดู** — ต้นทุนต่อวัน · เวลาตอบ · อัตรา error · อัตราที่ผู้ใช้กดว่าผิด · alert เมื่อเกินเกณฑ์ · เพดานค่าใช้จ่ายที่ผู้ให้บริการ
3. **วนปรับปรุง** — คำตอบที่ผู้ใช้แจ้งว่าผิด → ปิดชื่อแล้วเพิ่มเป็นกรณีทดสอบ → แก้ → รันชุดเต็ม
4. **เมื่อคำตอบแย่ลง** — model ของผู้ให้บริการเปลี่ยนรุ่น · เอกสารใน RAG เปลี่ยน · ตรวจอะไรก่อน → ย้อนรุ่น prompt หรือ model ได้อย่างไร
