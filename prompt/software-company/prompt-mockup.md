# prompt-mockup — สร้าง ตรวจ และแก้ mockup ที่กดได้จริง

ยังไม่ได้ทดสอบจริง

ใช้คู่กับ plugin `software-company` · ไฟล์นี้รวม prompt 3 ฉบับ ทุกฉบับทำงานใน `mockup/` · `prompt-new-project.md` ฉบับ 5 และ 6 ชี้มาที่ฉบับ 1 และ 2 · เทียบหน้าจอจริงกับ mockup ใช้ `prompt-explore.md` ฉบับ 4

## วิธีใช้

วางทั้งไฟล์ใน Claude Code, Codex CLI หรือ Gemini CLI ที่รากโฟลเดอร์โปรเจกต์ แล้วพิมพ์ต่อท้ายว่าจะทำฉบับไหน เช่น `ทำข้อ 1 และ 2` หรือ `ทำข้อ 3`

**วนจนเสร็จ (agent loop):** ทุกฉบับวน ทำ → ตรวจ → แก้ → ตรวจซ้ำ จนผ่านทุกข้อที่ฉบับนั้นต้องมี · ตรวจด้วยหลักฐานจริง (เปิดไฟล์ · รันคำสั่ง · เทียบแหล่ง) ไม่ใช่คำบอกของตัวที่ทำ · รอบตรวจใช้ `reviewer` ตัวใหม่ทุกรอบ · ไม่ผ่าน → แก้ที่ต้นเหตุแล้วตรวจซ้ำทั้งข้อเดิมและจุดที่แก้ · เหลือแค่ข้อระดับต่ำ → ปิดได้แล้วลงรายงาน · ครบเพดานรอบ (งานกลาง 3 · งานใหญ่หรืองานเสี่ยง 5) ยังไม่ผ่าน → ติดป้าย `ติด` ทำส่วนอื่นให้จบ แล้วรายงานข้อที่เหลือ · รายละเอียดอยู่ใน skill `superuser` กฎข้อ 3

## กฎร่วมของไฟล์นี้

- ไม่มี `docs/README.md` → ถามผู้ใช้ครั้งเดียวก่อนเริ่ม: รหัสโปรเจกต์ · แพลตฟอร์ม (web · mobile · windows) · **แอปหรือโปรเจกต์ที่ชอบหน้าตา** (ลิงก์ · ชื่อแอป · path ในเครื่อง · คำบรรยาย · ไม่มี → เสนอ 3 แนวให้เลือก) · สีแบรนด์ใช้ถ้าผู้ใช้ให้มา ไม่มี → ได้จากทิศทางภาพที่เลือก (ฉบับ 1 ขั้น A) + `(รอยืนยัน)` ไม่หยุดถาม · มีไฟล์แต่ช่องแพลตฟอร์มว่าง → ถามแพลตฟอร์มก่อนเริ่ม แล้วเขียนลง `docs/README.md`
- คำถามตอนเริ่ม (ถามรวมครั้งเดียวกับข้อข้างบน ไม่ว่ามี `docs/README.md` หรือไม่): **เลือกแนวภาพเองไหม** (ใช่ → หยุดให้เลือกที่ฉบับ 1 ขั้น A ข้อ 5 · ไม่ → ผู้ตรวจเลือกให้) · มี mockup เดิมแล้วและสั่งทำใหม่ → **คงหน้าตาเดิมหรือออกแบบใหม่** (ไม่ตอบ = ออกแบบใหม่)
- **mockup เป็นไฟล์เดียว** `mockup/<รหัส>-mockup.html`: ทุกหน้าจอเป็น `<section id="s-<หน้าจอ>">` · สลับหน้าจอด้วย hash (`#s-login`) · CSS ของ skill แพลตฟอร์มและ JavaScript ฝังในไฟล์ (ไม่มี `<link>` ไป CSS ภายนอก ยกเว้นฟอนต์) · หน้าแรก `#s-start` มีตาราง "หน้าจอ → FR ที่รองรับ" (มี user story → เพิ่มคอลัมน์ `US-xxx`) ลิงก์ไปทุก section และหัวข้อ "ประวัติการแก้" · id ขึ้นต้น `s-` เสมอ ไม่ให้ชื่ออย่าง `#add` `#feed` ถูกตัวตรวจอ่านเป็นสี
- ตัวตรวจสี hardcode คือ `skills/web-app-design/scripts/check-design-tokens.mjs` ในโฟลเดอร์ที่ติดตั้ง plugin · token ฝังอยู่ในไฟล์ mockup จึงใช้ไฟล์ mockup เป็นไฟล์ token เอง (สีดิบได้เฉพาะบล็อก token ก่อนเส้นแบ่ง) · คำสั่งตามแพลตฟอร์ม:
  - web → `node <ตัวตรวจ> mockup/<รหัส>-mockup.html mockup --ext html`
  - windows → `node <ตัวตรวจ> mockup/<รหัส>-mockup.html mockup --ext html --marker "Type ramp" --require "<token ชุด Fluent>"` — ชุด `--require` อยู่ใน `windows-app-design` ข้อ 6
  - mobile → ส่ง `--require` ชุดใน `mobile-app-design` ข้อ 7
  - รันไม่ได้ → ตรวจ token ด้วยมือเทียบกับไฟล์ CSS ของ skill แพลตฟอร์ม แล้วจดไว้
- mockup คือข้อกำหนดที่มองเห็นได้ — ไม่ใส่ฟีเจอร์ที่ SRS ไม่มี · ไม่ต่อ backend จริง ข้อมูลเป็นค่าตัวอย่างในไฟล์ **ที่เหมือนของจริง** (ห้ามกล่องเทาว่างแทนเนื้อหา · ภาพจำลองวาดด้วย SVG/CSS)
- **mockup มี 2 ด่าน และต้องผ่านทั้งคู่:** ถูกต้อง (FR ครบ · กดได้ · 5 สถานะ · คอนทราสต์ · ไม่มีสี hardcode) **และ** สวย (ด่านสวย 5 แกนของ `ui-craft` ข้อ 9 · ทุกแกน ≥ 4 เทียบภาพแอปอ้างอิง) · ผ่านด่านถูกต้องอย่างเดียว = ยังไม่เสร็จ
- หมายเหตุของทีม (รหัส Q-/D- · "รอยืนยัน" · ข้อสมมติ) อยู่ในกล่อง MOCKUP ONLY หรือป้าย "หมายเหตุ mockup" ที่หน้าตาต่างจากข้อความโปรแกรม ห้ามปนในข้อความที่ผู้ใช้จะเห็น
- ห้ามแก้ SRS · FSD · `docs/USER-STORIES.md` · ไฟล์ใน `qa/` — เจอจุดขัดกันให้ลง `## คำถามค้าง` ใน `docs/BUILD-PLAN.md`
- มี `docs/research/` → อ้างรหัส `IMP-xx` / เลขแหล่ง ทุกครั้งที่หยิบแบบหน้าจอจากแอปต้นแบบมาใช้ · ห้ามลอกโลโก้ สี หรือภาพของแอปต้นแบบ

## 1. สร้าง mockup ที่กดได้จริง

agent `ux-designer` (ขั้น A) · `developer` (ขั้น B–C · มี shell) · `graphic-designer` (โลโก้) · skill `ui-craft` (ข้อ 0.1 ทิศทางภาพ · ข้อ 9 ด่านสวย) + skill ตามแพลตฟอร์มใน `docs/README.md`: web → `web-app-design` · mobile → `mobile-app-design` · windows → `windows-app-design` · `graphic-design` · `parallel-attempts-pick-best`

**ผลลัพธ์:** `docs/design/<รหัส>-design-directions.html` · `assets/logo/` · `mockup/<รหัส>-mockup.html` ไฟล์เดียว (ตามกฎร่วมข้างบน) · ภาพตรวจลง `_to_delete/`

### ขั้น A — ทิศทางภาพ (ทำก่อนวาดหน้าจอใด ๆ)

ทำตาม `ui-craft` ข้อ 0.1 ทั้ง 6 ขั้น (หน้าจอพระเอก · แอปอ้างอิง · 3 แนวขนาน · หน้าเทียบ · เลือก 1 · ตัวตนครบชุด) · ส่วนเฉพาะของไฟล์นี้:

1. อ่าน `docs/README.md` (แพลตฟอร์ม · แอปอ้างอิงหน้าตา · `doc-theme`) · ช่องแพลตฟอร์มว่าง → รวมไว้ในคำถามเดียวตอนเริ่ม · ไม่มีคำตอบ → web แล้วจดลง **ตัดสินใจเอง** · อ่าน SRS หรือ BRD ที่มีอยู่
2. 3 แนว: `ux-designer` ตัวใหม่แนวละตัว (`parallel-attempts-pick-best`) · ภาพแอปอ้างอิงเก็บที่ `_to_delete/ref-shots/` · หน้าเทียบ `docs/design/<รหัส>-design-directions.html`
3. เลือกแนวตามคำตอบตอนเริ่ม (กฎร่วม) · โลโก้โดย `graphic-designer` ลง `assets/logo/` · สีแบรนด์ที่ใช้จริงเขียนกลับลง `docs/README.md` ช่อง `doc-theme`

### ขั้น B — สร้าง mockup ตามแนวที่เลือก

1. ทำรายการ "หน้าจอ × FR" ให้ทุก FR ที่ผู้ใช้เห็นมีหน้าจอรองรับ · มี `docs/USER-STORIES.md` → ไล่ AC ของแต่ละ story ให้ทุกขั้นใน AC ทำได้บนหน้าจอ
2. **ทำ 3 หน้าจอหลักให้ผ่านด่านสวยก่อน** (หน้าจอพระเอก + หน้าใช้บ่อยที่สุด 2 หน้า) แล้วค่อยขยายไปหน้าที่เหลือโดยใช้คอมโพเนนต์จากหน้าหลัก
3. token มาจาก skill แพลตฟอร์มเป็นพื้น แล้วทับด้วย token ของแนวที่เลือก (สีแบรนด์ · ธีมเริ่มต้น · พื้นผิว) ในบล็อก token · **ห้ามใส่สี hardcode นอกบล็อก token**
4. **ทุกปุ่ม ลิงก์ และฟอร์มต้องทำงานได้จริง** — กดแล้วไปหน้าจอถัดไป เปิด/ปิด dialog เปลี่ยน tab หรือแสดงข้อความ ด้วย JavaScript เล็ก ๆ ในไฟล์ ห้ามมีปุ่มที่กดแล้วไม่เกิดอะไร (ปุ่มที่ตั้งใจให้ปิดไว้ต้อง `disabled` พร้อมเหตุผลที่มองเห็นได้)
5. ทุกหน้าจอที่มีข้อมูลต้องมีครบ **5 สถานะ** สลับดูได้ในหน้าเดียว (ปุ่มสลับวางที่มุมหน้าจอ มีเฉพาะใน mockup): ว่าง · กำลังโหลด · ผิดพลาด · บางส่วน · สำเร็จ
6. ข้อความบนหน้าจอเป็นภาษาของผู้ใช้จริง ใช้ข้อมูลตัวอย่างที่สมจริง ไม่ใช้ lorem ipsum · ข้อความ error ตรงกับที่ SRS/FSD กำหนด
7. ทำหน้าแรก `#s-start` ด้วย `ui-craft/scripts/mockup-start-page.py` ตาม `ui-craft/references/mockup-start-page.md` — ภาพย่อจริงทุกหน้าจอ + ตารางหน้าจอ → FR → US · ทุกหน้าจอในตารางต้องมี section จริง และทุก section อยู่ในตาราง

### ขั้น C — พิสูจน์ก่อนส่ง (developer รันจริง · agent หลักรันถ้า subagent ไม่มี shell)

1. รัน `check-design-tokens.mjs` ตามแพลตฟอร์มในกฎร่วม — ต้องไม่มีสี hardcode
2. Playwright: ทุก section × 5 สถานะ × 2 ธีม · console error 0 · id ซ้ำ 0 · กดทุกปุ่มแล้วมีผล · คอนทราสต์ ≥ 4.5:1 รวม placeholder · สคริปต์เก็บใน `_to_delete/mockup-check/`
3. ถ่ายภาพทุก section (`<ไฟล์>#s-<หน้าจอ>`) ทั้ง 2 ธีม ที่ความกว้างโทรศัพท์/เดสก์ท็อปตามแพลตฟอร์ม แล้วเปิดดูจริงอย่างน้อยหน้าจอหลัก 3 หน้า · ห้ามประกาศว่า "สวย" เอง — ส่งฉบับ 2
4. อัปเดต `docs/README.md` ว่ามี mockup แล้ว

### กฎเฉพาะฉบับนี้

- เจอ FR ที่ยังไม่มีหน้าจอรองรับ → ทำหน้าจอเพิ่ม หรือลงคำถามค้าง
- **มี mockup เดิมและสั่งทำใหม่ หรือหน้าตาเดิมไม่ผ่านด่านสวย (ไม่มีคะแนนบันทึกใน `docs/BUILD-PLAN.md` = ไม่ผ่าน) → เริ่มขั้น A ใหม่** · ห้ามรวมไฟล์เก่าแล้วคงหน้าตาเดิม เว้นแต่ผู้ใช้สั่งให้คง (`ui-craft` ข้อ 0 ข้อยกเว้น) · ไฟล์เก่าย้ายไป `_to_delete/old-mockup/` ไม่ลบ
- ค่าตั้งต้นของ skill แพลตฟอร์ม (เช่น Fluent สว่างของ `windows-app-design`) คือพื้น ไม่ใช่หน้าตาสุดท้าย
- ทำเสร็จแล้วส่งฉบับ 2 (การตรวจเดียวของ mockup · 2 ด่าน)

## 2. ตรวจ mockup 2 ด่าน (อ่านอย่างเดียว)

ใช้ subagent ที่ **ไม่ได้สร้างหรือแก้** mockup ตรวจ ห้ามแก้ไฟล์ · **2 ตัวแยกกัน:** `qa-tester` ตัวใหม่ (ด่านถูกต้อง · เขียนสคริปต์ตรวจเองใหม่ ไม่ใช้สคริปต์ของตัวสร้าง) + `graphic-designer` ตัวใหม่ (ด่านสวย · ไม่มี → `general-purpose`) · skill `ui-craft` + `e2e-testing-patterns`

### ด่าน 1 — ถูกต้อง (6 เรื่อง)

1. **ปุ่มหลอก** — เปิดไฟล์ mockup ด้วย Playwright ทีละ section (`<ไฟล์>#s-<หน้าจอ>` ตามตารางหน้าแรก) คลิกทุก `button` `a` `[role=button]` `input[type=submit]` ที่มองเห็นใน section นั้น บันทึกตัวที่ไม่เปลี่ยน hash ไม่เปลี่ยน DOM และไม่แสดงข้อความ (ยกเว้นที่ `disabled` พร้อมเหตุผล) · ผู้ตรวจไม่มี shell → agent หลักรัน Playwright แล้วส่งผลให้
2. **5 สถานะ** — หน้าจอที่มีข้อมูลต้องสลับเห็น ว่าง · กำลังโหลด · ผิดพลาด · บางส่วน · สำเร็จ ครบ
3. **สี** — รัน `check-design-tokens.mjs` (path และวิธีรันตามกฎร่วมข้างบน) ไม่มีสี hardcode · ความต่างสีตัวอักษรผ่านเกณฑ์ตาม `ui-craft`
4. **ความครอบคลุม FR** — ทุก FR ที่ผู้ใช้เห็นมีหน้าจอรองรับ และทุกหน้าจอผูกกับ FR อย่างน้อย 1 ข้อ
5. **เดินตาม story** — มี `docs/USER-STORIES.md` → ไล่ AC ของ story สถานะ Ready ทีละข้อบน mockup · ขั้นไหนกดต่อไม่ได้ให้บันทึก
6. **ลิงก์เสียและไฟล์เดียวจริง** — ทุก `href="#s-…"` มี section ปลายทาง · ไม่มี `<link>` หรือ `<script src>` ไปไฟล์ในเครื่อง (ฟอนต์ภายนอกได้) · ตารางหน้าแรกตรงกับ section ที่มีจริง

### ด่าน 2 — สวย (ดูภาพจริง ไม่อ่านโค้ด)

ทำตามด่านสวยใน `ui-craft/references/states-and-checks.md` ชุดที่ 3 (ภาพ · ผู้ตรวจ 2 ตัวใช้คะแนนที่ต่ำกว่า · 5 แกนพร้อมจุดยึดคะแนน 4 · เพดานรอบ) · ไม่ผ่าน → ปัญหา 2–3 ข้อต่อหน้าจอพร้อมวิธีแก้ระดับ CSS (ห้ามชม)

ตารางคะแนนด่านสวย 5 แกน · path ภาพที่ใช้ตัดสิน · ปิดท้ายด้วยสรุป 1 บรรทัด: **ผ่าน** (ด่าน 1 ไม่มีสูงและกลาง **และ** ด่าน 2 ทุกแกน ≥ 4) / ไม่ผ่าน และจำนวนปัญหาแต่ละระดับ

### กฎเฉพาะฉบับนี้

- ไม่ผ่าน → ตัวแก้ตัวใหม่แก้ แล้วส่งผู้ตรวจตัวใหม่ทั้ง 2 ด่านอีกรอบ · เพดานรอบตามด่านสวยใน `ui-craft` · ครบเพดานยังไม่ผ่านด่านสวย → กลับไปฉบับ 1 ขั้น A พร้อมคะแนนทุกรอบ ไม่แก้ทีละจุดต่อ · คะแนนทุกรอบลง `docs/BUILD-PLAN.md`
- หัวหน้าทีมแก้เองได้เฉพาะข้อความจุดเดียว และต้องรันสคริปต์ตรวจจุดนั้นซ้ำ

### ลำดับ

1. แยกแต่ละเรื่องเป็น 3 กลุ่ม: **แก้หน้าตา** (ตรงกับ SRS อยู่แล้ว) → แก้ได้เลย · **เปลี่ยนพฤติกรรม** (ขัดกับ FR หรือ AC) → แก้ได้เฉพาะเมื่อมี CR ที่อนุมัติแล้ว ไม่มี → ลงคำถามค้างและไม่แก้ · **ไม่ชัด** ("ดูไม่ทันสมัย") → ตีความเป็นข้อแก้ที่ตรวจได้ 1–3 ข้อ แล้วลงใน `## ตัดสินใจเอง` · **"ไม่สวย" "ไม่ว้าว" "อยากได้แบบแอป X"** → ให้คะแนนด่านสวยก่อน · ต่ำกว่า 4 ตั้งแต่ 2 แกนขึ้นไป → ทำฉบับ 1 ขั้น A ใหม่ (ใช้แอป X เป็นแอปอ้างอิง) ไม่แก้ทีละจุด
2. หาว่าแต่ละเรื่องกระทบหน้าจอไหนบ้าง (`blast-radius`) — แก้ token หรือ CSS ร่วม = กระทบทุกหน้า
3. แก้เฉพาะจุด ไม่เขียนหน้าใหม่ทั้งหน้า (ยกเว้นกรณีกลับไปขั้น A) · คงกฎของฉบับ 1 ทุกข้อ (ปุ่มกดได้ · 5 สถานะ · ไม่มีสี hardcode · ผ่านด่านสวย)
4. รัน `check-design-tokens.mjs` (ตามกฎร่วมข้างบน) แล้วทำฉบับ 2 (ทั้ง 2 ด่าน) กับหน้าจอที่แก้ และข้อเดิมทุกข้อของรอบก่อน
5. เพิ่มแถวใน "ประวัติการแก้" ของหน้าแรก `#s-start`: วันที่ · หน้าจอ · แก้อะไร · ที่มา (ความเห็นลูกค้า / CR-xxx)

### กฎเฉพาะฉบับนี้

- mockup ที่ส่งลูกค้าไปแล้วให้เก็บรุ่นก่อนแก้ไว้ใน `_to_delete/mockup-<วันที่>/` เพื่อเทียบ
- รายงานท้ายงาน: เรื่องที่แก้แล้ว · เรื่องที่ไม่แก้และเหตุผล · เอกสารที่อาจต้องแก้ตาม (FSD · test case · user manual) — บอกเท่านั้น ไม่แก้เอง
