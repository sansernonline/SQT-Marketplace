# prompt-mockup — สร้าง ตรวจ และแก้ mockup ที่กดได้จริง

ใช้คู่กับ plugin `software-company` · ไฟล์นี้รวม prompt 3 ฉบับ ทุกฉบับทำงานใน `mockup/` · `prompt-new-project.md` ฉบับ 5 และ 6 ชี้มาที่ฉบับ 1 และ 2 · เทียบหน้าจอจริงกับ mockup ใช้ `prompt-explore.md` ฉบับ 4

## วิธีใช้

วางทั้งไฟล์ใน Claude Code, Codex CLI หรือ Gemini CLI ที่รากโฟลเดอร์โปรเจกต์ แล้วพิมพ์ต่อท้ายว่าจะทำฉบับไหน เช่น `ทำข้อ 1 และ 2` หรือ `ทำข้อ 3`

<!-- rules:begin -->
**กฎการทำงาน (agent ต้องทำตาม):** เปิด skill `superuser` ก่อนเริ่ม แล้วทำตาม playbook ที่ฉบับนั้นระบุ (ไม่ระบุ → `project-docs`) · กฎร่วม (ถามครั้งเดียว · ทำจบรอบเดียว · ตัดสินใจเอง · รายงานสถานะ) อยู่ใน skill `superuser` และ playbook ที่เดียว · ตัดสินใจเองและสถานะลง `docs/BUILD-PLAN.md` (ยังไม่มี → สร้าง) · ไฟล์ทำงานของ SuperUser (`CONTEXT.md` · `IMPROVEMENTS.md` · log) อยู่ใต้ `.claude/superuser/` ตาม `project-doc-set` ข้อ 1 ไม่วางที่รากโปรเจกต์ · ใช้ skill และ agent ของ plugin `software-company` เท่านั้น (ไม่ใช้ตัวชื่อซ้ำของ plugin อื่น) · เปิด skill ไม่ได้ → อ่าน `skills/<ชื่อ>/SKILL.md` ของ plugin · ไม่มี agent → ใช้ agent ทั่วไปพร้อมเปิด `agents/<ชื่อ>.md` · หาไม่เจอทั้ง 2 ทาง → หยุดและบอกผู้ใช้ · ไม่มี `learning-reviewer` → ข้ามรอบเรียนรู้แล้วจดไว้
<!-- rules:end -->

**ภาษา:** ข้อความบนหน้าจอและรายงานเขียนตาม skill `human-writing`

| # | งาน | ได้ไฟล์ |
|---|---|---|
| 1 | สร้าง mockup ที่กดได้จริง | `mockup/<รหัส>-mockup.html` ไฟล์เดียว — ทุกหน้าจอเป็น section · หน้าแรกเป็นตาราง หน้าจอ → FR · CSS/JS ฝังในไฟล์ |
| 2 | ตรวจ mockup (อ่านอย่างเดียว) | ตารางปัญหาในคำตอบ (เขียนลง `_to_delete/mockup-review.md` ถ้ายาวเกิน 40 แถว) |
| 3 | แก้ mockup ตามความเห็นลูกค้าหรือคำขอเปลี่ยน | `mockup/<รหัส>-mockup.html` ที่แก้ · ประวัติการแก้ในหน้าแรกของไฟล์ |

## กฎร่วมของไฟล์นี้

- ไม่มี `docs/README.md` → ถามผู้ใช้ 3 ค่าก่อนเริ่ม: รหัสโปรเจกต์ · แพลตฟอร์ม (web · mobile · windows) · สีแบรนด์ · มีไฟล์แต่ช่องแพลตฟอร์มว่าง → ถามแพลตฟอร์มก่อนเริ่ม แล้วเขียนลง `docs/README.md`
- **mockup เป็นไฟล์เดียว** `mockup/<รหัส>-mockup.html`: ทุกหน้าจอเป็น `<section id="s-<หน้าจอ>">` · สลับหน้าจอด้วย hash (`#s-login`) · CSS ของ skill แพลตฟอร์มและ JavaScript ฝังในไฟล์ (ไม่มี `<link>` ไป CSS ภายนอก ยกเว้นฟอนต์) · หน้าแรก `#s-start` มีตาราง "หน้าจอ → FR ที่รองรับ" (มี user story → เพิ่มคอลัมน์ `US-xxx`) ลิงก์ไปทุก section และหัวข้อ "ประวัติการแก้" · id ขึ้นต้น `s-` เสมอ ไม่ให้ชื่ออย่าง `#add` `#feed` ถูกตัวตรวจอ่านเป็นสี
- ตัวตรวจสี hardcode คือ `skills/web-app-design/scripts/check-design-tokens.mjs` ในโฟลเดอร์ที่ติดตั้ง plugin · token ฝังอยู่ในไฟล์ mockup จึงใช้ไฟล์ mockup เป็นไฟล์ token เอง (สีดิบได้เฉพาะบล็อก token ก่อนเส้นแบ่ง) · คำสั่งตามแพลตฟอร์ม:
  - web → `node <ตัวตรวจ> mockup/<รหัส>-mockup.html mockup --ext html`
  - windows → `node <ตัวตรวจ> mockup/<รหัส>-mockup.html mockup --ext html --marker "Type ramp" --require "<token ชุด Fluent>"` — ชุด `--require` อยู่ใน `windows-app-design` ข้อ 6
  - mobile → ส่ง `--require` ชุดใน `mobile-app-design` ข้อ 6
  - รันไม่ได้ → ตรวจ token ด้วยมือเทียบกับไฟล์ CSS ของ skill แพลตฟอร์ม แล้วจดไว้
- mockup คือข้อกำหนดที่มองเห็นได้ — ไม่ใส่ฟีเจอร์ที่ SRS ไม่มี · ไม่ต่อ backend จริง ข้อมูลเป็นค่าตัวอย่างในไฟล์
- ห้ามแก้ SRS · FSD · `docs/USER-STORIES.md` · ไฟล์ใน `qa/` — เจอจุดขัดกันให้ลง `## คำถามค้าง` ใน `docs/BUILD-PLAN.md`
- มี `docs/research/` → อ้างรหัส `IMP-xx` / เลขแหล่ง ทุกครั้งที่หยิบแบบหน้าจอจากแอปต้นแบบมาใช้ · ห้ามลอกโลโก้ สี หรือภาพของแอปต้นแบบ

## 1. สร้าง mockup ที่กดได้จริง

agent `ux-designer` · skill `ui-craft` + skill ตามแพลตฟอร์มใน `docs/README.md`: web → `web-app-design` · mobile → `mobile-app-design` · windows → `windows-app-design`
**ต้องมีก่อน:** `docs/README.md` · SRS หรือ BRD (`docs/<รหัส>-SRS-*.docx` / `docs/<รหัส>-BRD-*.docx` อ่านด้วย `anthropic-skills:docx` · ทำคู่กับ SRS ได้ → ใช้ร่างใน `_to_delete/drafts/`) · `docs/USER-STORIES.md` ถ้ามี
**ผลลัพธ์:** `mockup/<รหัส>-mockup.html` ไฟล์เดียว (ตามกฎร่วมข้างบน) · ภาพตรวจลง `_to_delete/`

### หน้าจอที่ต้องทำ (ผู้ใช้กรอก · ว่างให้ agent เสนอจาก FR แล้วทำต่อเลย ลงรายการหน้าจอที่เสนอใน `## ตัดสินใจเอง`)

- <!-- ชื่อหน้าจอ · FR ที่หน้าจอนี้รองรับ -->

### ลำดับ

1. อ่าน `docs/README.md` (แพลตฟอร์ม · `doc-theme` accent) · ช่องแพลตฟอร์มว่าง → ถามผู้ใช้ก่อนทำต่อ (ไม่เดาเอง) แล้วอ่าน SRS หรือ BRD ที่มีอยู่ · ทำรายการ "หน้าจอ × FR" ให้ทุก FR ที่ผู้ใช้เห็นมีหน้าจอรองรับ · มี `docs/USER-STORIES.md` → ไล่ AC ของแต่ละ story ให้ทุกขั้นใน AC ทำได้บนหน้าจอ
2. ทุกหน้าจอใช้ token สีและ CSS จาก skill ของแพลตฟอร์ม · **ห้ามใส่สี hardcode**
3. **ทุกปุ่ม ลิงก์ และฟอร์มต้องทำงานได้จริง** — กดแล้วไปหน้าจอถัดไป เปิด/ปิด dialog เปลี่ยน tab หรือแสดงข้อความ ด้วย JavaScript เล็ก ๆ ในไฟล์ ห้ามมีปุ่มที่กดแล้วไม่เกิดอะไร (ปุ่มที่ตั้งใจให้ปิดไว้ต้อง `disabled` พร้อมเหตุผลที่มองเห็นได้)
4. ทุกหน้าจอที่มีข้อมูลต้องมีครบ **5 สถานะ** สลับดูได้ในหน้าเดียว (ปุ่มสลับวางที่มุมหน้าจอ มีเฉพาะใน mockup): ว่าง · กำลังโหลด · ผิดพลาด · บางส่วน · สำเร็จ
5. ข้อความบนหน้าจอเป็นภาษาของผู้ใช้จริง ใช้ข้อมูลตัวอย่างที่สมจริง ไม่ใช้ lorem ipsum · ข้อความ error ตรงกับที่ SRS กำหนด
6. ทำหน้าแรก `#s-start` ตามกฎร่วม — ทุกหน้าจอในตารางต้องมี section จริง และทุก section อยู่ในตาราง
7. ตรวจเอง (agent หลักรันถ้า subagent ไม่มี shell): รัน `check-design-tokens.mjs` ตามแพลตฟอร์มในกฎร่วม — ต้องไม่มีสี hardcode · ถ่ายภาพทุก section (`<ไฟล์>#s-<หน้าจอ>`) ที่ความกว้างโทรศัพท์/เดสก์ท็อปตามแพลตฟอร์ม แล้วเปิดดูจริง
8. อัปเดต `docs/README.md` ว่ามี mockup แล้ว

### กฎเฉพาะฉบับนี้

- เจอ FR ที่ยังไม่มีหน้าจอรองรับ → ทำหน้าจอเพิ่ม หรือลงคำถามค้าง
- ทำเสร็จแล้วให้ทำฉบับ 2 ต่อด้วย subagent ตัวใหม่ก่อนส่งงาน

## 2. ตรวจ mockup (อ่านอย่างเดียว)

ใช้ subagent ที่ **ไม่ได้สร้าง** mockup ตรวจ ห้ามแก้ไฟล์ · skill `ui-craft` + `e2e-testing-patterns`
**ต้องมีก่อน:** `mockup/<รหัส>-mockup.html` · `docs/<รหัส>-SRS-*.docx` (อ่านด้วย `anthropic-skills:docx`) · `docs/README.md`
**ผลลัพธ์:** ตารางปัญหาในคำตอบ (เขียนลง `_to_delete/mockup-review.md` ถ้ายาวเกิน 40 แถว)

### ตรวจ 6 เรื่อง

1. **ปุ่มหลอก** — เปิดไฟล์ mockup ด้วย Playwright ทีละ section (`<ไฟล์>#s-<หน้าจอ>` ตามตารางหน้าแรก) คลิกทุก `button` `a` `[role=button]` `input[type=submit]` ที่มองเห็นใน section นั้น บันทึกตัวที่ไม่เปลี่ยน hash ไม่เปลี่ยน DOM และไม่แสดงข้อความ (ยกเว้นที่ `disabled` พร้อมเหตุผล) · ผู้ตรวจไม่มี shell → agent หลักรัน Playwright แล้วส่งผลให้
2. **5 สถานะ** — หน้าจอที่มีข้อมูลต้องสลับเห็น ว่าง · กำลังโหลด · ผิดพลาด · บางส่วน · สำเร็จ ครบ
3. **สี** — รัน `check-design-tokens.mjs` (path และวิธีรันตามกฎร่วมข้างบน) ไม่มีสี hardcode · ความต่างสีตัวอักษรผ่านเกณฑ์ตาม `ui-craft`
4. **ความครอบคลุม FR** — ทุก FR ที่ผู้ใช้เห็นมีหน้าจอรองรับ และทุกหน้าจอผูกกับ FR อย่างน้อย 1 ข้อ
5. **เดินตาม story** — มี `docs/USER-STORIES.md` → ไล่ AC ของ story สถานะ Ready ทีละข้อบน mockup · ขั้นไหนกดต่อไม่ได้ให้บันทึก
6. **ลิงก์เสียและไฟล์เดียวจริง** — ทุก `href="#s-…"` มี section ปลายทาง · ไม่มี `<link>` หรือ `<script src>` ไปไฟล์ในเครื่อง (ฟอนต์ภายนอกได้) · ตารางหน้าแรกตรงกับ section ที่มีจริง

### รูปแบบรายงาน

| # | section (`#s-…`) | ปัญหา | ระดับ (สูง/กลาง/ต่ำ) | วิธีแก้ที่แนะนำ |
|---|---|---|---|---|

ปิดท้ายด้วยสรุป 1 บรรทัด: ผ่าน / ไม่ผ่าน และจำนวนปัญหาแต่ละระดับ

## 3. แก้ mockup ตามความเห็นลูกค้าหรือคำขอเปลี่ยน

agent `ux-designer` · skill `ui-craft` + skill ตามแพลตฟอร์ม · `blast-radius`
**ต้องมีก่อน:** `mockup/<รหัส>-mockup.html` · `docs/<รหัส>-SRS-*.docx` · `docs/change/CR-<เลข 3 หลัก>-<เรื่อง>.md` ถ้าเป็นคำขอเปลี่ยน (จาก `prompt-change.md`)
**ผลลัพธ์:** `mockup/<รหัส>-mockup.html` ที่แก้ · หัวข้อ "ประวัติการแก้" ในหน้าแรก `#s-start`

### สิ่งที่ต้องแก้ (ผู้ใช้กรอก · 1 บรรทัดต่อ 1 เรื่อง)

- <!-- หน้าจอ · สิ่งที่ลูกค้าพูดหรือขอ (คำพูดจริง) · เลข CR ถ้ามี -->

### ลำดับ

1. แยกแต่ละเรื่องเป็น 3 กลุ่ม: **แก้หน้าตา** (ตรงกับ SRS อยู่แล้ว) → แก้ได้เลย · **เปลี่ยนพฤติกรรม** (ขัดกับ FR หรือ AC) → แก้ได้เฉพาะเมื่อมี CR ที่อนุมัติแล้ว ไม่มี → ลงคำถามค้างและไม่แก้ · **ไม่ชัด** ("ดูไม่ทันสมัย") → ตีความเป็นข้อแก้ที่ตรวจได้ 1–3 ข้อ แล้วลงใน `## ตัดสินใจเอง`
2. หาว่าแต่ละเรื่องกระทบหน้าจอไหนบ้าง (`blast-radius`) — แก้ token หรือ CSS ร่วม = กระทบทุกหน้า
3. แก้เฉพาะจุด ไม่เขียนหน้าใหม่ทั้งหน้า · คงกฎของฉบับ 1 ทุกข้อ (ปุ่มกดได้ · 5 สถานะ · ไม่มีสี hardcode)
4. รัน `check-design-tokens.mjs` (ตามกฎร่วมข้างบน) แล้วทำฉบับ 2 เฉพาะหน้าจอที่แก้ ด้วย subagent ตัวใหม่
5. เพิ่มแถวใน "ประวัติการแก้" ของหน้าแรก `#s-start`: วันที่ · หน้าจอ · แก้อะไร · ที่มา (ความเห็นลูกค้า / CR-xxx)

### กฎเฉพาะฉบับนี้

- mockup ที่ส่งลูกค้าไปแล้วให้เก็บรุ่นก่อนแก้ไว้ใน `_to_delete/mockup-<วันที่>/` เพื่อเทียบ
- รายงานท้ายงาน: เรื่องที่แก้แล้ว · เรื่องที่ไม่แก้และเหตุผล · เอกสารที่อาจต้องแก้ตาม (FSD · test case · user manual) — บอกเท่านั้น ไม่แก้เอง
