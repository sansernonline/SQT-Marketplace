# prompt-existing-code — มีแอปอยู่แล้ว ได้รับมอบหมายให้ทำเอกสาร

ใช้คู่กับ plugin `software-company` · ไฟล์นี้รวม prompt 5 ฉบับ · ใช้เมื่อมีแอปที่ใช้งานอยู่แล้วแต่เอกสารไม่มีหรือไม่ตรง แล้วต้องทำ spec คู่มือ หรือเอกสารเทคนิค · ทุกฉบับเขียนเอกสารอย่างเดียว ไม่แก้โค้ด

## วิธีใช้

วางทั้งไฟล์ใน Claude Code, Codex CLI หรือ Gemini CLI ที่รากโฟลเดอร์โปรเจกต์ แล้วพิมพ์ต่อท้ายว่าจะทำฉบับไหน เช่น `ทำทั้งหมด` หรือ `ทำข้อ 3 และ 4`

<!-- rules:begin -->
**กฎการทำงาน (agent ต้องทำตาม):** เปิด skill `superuser` ก่อนเริ่ม แล้วทำตาม playbook ที่ฉบับนั้นระบุ (ไม่ระบุ → `project-docs`) · กฎร่วม (ถามครั้งเดียว · ทำจบรอบเดียว · ตัดสินใจเอง · รายงานสถานะ) อยู่ใน skill `superuser` และ playbook ที่เดียว · ตัดสินใจเองและสถานะลง `docs/BUILD-PLAN.md` (ยังไม่มี → สร้าง) · ไฟล์ทำงานของ SuperUser (`CONTEXT.md` · `IMPROVEMENTS.md` · log) อยู่ใต้ `.claude/superuser/` ตาม `project-doc-set` ข้อ 1 ไม่วางที่รากโปรเจกต์ · ใช้ skill และ agent ของ plugin `software-company` เท่านั้น (ไม่ใช้ตัวชื่อซ้ำของ plugin อื่น) · เปิด skill ไม่ได้ → อ่าน `skills/<ชื่อ>/SKILL.md` ของ plugin · ไม่มี agent → ใช้ agent ทั่วไปพร้อมเปิด `agents/<ชื่อ>.md` · หาไม่เจอทั้ง 2 ทาง → ข้ามชิ้นนั้น ทำส่วนอื่นให้จบ แล้วรายงานว่าติด · ไม่มี `reviewer` หรือ `brainstormer` (plugin เวอร์ชันเก่า) → `general-purpose` ตัวใหม่ทำหน้าที่เดียวกัน (ตรวจอย่างเดียว ไม่แก้ · เสนอ 2–3 ทาง) · ไม่มี `learning-reviewer` → ข้ามรอบเรียนรู้แล้วจดไว้
<!-- rules:end -->

**ภาษาและรูป:** ทุกเอกสารเขียนตาม skill `human-writing` · รูปในเอกสารส่งมอบใช้แบบเดียวกันทั้งชุด: ผังระบบ · flow · ผังคลาวด์ → `diagram-figures` · Mermaid (`software-diagrams`) ใช้ได้เฉพาะเอกสารภายในทีม

**แอปที่มีอยู่แล้ว (ใช้ทุกฉบับ):** `docs/` และ `qa/` อยู่ที่รากโปรเจกต์ · README และ CHANGELOG อยู่ใน repo ของแอป · รากโปรเจกต์เป็น repo เดียวกับแอป → เอกสารเข้า branch เดียวกับโค้ด · ก่อนรันแอปหรือ seed ให้ชี้ที่เก็บข้อมูล (เช่น `DATA_DIR` · connection string) ไปที่ `_to_delete/` ห้ามรันกับข้อมูลจริง · คำสั่ง test ที่ repo ประกาศไว้พัง → รายงานผลของคำสั่งนั้นตรงตัว แล้วบอกคำสั่งที่ใช้แทนแยกบรรทัด · ห้ามมีรหัสผ่านหรือค่าลับในเอกสารและภาพ แม้เป็นบัญชีทดสอบ · ไม่มี `stack-*` ที่ตรงภาษา → ข้ามแล้วบอกในรายงาน

**ข้อมูลแอป (ผู้ใช้กรอก ใช้ร่วมทุกฉบับ):**

- วิธีรันแอป · ชื่อตัวแปรบัญชีทดสอบแต่ละบทบาท (ใส่ใน environment variable ไม่ใช่ในไฟล์):

| # | เอกสาร | ได้ไฟล์ |
|---|---|---|
| 1 | ย้อนสร้างเอกสารจากโค้ดที่มีอยู่ (Reverse Spec) | ไฟล์ใน `docs/as-is/` |
| 2 | SRS ฉบับส่งมอบจากสภาพปัจจุบัน | `docs/srs.md` |
| 3 | FSD ต่อโมดูลจากสภาพปัจจุบัน | `docs/fsd-<โมดูล>.md` |
| 4 | เอกสารเชิงเทคนิค (API · data dictionary) · runbook ทำที่ `prompt-release.md` ฉบับ 3 | ตามชนิดที่เลือก |
| 5 | คู่มือผู้ใช้ | ทำที่ `prompt-manual.md` ฉบับ 1 |

**ลำดับที่แนะนำ:** ทำฉบับ 1 ก่อนเสมอ เพราะฉบับ 2–5 อ่านจาก `docs/as-is/` · ต้องการแค่คู่มือ → ทำฉบับ 1 เฉพาะ `features.md` (พร้อม `findings.md` · `README.md` ที่ทำเสมอ) แล้วไปฉบับ 5 ได้เลย

## 1. ย้อนสร้างเอกสารจากโค้ดที่มีอยู่ (Reverse Spec)

agent `solution-architect` + `system-analyst` · skill `legacy-spec-recovery` · `architecture-patterns` · `software-diagrams` · `database-design` · `prior-art-review` · `polished-document-style`
**ผลลัพธ์:** ไฟล์ใน `docs/as-is/` — **อ่านโค้ดอย่างเดียว ห้ามแก้โค้ด** · รัน test และเปิดแอปบนเครื่องได้ตามกฎแอปที่มีอยู่แล้วข้างบน (แทน rule 4 ของ `legacy-spec-recovery`) · ทุกข้อความในเอกสารคือ "สิ่งที่โค้ดทำ" ไม่ใช่ "สิ่งที่ควรทำ"

### ขอบเขต (ผู้ใช้กรอก)

- ระบบนี้ทำอะไรโดยย่อ (ตามที่ผู้ใช้เข้าใจ):
- โฟลเดอร์/โมดูลที่ต้องย้อน (เว้นว่าง = ทั้ง repo ยกเว้น `node_modules` `bin` `obj` `dist` `.git` และไฟล์ generate):
- เอกสารเดิมที่พอมี (README, wiki, บันทึกเก่า):
- ต้องการเอกสารชุดไหน: ☐ ภาพรวม/สถาปัตยกรรม ☐ ข้อมูล ☐ API ☐ รายการฟังก์ชัน (FR) ☐ การตั้งค่า/การรัน
- ทำเสมอแม้ไม่ติ๊ก: `findings.md` · `docs/as-is/README.md` · และไฟล์ที่ฉบับอื่นที่สั่งในรอบเดียวกันต้องใช้ (ฉบับ 2 และ 5 → `features.md` · ฉบับ 3 → `overview.md` · ฉบับ 4 → `api.md` หรือ `data.md`)

### วิธีทำ

1. **สำรวจโครงก่อน** — รายการโฟลเดอร์ ภาษา เฟรมเวิร์ก จุดเริ่มต้นของโปรแกรม ไฟล์ตั้งค่า (รอบแรกอ่านลึกไม่เกิน 2 ระดับโฟลเดอร์) · repo ใหญ่ → ส่ง subagent 1 ตัวต่อโมดูล ให้ส่งกลับเฉพาะสรุปตามหัวข้อด้านล่าง
2. เขียนเอกสารตามที่เลือก แต่ละไฟล์ระบุ **ระดับความมั่นใจ** ต่อข้อ: `จากแหล่ง` ✅ อ่านในโค้ด (ชี้ไฟล์:บรรทัด) · `จากแหล่ง` 📄 จากเอกสารเดิม (มั่นใจกลาง) · `อนุมาน` 🟡 (จากชื่อหรือโครง) · `ยังไม่ตรวจ` ❓ — ป้ายชุดเดียวกับ `legacy-spec-recovery` และ `evidence` ของ superuser · เอกสารเดิมขัดกับโค้ด → ลงทั้ง 2 ป้ายและเป็นคำถามถึงเจ้าของระบบ
3. ส่วนที่เป็น "เจตนาทางธุรกิจ" ที่โค้ดบอกไม่ได้ → ลงเป็นคำถามถึงเจ้าของระบบ ห้ามเดา

### เอกสารที่ได้ (เลือกตามขอบเขต)

| ไฟล์ | เนื้อหา |
|---|---|
| `docs/as-is/overview.md` | ระบบทำอะไร · ผู้ใช้/ระบบภายนอก · เทคโนโลยี · C4 context + container (Mermaid ไม่เกิน 7 กล่อง) · วิธี build/รัน/ทดสอบที่ทำได้จริง |
| `docs/as-is/data.md` | ตาราง/collection · คอลัมน์ · ความสัมพันธ์ (ER) · ข้อมูลส่วนบุคคลที่พบ |
| `docs/as-is/api.md` | endpoint ทั้งหมดที่พบ: เมธอด+path · ผู้เรียก/การยืนยันตัวตน · ข้อมูลเข้า-ออกหลัก |
| `docs/as-is/features.md` | รายการสิ่งที่โค้ดทำได้ ใช้รหัสชั่วคราว `AS-001…` · ข้อละ 1 ประโยค + ตำแหน่งในโค้ด + ระดับความมั่นใจ · ใช้เป็นร่างตั้งต้นของ SRS |
| `docs/as-is/config-and-run.md` | ตัวแปรสภาพแวดล้อม/ไฟล์ตั้งค่า (ชื่อ+ความหมาย **ไม่ใส่ค่าลับ**) · ระบบภายนอกที่ต้องต่อ |
| `docs/as-is/findings.md` | สิ่งที่น่ากังวลที่เจอระหว่างอ่าน (โค้ดที่ไม่ถูกเรียกใช้ · ไม่มี test · คีย์ฝังในโค้ด · ช่องโหว่ชัดเจน) เป็นตารางสั้น ไม่ใช่รายงานตรวจเต็ม · และ **คำถามถึงเจ้าของระบบ** · ทำเสมอ |
| `docs/as-is/README.md` | สารบัญไฟล์ใน `docs/as-is/` · ตารางความครอบคลุม (ส่วนไหนอ่านแล้ว ส่วนไหนยัง) ตาม `legacy-spec-recovery` · ทำเสมอ |

### กฎเฉพาะฉบับนี้

- ทุกข้อเท็จจริงต้องชี้ไฟล์:บรรทัดได้ · ข้อที่ชี้ไม่ได้ → ติดป้าย `อนุมาน`
- ไม่สรุปว่าโค้ด "ถูก" หรือ "ควรเป็นอย่างไร" · เขียนแต่สภาพปัจจุบัน · ข้อเสนอแนะใส่ใน `findings.md` เท่านั้น
- ค้นโค้ดต้องจำกัดขอบเขต (ระบุ path/glob) ทุกครั้ง
- ชื่อไฟล์ใช้ตามตารางข้างบน ไม่ใช้ชื่อ `01-…06-` ของ `legacy-spec-recovery` · ใช้ skill นั้นเพื่อวิธีทำ (ป้าย · ชั้นหลักฐาน · ตารางความครอบคลุมใน `docs/as-is/README.md`) · กฎธุรกิจที่อ่านได้จากโค้ดลงหัวข้อแยกท้าย `features.md`
- ก่อนส่ง เปิดไฟล์:บรรทัดที่อ้างจริงอย่างน้อย 2 จุดต่อไฟล์ต้นทาง รวมไฟล์ HTML และไฟล์ตั้งค่า · นับเลขบรรทัดจากไฟล์ใน repo ไม่ใช่จากผลค้นหาที่ตัดหรือรวมบรรทัด · ไฟล์ไหนผิด 1 จุด → ตรวจทุกจุดของไฟล์นั้นใหม่ · บอกจำนวนจุดที่ตรวจในรายงาน

## 2. SRS ฉบับส่งมอบจากสภาพปัจจุบัน

agent `business-analyst` + `system-analyst` · skill `srs-writing` · `polished-document-style`
**ต้องมีก่อน:** `docs/as-is/features.md` จากฉบับ 1
**ผลลัพธ์:** `docs/srs.md` โครงตาม skill `srs-writing` (หัวข้อเดียวกับ `prompt-new-project.md` ฉบับ 3) — **ไม่แก้โค้ด · ไม่แก้ข้อความเดิมใน `docs/as-is/`** (เพิ่มแถวใหม่ใน `findings.md` ได้ ใช้กับฉบับ 3–5 ด้วย)

### ลำดับ

1. ยก `AS-xxx` แต่ละข้อขึ้นเป็น FR · เก็บรหัสเดิมไว้ในคอลัมน์ "ที่มา" ให้ย้อนกลับไปหาโค้ดได้
2. รวมข้อที่ซ้ำ แยกข้อที่ใหญ่เกิน · บทบาทผู้ใช้ดึงจากการตรวจสิทธิ์ในโค้ด
3. ทุก FR ติดระดับความมั่นใจต่อจากฉบับ 1 · ข้อ `อนุมาน` หรือ `ยังไม่ตรวจ` รวมไว้ในหัวข้อ "รอเจ้าของระบบยืนยัน" ท้ายเอกสาร
4. NFR (ความเร็ว ความพร้อมใช้ ความปลอดภัย) ที่โค้ดไม่ได้บอก → ใส่ `(รอยืนยัน)` ห้ามตั้งตัวเลขเอง · ข้อนี้แทนกฎ "NFR ต้องมีตัวเลข" ของ `prompt-new-project.md` ฉบับ 3
5. ระบบเดิมไม่มี BRD → ตารางสืบย้อนใช้ `AS → FR → test` แทน `BR → FR` · คอลัมน์ความสำคัญใส่ `(รอยืนยัน)` ให้เจ้าของระบบจัด

### กฎเฉพาะฉบับนี้

- SRS นี้บรรยายสิ่งที่ระบบทำ **ตอนนี้** · ความต้องการใหม่ไม่ใส่ที่นี่ ให้ทำเป็น change request ตาม `prompt-change.md` ฉบับ 1
- เขียนหน้าแรกให้ชัดว่า "เอกสารนี้ย้อนสร้างจากโค้ด ณ commit `<hash>` วันที่ `<วันที่>`"

## 4. เอกสารเชิงเทคนิค (เลือกหนึ่งชนิดต่อครั้ง)

agent `technical-writer` หรือ `system-analyst` · skill `polished-document-style` · `software-diagrams` · `api-conventions` (API-SPEC) · `database-design` (DATA-DICTIONARY)
**ต้องมีก่อน:** ไฟล์ที่เกี่ยวใน `docs/as-is/` จากฉบับ 1
**ผลลัพธ์:** หัวข้อและที่เก็บไฟล์ตาม `prompt-new-project.md` ฉบับ 10 (`docs/API-SPEC.md` · `docs/DATA-DICTIONARY.md`) — **ไม่แก้โค้ด**

**ชนิดที่ต้องการ:** <!-- API-SPEC / DATA-DICTIONARY --> · RUNBOOK → ทำที่ `prompt-release.md` ฉบับ 3 โดยใช้ `docs/as-is/overview.md` และ `config-and-run.md` เป็นข้อมูลระบบ

### กฎเฉพาะฉบับนี้

- API-SPEC อ่านจาก `docs/as-is/api.md` แล้วเติมจากโค้ด · DATA-DICTIONARY อ่านจาก `docs/as-is/data.md` และ schema หรือ migration จริง
- บรรยายสิ่งที่มีอยู่ ไม่ใช่สิ่งที่ควรมี · ส่วนที่ขาด เช่น endpoint ไม่มี health check → ลงใน `docs/as-is/findings.md` ไม่ใช่ในเอกสารนี้
- หัวข้อของฉบับ 10 ที่โค้ดไม่มี (ping · health · version) ไม่ต้องใส่ · รูปแบบ error บันทึกตามที่โค้ดส่งจริง ไม่แปลงเป็น problem+json
- ฟิลด์บังคับหรือไม่ · ค่าเริ่มต้น · รหัส error ยืนยันด้วยการเรียก API จริงบนเครื่อง ไม่อ่านจากโค้ดอย่างเดียว
