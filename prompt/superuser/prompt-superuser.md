# prompt-superuser — งานทั่วไป + ฉบับกลางที่ใช้ได้กับทุก plugin

ใช้คู่กับ plugin `superuser` (ฉบับ 1–3 และ 6) หรือ plugin ใดก็ได้ในชุด (ฉบับ 4–5) · ไฟล์นี้รวม prompt 6 ฉบับ · 1 ฉบับ = 1 งาน

## วิธีใช้

1. เปิด Claude Code, Codex CLI หรือ Gemini CLI ที่**โฟลเดอร์งาน**
2. กรอกช่อง "ผู้ใช้กรอก" ของฉบับที่จะทำ · ฉบับ 4–5 ใส่ชื่อ plugin ในช่อง "plugin"
3. วางทั้งไฟล์ แล้วพิมพ์ต่อท้ายว่าจะทำฉบับไหน เช่น `ทำข้อ 1`

**กฎการทำงาน (agent ต้องทำตาม):** ฉบับ 1–3 และ 6 เปิด skill `superuser` ของ plugin `superuser` · ฉบับ 4–5 เปิด skill `superuser` ของ plugin ที่ผู้ใช้กรอก · แล้วทำตาม playbook ที่ฉบับนั้นระบุทุกขั้น · กฎร่วม (อ่าน `.claude/superuser/CONTEXT.md` ก่อนเริ่ม · ถามแบบเลือกคำตอบตอนเริ่มและตอนจบ ไม่หยุดถามกลางทาง · บันทึกการตัดสินใจ · รายการ "รออนุมัติ" · รอบเรียนรู้ · ตารางสถานะตอนจบ) อยู่ใน skill นั้นที่เดียว ไม่เขียนซ้ำที่นี่ · ช่อง "ผู้ใช้กรอก" ที่ยังว่างและจุดที่ต้องเลือก → ถามรวมครั้งเดียวก่อนเริ่ม แบบเลือกคำตอบ ทุกตัวเลือกมีหลักฐาน ไม่ได้คำตอบ → ใส่ `(รอยืนยัน)` แล้วทำต่อ · เปิดผ่านคำสั่ง skill ไม่ได้ → อ่าน `skills/<ชื่อ>/SKILL.md` ในโฟลเดอร์ plugin แทน · หาไม่เจอ → ข้ามชิ้นนั้น ทำส่วนอื่นให้จบ แล้วรายงานว่าติด

**ภาษาและไฟล์:** เขียนตาม `human-writing` · โครงคำตอบตาม `answer-shape`

| # | งาน | plugin | playbook | ได้ไฟล์ |
|---|---|---|---|---|
| 1 | หาข้อมูลที่ยืนยันได้ | `superuser` | `research` | `docs/research/<หัวข้อ>.md` (ไม่มี `docs/` → โฟลเดอร์งาน) |
| 2 | ทำเอกสารที่คนอื่นจะอ่าน | `superuser` | `document` | `docs/<ชื่อเอกสาร>.md` (+ `.docx` / `.pdf` ถ้าขอ · ไม่มี `docs/` → โฟลเดอร์งาน) |
| 3 | ตรวจงานก่อนส่ง | `superuser` | `review` | คำตัดสินในคำตอบ · ไม่สร้างไฟล์ |
| 4 | งานยาวที่ผู้ใช้ไม่อยู่ดู | ทุก plugin | `unattended-run` | ตามงาน · `.claude/superuser/CONTEXT.md` อัปเดตทุกชิ้น |
| 5 | รวมบทเรียนเข้า skill | ทุก plugin | `learn-from-session` | ตารางเสนอแก้ skill (เดิม → ใหม่) |
| 6 | ทำ superuser ให้ plugin สาขาใหม่ | `superuser` | — (ตาม `ADAPT.md`) | โฟลเดอร์ plugin ใหม่ใน repo |

ใช้ต่อกัน: งานใหญ่ที่ยังไม่รู้ข้อมูล → 1 → 2 → 3 · ทำงานกับ plugin ไหนสักพักแล้วทีมพลาดซ้ำ → 5

## 1. หาข้อมูลที่ยืนยันได้

playbook `research` (Reranker · ReAct ตาม `agent-patterns`)
**ผลลัพธ์:** `docs/research/<หัวข้อ>.md` — คำตอบก่อน ตารางคะแนนแหล่งไว้ท้าย · ทุกข้ออ้างมีป้าย `ตรวจจริง` · `จากแหล่ง` · `อนุมาน` · `ยังไม่ตรวจ` · ข้อมูลของผู้ใช้ที่ไม่รู้ใส่ `(รอยืนยัน)`

### ข้อมูล (ผู้ใช้กรอก)

- คำถาม 1–3 ข้อ:
- จะเอาคำตอบไปทำอะไร:
- ตอบได้แค่ไหนถึงพอ (ตัวเลขเดียว · เทียบตัวเลือก · ภาพรวม):
- แหล่งที่ต้องใช้ / ห้ามใช้:
- ภาษา / ประเทศ / ช่วงเวลาของข้อมูล:

### ต้องมีในผลงาน

1. คำตอบตรงคำถาม 1 ย่อหน้า
2. ทุกตัวเลขและข้ออ้างมีลิงก์ · วันที่ตรวจ · ป้าย
3. แหล่งขัดกัน → บอกว่าขัดตรงไหน และใช้ค่าจากแหล่งทางการ
4. เรื่องที่ยังไม่รู้ บอกตรง ๆ
5. ตารางคะแนนแหล่ง (ตรงคำถาม · น่าเชื่อถือ · ใหม่พอ · ครบ)

## 2. ทำเอกสารที่คนอื่นจะอ่าน

playbook `document` (Planning · Reflection)
**ผลลัพธ์:** `docs/<ชื่อเอกสาร>.md` (+ `.docx` / `.pdf` ถ้าขอ) · **รออนุมัติ:** ส่งถึงผู้อ่าน

### ข้อมูล (ผู้ใช้กรอก)

- เอกสารอะไร (รายงาน · แผน · สรุป · จดหมาย · ข้อความสำคัญ):
- ผู้อ่านคือใคร / อ่านแล้วต้องทำอะไร:
- ข้อเท็จจริงและไฟล์ประกอบ (path):
- ความยาว / รูปแบบไฟล์:
- ภาษา:

### ต้องมีในผลงาน

1. ข้อสรุปขึ้นก่อน → เหตุผล → รายละเอียด → สิ่งที่ผู้อ่านต้องทำ
2. ข้อเท็จจริงที่ไม่มีหลักฐาน → `(รอยืนยัน)` ไม่แต่ง
3. ตรวจโดย agent ตัวใหม่ที่อ่านแบบผู้อ่านจริง ก่อนส่ง

## 3. ตรวจงานก่อนส่ง

playbook `review` · agent ตัวใหม่อย่างน้อย 2 มุม (ผู้ทำ · ผู้รับ)
**ผลลัพธ์:** คำตัดสิน `ผ่าน / แก้ก่อนส่ง` · **ไม่แก้ไฟล์เอง**

### ข้อมูล (ผู้ใช้กรอก)

- ไฟล์ที่จะให้ตรวจ:
- จะส่งให้ใคร / ใช้ทำอะไร:
- เกณฑ์ที่ต้องผ่าน (ถ้ามี):

### ต้องมีในผลงาน

1. คำตัดสิน 1 บรรทัด
2. ตารางปัญหาที่ยืนยันแล้ว: ตำแหน่ง · ปัญหา · ระดับ (สูง / กลาง / ต่ำ) · วิธีแก้ (เดิม → ใหม่)
3. ข้อที่ตรวจแล้วผ่าน

## 4. งานยาวที่ผู้ใช้ไม่อยู่ดู

playbook `unattended-run` ของ plugin ที่กรอก
**ผลลัพธ์:** งานตามที่สั่ง · `.claude/superuser/CONTEXT.md` หัวข้อ "รับงานต่อ" อัปเดตทุกชิ้น · รายงานครั้งเดียวตอนจบ

### ข้อมูล (ผู้ใช้กรอก)

- plugin:
- งานทั้งหมด (เช่น "เตรียมสมัคร 5 ตำแหน่งให้ครบชุด" · "ลงสินค้าใหม่ 20 ตัว"):
- เสร็จเมื่อ (ไฟล์ไหนต้องมี · ตารางไหนต้องครบ):
- สิ่งที่ห้ามทำเองแม้ไม่มีใครอยู่ (นอกเหนือจาก "รออนุมัติ" ของ plugin):
- จะกลับมาดูเมื่อไร:

### ต้องมีในผลงาน

1. เงื่อนไขจบที่ตรวจได้ เขียนไว้บนสุดของ `.claude/superuser/CONTEXT.md` ก่อนเริ่ม
2. ทุกชิ้น: สถานะ `เสร็จ` / `ติด` (พร้อมเหตุผล) · ชิ้นที่พัง 2 รอบ → แตกขั้นย่อย · ครบ 3 รอบ → `ติด` แล้วไปชิ้นอื่น
3. รายงานตอนจบ: เสร็จอะไร · ติดอะไร · ตัดสินใจเองกี่ข้อ · รออนุมัติอะไร · ค้างอะไรให้ผู้ใช้ตัดสิน

## 5. รวมบทเรียนเข้า skill

playbook `learn-from-session` ของ plugin ที่กรอก
**ผลลัพธ์:** ตารางเสนอแก้ skill (skill · เดิม → ใหม่ · หลักฐาน · ครั้ง) · **ยังไม่แก้ไฟล์** จนผู้ใช้เห็นด้วย

### ข้อมูล (ผู้ใช้กรอก)

- plugin:
- โปรเจกต์ที่ใช้งานมา (path · หลายที่ได้):
- เรื่องที่ทีมพลาดซ้ำที่ผู้ใช้สังเกตเอง (ถ้ามี):
- path ของ repo SQT-Marketplace (เว้นว่าง = เปิด agent ที่ราก repo นั้นอยู่แล้ว):

### ต้องมีในผลงาน

1. รวบรวมจากคิวกลาง `~/.claude/superuser/improvements.md` · `.claude/superuser/learn/` · `.claude/superuser/IMPROVEMENTS.md` ของทุกโปรเจกต์ที่กรอก
2. เรื่องที่เกิดครั้งเดียว → ทิ้ง · เกิดซ้ำ → ทำเป็นตัวตรวจ ไม่ใช่คำเตือน
3. ตารางเสนอแก้ เรียงตามจำนวนครั้ง
4. ผู้ใช้เห็นด้วย → แก้ทีละย่อหน้า · คำสั่ง `node scripts/...` รันที่ราก repo SQT-Marketplace (เปิด agent ที่นั่น หรือกรอก path ของ repo ในช่อง "ผู้ใช้กรอก") · ของกลางแก้ที่ plugin `superuser` แล้วรัน `node scripts/sync/sync-superuser.mjs` · แก้ใน repo แล้วรัน `node scripts/check/validate-marketplace.mjs` ให้ผ่าน
5. ปิดรายการในคิวกลางและ `.claude/superuser/IMPROVEMENTS.md` (ช่อง "ควรรวมไหม" · "รวมแล้ว")

## 6. ทำ superuser ให้ plugin สาขาใหม่

ทำตาม `ADAPT.md` ของ plugin `superuser` · เปิดที่**ราก repo SQT-Marketplace**
**ผลลัพธ์:** `plugins/<ชื่อ plugin>/` ที่ผ่าน `validate-marketplace.mjs` · ไฟล์ prompt แยกตามสถานการณ์ + `README.md` ใน `prompt/<ชื่อ plugin>/` · แถวใหม่ใน `prompt/README.md`

### ข้อมูล (ผู้ใช้กรอก)

- ชื่อ plugin (ตัวพิมพ์เล็ก ขีดกลาง):
- สาขางาน / ผู้ใช้คือใคร:
- งานที่ทำบ่อย 4–8 อย่าง (จะกลายเป็น playbook):
- บทบาท agent 2–5 บทบาท:
- เรื่องที่ต้อง "รออนุมัติ" เสมอในสาขานี้:
- ขอบเขตที่ห้ามข้าม (เช่น ไม่วินิจฉัย · ไม่ใช่คำแนะนำการลงทุน):

### ต้องมีในผลงาน

1. โครง plugin ตามข้อ 2 ของ `ADAPT.md` · ของกลางมาจาก `sync-superuser.mjs` ไม่คัดลอกมือ
2. playbook ของสาขาตาม `playbook-template` · `review` และ `unattended-run` ปรับตัวอย่างให้เข้าสาขา
3. skill ของสาขา: description บอกว่า "ใช้เมื่อ" ชัด · ไม่ซ้ำกับ skill ที่มีอยู่แล้วใน plugin อื่น
4. ผล `validate-marketplace.mjs` ผ่าน · รัน `sync-docs.mjs` แล้ว · build ได้ด้วย `scripts/build-dist.cmd`
5. `prompt/<ชื่อ plugin>/` แบบเดียวกับสาขาอื่น: ไฟล์ `prompt-<สถานการณ์>.md` 4–5 ไฟล์ (ไฟล์ละ 2–5 ฉบับ) · `README.md` มีตาราง "รายการไฟล์" และ "เลือกจากสถานการณ์" 16–20 แถว
6. ลองงานจริง 3 งาน (เล็ก · กลาง · ใหญ่) แล้วรายงานว่าจัดขนาดและเลือก playbook ถูกไหม
