# prompt-handover — เอกสารส่งมอบและปิดโครงการ

ใช้คู่กับ plugin `software-company` · ไฟล์นี้รวม prompt 2 ฉบับ แต่ละฉบับสร้างเอกสารหนึ่งชุด · ไฟล์แยกรายฉบับอยู่ในโฟลเดอร์ `prompt-handover/`

## วิธีใช้

วางทั้งไฟล์ใน Claude Code ที่รากโฟลเดอร์โปรเจกต์ แล้วพิมพ์ต่อท้ายว่าจะทำฉบับไหน เช่น `ทำทั้งหมด` หรือ `ทำข้อ 3 และ 4`

**กฎการทำงานของไฟล์รวม (agent ต้องทำตาม):**

1. ทำทีละฉบับตามลำดับในตาราง ข้ามฉบับที่ผู้ใช้ไม่ได้สั่ง
2. **จบแต่ละฉบับให้หยุด** อัปเดตตารางสถานะใน `docs/BUILD-PLAN.md` ตามข้อ "รายงานสถานะ" ในกฎร่วม แล้วแสดงในคำตอบ: แถวที่เปลี่ยน · ค้างอยู่ · ฉบับถัดไป — รอผู้ใช้พิมพ์ `ต่อ` หรือสั่งแก้ **ห้ามเริ่มฉบับถัดไปเอง**
3. ช่องที่เขียนว่า "ผู้ใช้กรอก" ของฉบับไหนยังว่าง ให้ถามตอนเริ่มฉบับนั้น ไม่ต้องถามทั้งหมดตั้งแต่ต้น
4. ฉบับหลังใช้ผลของฉบับก่อนเป็นข้อมูลนำเข้า — อ่านจากดิสก์ใหม่ทุกครั้ง (ผู้ใช้อาจแก้ไปแล้ว)

| # | เอกสาร | ได้ไฟล์ |
|---|---|---|
| 1 | เอกสารส่งมอบงาน (Handover) | `docs/handover.md` |
| 2 | เอกสารทบทวนโครงการ (Retrospective) | `docs/retrospective.md` |

## กฎร่วมทุกฉบับ

- อ่าน `docs/BUILD-PLAN.md` (หัวข้อ `สถานะล่าสุด`) และ `docs/README.md` ก่อน (ถ้ามี) — สถานะงาน รหัสโปรเจกต์ ขนาดงาน ธีมสี อยู่ที่นั่น · ไม่มีให้ถามเฉพาะค่าที่ขาด
- **ที่เก็บไฟล์** (ตาม skill `project-doc-set`): `ref/` ไฟล์ที่ได้รับมา อ่านอย่างเดียว · `docs/` เอกสารที่เราเขียน (รูปใน `docs/figures/`) · `mockup/` UI mockup · `qa/` test case ผลทดสอบ รายงานบั๊ก · `assets/` โลโก้ ไอคอน · `_to_delete/` ของชั่วคราว — สร้างโฟลเดอร์เมื่อมีของจริงเท่านั้น
- อ่านไฟล์จากดิสก์ก่อนแก้ · ไฟล์ยาวเกิน 300 บรรทัดอ่านเฉพาะช่วง · ต้องเปิดเกิน 3 ไฟล์เพื่อตอบเรื่องเดียว ให้ส่ง subagent
- ข้อมูลไม่พอหรือเอกสารขัดกัน → รวมเป็นคำถามท้ายคำตอบแล้ว **หยุด** ห้ามเดา ห้ามแต่งตัวเลข/ชื่อ/วันที่
- ตัวย่อทุกตัวกางเต็มครั้งแรก เช่น Software Requirements Specification (SRS) · ของชั่วคราวลง `_to_delete/`
- ตั้งชื่อไฟล์ตาม skill `document-naming` · รูปแบบเอกสารตาม `polished-document-style`
- **รายงานสถานะทุกครั้งที่จบฉบับ** (ใช้ skill `status-report` ถ้ามี) ลง `docs/BUILD-PLAN.md` — ไม่มีไฟล์ให้สร้าง · แก้เฉพาะสองหัวข้อนี้ ไม่แตะหัวข้ออื่นในไฟล์:
  - `## สถานะล่าสุด` **เขียนทับทั้งหัวข้อ**: วันที่เวลา · ตาราง `| รายการ | ประเภท | สถานะ | ผลตรวจ | ค้าง / หมายเหตุ |` ครบทุกเอกสารและงานของโปรเจกต์ (รายการที่รอบนี้ไม่ได้แตะ คัดลอกค่าเดิม) · ตามด้วย **ค้างอยู่** (คำถามที่ต้องมีคนตอบ พร้อมบอกว่าถามใคร ไม่มีเขียน `ไม่มี`) และ **ถัดไป** (ไม่เกิน 3 อย่าง)
  - สถานะเอกสาร: `ยังไม่เริ่ม` · `DRAFT` · `REVIEW` — `APPROVED` ผู้ใช้ตั้งเองเท่านั้น · ผลตรวจ: `ผ่าน — <หลักฐาน>` · `ไม่ผ่าน — <อะไร>` · `ยังไม่ตรวจ` — **ห้ามเขียน `ผ่าน` ถ้าไม่ได้ตรวจหรือรันจริง**
  - `## ประวัติสถานะ` เพิ่มหนึ่งบรรทัดบนสุด: `วันที่ เวลา · งาน · สถานะ · ผล · ค้างกี่ข้อ`
- คำตอบตอนจบ: แสดงเฉพาะแถวที่เปลี่ยน + ค้างอยู่ + ถัดไป แล้วบอกว่าตารางเต็มอยู่ใน `docs/BUILD-PLAN.md` — ไม่คัดลอกเนื้อเอกสารกลับมา

## 1. เอกสารส่งมอบงาน (Handover)

agent `technical-writer` + `project-manager` · skill `work-session-context` · `onboard` (software-company:onboard) · `polished-document-style`
**ต้องมีก่อน:** เอกสารของโปรเจกต์ที่มีอยู่ (ใช้เป็นแหล่งอ้างอิง ไม่คัดลอกซ้ำ)
**ผลลัพธ์:** `docs/handover.md` — ผู้รับอ่านแล้วต้องรับช่วงได้โดยไม่ต้องถามผู้ส่งเรื่องพื้นฐาน

### ข้อมูลการส่งมอบ (ผู้ใช้กรอก)

- ส่งต่อให้ใคร (ทีม/บทบาท) และวันที่ส่ง:
- ผู้รับมีพื้นฐานแค่ไหน (รู้เทคโนโลยีนี้ไหม / รู้ธุรกิจไหม):
- งานที่ส่งมอบ: ☐ โค้ด ☐ เอกสาร ☐ การดูแลระบบที่รันอยู่ ☐ ผู้ติดต่อฝั่งลูกค้า
- ช่วงที่ผู้ส่งยังช่วยตอบคำถามได้ถึงเมื่อไร:

### หัวข้อที่ต้องมีในเอกสาร

1. **อ่านก่อน (หน้าเดียว)** — ระบบคืออะไร ใครใช้ สถานะตอนนี้ (พร้อมใช้ / กำลังทำ / หยุด) อะไรเสร็จ อะไรค้าง
2. **แผนที่เอกสาร** — ตารางไฟล์เอกสารทั้งหมดใน `docs/` พร้อมสถานะและ "อ่านเมื่อไร" (ดึงจาก `docs/README.md`)
3. **เริ่มทำงานวันแรก** — ติดตั้ง/รัน/ทดสอบตามลำดับ พร้อมคำสั่งจริงที่ลองแล้ว (ลองรันเองก่อนเขียน ถ้ารันไม่ได้ให้บันทึกว่ารันไม่ได้ตรงไหน)
4. **โครงสร้างและการตัดสินใจสำคัญ** — สถาปัตยกรรมโดยสรุป + ลิงก์ ADR ที่ผู้รับต้องรู้ "ทำไมเป็นแบบนี้"
5. **สภาพแวดล้อมและการเข้าถึง** — รายการระบบ/บัญชี/สิทธิ์ที่ผู้รับต้องมี (ชื่อระบบ + ใครอนุมัติ **ไม่ใส่รหัสผ่านหรือคีย์**)
6. **งานค้างและปัญหาที่รู้** — ตาราง: เรื่อง · สถานะ · ผลกระทบ · ข้อเสนอขั้นต่อไป (ดึงจาก BUILD-PLAN คำถามค้าง บั๊กที่เปิดอยู่)
7. **ความเสี่ยงและสิ่งที่ต้องระวัง** — ของที่เคยพัง ส่วนที่เปราะ งานที่มีกำหนดเวลา (ใบรับรองหมดอายุ ต่อสัญญา)
8. **ผู้เกี่ยวข้อง** — บทบาท · เรื่องที่ถามได้ · ช่องทาง (เว้นให้เติม)
9. **Checklist ส่งมอบ** — ช่องติ๊กได้: โอนสิทธิ์ · ส่งมอบรหัส/คีย์ผ่านช่องทางปลอดภัย · ผู้รับรันระบบได้เอง · นัดถามตอบ

### กฎเฉพาะฉบับนี้

- **ห้ามใส่ความลับ** (รหัสผ่าน token คีย์ connection string) ในเอกสาร
- ทุกคำสั่งที่เขียนต้องเคยลองรันจริงในรอบนี้ ข้อที่ไม่ได้ลองให้ติดป้าย `ยังไม่ได้ลองรัน`
- ข้อมูลที่ไม่มี (ชื่อคน ช่องทาง วันที่) → ช่องว่างให้เติม ห้ามแต่ง

## 2. เอกสารทบทวนโครงการ (Retrospective)

agent `project-manager` · skill `software-company:retrospective` · `postmortem-template` (เมื่อมีเหตุร้ายแรง) · `polished-document-style`
**ผลลัพธ์:** `docs/retrospective.md` — เขียนแบบไม่โทษตัวบุคคล (blameless): พูดถึง "กระบวนการและระบบ" ไม่ใช่ "ใครทำพลาด"

### ช่วงที่ทบทวน (ผู้ใช้กรอก)

- โครงการ/ช่วงเวลา/สปรินต์ที่ทบทวน:
- เรื่องที่อยากให้เน้น (ถ้ามี):
- ความเห็นจากทีม (แปะข้อความดิบได้ ไม่ต้องเรียบเรียง):

### ข้อมูลที่ต้องดึงมาเอง (ข้อเท็จจริงก่อนความรู้สึก)

1. แผนเทียบจริง — `docs/project-plan.md` / `docs/BUILD-PLAN.md`: กำหนด vs เสร็จจริง ข้อที่ `ติด` กี่ข้อ ติดเพราะอะไร
2. `git log` ในช่วงนั้น (จำกัดไม่เกิน 200 บรรทัด): จำนวน commit ตามประเภท (`feat` `fix`) แนวโน้มแก้ซ้ำ
3. change request และบั๊ก (`docs/change/` `qa/bugs/`): กี่เรื่อง จากต้นเหตุอะไร
4. ประวัติสถานะเอกสารและ `คำถามค้าง` ที่ค้างนานที่สุด
5. ตัวเลขที่ไม่มีข้อมูล → `(ไม่มีข้อมูล)` ห้ามประมาณ

### หัวข้อที่ต้องมีในเอกสาร

1. สรุปสั้น — เป้าหมายเดิม ผลที่ได้ จริงเทียบแผน (ตัวเลข 3–5 ตัว)
2. ไทม์ไลน์เหตุการณ์สำคัญ (ตารางหรือ Mermaid timeline)
3. **ที่ทำได้ดี (Keep)** — พร้อมหลักฐาน · ทำไมได้ผล
4. **ที่ไม่ดี (Problem)** — อาการ → สาเหตุราก (ถามทำไมซ้ำได้ถึง 3–5 ชั้น) · มองที่กระบวนการ
5. **ลองทำใหม่ (Try)** — ตารางข้อเสนอลงมือได้:

   | # | สิ่งที่จะทำ | แก้ปัญหาข้อไหน | เจ้าของ (บทบาท) | กำหนด | วัดผลอย่างไร |
   |---|---|---|---|---|---|

6. สิ่งที่นำไปปรับชุด prompt / เอกสาร / เทมเพลตได้ (ถ้ามี)
7. คำถามถึงทีมที่ข้อมูลยังตอบไม่ได้

### กฎเฉพาะฉบับนี้

- ไม่ระบุชื่อบุคคลเป็นต้นเหตุ · ความเห็นทีมอ้างได้โดยไม่ระบุผู้พูด
- ข้อเสนอต้องทำแล้ววัดผลได้ ข้อที่เป็นความรู้สึกลอย ๆ ให้ย้ายไปท้ายเอกสารเป็น "ข้อสังเกต"
- ผู้ใช้เป็นคนตรวจและเติมความเห็นทีม — ส่วนที่ต้องเติมเว้นหัวข้อไว้พร้อมข้อความ `(รอทีมเติม)`
