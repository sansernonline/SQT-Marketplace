# prompt-new-project — สร้างเอกสารโปรเจกต์ใหม่ (spec + mockup)

ใช้คู่กับ plugin `software-company` · ไฟล์นี้รวม prompt 14 ฉบับ (0–13) · ฉบับ 0 research แอปต้นแบบ ใช้เมื่อมีแอปที่อยากได้แบบเดียวกัน แต่ละฉบับสร้างเอกสารหนึ่งชุด · ฉบับที่ 10 สร้าง prompt agent-loop เฉพาะโปรเจกต์ไว้ใช้เขียนโปรแกรมต่อ

## วิธีใช้

วางทั้งไฟล์ใน Claude Code, Codex CLI หรือ Gemini CLI ที่รากโฟลเดอร์โปรเจกต์ แล้วพิมพ์ต่อท้ายว่าจะทำฉบับไหน เช่น `ทำทั้งหมด` หรือ `ทำข้อ 3 และ 4`

**กฎการทำงานของไฟล์รวม (agent ต้องทำตาม):**

1. ทำทีละฉบับตามลำดับในตาราง ข้ามฉบับที่ผู้ใช้ไม่ได้สั่ง
2. **จบแต่ละฉบับให้หยุด** อัปเดตตารางสถานะใน `docs/BUILD-PLAN.md` ตามข้อ "รายงานสถานะ" ในกฎร่วม แล้วแสดงในคำตอบ: แถวที่เปลี่ยน · ค้างอยู่ · ฉบับถัดไป — รอผู้ใช้พิมพ์ `ต่อ` หรือสั่งแก้ **ห้ามเริ่มฉบับถัดไปเอง**
3. ช่องที่เขียนว่า "ผู้ใช้กรอก" ของฉบับไหนยังว่าง ให้ถามตอนเริ่มฉบับนั้น ไม่ต้องถามทั้งหมดตั้งแต่ต้น
4. ฉบับหลังใช้ผลของฉบับก่อนเป็นข้อมูลนำเข้า — อ่านจากดิสก์ใหม่ทุกครั้ง (ผู้ใช้อาจแก้ไปแล้ว)

## กฎร่วมทุกฉบับ

- อ่าน `docs/BUILD-PLAN.md` (หัวข้อ `สถานะล่าสุด`) และ `docs/README.md` ก่อน (ถ้ามี) — สถานะงาน รหัสโปรเจกต์ ขนาดงาน ธีมสี อยู่ที่นั่น · ถ้าไม่มี ให้ถามผู้ใช้เฉพาะค่าที่ขาด (รหัสโปรเจกต์ ขนาดงาน สีแบรนด์)
- **ที่เก็บไฟล์** (ตาม skill `project-doc-set`): `ref/` ไฟล์ที่ได้รับมา อ่านอย่างเดียว · `docs/` เอกสารที่เราเขียน (รูปใน `docs/figures/`) · `mockup/` UI mockup · `qa/` test case ผลทดสอบ รายงานบั๊ก · `assets/` โลโก้ ไอคอน · `_to_delete/` ของชั่วคราว — สร้างโฟลเดอร์เมื่อมีของจริงเท่านั้น
- มี `docs/research/` (จากฉบับ 0) → ใช้เป็นข้อมูลนำเข้าของ BRD · SRS · mockup และอ้างรหัส `IMP-xx` / เลขแหล่ง ทุกครั้งที่หยิบข้อเสนอหรือ feature จากแอปต้นแบบมาใช้
- อ่านไฟล์จากดิสก์ก่อนแก้ · ไฟล์ยาวเกิน 300 บรรทัดอ่านเฉพาะช่วง
- ข้อมูลไม่พอหรือเอกสารขัดกัน → รวมเป็นคำถามท้ายคำตอบแล้ว **หยุด** ห้ามเดา ห้ามแต่งตัวเลข/ชื่อ/วันที่
- ตัวย่อทุกตัวกางเต็มครั้งแรก เช่น Software Requirements Specification (SRS) · ของชั่วคราวลง `_to_delete/`
- ตั้งชื่อไฟล์ตาม skill `document-naming` · รูปแบบเอกสารตาม skill `polished-document-style` · ภาพและไดอะแกรมตาม `software-diagrams` / `markdown-visuals`
- ข้อความภาษาไทยเขียนให้คนทั่วไปอ่านเข้าใจ ไม่ใช้ศัพท์ที่ไม่จำเป็น
- **รายงานสถานะทุกครั้งที่จบฉบับ** (ใช้ skill `status-report` ถ้ามี) ลง `docs/BUILD-PLAN.md` — ไม่มีไฟล์ให้สร้าง · แก้เฉพาะสองหัวข้อนี้ ไม่แตะหัวข้ออื่นในไฟล์:
  - `## สถานะล่าสุด` **เขียนทับทั้งหัวข้อ**: วันที่เวลา · ตาราง `| รายการ | ประเภท | สถานะ | ผลตรวจ | ค้าง / หมายเหตุ |` ครบทุกเอกสารและงานของโปรเจกต์ (รายการที่รอบนี้ไม่ได้แตะ คัดลอกค่าเดิม) · ตามด้วย **ค้างอยู่** (คำถามที่ต้องมีคนตอบ พร้อมบอกว่าถามใคร ไม่มีเขียน `ไม่มี`) และ **ถัดไป** (ไม่เกิน 3 อย่าง)
  - สถานะเอกสาร: `ยังไม่เริ่ม` · `DRAFT` · `REVIEW` — `APPROVED` ผู้ใช้ตั้งเองเท่านั้น · ผลตรวจ: `ผ่าน — <หลักฐาน>` · `ไม่ผ่าน — <อะไร>` · `ยังไม่ตรวจ` — **ห้ามเขียน `ผ่าน` ถ้าไม่ได้ตรวจหรือรันจริง**
  - `## ประวัติสถานะ` เพิ่มหนึ่งบรรทัดบนสุด: `วันที่ เวลา · งาน · สถานะ · ผล · ค้างกี่ข้อ`
- คำตอบตอนจบ: แสดงเฉพาะแถวที่เปลี่ยน + ค้างอยู่ + ถัดไป แล้วบอกว่าตารางเต็มอยู่ใน `docs/BUILD-PLAN.md` — ไม่คัดลอกเนื้อเอกสารกลับมา

## 1. เขียนแผนโครงการ (Project Plan)

agent `project-manager` · skill `simplicity-first` · `polished-document-style`
**ต้องมีก่อน:** `docs/README.md` (ถ้ามี)
**ผลลัพธ์:** `docs/project-plan.md`

### หัวข้อที่ต้องมี

1. เป้าหมายและขอบเขต — ทำอะไร **ไม่ทำ**อะไร (ประโยคละข้อ)
2. ผู้เกี่ยวข้อง — ใครตัดสินใจ ใครใช้ ใครเซ็นรับ
3. สิ่งส่งมอบ — ดึงรายการจากตารางเอกสารใน `docs/README.md` บวกตัวโปรแกรม
4. ไทม์ไลน์ — เป็นช่วง (สัปดาห์) ตามขนาดงาน พร้อมจุดตรวจ (milestone) ที่ผู้ใช้เห็นผลได้ · ใช้ Gantt ด้วย Mermaid เมื่อมีตั้งแต่ 5 กิจกรรม
5. ความเสี่ยงและข้อสมมติ — ตาราง: ความเสี่ยง · ผลกระทบ · วิธีรับมือ · เจ้าของ
6. เกณฑ์ส่งมอบ/ปิดงาน — ตรวจได้ด้วยเครื่องหรือด้วยการลงนาม ไม่ใช้คำว่า "ใช้งานได้ดี"

### กฎเฉพาะฉบับนี้

- ตัวเลขระยะเวลา/งบที่ผู้ใช้ไม่ได้ให้ → ใส่ `(รอยืนยัน)` ห้ามประมาณเอง
- ไม่ใส่แผนรายวัน ไม่ใส่ทรัพยากรที่ไม่มีข้อมูล

## 2. เขียน Business Requirements Document (BRD)

agent `business-analyst` · skill `user-story-writer` · `simplicity-first` · `polished-document-style` · ขนาด L (M ถ้าจำเป็น)
**ต้องมีก่อน:** `docs/README.md` · ไฟล์อ้างอิงของผู้ว่าจ้างใน `ref/` (ถ้ามี)
**ผลลัพธ์:** `docs/brd.md`

### หัวข้อที่ต้องมี

1. ปัญหาทางธุรกิจ — เกิดกับใคร บ่อยแค่ไหน เสียอะไร (ตัวเลขจริงที่ผู้ใช้ให้ ถ้าไม่มีใส่ `(รอยืนยัน)`)
2. เป้าหมายและตัวชี้วัดความสำเร็จ — วัดด้วยอะไร ก่อน/หลังเท่าไร
3. ผู้มีส่วนได้ส่วนเสียและบทบาท
4. กระบวนการปัจจุบัน (as-is) และที่ต้องการ (to-be) — แผนภาพ flowchart ด้วย Mermaid
5. ความต้องการทางธุรกิจ — รหัส `BR-001…` ข้อละหนึ่งประโยค มีผู้ขอและลำดับความสำคัญ (ต้องมี / ควรมี / อยากมี)
6. ข้อจำกัด ข้อสมมติ ความเสี่ยง
7. ขอบเขต — อยู่ในขอบเขต / นอกขอบเขต

### กฎเฉพาะฉบับนี้

- เขียนเป็นภาษาธุรกิจ ไม่ระบุเทคโนโลยีหรือหน้าจอ (ไว้ใน SRS/FSD)
- ทุก `BR` ต้องตอบได้ว่า "ถ้าไม่ทำแล้วเสียอะไร"

## 3. เขียน Software Requirements Specification (SRS)

agent `business-analyst` หรือ `system-analyst` · skill `srs-writing` · `user-story-writer` · `software-diagrams` · `polished-document-style`
**ต้องมีก่อน:** `docs/README.md` · `docs/brd.md` (ถ้าขนาดงานมี BRD)
**ผลลัพธ์:** `docs/srs.md`

### หัวข้อที่ต้องมี

ตามโครงของ skill `srs-writing` (อ้างอิง ISO/IEC/IEEE 29148) อย่างน้อย:

1. ภาพรวมระบบ ผู้ใช้ และบริบท (ไดอะแกรมบริบทหนึ่งภาพ)
2. ข้อกำหนดเชิงหน้าที่ (Functional Requirement — FR) รหัส `FR-001…` **หนึ่งข้อ = หนึ่งประโยค = หนึ่งผู้กระทำ** พร้อมเกณฑ์ยอมรับแบบ Given-When-Then และอ้าง `BR-xxx` ที่มันตอบ
3. ข้อกำหนดที่ไม่ใช่หน้าที่ (Non-Functional Requirement — NFR) `NFR-001…` ใส่ตัวเลขทุกข้อ (เวลาตอบ จำนวนผู้ใช้พร้อมกัน ความพร้อมใช้งาน) ไม่ใช้คำคุณศัพท์
4. ข้อมูลและกฎธุรกิจ — รายการข้อมูลหลักและกฎการคำนวณ/ตรวจสอบ
5. อินเทอร์เฟซภายนอก (ระบบอื่น/อุปกรณ์) · ข้อจำกัด · ข้อสมมติ
6. ตารางสืบย้อน `BR → FR → (ภายหลัง) test`

### กฎเฉพาะฉบับนี้

- ไม่ใส่วิธีทำ (solution) ลงในข้อกำหนด · ข้อกำหนดที่ตรวจไม่ได้ให้เขียนใหม่หรือย้ายไปคำถามค้าง
- ข้อกำหนดที่ทำให้ต้องเก็บข้อมูลส่วนบุคคล ทำเครื่องหมาย `[PDPA]` (Personal Data Protection Act)
- จบงานรายงานจำนวน FR / NFR และข้อที่ยังกำกวม

### ลำดับ

1. อ่าน `docs/README.md` (แพลตฟอร์ม · `doc-theme` accent) แล้วอ่าน SRS หรือ BRD ที่มีอยู่ · ทำรายการ "หน้าจอ × FR" ให้ทุก FR ที่ผู้ใช้เห็นมีหน้าจอรองรับ
2. ทุกหน้าจอใช้ token สีและ CSS จาก skill ของแพลตฟอร์ม · **ห้ามใส่สี hardcode**
3. **ทุกปุ่ม ลิงก์ และฟอร์มต้องทำงานได้จริง** — กดแล้วไปหน้าจอถัดไป เปิด/ปิด dialog เปลี่ยน tab หรือแสดงข้อความ ด้วย JavaScript เล็ก ๆ ในไฟล์ ห้ามมีปุ่มที่กดแล้วไม่เกิดอะไร (ปุ่มที่ตั้งใจให้ปิดไว้ต้อง `disabled` พร้อมเหตุผลที่มองเห็นได้)
4. ทุกหน้าจอที่มีข้อมูลต้องมีครบ **5 สถานะ** สลับดูได้ในหน้าเดียว (ปุ่มสลับมุมหน้าจอเฉพาะ mockup): ว่าง · กำลังโหลด · ผิดพลาด · บางส่วน · สำเร็จ
5. ข้อความบนหน้าจอเป็นภาษาของผู้ใช้จริง ใช้ข้อมูลตัวอย่างที่สมจริง ไม่ใช้ lorem ipsum
6. ทำ `mockup/index.html` ลิงก์ทุกหน้าจอ พร้อมตาราง "หน้าจอ → FR ที่รองรับ"
7. ตรวจเอง: รัน `check-design-tokens.mjs` (จาก `web-app-design`) กับ `mockup/` — ต้องไม่มีสี hardcode · เปิดแต่ละหน้าที่ความกว้างโทรศัพท์/เดสก์ท็อปตามแพลตฟอร์ม
8. อัปเดต `docs/README.md` ว่ามี mockup แล้ว

### กฎเฉพาะฉบับนี้

- mockup คือข้อกำหนดที่มองเห็นได้ — ไม่ใส่ฟีเจอร์ที่ SRS ไม่มี · เจอ FR ที่หน้าจอยังไม่ครอบคลุมให้ทำเพิ่มหรือลงคำถามค้าง
- ไม่ต่อ backend จริง ข้อมูลเป็นค่าตัวอย่างในไฟล์

## 7. เขียน Functional Specification Document (FSD) ต่อโมดูล

agent `system-analyst` · skill `fsd-writing` · `software-diagrams` · `polished-document-style`

**โมดูลที่ทำ:** <!-- ชื่อโมดูล หรือ "ทุกโมดูลตามที่ architecture แบ่ง" -->
**ผลลัพธ์:** `docs/fsd-<โมดูล>.md` (หนึ่งไฟล์ต่อโมดูล)

### หัวข้อต่อโมดูล

1. ขอบเขตโมดูล — FR ที่รับผิดชอบ (รหัสครบ)
2. หน้าจอ — อ้างไฟล์ใน `mockup/` ไม่อธิบายซ้ำสิ่งที่ mockup แสดงอยู่แล้ว เขียนเฉพาะพฤติกรรมที่มองไม่เห็น
3. กฎการทำงานทีละ FR — เงื่อนไข ลำดับ ผลลัพธ์ ข้อความ error ทุกกรณี
4. ข้อมูลที่อ่าน/เขียน — ตารางและฟิลด์ พร้อมกฎตรวจสอบ
5. API ที่หน้าจอเรียก — ถ้ามี `docs/API-SPEC.md` ให้อ้าง ไม่คัดลอกซ้ำ
6. Sequence diagram ของกระบวนการที่มีมากกว่า 2 ผู้กระทำ · State diagram ของข้อมูลที่มีสถานะ
7. กรณีขอบ: ข้อมูลว่าง ซ้ำ เกินขนาด สิทธิ์ไม่พอ ทำพร้อมกัน

### กฎเฉพาะฉบับนี้

- ทุกข้อความต้องตรวจได้ (ให้ tester อ่านแล้วเขียน test ได้ทันที) · ไม่ตรงกับ SRS/mockup ให้ลงคำถามค้าง ห้ามเลือกเอง
- ทุก FR ของโมดูลต้องปรากฏใน FSD อย่างน้อยหนึ่งครั้ง — ท้ายไฟล์มีตาราง FR → หัวข้อใน FSD

## 8. เขียนแผนทดสอบ (Test Plan) และ test case

agent `qa-tester` · skill `test-case-template` · `testing-standards` · `e2e-testing-patterns` · ขนาด L ใช้ skill `xlsx` สำหรับตาราง test case

### หัวข้อที่ต้องมีใน `docs/test-plan.md`

1. ขอบเขตการทดสอบ — ทดสอบอะไร **ไม่ทดสอบ**อะไร
2. กลยุทธ์ตามระดับ: unit · integration · E2E — สัดส่วนและเครื่องมือ (ถามผู้ใช้ก่อนถ้ายังไม่เลือกเฟรมเวิร์ก ตาม `testing-standards`)
3. สภาพแวดล้อมและข้อมูลทดสอบ
4. ลิงก์ไปไฟล์ test case ใน `qa/` — **ไม่คัดลอกรายการ test case มาไว้ในแผน**
5. ตาราง FR → รหัส test case (ความครอบคลุม) · FR ที่ยังไม่มี test ต้องเห็นชัด
6. เกณฑ์ผ่าน/ไม่ผ่านและเกณฑ์ออกจากการทดสอบ
7. **คำสั่งรัน test หนึ่งบรรทัด** — เมื่อได้แล้วใส่ในช่อง "คำสั่งรัน test" ของ `docs/README.md` พร้อมคำสั่ง smoke ถ้ากำหนดได้

### `qa/<รหัส>-test-cases.md`

ตามรูปแบบ `test-case-template` (รหัส `TC-<โมดูล>-NNN`) — ต่อ FR: ปกติ · ขอบเขต (boundary) · ผิดพลาด (negative) · สิทธิ์ · ไม่ต่ำกว่า 1 ปกติ + 1 ผิดพลาดต่อ FR · ทุกข้ออ้างรหัส FR

### กฎเฉพาะฉบับนี้

- test case ต้องอ่านแล้วทำตามได้ทันที: ขั้นตอน · ข้อมูลเข้า · ผลที่คาด (ตัวเลข/ข้อความจริง)
- ตัวเลขเป้าหมายความครอบคลุมใช้ตาม `testing-standards` ไม่ตั้งเอง

## 10. สร้าง prompt agent-loop ของโปรเจกต์นี้

agent `solution-architect` + `project-manager` · skill `spec-to-code-loop` · `testing-standards` · `simplicity-first`
**ต้องมีก่อน:** `docs/srs.md` · `mockup/` (ถ้ามีหน้าจอ) · `docs/architecture.md` · `docs/fsd-*.md` · `docs/test-plan.md` (เท่าที่ขนาดงานมี)
**ผลลัพธ์:** `docs/AGENT-LOOP.md` ไฟล์เดียว — prompt สำเร็จรูปที่ผู้ใช้จะเอาไปสั่งให้ agent เขียนโปรแกรมของโปรเจกต์นี้ทีละข้อกำหนด · **ฉบับนี้เขียน prompt อย่างเดียว ห้ามเริ่มเขียนโค้ด ห้ามรัน loop**

### ข้อมูลที่ต้องดึงจากเอกสารของโปรเจกต์ใส่ลงใน prompt (ห้ามเว้นเป็นตัวแปรลอย ๆ)

1. ชื่อโปรเจกต์ · เป้าหมายหนึ่งประโยค · path จริงของเอกสารนำเข้าทุกไฟล์
2. เทคโนโลยี/เฟรมเวิร์กจาก `docs/architecture.md` · โครงโฟลเดอร์โค้ดที่ตั้งใจ
3. คำสั่ง install · test · smoke · รันแอป และ URL — จาก `docs/test-plan.md` / `docs/README.md` · ถ้ายังไม่มี ให้กำหนดว่า "ข้อแรกของแผนคือตั้งโครงโปรเจกต์และคำสั่งเหล่านี้" ห้ามแต่งคำสั่ง
4. รายการรหัสข้อกำหนด (`FR-…`) ทั้งหมดจาก SRS พร้อมลำดับการพึ่งพาที่แนะนำ · FR ไหนมีหน้าจอ ให้ระบุไฟล์ mockup ที่ต้องเทียบ
5. test case ที่ต้องผ่านต่อ FR (อ้างรหัสจาก test plan ถ้ามี)
6. ข้อห้ามเฉพาะโปรเจกต์ (เช่น ห้ามต่อระบบจริง ห้ามใช้ข้อมูลส่วนบุคคลจริง) จาก NFR/สถาปัตยกรรม

### โครงของ `docs/AGENT-LOOP.md` ที่ต้องเขียน

1. **วิธีใช้** (สำหรับผู้ใช้ อ่านใน 30 วินาที): รันใน repo โค้ดที่เป็น git และอยู่บน branch แยก · ใช้ได้ 2 แบบ — วางทีละรอบในหน้าต่างใหม่ (context สะอาด) หรือสั่ง `/loop อ่านและทำตาม docs/AGENT-LOOP.md` ให้วนเอง (`/loop` มีเฉพาะ Claude Code — เครื่องมืออื่นใช้แบบวางทีละรอบ) · สั่งหยุดด้วยไฟล์ `_to_delete/STOP`
2. **บริบทโปรเจกต์**: ข้อมูลข้อ 1–6 ข้างบน
3. **ไฟล์สถานะ `docs/BUILD-PLAN.md`** — ทุกรอบอ่านไฟล์นี้ก่อน สถานะอยู่ในไฟล์ ไม่อยู่ในหัว agent:
   - ตารางค่าคงที่บนสุด `| รายการ | ค่า |` แถว `test` `smoke` `รันแอป` `URL แอป` (ค่าอยู่ใน backtick)
   - ตารางงาน หัวตาราง `| # | รหัส | ข้อกำหนด | ไฟล์อ้างอิง | เกณฑ์เสร็จ | สถานะ | commit |` หนึ่งแถว = หนึ่ง FR = หนึ่ง commit · สถานะใช้แค่ `รอทำ` `กำลังทำ` `เสร็จ` `ติด`
   - หัวข้อ `## คำถามค้าง` และ `## ผลปิดงาน`
   - หัวข้อ `## สถานะล่าสุด` และ `## ประวัติสถานะ` (มีอยู่แล้วจากตอนทำเอกสาร) — **เก็บไว้ ห้ามลบ** ตารางงานวางต่อจากสองหัวข้อนี้
4. **หนึ่งรอบทำอะไร** — ตัดสินจากสถานะในไฟล์ ตามลำดับนี้:
   - `BUILD-PLAN.md` ยังไม่มีตารางงาน (ไม่มีไฟล์ หรือมีแต่หัวข้อสถานะจากตอนทำเอกสาร) → **รอบวางแผน**: เพิ่มตารางค่าคงที่และตารางงานจาก FR ข้อ 4 แล้วหยุด ให้ผู้ใช้อ่านก่อน
   - มีแถว `ติด` → หยุด แจ้งคำถามค้าง
   - มีแถวที่ยังไม่ `เสร็จ` → ทำแถวแรก: test ของข้อนี้ก่อนและเห็นแดงด้วยเหตุผลที่ถูก → โค้ดน้อยที่สุดให้เขียว → test ทั้งชุดเขียว → ข้อที่มีหน้าจอ ถ่ายภาพหน้าจอจริงเทียบ mockup → `git commit` ข้อเดียว `feat(<โมดูล>): … [FR-xxx]` → อัปเดตแถวเป็น `เสร็จ` + เลข commit
   - ทุกแถว `เสร็จ` แต่ test/smoke แดง → **รอบแก้**: หาสาเหตุหลักหนึ่งข้อ แก้เฉพาะจุด commit `fix:`
   - ทุกแถว `เสร็จ` และ test กับ smoke คืนค่า 0 → **รอบปิดงาน**: เขียนตารางสืบย้อน FR → test → commit ใน `## ผลปิดงาน` แล้วจบ
5. **เงื่อนไขจบที่ตรวจด้วยเครื่องได้**: ทุกแถว `เสร็จ` **และ** คำสั่ง test คืนค่า 0 **และ** คำสั่ง smoke คืนค่า 0 — agent ต้องรันคำสั่งเองแล้วรายงานผลจริง ห้ามสรุปว่าผ่านจากการอ่านโค้ด
6. **เพดาน**: แถวเดิมไม่จบใน 3 รอบ → ตั้ง `ติด` พร้อมเหตุผล แล้วหยุด · รอบแก้ไม่ผ่าน 3 ครั้ง → หยุด
7. **รายงานสถานะทุกรอบ** (skill `status-report`): เขียนทับ `## สถานะล่าสุด` — แถวโค้ดรวมเป็นช่วงรหัสตามสถานะ (`FR-001 ถึง FR-012 · เสร็จ · ผ่าน — test 48/48`) แถวเอกสารคงค่าเดิม · ผลตรวจเอาจากคำสั่ง test/smoke ที่รันจริงในรอบนั้น · **ค้างอยู่** = แถว `ติด` และคำถามค้าง · **ถัดไป** = แถวงานถัดไป — แล้วเพิ่มหนึ่งบรรทัดใน `## ประวัติสถานะ`
8. **บรรทัดสุดท้ายของทุกรอบ** ต้องเป็นหนึ่งใน `LOOP-STATUS: CONTINUE` · `LOOP-STATUS: PLAN-READY` · `LOOP-STATUS: BLOCKED` · `LOOP-STATUS: DONE` เพื่อให้คนหรือสคริปต์ตัดสินได้ว่าจะวนต่อไหม (ใช้กับ `/loop`: เมื่อเป็น `BLOCKED` `PLAN-READY` หรือ `DONE` ให้หยุดวน)
9. **ข้อห้าม**: ห้ามแก้ SRS/FSD/mockup (เจอจุดผิดให้ลงคำถามค้าง) · ห้ามลบหรือผ่อน test ให้ผ่าน · ห้าม commit โค้ดที่ test แดง · ห้ามรอคำตอบกลางรอบ — คำถามลง `## คำถามค้าง` แล้วจบรอบ · ของชั่วคราวลง `_to_delete/`

### กฎเฉพาะฉบับนี้

- prompt ที่ได้ต้องใช้ได้ทันทีโดยไม่ต้องแก้ — ทุกค่าเป็นของจริงของโปรเจกต์ ค่าที่ยังไม่รู้เขียนว่า `(ยังไม่มี — ข้อแรกของแผนต้องตั้ง)` ไม่ใช่ `<ใส่ค่า>`
- ยาวไม่เกิน ~150 บรรทัด อ้างเอกสารด้วย path แทนการคัดลอกเนื้อหา
- เอกสารขัดกัน (เช่น FR ที่ไม่มี mockup หรือ mockup ที่ไม่มี FR) → ลงรายการไว้ในคำตอบเป็นคำถามค้าง แล้วหยุดก่อนเขียน prompt

## 11. เขียนคู่มือผู้ใช้จากโปรแกรมจริง

agent `technical-writer` · skill `polished-document-style` · `branded-document-design` (ตอน render)
**ต้องมีก่อน:** `docs/README.md` · โปรแกรมที่รันได้ (ดู "คำสั่งรันแอป" ใน `docs/README.md`) · `docs/srs.md`
**ผลลัพธ์:** `docs/user-guide.md` · ภาพหน้าจอใน `docs/figures/`

### ลำดับ

1. รันแอปตามคำสั่งใน `docs/README.md` ถ้ารันไม่ได้ ให้หยุดและบอก — **ห้ามเขียนคู่มือจาก mockup หรือจินตนาการ**
2. แยกคู่มือตามบทบาทผู้ใช้ที่ SRS ระบุ (ผู้ใช้ทั่วไป / ผู้ดูแล) ถ้ามีมากกว่าหนึ่งบทบาท
3. ต่อหนึ่งงานที่ผู้ใช้ทำ: เป้าหมายหนึ่งบรรทัด · ขั้นตอนเลขลำดับ (หนึ่งการกระทำต่อข้อ) · ภาพหน้าจอจริงที่ถ่ายด้วยเครื่องมือ (Playwright) พร้อมคำบรรยายใต้ภาพ · ผลที่ควรเห็น
4. ส่วนแก้ปัญหา: ข้อความ error ที่ผู้ใช้อาจเจอจริง → สาเหตุ → วิธีแก้ (ดึงจากโปรแกรม ไม่แต่ง)
5. ภาษาง่าย ประโยคสั้น ไม่มีศัพท์เทคนิคที่ผู้ใช้ไม่ต้องรู้ · ใช้ชื่อปุ่ม/เมนูตรงกับหน้าจอทุกตัวอักษร
6. ท้ายเล่ม: คำศัพท์ และช่องทางขอความช่วยเหลือ (ถ้าผู้ใช้ให้ข้อมูล)

### กฎเฉพาะฉบับนี้

- ขั้นตอนไหนลองทำแล้วไม่ได้ผลตามที่เขียน ให้ลงคำถามค้างว่าเป็นบั๊กหรือคู่มือผิด ห้ามเขียนให้ดูผ่าน

- ไฟล์ระหว่างทาง (ภาพที่แปลง ไฟล์ทดลอง) ลง `_to_delete/`
