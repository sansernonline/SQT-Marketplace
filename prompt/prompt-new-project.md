# prompt-new-project — สร้างเอกสารโปรเจกต์ใหม่ (spec + mockup)

ใช้คู่กับ plugin `software-company` · ไฟล์นี้รวม prompt 14 ฉบับ (0–13) · ฉบับ 0 research แอปต้นแบบ ใช้เมื่อมีแอปที่อยากได้แบบเดียวกัน แต่ละฉบับสร้างเอกสารหนึ่งชุด · ฉบับที่ 10 สร้าง prompt agent-loop เฉพาะโปรเจกต์ไว้ใช้เขียนโปรแกรมต่อ

## วิธีใช้

วางทั้งไฟล์ใน Claude Code, Codex CLI หรือ Gemini CLI ที่รากโฟลเดอร์โปรเจกต์ แล้วพิมพ์ต่อท้ายว่าจะทำฉบับไหน เช่น `ทำทั้งหมด` หรือ `ทำข้อ 3 และ 4`

**กฎการทำงาน (agent ต้องทำตาม):** เปิด skill `agent-team` ก่อนเริ่ม แล้วทำตาม playbook `project-docs` ทุกขั้น — กฎร่วม (ถามครั้งเดียว · ทำจบรอบเดียว · ตัดสินใจเอง · รายงานสถานะ · ที่เก็บไฟล์) อยู่ที่นั่นที่เดียว · เปิด skill ไม่ได้ ให้หยุดและบอกผู้ใช้ ห้ามทำต่อโดยไม่มีกฎ

## กฎเฉพาะไฟล์นี้

- ไม่มี `docs/BUILD-PLAN.md` และ `docs/README.md` → ค่าที่ต้องถามคือ รหัสโปรเจกต์ ขนาดงาน สีแบรนด์
- มี `docs/research/` (จากฉบับ 0) → ใช้เป็นข้อมูลนำเข้าของ BRD · SRS · mockup และอ้างรหัส `IMP-xx` / เลขแหล่ง ทุกครั้งที่หยิบข้อเสนอหรือ feature จากแอปต้นแบบมาใช้
- หยุดก่อนครบได้เพิ่มอีกข้อ: ฉบับ 11 ที่รันแอปไม่ได้
- ภาพและไดอะแกรมตาม skill `software-diagrams` / `markdown-visuals`
- ข้อความภาษาไทยเขียนให้คนทั่วไปอ่านเข้าใจ ไม่ใช้ศัพท์ที่ไม่จำเป็น

## 0. Research แอปต้นแบบ

agent `product-manager` (มีเครื่องมือค้นเว็บ) · skill `reference-app-research` · `ui-craft` · `simplicity-first`
**ใช้เมื่อ:** ผู้ใช้บอกว่าอยากได้แอปแบบเดียวกับแอปที่มีอยู่แล้ว — ไม่มีแอปต้นแบบ ข้ามฉบับนี้
**ผลลัพธ์:** `docs/research/<ชื่อแอป>-research.md` ไฟล์เดียว · บันทึกดิบใน `_to_delete/research/`

### แอปต้นแบบ (ผู้ใช้กรอก)

- ชื่อแอปและลิงก์ (เช่น MobaXterm — https://mobaxterm.mobatek.net/):

- เราจะทำให้ใครใช้ บนแพลตฟอร์มไหน:
- อยากได้เหมือนทั้งแอป หรือเฉพาะส่วนไหน:
- สิ่งที่ไม่ชอบในแอปนั้นอยู่แล้ว (ถ้ามี):
- คู่แข่งที่อยากให้เทียบด้วย (เว้นว่าง = ให้เลือกเอง 2–4 ตัว):

### หัวข้อที่ต้องมี

ตามโครงของ skill `reference-app-research` ข้อ 5: สรุป 5 บรรทัด · ขอบเขตและวิธี · feature · UI · UX (งานหลัก 3–5 อย่าง นับขั้นตอน) · ข้อดีข้อเสียพร้อมความถี่จากเสียงผู้ใช้ · เทียบคู่แข่ง · **ข้อเสนอปรับปรุง `IMP-xx`** · ไม่ควรลอก · ยังไม่รู้ · ตารางส่งต่อไป BRD/SRS/mockup · แหล่งอ้างอิงพร้อมวันที่

- ทุกข้อเท็จจริงมีเลขแหล่ง ข้อมูลโฆษณาของเขาไม่ใช่หลักฐานว่า "ดี"
- ห้ามติดตั้งหรือรันแอปของเขา ห้ามล็อกอิน/สมัคร · ห้ามคัดลอกภาพ ข้อความ โลโก้ มาใส่เอกสาร (ลิงก์ได้)
- ฉบับต่อไป (BRD · SRS · mockup) ต้องอ่านไฟล์นี้และอ้างรหัส `IMP-xx` / เลขแหล่ง เมื่อหยิบข้อเสนอไปใช้

## 1. เขียนแผนโครงการ (Project Plan)

agent `project-manager` · skill `simplicity-first` · `polished-document-style`
**ต้องมีก่อน:** `docs/README.md` (ถ้ามี)
**ผลลัพธ์:** `docs/project-plan.md`

### หัวข้อที่ต้องมี

1. เป้าหมายและขอบเขต — ทำอะไร **ไม่ทำ**อะไร (ประโยคละข้อ)
2. ผู้เกี่ยวข้อง — ใครตัดสินใจ ใครใช้ ใครเซ็นรับ
3. สิ่งส่งมอบ — ดึงรายการจากตารางเอกสารใน `docs/README.md` บวกตัวโปรแกรม
4. ไทม์ไลน์ — เป็นช่วง (สัปดาห์) ตามขนาดงาน พร้อมจุดตรวจ (milestone) ที่ผู้ใช้เห็นผลได้ · ใช้ Gantt ด้วย Mermaid เมื่อมีตั้งแต่ 5 กิจกรรม
5. ความเสี่ยงและข้อสมมติ — ตาราง: ความเสี่ยง · ผลกระทบ · วิธีรับมือ · เจ้าของ
6. เกณฑ์ส่งมอบ/ปิดงาน — ตรวจได้ด้วยเครื่องหรือด้วยการลงนาม ไม่ใช้คำว่า "ใช้งานได้ดี"

### กฎเฉพาะฉบับนี้

- ตัวเลขระยะเวลา/งบที่ผู้ใช้ไม่ได้ให้ → ใส่ `(รอยืนยัน)` ห้ามประมาณเอง
- ไม่ใส่แผนรายวัน ไม่ใส่ทรัพยากรที่ไม่มีข้อมูล

## 2. เขียน Business Requirements Document (BRD)

agent `business-analyst` · skill `user-story-writer` · `simplicity-first` · `polished-document-style` · ขนาด L (M ถ้าจำเป็น)
**ต้องมีก่อน:** `docs/README.md` · ไฟล์อ้างอิงของผู้ว่าจ้างใน `ref/` (ถ้ามี)
**ผลลัพธ์:** `docs/brd.md`

### หัวข้อที่ต้องมี

1. ปัญหาทางธุรกิจ — เกิดกับใคร บ่อยแค่ไหน เสียอะไร (ตัวเลขจริงที่ผู้ใช้ให้ ถ้าไม่มีใส่ `(รอยืนยัน)`)
2. เป้าหมายและตัวชี้วัดความสำเร็จ — วัดด้วยอะไร ก่อน/หลังเท่าไร
3. ผู้มีส่วนได้ส่วนเสียและบทบาท
4. กระบวนการปัจจุบัน (as-is) และที่ต้องการ (to-be) — แผนภาพ flowchart ด้วย Mermaid
5. ความต้องการทางธุรกิจ — รหัส `BR-001…` ข้อละหนึ่งประโยค มีผู้ขอและลำดับความสำคัญ (ต้องมี / ควรมี / อยากมี)
6. ข้อจำกัด ข้อสมมติ ความเสี่ยง
7. ขอบเขต — อยู่ในขอบเขต / นอกขอบเขต

### กฎเฉพาะฉบับนี้

- เขียนเป็นภาษาธุรกิจ ไม่ระบุเทคโนโลยีหรือหน้าจอ (ไว้ใน SRS/FSD)
- ทุก `BR` ต้องตอบได้ว่า "ถ้าไม่ทำแล้วเสียอะไร"

## 3. เขียน Software Requirements Specification (SRS)

agent `business-analyst` หรือ `system-analyst` · skill `srs-writing` · `user-story-writer` · `software-diagrams` · `polished-document-style`
**ต้องมีก่อน:** `docs/README.md` · `docs/brd.md` (ถ้าขนาดงานมี BRD)
**ผลลัพธ์:** `docs/srs.md`

### หัวข้อที่ต้องมี

ตามโครงของ skill `srs-writing` (อ้างอิง ISO/IEC/IEEE 29148) อย่างน้อย:

1. ภาพรวมระบบ ผู้ใช้ และบริบท (ไดอะแกรมบริบทหนึ่งภาพ)
2. ข้อกำหนดเชิงหน้าที่ (Functional Requirement — FR) รหัส `FR-001…` **หนึ่งข้อ = หนึ่งประโยค = หนึ่งผู้กระทำ** พร้อมเกณฑ์ยอมรับแบบ Given-When-Then และอ้าง `BR-xxx` ที่มันตอบ
3. ข้อกำหนดที่ไม่ใช่หน้าที่ (Non-Functional Requirement — NFR) `NFR-001…` ใส่ตัวเลขทุกข้อ (เวลาตอบ จำนวนผู้ใช้พร้อมกัน ความพร้อมใช้งาน) ไม่ใช้คำคุณศัพท์
4. ข้อมูลและกฎธุรกิจ — รายการข้อมูลหลักและกฎการคำนวณ/ตรวจสอบ
5. อินเทอร์เฟซภายนอก (ระบบอื่น/อุปกรณ์) · ข้อจำกัด · ข้อสมมติ
6. ตารางสืบย้อน `BR → FR → (ภายหลัง) test`

### กฎเฉพาะฉบับนี้

- ไม่ใส่วิธีทำ (solution) ลงในข้อกำหนด · ข้อกำหนดที่ตรวจไม่ได้ให้เขียนใหม่หรือย้ายไปคำถามค้าง
- ข้อกำหนดที่ทำให้ต้องเก็บข้อมูลส่วนบุคคล ทำเครื่องหมาย `[PDPA]` (Personal Data Protection Act)
- จบงานรายงานจำนวน FR / NFR และข้อที่ยังกำกวม

## 4. สร้าง mockup ที่กดได้จริง

agent `ux-designer` · skill `ui-craft` + skill ตามแพลตฟอร์มใน `docs/README.md`: web → `web-app-design` · mobile → `mobile-app-design` · windows → `windows-app-design`
**ต้องมีก่อน:** `docs/README.md` · `docs/srs.md` หรือ `docs/brd.md` (ทำคู่กับ SRS ได้)
**ผลลัพธ์:** `mockup/<หน้าจอ>.html` หนึ่งไฟล์ต่อหน้าจอ · `mockup/index.html` เป็นสารบัญ · ไฟล์ CSS ของ skill วางคู่ใน `mockup/`

### หน้าจอที่ต้องทำ (ผู้ใช้กรอก · ว่างให้ agent เสนอจาก FR แล้วทำต่อเลย ลงรายการหน้าจอที่เสนอใน `## ตัดสินใจเอง`)

- <!-- ชื่อหน้าจอ · FR ที่หน้าจอนี้รองรับ -->

### ลำดับ

1. อ่าน `docs/README.md` (แพลตฟอร์ม · `doc-theme` accent) แล้วอ่าน SRS หรือ BRD ที่มีอยู่ · ทำรายการ "หน้าจอ × FR" ให้ทุก FR ที่ผู้ใช้เห็นมีหน้าจอรองรับ
2. ทุกหน้าจอใช้ token สีและ CSS จาก skill ของแพลตฟอร์ม · **ห้ามใส่สี hardcode**
3. **ทุกปุ่ม ลิงก์ และฟอร์มต้องทำงานได้จริง** — กดแล้วไปหน้าจอถัดไป เปิด/ปิด dialog เปลี่ยน tab หรือแสดงข้อความ ด้วย JavaScript เล็ก ๆ ในไฟล์ ห้ามมีปุ่มที่กดแล้วไม่เกิดอะไร (ปุ่มที่ตั้งใจให้ปิดไว้ต้อง `disabled` พร้อมเหตุผลที่มองเห็นได้)
4. ทุกหน้าจอที่มีข้อมูลต้องมีครบ **5 สถานะ** สลับดูได้ในหน้าเดียว (ปุ่มสลับมุมหน้าจอเฉพาะ mockup): ว่าง · กำลังโหลด · ผิดพลาด · บางส่วน · สำเร็จ
5. ข้อความบนหน้าจอเป็นภาษาของผู้ใช้จริง ใช้ข้อมูลตัวอย่างที่สมจริง ไม่ใช้ lorem ipsum
6. ทำ `mockup/index.html` ลิงก์ทุกหน้าจอ พร้อมตาราง "หน้าจอ → FR ที่รองรับ"
7. ตรวจเอง: รัน `check-design-tokens.mjs` (จาก `web-app-design`) กับ `mockup/` — ต้องไม่มีสี hardcode · เปิดแต่ละหน้าที่ความกว้างโทรศัพท์/เดสก์ท็อปตามแพลตฟอร์ม
8. อัปเดต `docs/README.md` ว่ามี mockup แล้ว

### กฎเฉพาะฉบับนี้

- mockup คือข้อกำหนดที่มองเห็นได้ — ไม่ใส่ฟีเจอร์ที่ SRS ไม่มี · เจอ FR ที่หน้าจอยังไม่ครอบคลุมให้ทำเพิ่มหรือลงคำถามค้าง
- ไม่ต่อ backend จริง ข้อมูลเป็นค่าตัวอย่างในไฟล์

## 5. ตรวจ mockup (อ่านอย่างเดียว)

ใช้ subagent ที่ **ไม่ได้สร้าง** mockup ตรวจ ห้ามแก้ไฟล์ · skill `ui-craft` + `e2e-testing-patterns`
**ต้องมีก่อน:** `mockup/` · `docs/srs.md` · `docs/README.md`
**ผลลัพธ์:** ตารางปัญหาในคำตอบ (เขียนลง `_to_delete/mockup-review.md` ถ้ายาวเกิน 40 แถว)

### ตรวจ 5 เรื่อง

1. **ปุ่มหลอก** — เปิดทุกไฟล์ใน `mockup/` ด้วย Playwright คลิกทุก `button` `a` `[role=button]` `input[type=submit]` บันทึกตัวที่ไม่เปลี่ยนหน้า ไม่เปลี่ยน DOM และไม่แสดงข้อความ (ยกเว้นที่ `disabled` พร้อมเหตุผล)
2. **5 สถานะ** — หน้าจอที่มีข้อมูลต้องสลับเห็น ว่าง · กำลังโหลด · ผิดพลาด · บางส่วน · สำเร็จ ครบ
3. **สี** — รัน `check-design-tokens.mjs` ไม่มีสี hardcode · ความต่างสีตัวอักษรผ่านเกณฑ์ตาม `ui-craft`
4. **ความครอบคลุม FR** — ทุก FR ที่ผู้ใช้เห็นมีหน้าจอรองรับ และทุกหน้าจอผูกกับ FR อย่างน้อยหนึ่งข้อ
5. **ลิงก์เสีย** — ลิงก์ภายในทุกอันเปิดได้ ภาพ/CSS โหลดครบ

- ทุก FR ของโมดูลต้องปรากฏใน FSD อย่างน้อยหนึ่งครั้ง — ท้ายไฟล์มีตาราง FR → หัวข้อใน FSD

## 10. สร้าง prompt agent-loop ของโปรเจกต์นี้

agent `solution-architect` + `project-manager` · skill `agent-team` (อ่าน playbook `unattended-run` `feature` `bug-fix` `visual-parity` `pickup-and-pause` ก่อนเขียน) · `spec-to-code-loop` · `app-verifier-setup` · `testing-standards` · `simplicity-first`
**ต้องมีก่อน:** `docs/srs.md` · `mockup/` (ถ้ามีหน้าจอ) · `docs/architecture.md` · `docs/fsd-*.md` · `docs/test-plan.md` (เท่าที่ขนาดงานมี) — ชื่อไฟล์จริงดูจากสารบัญ `docs/README.md` ถ้าโปรเจกต์ตั้งชื่อต่างจากนี้
**ผลลัพธ์:** `docs/AGENT-LOOP.md` ไฟล์เดียว — prompt สำเร็จรูปที่ผู้ใช้จะเอาไปสั่งให้ agent เขียนโปรแกรมของโปรเจกต์นี้ทีละข้อกำหนด · **ฉบับนี้เขียน prompt อย่างเดียว ห้ามเริ่มเขียนโค้ด ห้ามรัน loop**

### ข้อมูลที่ต้องดึงจากเอกสารของโปรเจกต์ใส่ลงใน prompt (ห้ามเว้นเป็นตัวแปรลอย ๆ)

1. ชื่อโปรเจกต์ · เป้าหมายหนึ่งประโยค · path จริงของเอกสารนำเข้าทุกไฟล์
2. เทคโนโลยี/เฟรมเวิร์กจาก `docs/architecture.md` · โครงโฟลเดอร์โค้ดที่ตั้งใจ
3. คำสั่ง install · test · smoke · รันแอป และ URL — จาก `docs/test-plan.md` / `docs/README.md` · ถ้ายังไม่มี ให้กำหนดว่า "ข้อแรกของแผนคือตั้งโครงโปรเจกต์และคำสั่งเหล่านี้" ห้ามแต่งคำสั่ง
4. รายการรหัสข้อกำหนด (`FR-…`) ทั้งหมดจาก SRS พร้อมลำดับการพึ่งพาที่แนะนำ · FR ไหนมีหน้าจอ ให้ระบุไฟล์ mockup ที่ต้องเทียบ
5. test case ที่ต้องผ่านต่อ FR (อ้างรหัสจาก test plan ถ้ามี)
6. ข้อห้ามเฉพาะโปรเจกต์ (เช่น ห้ามต่อระบบจริง ห้ามใช้ข้อมูลส่วนบุคคลจริง) จาก NFR/สถาปัตยกรรม
7. skill ตรวจแอปของโปรเจกต์ (สร้างด้วย `app-verifier-setup`) — path และคำสั่งเริ่ม · ถ้ายังไม่มี ให้กำหนดว่า "ข้อที่สองของแผนคือสร้าง verify skill" ต่อจากการตั้งโครงโปรเจกต์

### โครงของ `docs/AGENT-LOOP.md` ที่ต้องเขียน

1. **วิธีใช้** (สำหรับผู้ใช้ อ่านใน 30 วินาที): รันใน repo โค้ดที่เป็น git บน branch งานแยก (เช่น `build/loop`) · ใช้ได้ 2 แบบ — วางทีละรอบในหน้าต่างใหม่ (context สะอาด) หรือสั่ง `/loop อ่านและทำตาม docs/AGENT-LOOP.md` ให้วนเอง (`/loop` มีเฉพาะ Claude Code — เครื่องมืออื่นใช้แบบวางทีละรอบ) · สั่งหยุดด้วยไฟล์ `_to_delete/STOP` · เขียนให้ชัดว่า **การสั่งรัน loop = อนุญาตให้ `git commit` บน branch งานนี้เท่านั้น** ห้าม commit/merge ลง branch หลัก ห้าม push (รายการ "หยุดถามเสมอ" ของ `agent-team` ยกเว้น commit เมื่ออนุญาตไว้ในไฟล์นี้ — ถ้าไม่เขียน agent จะหยุดถามทุก commit และ loop เดินไม่ได้)
2. **บริบทโปรเจกต์**: ข้อมูลข้อ 1–7 ข้างบน
3. **A-Team ทุกรอบ** — เปิด skill `agent-team` ก่อนทำอย่างอื่น · `unattended-run` คือกรอบของทั้ง loop · ทุกรอบมี **playbook หลักหนึ่งตัว** จากตารางนี้ (`pickup-and-pause` คือขั้นเปิด/ปิดรอบ · `visual-parity` คือขั้นพิสูจน์ของแถวหน้าจอ ไม่นับเป็น playbook หลัก) แล้วคัดขั้นตอนของ playbook หลักลง todo ตรงตัว:

   | สถานการณ์ของรอบ | playbook |
   |---|---|
   | เริ่มทุกรอบ — อ่านสถานะ ตรวจ `git status` · `git log` · `git worktree list` ว่าตรงกับแถวที่ `เสร็จ` · ของที่ยังไม่ commit: ของแถว `กำลังทำ` ใช้ต่อ · ไม่ใช่ บันทึกเป็น `_to_delete/pause-<วันที่>.patch` แล้ว `git stash` | `pickup-and-pause` (pickup) |
   | ยังไม่มีโค้ด — แถวตั้งโครงโปรเจกต์และคำสั่ง | `new-project` |
   | แถวข้อกำหนดทั่วไป | `feature` |
   | แถวที่มีหน้าจอ | `feature` แล้วต่อด้วย `visual-parity` เทียบ mockup |
   | รอบแก้ (test/smoke แดง) | `bug-fix` |
   | รอบปิดงาน | `review` + skill `security-gate` |
   | รอบถูกตัดกลางทาง หรือ context ใกล้เต็ม | `pickup-and-pause` (pause) |

   **บทบาท** (ตาม `agent-team` ข้อ 5): agent หลักประสานงาน เขียน `docs/BUILD-PLAN.md` คนเดียว และไม่เขียนโค้ดเอง · โค้ดของแต่ละแถวส่ง subagent `developer` ตัวใหม่ · แปลง test case เป็น test อัตโนมัติและขับแอปตรวจ ใช้ `qa-tester` · ก่อน commit มีผู้ตรวจตัวใหม่ที่ไม่ได้เขียนโค้ด (ดีไซน์ข้ามโมดูลหรือแตะความปลอดภัย ใช้ `adversarial-review-panel`) · แถวที่เพิ่ม dependency หรือแตะ login สิทธิ์ ไฟล์ ข้อมูลส่วนบุคคล → `security-gate` ก่อน commit · ทุก diff ผ่านเกณฑ์โค้ดสามข้อของ `agent-team` · แถวที่แผนจัดเป็นกลุ่มขนานและไม่แตะไฟล์เดียวกัน ใช้ `parallel-split-and-merge` แยก worktree ต่อแถว ยัง commit แถวละหนึ่ง · กฎเหล่านี้อ้างชื่อ skill ไม่คัดลอกเนื้อมาเขียนซ้ำ
4. **ไฟล์สถานะ `docs/BUILD-PLAN.md`** — ทุกรอบอ่านไฟล์นี้ก่อน สถานะอยู่ในไฟล์ ไม่อยู่ในหัว agent:
   - ตารางค่าคงที่ `| รายการ | ค่า |` แถว `test` `smoke` `รันแอป` `URL แอป` (ค่าอยู่ใน backtick)
   - ตารางงาน — มีอยู่แล้วจากการวางแผน ใช้หัวตารางเดิมได้ ขอให้มีคอลัมน์ `เกณฑ์เสร็จ` `สถานะ` `commit` · ยังไม่มี ใช้ `| # | รหัส | ข้อกำหนด | ไฟล์อ้างอิง | เกณฑ์เสร็จ | สถานะ | commit |` · หนึ่งแถว = หนึ่งก้อนงานที่ commit ได้ในครั้งเดียว (FR เดียว หรือกลุ่ม FR ที่แยกไม่ได้) · สถานะใช้แค่ `รอทำ` `กำลังทำ` `เสร็จ` `ติด`
   - ยังไม่มี verify skill → ต้องมีแถว "สร้าง verify skill (`app-verifier-setup`)" ต่อจากแถวตั้งโครง — **เขียนลงตารางจริง** ไม่ใช่แค่บอกใน prompt
   - หัวข้อ `## คำถามค้าง` และ `## ผลปิดงาน`
   - หัวข้อ `## สถานะล่าสุด` `## ประวัติสถานะ` และ `## ตัดสินใจเอง` (มีอยู่แล้วจากตอนทำเอกสาร) — **เก็บไว้ ห้ามลบ**
5. **ด่านก่อนแถวโค้ดแรก**: การตัดสินใจที่ผูกทั้งโปรเจกต์และย้อนยาก (ภาษา เฟรมเวิร์ก ฐานข้อมูล — ADR ที่ยังเป็น "เสนอ") ต้องยืนยันแล้ว · ยังไม่ยืนยัน → ไม่เริ่มแถวโค้ด จบรอบด้วย `BLOCKED` พร้อมคำถามใน `## คำถามค้าง` · ระบุชื่อ ADR ที่ต้องยืนยันลงใน prompt
6. **หนึ่งรอบทำอะไร** — ตัดสินจากไฟล์ ตามลำดับนี้:
   - มีไฟล์ `_to_delete/STOP` → ไม่ทำงาน · เพิ่มบรรทัด `หยุดตามไฟล์ STOP` ใน `## ประวัติสถานะ` อย่างเดียว → `BLOCKED`
   - ด่านข้อ 5 ยังไม่ผ่าน → `BLOCKED` · ผ่านแล้วแต่คำถามของด่านยังเปิด → ย้ายไป "ข้อที่ปิดแล้ว" แล้วตรวจข้อถัดไปในรอบเดียวกัน
   - `BUILD-PLAN.md` ยังไม่มีตารางงาน → **รอบวางแผน**: เพิ่มตารางค่าคงที่และตารางงานจาก FR ข้อ 4 แล้ว**ทำแถวแรกต่อในรอบเดียวกัน** · หยุดที่แผนเฉพาะเมื่อผู้ใช้สั่ง `วางแผนอย่างเดียว` (ต่างจาก skill `spec-to-code-loop` ที่หยุดหลังวางแผนเสมอ — ไฟล์ prompt นี้ตั้งใจให้ทำต่อ)
   - มีแถว `กำลังทำ` ค้างจากรอบก่อน → ทำแถวนั้นต่อก่อน (นับเป็นอีกหนึ่งครั้งของแถวนั้น)
   - มีแถว `รอทำ` ที่ **ทุกแถวที่มันพึ่ง `เสร็จ` แล้ว** และไม่มีคำถามค้างที่ระบุเลขแถวนั้น → ทำแถวแรก: ตั้ง `กำลังทำ` และเพิ่มบรรทัด `แถว N · ครั้งที่ k · เริ่ม` ใน `## ประวัติสถานะ` ทันที → test ของแถวก่อนและเห็นแดงด้วยเหตุผลที่ถูก → โค้ดน้อยที่สุดให้เขียว → test ทั้งชุดเขียว → แถวที่มีหน้าจอ ขับแอปจริงด้วย verify skill เทียบ mockup → ผู้ตรวจผ่าน → `git commit` ครั้งเดียว `feat(<โมดูล>): … [FR-xxx]` → ตั้ง `เสร็จ` + เลข commit
   - ยังมีแถวไม่เสร็จ แต่ไม่มีแถวไหนทำได้ (ที่เหลือ `ติด` · พึ่งแถวที่ยังไม่เสร็จ · หรือติดคำถามค้าง) → สรุปว่าแต่ละแถวรออะไร → `BLOCKED`
   - ทุกแถว `เสร็จ` แต่ test หรือ smoke แดง → **รอบแก้** (เพิ่มบรรทัด `รอบแก้ · ครั้งที่ k · เริ่ม`): หาต้นเหตุหนึ่งข้อ แก้เฉพาะจุด commit `fix(<โมดูล>): …`
   - ทุกแถว `เสร็จ` และ test กับ smoke คืนค่า 0 → **รอบปิดงาน**: ตรวจตาม `review` + `security-gate` แล้วเขียนตารางสืบย้อน FR → test → commit ใน `## ผลปิดงาน` → `DONE`
   - **นิยามที่ prompt ต้องเขียนให้ชัด:** "พึ่ง" ดูจากอะไร (คอลัมน์พึ่งแถว หรือกลุ่มขนาน/ต่อเนื่องในแผน) · คำถามค้างบล็อกแถวเฉพาะเมื่อระบุเลขแถว · path ในตารางนับจากโฟลเดอร์ไหน · เกณฑ์ที่พิสูจน์ได้เฉพาะหลัง push (เช่น CI) ผ่านอย่างไรในรอบ loop · แถวที่ไม่มีโค้ด (ตัดสินใจ/ยืนยันถ้อยคำ) ปิดอย่างไรโดยไม่ commit · แถวที่ไม่อยู่ในกลุ่มใดพึ่งอะไร
7. **เงื่อนไขจบที่ตรวจด้วยเครื่องได้**: ทุกแถว `เสร็จ` **และ** คำสั่ง test คืนค่า 0 **และ** คำสั่ง smoke คืนค่า 0 — agent ต้องรันคำสั่งเองแล้วรายงานผลจริง ห้ามสรุปว่าผ่านจากการอ่านโค้ด
8. **เพดาน**: นับครั้งจากบรรทัด `แถว N · ครั้งที่ k · เริ่ม` (เขียนตอนเริ่ม ไม่ใช่ตอนจบ — รอบที่พังกลางทางจึงถูกนับ) · หยุดแบบตั้งใจ (`pickup-and-pause` pause) เขียน `แถว N · พัก` ไม่นับ · แถวเดิมไม่จบในครั้งที่ 3 → ตั้ง `ติด` พร้อมเหตุผลหนึ่งบรรทัด แล้วไปแถวถัดไปที่ไม่พึ่งแถวนี้ (ตาม `unattended-run`) · รอบแก้ไม่ผ่าน 3 ครั้งติดกัน → `BLOCKED`
9. **ท้ายทุกรอบ** (ยกเว้นรอบที่หยุดตามไฟล์ STOP): skill `status-report` เขียนทับ `## สถานะล่าสุด` — แถวโค้ดรวมเป็นช่วงรหัสตามสถานะ (`FR-001 ถึง FR-012 · เสร็จ · ผ่าน — test 48/48`) แถวเอกสารคงค่าเดิม · ผลตรวจเอาจากคำสั่งที่รันจริงในรอบนั้น · **ค้างอยู่** = แถว `ติด` และคำถามค้าง · **ถัดไป** = แถวงานถัดไป — แล้วเพิ่มหนึ่งบรรทัดใน `## ประวัติสถานะ` · การตัดสินใจเองลง `## ตัดสินใจเอง` ด้วย skill `decision-log` · คำตอบบอก principle ที่ใช้และติดป้าย `วัดจริง` / `อนุมาน` / `เดา` ตาม `agent-team` ข้อ 7
10. **บรรทัดสุดท้ายของทุกรอบ** ต้องเป็นหนึ่งใน `LOOP-STATUS: CONTINUE` · `LOOP-STATUS: PLAN-READY` (เฉพาะสั่ง `วางแผนอย่างเดียว`) · `LOOP-STATUS: BLOCKED` · `LOOP-STATUS: DONE` (ใช้กับ `/loop`: เมื่อเป็น `BLOCKED` `PLAN-READY` หรือ `DONE` ให้หยุดวน)
11. **ข้อห้าม**: ห้ามแก้ SRS/FSD/mockup/ไฟล์ test case (เจอจุดผิดให้ลงคำถามค้าง) · ห้ามลบหรือผ่อน test ให้ผ่าน · ห้าม commit โค้ดที่ test แดง · subagent ห้ามเขียน `docs/BUILD-PLAN.md` · ห้ามรอคำตอบกลางรอบ — คำถามข้อเท็จจริงลง `## คำถามค้าง` แล้วทำแถวถัดไปที่ไม่ติดคำถามนั้น · คำถามที่เป็นการตัดสินใจให้เลือกทางผลกระทบน้อยสุดเองแล้วลง `## ตัดสินใจเอง` ไม่ตั้ง `ติด` · ของชั่วคราวลง `_to_delete/`

### กฎเฉพาะฉบับนี้

- prompt ที่ได้ต้องใช้ได้ทันทีโดยไม่ต้องแก้ — ทุกค่าเป็นของจริงของโปรเจกต์ ค่าที่ยังไม่รู้เขียนว่า `(ยังไม่มี — ข้อแรกของแผนต้องตั้ง)` ไม่ใช่ `<ใส่ค่า>`
- ยาวไม่เกิน ~170 บรรทัด อ้างเอกสารด้วย path แทนการคัดลอกเนื้อหา · อ้าง skill ด้วยชื่อแทนการคัดลอกกฎ
- **ตรวจก่อนส่ง:** ให้ subagent ตัวใหม่อ่าน prompt ที่ได้แบบ agent ที่ไม่เคยเห็นโปรเจกต์ แล้วไล่สถานการณ์ 6 แบบ — เริ่มครั้งแรก · แถวค้าง `กำลังทำ` · แถว `ติด` · test แดงหลังทุกแถวเสร็จ · ADR ยังไม่ยืนยัน · มีไฟล์ STOP — ทุกแบบต้องรู้ว่าทำอะไรและจบด้วย LOOP-STATUS ใด โดยไม่ต้องถามคน
- เอกสารขัดกัน (เช่น FR ที่ไม่มี mockup หรือ mockup ที่ไม่มี FR) → ลงเป็นคำถามค้างใน `docs/BUILD-PLAN.md` แล้วเขียน prompt ต่อ (FR ที่ไม่มี mockup เข้าตารางงานพร้อมหมายเหตุ `ไม่มี mockup` · mockup ที่ไม่มี FR ไม่เข้าตารางงาน)

## 11. เขียนคู่มือผู้ใช้จากโปรแกรมจริง

agent `technical-writer` · skill `polished-document-style` · `branded-document-design` (ตอน render)
**ต้องมีก่อน:** `docs/README.md` · โปรแกรมที่รันได้ (ดู "คำสั่งรันแอป" ใน `docs/README.md`) · `docs/srs.md`
**ผลลัพธ์:** `docs/user-guide.md` · ภาพหน้าจอใน `docs/figures/`

### ลำดับ

1. รันแอปตามคำสั่งใน `docs/README.md` ถ้ารันไม่ได้ ให้หยุดและบอก — **ห้ามเขียนคู่มือจาก mockup หรือจินตนาการ**
2. แยกคู่มือตามบทบาทผู้ใช้ที่ SRS ระบุ (ผู้ใช้ทั่วไป / ผู้ดูแล) ถ้ามีมากกว่าหนึ่งบทบาท
3. ต่อหนึ่งงานที่ผู้ใช้ทำ: เป้าหมายหนึ่งบรรทัด · ขั้นตอนเลขลำดับ (หนึ่งการกระทำต่อข้อ) · ภาพหน้าจอจริงที่ถ่ายด้วยเครื่องมือ (Playwright) พร้อมคำบรรยายใต้ภาพ · ผลที่ควรเห็น
4. ส่วนแก้ปัญหา: ข้อความ error ที่ผู้ใช้อาจเจอจริง → สาเหตุ → วิธีแก้ (ดึงจากโปรแกรม ไม่แต่ง)
5. ภาษาง่าย ประโยคสั้น ไม่มีศัพท์เทคนิคที่ผู้ใช้ไม่ต้องรู้ · ใช้ชื่อปุ่ม/เมนูตรงกับหน้าจอทุกตัวอักษร
6. ท้ายเล่ม: คำศัพท์ และช่องทางขอความช่วยเหลือ (ถ้าผู้ใช้ให้ข้อมูล)

### กฎเฉพาะฉบับนี้

- ขั้นตอนไหนลองทำแล้วไม่ได้ผลตามที่เขียน ให้ลงคำถามค้างว่าเป็นบั๊กหรือคู่มือผิด ห้ามเขียนให้ดูผ่าน
