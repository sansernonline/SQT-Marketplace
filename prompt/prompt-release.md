# prompt-release — เอกสาร deploy และออกรุ่น

ใช้คู่กับ plugin `software-company` · ไฟล์นี้รวม prompt 3 ฉบับ แต่ละฉบับสร้างเอกสารหนึ่งชุด · ไฟล์แยกรายฉบับอยู่ในโฟลเดอร์ `prompt-release/`

## วิธีใช้

วางทั้งไฟล์ใน Claude Code ที่รากโฟลเดอร์โปรเจกต์ แล้วพิมพ์ต่อท้ายว่าจะทำฉบับไหน เช่น `ทำทั้งหมด` หรือ `ทำข้อ 3 และ 4`

**กฎการทำงานของไฟล์รวม (agent ต้องทำตาม):**

1. ทำทีละฉบับตามลำดับในตาราง ข้ามฉบับที่ผู้ใช้ไม่ได้สั่ง
2. **จบแต่ละฉบับให้หยุด** อัปเดตตารางสถานะใน `docs/BUILD-PLAN.md` ตามข้อ "รายงานสถานะ" ในกฎร่วม แล้วแสดงในคำตอบ: แถวที่เปลี่ยน · ค้างอยู่ · ฉบับถัดไป — รอผู้ใช้พิมพ์ `ต่อ` หรือสั่งแก้ **ห้ามเริ่มฉบับถัดไปเอง**
3. ช่องที่เขียนว่า "ผู้ใช้กรอก" ของฉบับไหนยังว่าง ให้ถามตอนเริ่มฉบับนั้น ไม่ต้องถามทั้งหมดตั้งแต่ต้น
4. ฉบับหลังใช้ผลของฉบับก่อนเป็นข้อมูลนำเข้า — อ่านจากดิสก์ใหม่ทุกครั้ง (ผู้ใช้อาจแก้ไปแล้ว)

| # | เอกสาร | ได้ไฟล์ |
|---|---|---|
| 1 | เอกสารแผน deploy และ CI/CD | `docs/deploy-guide.md` |
| 2 | บันทึกการออกรุ่น (Release Notes) | `docs/release-notes/v<เวอร์ชัน>.md` |
| 3 | คู่มือรับมือเหตุการณ์ (Runbook) | `docs/runbook.md` |

## กฎร่วมทุกฉบับ

- อ่าน `docs/BUILD-PLAN.md` (หัวข้อ `สถานะล่าสุด`) และ `docs/README.md` ก่อน (ถ้ามี) — สถานะงาน รหัสโปรเจกต์ ขนาดงาน ธีมสี อยู่ที่นั่น · ไม่มีให้ถามเฉพาะค่าที่ขาด
- **ที่เก็บไฟล์** (ตาม skill `project-doc-set`): `ref/` ไฟล์ที่ได้รับมา อ่านอย่างเดียว · `docs/` เอกสารที่เราเขียน (รูปใน `docs/figures/`) · `mockup/` UI mockup · `qa/` test case ผลทดสอบ รายงานบั๊ก · `assets/` โลโก้ ไอคอน · `_to_delete/` ของชั่วคราว — สร้างโฟลเดอร์เมื่อมีของจริงเท่านั้น
- อ่านไฟล์จากดิสก์ก่อนแก้ · ไฟล์ยาวเกิน 300 บรรทัดอ่านเฉพาะช่วง · ต้องเปิดเกิน 3 ไฟล์เพื่อตอบเรื่องเดียว ให้ส่ง subagent
- ข้อมูลไม่พอหรือเอกสารขัดกัน → รวมเป็นคำถามท้ายคำตอบแล้ว **หยุด** ห้ามเดา ห้ามแต่งตัวเลข/ชื่อ/วันที่
- ตัวย่อทุกตัวกางเต็มครั้งแรก เช่น Software Requirements Specification (SRS) · ของชั่วคราวลง `_to_delete/`
- ตั้งชื่อไฟล์ตาม skill `document-naming` · รูปแบบเอกสารตาม `polished-document-style`
- **รายงานสถานะทุกครั้งที่จบฉบับ** (ใช้ skill `status-report` ถ้ามี) ลง `docs/BUILD-PLAN.md` — ไม่มีไฟล์ให้สร้าง · แก้เฉพาะสองหัวข้อนี้ ไม่แตะหัวข้ออื่นในไฟล์:
  - `## สถานะล่าสุด` **เขียนทับทั้งหัวข้อ**: วันที่เวลา · ตาราง `| รายการ | ประเภท | สถานะ | ผลตรวจ | ค้าง / หมายเหตุ |` ครบทุกเอกสารและงานของโปรเจกต์ (รายการที่รอบนี้ไม่ได้แตะ คัดลอกค่าเดิม) · ตามด้วย **ค้างอยู่** (คำถามที่ต้องมีคนตอบ พร้อมบอกว่าถามใคร ไม่มีเขียน `ไม่มี`) และ **ถัดไป** (ไม่เกิน 3 อย่าง)
  - สถานะเอกสาร: `ยังไม่เริ่ม` · `DRAFT` · `REVIEW` — `APPROVED` ผู้ใช้ตั้งเองเท่านั้น · ผลตรวจ: `ผ่าน — <หลักฐาน>` · `ไม่ผ่าน — <อะไร>` · `ยังไม่ตรวจ` — **ห้ามเขียน `ผ่าน` ถ้าไม่ได้ตรวจหรือรันจริง**
  - `## ประวัติสถานะ` เพิ่มหนึ่งบรรทัดบนสุด: `วันที่ เวลา · งาน · สถานะ · ผล · ค้างกี่ข้อ`
- คำตอบตอนจบ: แสดงเฉพาะแถวที่เปลี่ยน + ค้างอยู่ + ถัดไป แล้วบอกว่าตารางเต็มอยู่ใน `docs/BUILD-PLAN.md` — ไม่คัดลอกเนื้อเอกสารกลับมา

## 1. เอกสารแผน deploy และ CI/CD

agent `devops-engineer` · skill `cicd-and-release` · `config-and-secrets` · `observability-basics` · `web-service-essentials` · `simplicity-first`
**ต้องมีก่อน:** `docs/architecture.md` (ถ้ามี) · โค้ดที่ build ได้
**ผลลัพธ์:** `docs/deploy-guide.md` — เอกสารเท่านั้น **ไม่สร้าง pipeline / ไม่แตะเซิร์ฟเวอร์ / ไม่ใส่ค่าลับจริง** (ร่างไฟล์ตัวอย่างอยู่ในเอกสารเป็นบล็อกโค้ด ไม่บันทึกลง repo)

### ข้อมูลการ deploy (ผู้ใช้กรอก)

- ที่ที่จะรัน (เครื่องเดียว / VM / container / cloud ชื่ออะไร):
- สภาพแวดล้อมที่ต้องมี (dev / test / staging / production):
- เครื่องมือ CI ที่ใช้อยู่ (GitHub Actions / Azure DevOps / GitLab / ยังไม่มี):
- ใครเป็นคน deploy และต้องอนุมัติกี่ขั้น:
- ข้อจำกัด (ช่วงเวลาหยุดระบบได้ งบ นโยบายองค์กร):

### หัวข้อที่ต้องมีในเอกสาร

1. ภาพรวม — ไดอะแกรม deployment หนึ่งภาพ (ใคร รันอะไร บนเครื่องไหน ไม่เกิน 7 กล่อง)
2. สภาพแวดล้อมแต่ละชั้น — ต่างกันตรงไหน (ข้อมูล โดเมน สิทธิ์)
3. ขั้นตอน build → test → package → deploy ทีละขั้น พร้อมคำสั่งจริงที่ค้นจากโปรเจกต์ (ไม่เดาคำสั่ง) และเงื่อนไขที่หยุด pipeline
4. ร่าง pipeline (บล็อกโค้ดในเอกสาร) ตามเครื่องมือ CI ที่ใช้
5. ค่าตั้งและความลับ — **ตารางชื่อตัวแปร** · ใช้ทำอะไร · ที่เก็บ (secret store / env) · ใครดูแล · **ไม่ใส่ค่า**
6. ฐานข้อมูล — migration รันตอนไหน สำรองก่อน deploy อย่างไร
7. การตรวจหลัง deploy — health / version endpoint, smoke test, สิ่งที่ต้องเห็นใน log
8. Rollback — เงื่อนไขที่ต้องถอย · ขั้นตอนทีละข้อ · ข้อมูลที่ย้อนไม่ได้
9. Checklist ก่อน/หลัง deploy (ช่องติ๊กได้)
10. ความเสี่ยงและสิ่งที่ยังไม่มี (เช่น ยังไม่มี staging)

### กฎเฉพาะฉบับนี้

- เริ่มจากแบบที่ง่ายที่สุดที่พอสำหรับขนาดงาน ไม่เสนอ Kubernetes / หลาย region ถ้าไม่มีเหตุผลจาก NFR
- ข้อมูลที่ไม่มี (ชื่อเซิร์ฟเวอร์ โดเมน) → `(รอยืนยัน)` ห้ามแต่ง

## 2. บันทึกการออกรุ่น (Release Notes)

agent `technical-writer` · skill `software-company:release-notes` · `commit-message-format` · `polished-document-style`
**ผลลัพธ์:** `docs/release-notes/v<เวอร์ชัน>.md` — เขียนเป็นภาษาผู้ใช้ ไม่ใช่ภาษาผู้พัฒนา

### ข้อมูลรุ่น (ผู้ใช้กรอก)

- เวอร์ชันใหม่:
- เวอร์ชัน/tag ก่อนหน้า (เว้นว่าง = ให้หา tag ล่าสุดเอง):
- วันที่ออกรุ่น:
- ผู้อ่านหลัก (ผู้ใช้ทั่วไป / ผู้ดูแลระบบ / ผู้ว่าจ้าง):

### วิธีทำ

1. ดึงรายการเปลี่ยนแปลงจาก `git log <tag เดิม>..HEAD --oneline` (จำกัดไม่เกิน 200 บรรทัด) แล้วอ่านรายละเอียดเฉพาะ commit ที่ไม่ชัดจากข้อความ · ถ้าไม่มี git ให้ถามผู้ใช้
2. ผูกแต่ละการเปลี่ยนแปลงกับ `FR` / `BUILD-PLAN.md` / change request / bug ที่เกี่ยว (ถ้ามี)
3. แยกกลุ่ม: **ของใหม่** · **ปรับปรุง** · **แก้ไขข้อผิดพลาด** · **ที่ต้องทำเมื่ออัปเกรด** (migration, ตั้งค่าใหม่) · **ข้อจำกัดที่ยังมี** · **เลิกใช้/เปลี่ยนพฤติกรรม** (breaking change ขึ้นก่อนสุด)
4. เขียนแต่ละข้อจากมุมผู้ใช้: "ตอนนี้คุณทำ … ได้แล้ว" แทน "เพิ่ม endpoint …" · ข้อความสั้น หนึ่งข้อหนึ่งเรื่อง
5. ข้าม commit ที่ผู้ใช้ไม่เห็นผล (refactor, เปลี่ยนชื่อตัวแปร, เครื่องมือภายใน) — รวมเป็นบรรทัดเดียว "ปรับปรุงภายใน" ได้ถ้าจำเป็น

### โครงเอกสาร

```
# <ชื่อโปรเจกต์> v<เวอร์ชัน> — <วันที่>
สรุป 2–3 ประโยค: รุ่นนี้เกี่ยวกับอะไร
## ที่ต้องทำก่อนอัปเกรด   (ถ้ามี)
## ของใหม่
## ปรับปรุง
## แก้ไขข้อผิดพลาด
## ข้อจำกัดที่ยังมี
```

### กฎเฉพาะฉบับนี้

- เขียนเฉพาะสิ่งที่พบใน commit / เอกสารจริง ห้ามแต่งฟีเจอร์หรือใส่คำโฆษณา
- ไม่ใส่ชื่อบุคคล เลข commit ดิบ หรือชื่อไฟล์ภายใน (อ้างรหัส FR/CR ได้)

## 3. คู่มือรับมือเหตุการณ์ (Runbook)

agent `devops-engineer` · skill `incident-runbook-template` · `observability-basics` · `logging-standards` · `postmortem-template` (ลิงก์ไปเมื่อเหตุจบ)
**ต้องมีก่อน:** `docs/architecture.md` · `docs/deploy-guide.md` (ถ้ามี)
**ผลลัพธ์:** `docs/runbook.md` — เอกสารเท่านั้น ไม่รันคำสั่งที่แตะระบบจริง (คำสั่งในเอกสารเป็นข้อความตัวอย่างที่ผู้เข้าเวรจะรันเอง)

### ข้อมูลระบบ (ผู้ใช้กรอก)

- ระบบอะไรพังแล้วกระทบใคร (ผู้ใช้กี่คน งานสำคัญช่วงไหน):
- ผู้เข้าเวร/ผู้ดูแล (ระบุเป็นบทบาท ช่องทางติดต่อเว้นว่างไว้ให้เติมเอง):
- เครื่องมือดู log / monitor ที่มี:
- เหตุการณ์ที่เคยเกิดหรือกังวล (ถ้ามี):

### หัวข้อที่ต้องมีในเอกสาร

1. **ก่อนเริ่ม (อ่านใน 1 นาที)** — ระบบคืออะไร · ส่วนประกอบ 1 ภาพ · ที่อยู่ของ log / dashboard / คำสั่งรัน-หยุด-ดูสถานะ
2. **ระดับความรุนแรง** — นิยาม 3–4 ระดับด้วยผลที่ผู้ใช้เห็น (ไม่ใช้คำว่า "ร้ายแรง" ลอย ๆ) และเวลาที่ต้องตอบสนอง (ค่าที่ผู้ใช้ไม่ได้ให้ = `(รอยืนยัน)`)
3. **การ์ดเหตุการณ์** ต่อหนึ่งเหตุ (เริ่มจากที่เกิดได้จริงกับระบบนี้ อ่านจากสถาปัตยกรรม เช่น แอปไม่ตอบ, ฐานข้อมูลเต็ม, เชื่อมระบบภายนอกไม่ได้, ล็อกอินไม่ได้, deploy แล้วพัง, ดิสก์เต็ม):
   อาการที่เห็น → ตรวจอะไรก่อน (คำสั่งจริงที่ค้นจากโปรเจกต์) → แก้ทีละขั้น → วิธียืนยันว่าหายแล้ว → เมื่อไรต้องเรียกใคร/ยกระดับ → ข้อควรระวัง (สิ่งที่ห้ามทำ)
4. **Rollback / กู้คืน** — อ้างอิง `docs/deploy-guide.md` · สำรองข้อมูลอยู่ที่ไหน กู้อย่างไร ทดสอบล่าสุดเมื่อไร (ไม่ทราบ = `(รอยืนยัน)`)
5. **การสื่อสาร** — ประกาศใคร ทางไหน ข้อความตัวอย่างสำหรับผู้ใช้ 1 แบบ
6. **หลังเหตุ** — บันทึกอะไรระหว่างแก้ · ทำ postmortem เมื่อไร (ใช้ `postmortem-template`)
7. ตารางติดต่อ (บทบาท · ช่องทาง ให้เติม) และประวัติเวอร์ชันของเอกสาร

### กฎเฉพาะฉบับนี้

- อ่านแล้วทำตามได้เวลาตีสามโดยไม่ต้องคิด: ขั้นตอนสั้น เลขลำดับ หนึ่งการกระทำต่อข้อ
- การ์ดไหนที่ค้นคำสั่งจริงไม่เจอ ให้เขียน `(ต้องเติมคำสั่ง)` ห้ามแต่งคำสั่ง
