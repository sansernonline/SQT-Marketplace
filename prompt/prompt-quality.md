# prompt-quality — เอกสารตรวจคุณภาพ

ใช้คู่กับ plugin `software-company` · ไฟล์นี้รวม prompt 3 ฉบับ แต่ละฉบับสร้างเอกสาร 1 ชุด

## วิธีใช้

วางทั้งไฟล์ใน Claude Code, Codex CLI หรือ Gemini CLI ที่รากโฟลเดอร์โปรเจกต์ แล้วพิมพ์ต่อท้ายว่าจะทำฉบับไหน เช่น `ทำทั้งหมด` หรือ `ทำข้อ 3 และ 4`

**กฎการทำงาน (agent ต้องทำตาม):** เปิด skill `superuser` ก่อนเริ่ม แล้วทำตาม playbook `project-docs` ทุกขั้น — กฎร่วม (ถามครั้งเดียว · ทำจบรอบเดียว · ตัดสินใจเอง · รายงานสถานะ · ที่เก็บไฟล์) อยู่ที่นั่นที่เดียว · เปิด skill ไม่ได้ ให้หยุดและบอกผู้ใช้ ห้ามทำต่อโดยไม่มีกฎ

**ภาษาและรูป:** ทุกเอกสารเขียนตาม skill `human-writing` · รูปในเอกสารส่งมอบใช้แบบเดียวกันทั้งชุด: ผังระบบ · flow · ผังคลาวด์ → `diagram-figures` · Mermaid (`software-diagrams`) ใช้ได้เฉพาะเอกสารภายในทีม

| # | เอกสาร | ได้ไฟล์ |
|---|---|---|
| 1 | รายงานตรวจความปลอดภัย (Security Review) | `docs/security-review.md` |
| 2 | รายงานรีวิวโค้ด (Code Review) | `docs/code-review.md` |
| 3 | รายงานเอกสารกับโค้ดที่ไม่ตรงกัน (Doc Sync) | `docs/doc-sync-report.md` |

## 1. รายงานตรวจความปลอดภัย (Security Review)

agent `security-engineer` · skill `software-company:security-scan` · `software-company:threat-model` · `auth-implementation-patterns` · `pdpa-compliance`
**ผลลัพธ์:** `docs/security-review.md` — **ห้ามแก้โค้ด** · ห้ามรันอะไรที่ส่งข้อมูลออกนอกเครื่องหรือแตะระบบจริง

### ขอบเขต (ผู้ใช้กรอก)

- ตรวจอะไร (ทั้ง repo / โมดูล / ฟีเจอร์ / ชุดไฟล์):
- สภาพแวดล้อมเป้าหมาย (เครื่องเดียว / เว็บสาธารณะ / ภายในองค์กร):
- ข้อมูลที่ระบบจัดการ (มีข้อมูลส่วนบุคคล การเงิน สุขภาพ ไหม):
- มาตรฐานที่ต้องผ่าน (PDPA, ISO 27001, PCI-DSS หรือไม่มี):

### สิ่งที่ตรวจ

1. **ข้อมูลลับในโค้ด** — คีย์ รหัสผ่าน token ในไฟล์/ประวัติ git (ค้นเฉพาะรูปแบบ ไม่คัดลอกค่าจริงลงรายงาน ให้แสดง `sk-…xxxx` แบบปิดบัง)
2. **OWASP Top 10** — injection · การยืนยันตัวตน/เซสชัน · การควบคุมสิทธิ์ (เรียก API ข้ามผู้ใช้ได้ไหม) · ตั้งค่าผิด · component เก่า · logging/monitoring
3. **Dependency** — แพ็กเกจที่มีช่องโหว่ที่รู้แล้ว (ใช้เครื่องมือของ ecosystem เช่น `npm audit` `pip-audit` `dotnet list package --vulnerable` ถ้ามีและรันแบบอ่านอย่างเดียว)
4. **การจัดการข้อมูล** — เข้ารหัสระหว่างส่ง/ตอนเก็บ · ข้อมูลส่วนบุคคลไหลไปไหน · log มีข้อมูลที่ไม่ควรมีไหม · เก็บนานแค่ไหน (PDPA)
5. **การอัปโหลด/ไฟล์/URL ที่ผู้ใช้ส่งมา** — ตรวจชนิด ขนาด path traversal SSRF
6. **Threat model ย่อ** (STRIDE) ของ flow ที่สำคัญ 2–3 อัน พร้อมแผนภาพ Mermaid 1 ภาพ

### รูปแบบรายงาน

- สรุปผู้บริหาร 5 บรรทัด: ภาพรวม · จำนวนข้อค้นพบแต่ละระดับ · 3 เรื่องที่ควรแก้ก่อน
- ตารางข้อค้นพบ:

  | # | ระดับ (วิกฤต/สูง/กลาง/ต่ำ) | เรื่อง | ตำแหน่ง (ไฟล์:บรรทัด) | หลักฐาน | ผลที่อาจเกิด | วิธีแก้ที่แนะนำ |
  |---|---|---|---|---|---|---|

- ส่วน "สิ่งที่ไม่ได้ตรวจ" เขียนให้ชัด — ห้ามให้อ่านแล้วเข้าใจว่าปลอดภัยทั้งหมด

### กฎเฉพาะฉบับนี้

- ทุกข้อค้นพบต้องมีหลักฐานที่ชี้ตำแหน่งได้ · ไม่แน่ใจให้ติดป้าย `ต้องยืนยัน` ห้ามรายงานเป็นช่องโหว่จริง
- ไม่เขียนโค้ดโจมตีหรือขั้นตอนเจาะระบบ บอกแค่สาเหตุ ผลกระทบ และวิธีแก้

## 2. รายงานรีวิวโค้ด (Code Review)

agent `developer` (ผู้รีวิว ต้องไม่ใช่ตัวที่เขียนโค้ดนั้น) · skill `code-review-checklist` · `readable-code` · `lazy-coding` · `error-handling-patterns` · `logging-standards`
**ผลลัพธ์:** `docs/code-review.md` — **ห้ามแก้โค้ด**

### ขอบเขต (ผู้ใช้กรอก)

- รีวิวอะไร (branch / commit ช่วงไหน / โมดูล / ทั้ง repo):
- เน้นเรื่องอะไรเป็นพิเศษ (ถ้ามี):
- มาตรฐานที่ทีมใช้ (style guide, lint config):

### วิธีทำ

1. กำหนดชุดไฟล์ที่รีวิวจาก `git diff` / `git log` ตามขอบเขต (รายการไฟล์ก่อน แล้วอ่านทีละไฟล์ อย่าอ่านทั้ง repo) · ข้ามไฟล์ที่ generate และ lock file
2. รัน test และ lint ของโปรเจกต์แบบอ่านอย่างเดียว (ถ้ามีคำสั่ง) แล้วบันทึกผลจริง
3. ตรวจตาม `code-review-checklist`: ความถูกต้อง · การจัดการ error · ความปลอดภัยเบื้องต้น · การออกแบบ (ความซับซ้อนเกินจำเป็น โค้ดซ้ำ) · ความอ่านง่าย · test (ครอบคลุมกรณีที่สำคัญไหม) · ประสิทธิภาพ (เฉพาะจุดที่เห็นชัด)
4. เทียบกับ SRS/FSD: โค้ดทำตามข้อกำหนดที่ระบุ (FR ที่เกี่ยว) ไหม

### รูปแบบรายงาน

- สรุป 5 บรรทัด: ตัดสิน (ผ่าน / ผ่านหลังแก้ / ไม่ผ่าน) · จำนวนข้อแต่ละระดับ · เรื่องที่ดี 1–2 ข้อ (ระบุให้เจาะจง)
- ตารางข้อสังเกต:

  | # | ระดับ (ต้องแก้ / ควรแก้ / ข้อเสนอ) | ไฟล์:บรรทัด | ปัญหา | ทำไมสำคัญ | ข้อเสนอแก้ |
  |---|---|---|---|---|---|

- ผล test/lint ที่รันจริง (คำสั่ง + ผล) · สิ่งที่ไม่ได้ตรวจ

### กฎเฉพาะฉบับนี้

- ทุกข้อต้องชี้ไฟล์:บรรทัดได้ · ข้อที่เป็นแค่ความชอบส่วนตัว ติดป้าย `ข้อเสนอ` อย่าปนกับ `ต้องแก้`
- ไม่เขียนโค้ดใหม่เป็นชุด แสดงตัวอย่างสั้นได้ไม่เกิน 10 บรรทัดต่อข้อ

## 3. รายงานเอกสารกับโค้ดที่ไม่ตรงกัน (Doc Sync)

agent `system-analyst` + `qa-tester` · skill `srs-writing` · `fsd-writing` · `test-case-template`
**ผลลัพธ์:** `docs/doc-sync-report.md` — **ห้ามแก้เอกสารหรือโค้ด** ผู้ใช้เป็นคนตัดสินว่าจะแก้ฝั่งไหน

### ขอบเขต (ผู้ใช้กรอก)

- เอกสารที่จะเทียบ (เช่น `docs/srs.md` `docs/fsd-*.md` `docs/API-SPEC.md` `docs/DATA-DICTIONARY.md` `docs/test-plan.md` `mockup/`):
- ส่วนของโค้ดที่เทียบ (ทั้ง repo / โมดูล):
- เหตุที่สงสัยว่าไม่ตรง (เช่น แก้โค้ดหลายรอบโดยไม่แก้เอกสาร):

### วิธีทำ

1. ทำรายการรหัสข้อกำหนด (`FR-…` `NFR-…`) จาก SRS และรายการ endpoint / ตาราง / หน้าจอ จากเอกสารที่เทียบ — ทีละเอกสาร
2. แต่ละรายการ หาในโค้ดและ test ว่ามีจริงไหม ทำตามที่เขียนไหม (ค้นแบบจำกัดขอบเขต: ระบุ path / glob ทุกครั้ง)
3. ไล่ย้อนกลับ: สิ่งที่มีในโค้ด (endpoint, ตาราง, หน้าจอ, ฟีเจอร์) แต่ **ไม่มี**ในเอกสารเลย
4. เทียบ mockup กับหน้าจอจริง: ปุ่ม/ข้อความ/สถานะที่ต่างกัน
5. ตรวจสถานะใน `docs/README.md` ว่าตรงความจริงไหม (เช่น `APPROVED` แต่เนื้อหาเก่า)

### รูปแบบรายงาน

| # | ประเภท | รหัส/รายการ | เอกสารบอกว่า | โค้ดทำจริง | หลักฐาน (ไฟล์:บรรทัด) | น่าจะแก้ฝั่งไหน | เหตุผล |
|---|---|---|---|---|---|---|---|

ประเภท: `โค้ดไม่มี` · `โค้ดต่างจากเอกสาร` · `เอกสารไม่มี` · `test ไม่ครอบคลุม` · `สถานะเอกสารไม่ตรง`
"น่าจะแก้ฝั่งไหน" = `แก้เอกสาร` / `แก้โค้ด` / `ต้องถามเจ้าของ` — ไม่แน่ใจให้ตอบ `ต้องถามเจ้าของ`

ปิดท้าย: สรุปตัวเลข (ตรงกัน / ไม่ตรง แยกประเภท) · ลำดับที่ควรแก้ก่อน 5 ข้อ · สิ่งที่ไม่ได้ตรวจ

### กฎเฉพาะฉบับนี้

- ทุกแถวต้องมีหลักฐานทั้ง 2 ฝั่ง (ตำแหน่งในเอกสาร + ตำแหน่งในโค้ด) · หาไม่เจอไม่ได้แปลว่าไม่มี · ให้ระบุว่า "ค้นด้วยคำ/path ไหนแล้ว"
