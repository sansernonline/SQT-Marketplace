# prompt-brownfield — เอกสารสภาพปัจจุบันจากโค้ดที่มีอยู่

ใช้คู่กับ plugin `software-company` · ไฟล์นี้รวม prompt 1 ฉบับ แต่ละฉบับสร้างเอกสารหนึ่งชุด · ไฟล์แยกรายฉบับอยู่ในโฟลเดอร์ `prompt-brownfield/`

## วิธีใช้

วางทั้งไฟล์ใน Claude Code, Codex CLI หรือ Gemini CLI ที่รากโฟลเดอร์โปรเจกต์ แล้วพิมพ์ต่อท้ายว่าจะทำฉบับไหน เช่น `ทำทั้งหมด` หรือ `ทำข้อ 3 และ 4`

**กฎการทำงานของไฟล์รวม (agent ต้องทำตาม):**

1. ทำทีละฉบับตามลำดับในตาราง ข้ามฉบับที่ผู้ใช้ไม่ได้สั่ง
2. **จบแต่ละฉบับให้หยุด** อัปเดตตารางสถานะใน `docs/BUILD-PLAN.md` ตามข้อ "รายงานสถานะ" ในกฎร่วม แล้วแสดงในคำตอบ: แถวที่เปลี่ยน · ค้างอยู่ · ฉบับถัดไป — รอผู้ใช้พิมพ์ `ต่อ` หรือสั่งแก้ **ห้ามเริ่มฉบับถัดไปเอง**
3. ช่องที่เขียนว่า "ผู้ใช้กรอก" ของฉบับไหนยังว่าง ให้ถามตอนเริ่มฉบับนั้น ไม่ต้องถามทั้งหมดตั้งแต่ต้น
4. ฉบับหลังใช้ผลของฉบับก่อนเป็นข้อมูลนำเข้า — อ่านจากดิสก์ใหม่ทุกครั้ง (ผู้ใช้อาจแก้ไปแล้ว)

| # | เอกสาร | ได้ไฟล์ |
|---|---|---|
| 1 | ย้อนสร้างเอกสารจากโค้ดที่มีอยู่ (Reverse Spec) | ไฟล์ใน `docs/as-is/` |

## กฎร่วมทุกฉบับ

- อ่าน `docs/BUILD-PLAN.md` (หัวข้อ `สถานะล่าสุด`) และ `docs/README.md` ก่อน (ถ้ามี) — สถานะงาน รหัสโปรเจกต์ ขนาดงาน ธีมสี อยู่ที่นั่น · ไม่มีให้ถามเฉพาะค่าที่ขาด
- **ที่เก็บไฟล์** (ตาม skill `project-doc-set`): `ref/` ไฟล์ที่ได้รับมา อ่านอย่างเดียว · `docs/` เอกสารที่เราเขียน (รูปใน `docs/figures/`) · `mockup/` UI mockup · `qa/` test case ผลทดสอบ รายงานบั๊ก · `assets/` โลโก้ ไอคอน · `_to_delete/` ของชั่วคราว — สร้างโฟลเดอร์เมื่อมีของจริงเท่านั้น
- อ่านไฟล์จากดิสก์ก่อนแก้ · ไฟล์ยาวเกิน 300 บรรทัดอ่านเฉพาะช่วง · ต้องเปิดเกิน 3 ไฟล์เพื่อตอบเรื่องเดียว ให้ส่ง subagent
- ข้อมูลไม่พอหรือเอกสารขัดกัน → รวมเป็นคำถามท้ายคำตอบแล้ว **หยุด** ห้ามเดา ห้ามแต่งตัวเลข/ชื่อ/วันที่
- ตัวย่อทุกตัวกางเต็มครั้งแรก เช่น Software Requirements Specification (SRS) · ของชั่วคราวลง `_to_delete/`
- ตั้งชื่อไฟล์ตาม skill `document-naming` · รูปแบบเอกสารตาม `polished-document-style`
- **รายงานสถานะทุกครั้งที่จบฉบับ** (ใช้ skill `status-report` ถ้ามี) ลง `docs/BUILD-PLAN.md` — ไม่มีไฟล์ให้สร้าง · แก้เฉพาะสองหัวข้อนี้ ไม่แตะหัวข้ออื่นในไฟล์:
  - `## สถานะล่าสุด` **เขียนทับทั้งหัวข้อ**: วันที่เวลา · ตาราง `| รายการ | ประเภท | สถานะ | ผลตรวจ | ค้าง / หมายเหตุ |` ครบทุกเอกสารและงานของโปรเจกต์ (รายการที่รอบนี้ไม่ได้แตะ คัดลอกค่าเดิม) · ตามด้วย **ค้างอยู่** (คำถามที่ต้องมีคนตอบ พร้อมบอกว่าถามใคร ไม่มีเขียน `ไม่มี`) และ **ถัดไป** (ไม่เกิน 3 อย่าง)
  - สถานะเอกสาร: `ยังไม่เริ่ม` · `DRAFT` · `REVIEW` — `APPROVED` ผู้ใช้ตั้งเองเท่านั้น · ผลตรวจ: `ผ่าน — <หลักฐาน>` · `ไม่ผ่าน — <อะไร>` · `ยังไม่ตรวจ` — **ห้ามเขียน `ผ่าน` ถ้าไม่ได้ตรวจหรือรันจริง**
  - `## ประวัติสถานะ` เพิ่มหนึ่งบรรทัดบนสุด: `วันที่ เวลา · งาน · สถานะ · ผล · ค้างกี่ข้อ`
- คำตอบตอนจบ: แสดงเฉพาะแถวที่เปลี่ยน + ค้างอยู่ + ถัดไป แล้วบอกว่าตารางเต็มอยู่ใน `docs/BUILD-PLAN.md` — ไม่คัดลอกเนื้อเอกสารกลับมา

## 1. ย้อนสร้างเอกสารจากโค้ดที่มีอยู่ (Reverse Spec)

agent `solution-architect` + `system-analyst` · skill `architecture-patterns` · `software-diagrams` · `database-design` · `prior-art-review` · `polished-document-style`
**ผลลัพธ์:** ไฟล์ใน `docs/as-is/` — **อ่านโค้ดอย่างเดียว ห้ามแก้โค้ด** · ทุกข้อความในเอกสารคือ "สิ่งที่โค้ดทำ" ไม่ใช่ "สิ่งที่ควรทำ"

### ขอบเขต (ผู้ใช้กรอก)

- ระบบนี้ทำอะไรโดยย่อ (ตามที่ผู้ใช้เข้าใจ):
- โฟลเดอร์/โมดูลที่ต้องย้อน (เว้นว่าง = ทั้ง repo ยกเว้น `node_modules` `bin` `obj` `dist` `.git` และไฟล์ generate):
- เอกสารเดิมที่พอมี (README, wiki, บันทึกเก่า):
- ต้องการเอกสารชุดไหน: ☐ ภาพรวม/สถาปัตยกรรม ☐ ข้อมูล ☐ API ☐ รายการฟังก์ชัน (FR) ☐ การตั้งค่า/การรัน

### วิธีทำ

1. **สำรวจโครงก่อน** — รายการโฟลเดอร์ ภาษา เฟรมเวิร์ก จุดเริ่มต้นของโปรแกรม ไฟล์ตั้งค่า (อ่านไม่เกิน 2 ระดับโฟลเดอร์ก่อน) · repo ใหญ่ให้ส่ง subagent ต่อโมดูลแล้วให้คืนเฉพาะสรุปตามหัวข้อด้านล่าง
2. เขียนเอกสารตามที่เลือก แต่ละไฟล์ระบุ **ระดับความมั่นใจ** ต่อข้อ: `ยืนยันจากโค้ด` (ชี้ไฟล์:บรรทัด) · `อนุมานจากชื่อ/โครง` · `ไม่ทราบ`
3. ส่วนที่เป็น "เจตนาทางธุรกิจ" ที่โค้ดบอกไม่ได้ → ลงเป็นคำถามถึงเจ้าของระบบ ห้ามเดา

### เอกสารที่ได้ (เลือกตามขอบเขต)

| ไฟล์ | เนื้อหา |
|---|---|
| `docs/as-is/overview.md` | ระบบทำอะไร · ผู้ใช้/ระบบภายนอก · เทคโนโลยี · C4 context + container (Mermaid ไม่เกิน 7 กล่อง) · วิธี build/รัน/ทดสอบที่ทำได้จริง |
| `docs/as-is/data.md` | ตาราง/collection · คอลัมน์ · ความสัมพันธ์ (ER) · ข้อมูลส่วนบุคคลที่พบ |
| `docs/as-is/api.md` | endpoint ทั้งหมดที่พบ: เมธอด+path · ผู้เรียก/การยืนยันตัวตน · ข้อมูลเข้า-ออกหลัก |
| `docs/as-is/features.md` | รายการความสามารถที่โค้ดทำ รหัสชั่วคราว `AS-001…` ข้อละประโยค + ตำแหน่งในโค้ด + ระดับความมั่นใจ — ใช้เป็นร่างตั้งต้นของ SRS |
| `docs/as-is/config-and-run.md` | ตัวแปรสภาพแวดล้อม/ไฟล์ตั้งค่า (ชื่อ+ความหมาย **ไม่ใส่ค่าลับ**) · ระบบภายนอกที่ต้องต่อ |
| `docs/as-is/findings.md` | สิ่งที่น่ากังวลที่เจอระหว่างอ่าน (โค้ดตาย test ไม่มี คีย์ในโค้ด ช่องโหว่ชัดเจน) ตารางสั้น ไม่ใช่รายงานตรวจเต็ม · และ **คำถามถึงเจ้าของระบบ** |

### กฎเฉพาะฉบับนี้

- ทุกข้อเท็จจริงต้องชี้ไฟล์:บรรทัดได้ ข้อที่ชี้ไม่ได้ติดป้าย `อนุมาน`
- ไม่สรุปว่าโค้ด "ถูก" หรือ "ควรเป็นอย่างไร" — เขียนแต่สภาพปัจจุบัน ข้อเสนอแนะไปอยู่ใน `findings.md` เท่านั้น
- ค้นโค้ดต้องจำกัดขอบเขต (ระบุ path/glob) ทุกครั้ง
