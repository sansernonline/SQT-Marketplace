# prompt-change — เอกสารงานเปลี่ยนแปลงหลังส่งมอบ

ใช้คู่กับ plugin `software-company` · ไฟล์นี้รวม prompt 2 ฉบับ แต่ละฉบับสร้างเอกสารหนึ่งชุด

## วิธีใช้

วางทั้งไฟล์ใน Claude Code, Codex CLI หรือ Gemini CLI ที่รากโฟลเดอร์โปรเจกต์ แล้วพิมพ์ต่อท้ายว่าจะทำฉบับไหน เช่น `ทำทั้งหมด` หรือ `ทำข้อ 3 และ 4`

**กฎการทำงาน (agent ต้องทำตาม):** เปิด skill `agent-team` ก่อนเริ่ม แล้วทำตาม playbook `project-docs` ทุกขั้น — กฎร่วม (ถามครั้งเดียว · ทำจบรอบเดียว · ตัดสินใจเอง · รายงานสถานะ · ที่เก็บไฟล์) อยู่ที่นั่นที่เดียว · เปิด skill ไม่ได้ ให้หยุดและบอกผู้ใช้ ห้ามทำต่อโดยไม่มีกฎ

| # | เอกสาร | ได้ไฟล์ |
|---|---|---|
| 1 | วิเคราะห์คำขอเปลี่ยน (Change Request) | `docs/change/CR-<เลข 3 หลัก>-<เรื่อง>.md` ไฟล์เดียว |
| 2 | รายงานบั๊กและแผนแก้ | `qa/bugs/BUG-<เลข 3 หลัก>-<เรื่อง>.md` |

---

## 1. วิเคราะห์คำขอเปลี่ยน (Change Request)

agent `business-analyst` + `system-analyst` · skill `srs-writing` · `simplicity-first` · `polished-document-style`
**ผลลัพธ์:** `docs/change/CR-<เลข 3 หลัก>-<เรื่อง>.md` ไฟล์เดียว — **ไม่แก้** SRS / FSD / mockup / โค้ด

### คำขอเปลี่ยน (ผู้ใช้กรอก)

- ใครขอ / วันที่:
- อยากให้เปลี่ยนอะไร (เล่าตามที่ผู้ขอพูด):
- ทำไมถึงต้องการ (ปัญหาที่เจอ):
- เร่งด่วนแค่ไหน / มีกำหนดวันไหม:
- ไฟล์อ้างอิง (อีเมล ภาพหน้าจอ บันทึกประชุม — วางไว้ใน `ref/`):

### หัวข้อที่ต้องมีในเอกสาร

1. สรุปคำขอ — ประโยคเดียว + เป็น "เพิ่ม / แก้ / ลบ" ของอะไร
2. ข้อกำหนดที่เกี่ยว — รหัส `BR` `FR` `NFR` ที่ถูกแตะ (อ่านจาก `docs/srs.md`) และที่ **ต้องเพิ่มใหม่**
3. ตารางผลกระทบ — ทุกแถวคือสิ่งที่ต้องแก้ตามมา

   | สิ่งที่กระทบ | ไฟล์/ส่วน | ต้องแก้อะไร | ขนาด (เล็ก/กลาง/ใหญ่) |
   |---|---|---|---|

   ตรวจให้ครบ: SRS · FSD · architecture · mockup · test plan / test case · API-SPEC · DATA-DICTIONARY · user guide · โค้ดและข้อมูลที่มีอยู่แล้ว (migration)
4. ทางเลือก 2–3 แบบ (รวมแบบ "ไม่ทำ" หรือ "ทำเล็กสุด") พร้อมข้อดี ข้อเสีย ผลต่อผู้ใช้ — แนะนำหนึ่งแบบพร้อมเหตุผล
5. ร่างข้อความที่จะแก้ในเอกสาร — เขียนเป็น "ก่อน → หลัง" ของ FR/ข้อความที่เปลี่ยน เพื่อให้ผู้ใช้อนุมัติแล้วค่อยนำไปแก้จริง
6. แถวงานที่จะเพิ่มใน `docs/BUILD-PLAN.md` (ถ้ามีแผนอยู่) รูปแบบเดียวกับตารางแผน
7. ความเสี่ยง · สิ่งที่ยังไม่รู้ · คำถามถึงผู้ขอ
8. สถานะ: `เสนอ` (ผู้ใช้เป็นคนเปลี่ยนเป็น `อนุมัติ` / `ปฏิเสธ`)

### กฎเฉพาะฉบับนี้

- ขนาดงาน/เวลา/เงินที่ไม่มีข้อมูลรองรับ → `(รอยืนยัน)` ห้ามประมาณเอง
- ถ้าคำขอขัดกับข้อกำหนดเดิมหรือเอกสารขัดกันเอง ให้ชี้ที่ตำแหน่งที่ขัด ห้ามเลือกข้างเอง

## 2. รายงานบั๊กและแผนแก้

agent `qa-tester` (รายงาน) + `developer` (หาสาเหตุ) · skill `bug-report-template` · `targeted-fix` · `test-case-template`
**ผลลัพธ์:** `qa/bugs/BUG-<เลข 3 หลัก>-<เรื่อง>.md` — **ไม่แก้โค้ด** เว้นแต่ข้างล่างติ๊ก `[x]`

- [ ] อนุญาตให้แก้โค้ดตามแผนด้วย (แก้เฉพาะจุด + test กันย้อนกลับ + commit `fix:` หนึ่งอัน)

### อาการที่พบ (ผู้ใช้กรอก)

- เกิดที่ไหน / ทำอะไรอยู่:
- คาดว่าจะเห็นอะไร / เห็นจริงอะไร:
- ข้อความ error / ภาพหน้าจอ / log (แปะหรือระบุไฟล์):
- เกิดทุกครั้งไหม / เริ่มเกิดตั้งแต่เมื่อไร:
- เวอร์ชัน / สภาพแวดล้อม:

### หัวข้อที่ต้องมีในเอกสาร

1. สรุปหนึ่งบรรทัด + ระดับความรุนแรง (วิกฤต / สูง / กลาง / ต่ำ) พร้อมเหตุผลว่าใครได้รับผลกระทบ
2. ขั้นตอนทำซ้ำ — เลขลำดับ ทำตามได้ทันที · ลองทำซ้ำเองถ้าทำได้ แล้วบอกว่า **ทำซ้ำได้ / ทำซ้ำไม่ได้** ตามจริง
3. สาเหตุ — ไฟล์:บรรทัดที่เป็นต้นเหตุ พร้อมหลักฐาน (ข้อความ log, โค้ดที่ผิด) · แยก "ยืนยันแล้ว" ออกจาก "สันนิษฐาน"
4. ข้อกำหนดที่เกี่ยว (FR ใน SRS) และว่าเอกสารหรือโค้ดเป็นฝ่ายผิด
5. แผนแก้ที่เล็กที่สุด — ไฟล์ที่จะแก้ · สิ่งที่จะไม่แตะ · ความเสี่ยงต่อส่วนอื่น
6. test กันย้อนกลับ — test ที่ต้องเพิ่ม (ชื่อ ข้อมูลเข้า ผลที่คาด) ซึ่งต้องแดงก่อนแก้และเขียวหลังแก้
7. บั๊กที่น่าจะเป็นแบบเดียวกันที่อื่น (ค้นแล้วเจอกี่จุด)

### กฎเฉพาะฉบับนี้

- ทำซ้ำไม่ได้ → เขียนตามจริงว่าไม่ได้ พร้อมข้อมูลที่ยังขาด ห้ามเดาสาเหตุให้ดูจบ
- ถ้าติ๊กอนุญาตแก้: ส่วนแก้โค้ดเปลี่ยนไปทำตาม playbook `bug-fix` ของ `agent-team` (รายงานบั๊กยังอยู่ใต้ `project-docs`) · แก้เฉพาะจุด รัน test ทั้งชุด รายงานผลจริง ถ้าแดงให้หยุดและบอก
