# scripts/evals/speed — เทียบความเร็ว superuser 2 รุ่น

แก้ skill แล้วอยากรู้ว่าดีขึ้นจริงไหม หรือใช้ superuser แล้วคุ้มไหม → รันงานชุดเดิม 2 แขน แล้วเทียบตัวเลข
ตัววัดคุณภาพคือ test ที่ซ่อนไว้ (agent มองไม่เห็น) เร็วขึ้นแต่ test ตก ไม่นับว่าดีขึ้น · ผลรายงานแยกตามขนาดงาน และบอกเรื่องที่ไม่ดีตรง ๆ (แพงขึ้นโดยไม่ดีขึ้น · อ้างว่าเสร็จแต่ตก · แก้นอกขอบเขต · ไม่เปิด skill)

## วิธีรัน

```powershell
# เทียบ commit ล่าสุด (รุ่นก่อน) กับไฟล์ที่แก้อยู่ตอนนี้ (รุ่นหลัง) · งาน t1 กับ t4 · รุ่นละ 2 รอบ
node scripts/evals/speed/run-bench.mjs --old HEAD --tasks t1,t4 --runs 2

# เทียบ 2 commit · ทุกงาน · รุ่นละ 3 รอบ · จำกัดรอบละ $5
node scripts/evals/speed/run-bench.mjs --old f105afc --new HEAD --tasks t1,t2,t3,t4 --runs 3 --budget 5
```

| ตัวเลือก | ค่าเริ่ม | ความหมาย |
|---|---|---|
| `--old` | (ต้องใส่) | รุ่นก่อน เป็น git ref · `none` = ไม่โหลด plugin เลย ใช้วัดว่าใช้ superuser แล้วประหยัดจริงไหม |
| `--new` | ไฟล์ในโฟลเดอร์ตอนนี้ | รุ่นหลัง ใส่ git ref ก็ได้ |
| `--tasks` | `all` (ทุกงานใน `tasks/`) | งานที่รัน คั่นด้วย `,` |
| `--runs` | `3` | รันกี่รอบต่อรุ่น · ผลแกว่งมาก ตัดสินจริงใช้ 5 รอบขึ้นไป |
| `--budget` | `8` | เพดานค่าใช้จ่ายต่อรอบ (ดอลลาร์) |
| `--parallel` | `4` | รันพร้อมกันกี่รอบ |
| `--prompt` | `lead` | `lead` = แขน new ได้ประโยค "ใช้ skill `superuser`" นำหน้า · `natural` = ทุกแขนได้แค่เนื้อ `TASK.md` ไม่สั่งให้ใช้ superuser (แขน new ยังโหลด plugin) ใช้วัดว่างานเล็กหลบ superuser เองจริงไหม |
| `--dry-run` | ไม่ใส่ | พิมพ์คำสั่งที่แต่ละแขนจะได้แล้วจบ ไม่เรียก `claude` ไม่เสียเงิน |
| `--save-ratios` | ไม่ใส่ | ใช้คู่กับ `--old none` · เขียนอัตราส่วนลง `plugins/superuser/hooks/bench-ratios.json` ให้ hook ประมาณค่า "ถ้าไม่ใช้ superuser" ใน `log/SUMMARY.md` |

- ใช้ `claude` ที่ล็อกอินอยู่ในเครื่อง · ค่าใช้จ่ายตัดจากบัญชีนั้น (รอบหนึ่งของ t4 ราว $0.5–1.2)
- ต้องมี Node 22 · Python + `pytest` (สำหรับ t2 · t4)
- ทุกแขนที่มี plugin โหลดแค่ `superuser` จาก repo รุ่นที่ระบุ ไม่มี plugin อื่นปน · ผลจึงเป็นของ superuser ล้วน · ผลใน `RESULTS.md` ก่อน 2026-11-17 โหลด `software-development` ปนด้วย เทียบกับผลหลังจากนี้ไม่ได้
- ทุกรอบรันในโฟลเดอร์ใหม่ใต้ `_to_delete/bench/runs/` · โหลดเฉพาะ plugin ที่เทียบ ไม่โหลด plugin ที่ติดตั้งในเครื่อง
- agent ได้สิทธิ์แค่อ่าน · แก้ไฟล์ · รัน test · git ในโฟลเดอร์ทดสอบ
- ผลรายรอบอยู่ใน `_to_delete/bench/runs/<งาน>-<รุ่น>-<รอบ>.json` · ตารางสรุปต่อท้าย `RESULTS.md`

ครอบคลุม 3 ขนาด × หลายชนิด: เล็ก (โค้ด · เอกสาร · ข้อมูล) · กลาง (โค้ดเงิน · โค้ดขนาน · โค้ดเสี่ยง · เอกสาร · ค้นคว้า) · ใหญ่ (โค้ด 2 งาน · ข้อมูล + รายงาน)

แต่ละงานมี `task.json`: `size` · `kind` · `touch` (regex ไฟล์ที่ควรแก้ ใช้จับการแก้นอกขอบเขต) · `checks` (regex ที่ต้องเจอในคำตอบสุดท้าย เช่นทัก spec gap ของ t2 t4) · งาน t8–t11 มี `reference/` คำตอบอ้างอิงที่ test ผ่านครบ

**ช่องโหว่ที่ตั้งใจใส่ไว้:** `SPEC.md` ของ t2 · t4 ไม่ได้บอกชนิดของ `discount_pct` แต่ test ที่ซ่อนไว้ส่งทศนิยม (`12.5`) → ทีมที่ดีต้องรับค่ากว้างไว้ หรืออย่างน้อย `reviewer` ต้องทักว่าข้อกำหนดเปิดไว้ (กฎ "Spec gaps" ใน agent `reviewer`)

## อ่านผล

ตารางแรก 1 แถวต่องานต่อแขน เรียงตามขนาด:

| คอลัมน์ | ความหมาย |
|---|---|
| เวลา · เวลา API · ค่าใช้จ่าย · token | ค่ากลางของทุกรอบ (ผลแกว่งแรง จึงไม่ใช้ค่าเฉลี่ย) · เวลา API มาจาก `duration_api_ms` ไม่รวมช่วงเครื่องพัก · token รวม cache และลูกทีม |
| ลูกทีม | จำนวน subagent เฉลี่ยต่อรอบ |
| เปิด superuser | รอบที่เรียก Skill `superuser` จริง (จาก transcript) · ถ้าไม่เปิด ผลของแขนนั้นไม่ได้มาจาก superuser |
| ผ่านครบ · $ ต่องานที่ผ่าน | รอบที่ test ที่ซ่อนไว้ผ่านทุกข้อ · ค่าใช้จ่ายรวม ÷ รอบที่ผ่าน (ถูกแต่ตกทุกรอบไม่ได้แปลว่าคุ้ม) |
| ไฟล์ที่แก้ · รอบที่แก้นอกขอบเขต | จาก `git diff` เทียบ commit ตั้งต้น · นอกขอบเขต = ไม่ตรง `touch` ของงาน |
| อ้างเกินจริง | คำตอบสุดท้ายมีคำว่าเสร็จ/ผ่านครบ แต่ test ที่ซ่อนไว้ตก (จับคำ หยาบ) |
| ข้อตรวจเพิ่ม | `checks` ของงานที่เจอในคำตอบ |
| ล้ม · ถูกปฏิเสธ | รอบที่ error หรือชนเพดาน `--budget` (นับเป็นไม่ผ่าน) · จำนวนคำสั่งที่ถูกปฏิเสธสิทธิ์ |

ตารางที่ 2 แยกตามขนาด (เล็ก · กลาง · ใหญ่ · ทุกงาน):

- **คุณภาพ** = ผลต่างสัดส่วนรอบที่ผ่านครบ พร้อมช่วง 95% แบบ Newcombe · ขอบล่าง > 0 = **ดีขึ้นจริง** · ขอบบน < 0 = **แย่ลงจริง** · คร่อม 0 = แยกไม่ออก
- **ค่าใช้จ่าย · เวลา · token** = ค่ากลางแขนใหม่ ÷ ค่ากลางแขนเทียบ หลังหารแต่ละงานด้วยค่ากลางของแขนเทียบในงานนั้น (งานใหญ่ไม่กลบงานเล็ก) · ช่วง 95% แบบ bootstrap สุ่มแต่ละแขนแยกกัน ไม่จับคู่รอบ เพราะรอบที่ 1 ของ 2 แขนไม่เกี่ยวกัน
- ท้ายตารางมีข้อสังเกตที่สคริปต์เขียนเองเสมอเมื่อเกิด: ขนาดไหนแพงขึ้นโดยคุณภาพไม่ดีขึ้นจริง · ขนาดไหนคุณภาพแย่ลงจริง · รอบที่อ้างเกินจริง · แก้นอกขอบเขต · ไม่เปิด superuser ทั้งที่สั่ง · ล้ม · เครื่องพัก · รอบน้อยกว่า 5

ตารางที่ 3 **ทีมรายรอบ** (เฉพาะรอบที่มีลูกทีม): หัวหน้าใช้ model อะไร เสียเท่าไร · ลูกทีมกี่ตัว · แต่ละตัวเป็นชนิดไหน (`worker` · `reviewer`) ได้ model/effort อะไร ได้งานอะไร (คำอธิบายที่หัวหน้าตั้งตอนส่งงาน) เสียเท่าไร · บรรทัดรายรอบตอนรันก็บอก model/effort ของลูกทีมทุกตัว · ค่าใช้จ่ายรายตัวคิดจาก token × `prices.json` ของ model-scorecard จึงเป็นค่าประมาณ (ต่างจากยอดจริงราว 10%) · ดูรอบที่รันไปแล้วด้วย `node scripts/evals/speed/team.mjs [t4-new-1 …]` (ฟรี · อ่าน transcript)

ตัดสินใจ: คุณภาพต้องไม่แย่ลงก่อน · แพงขึ้นจริงในขนาดไหนที่คุณภาพแยกไม่ออก = ขนาดนั้นยังไม่คุ้ม ต้องแก้ ไม่ใช่เอาไปเฉลี่ยกับขนาดอื่น · ช่วงคร่อม 1 ให้รันเพิ่มก่อนสรุป (5 รอบขึ้นไป)

## วัดว่า superuser ช่วยจริงไหม

```powershell
# ทุกงาน 11 ชิ้น × 5 รอบ × 2 แขน = 110 รอบ · ประมาณ $50–80 (ดูจำนวนรอบก่อนด้วย --dry-run)
node scripts/evals/speed/run-bench.mjs --old none --runs 5 --budget 5 --prompt natural --save-ratios
```

แขน `none` ได้คำสั่งเดียวกันทุกคำ ยกเว้นประโยคที่ให้ใช้ superuser และไม่โหลด plugin ใด ๆ · อยากรู้ว่าผู้ใช้ที่ไม่เอ่ยชื่อ superuser ได้อะไร (งานเล็กต้องไม่แพงขึ้น งานใหญ่ยังแตกงาน) ใส่ `--prompt natural` · ดูคำสั่งก่อนรันจริงด้วย `--dry-run` · `--save-ratios` เขียน `bench-ratios.json` ให้ hook ใช้ในหัวข้อ "คุ้มแค่ไหน" ของ `log/SUMMARY.md` · แก้ไฟล์นั้นแล้วต้องขึ้นรุ่น superuser และรัน `sync-superuser`

## แยกว่า token ที่เพิ่มมาจากไหน

```powershell
node scripts/evals/speed/breakdown.mjs              # ทุกรอบใน _to_delete/bench/runs (ฟรี · อ่าน transcript)
```

ได้ตารางต่องานต่อแขน: context รอบคุยแรก (ต้นทุนก่อนลงมือ = รายการ skill · agent · ข้อความ hook ตอนเริ่ม) · context รอบคุยสุดท้าย (รวมไฟล์ที่โหลดเมื่อเปิด skill) · จำนวนรอบคุย · context รวม · skill ที่เปิด · ใช้แยก 3 ต้นเหตุ: ต้นทุนคงที่ตั้งแต่รอบแรก · ไฟล์ที่โหลดระหว่างทาง · รอบคุยที่เพิ่ม · ตัวอย่างผลและวิธีอ่านอยู่ใน `RESULTS.md` หัวข้อ 2026-11-11
