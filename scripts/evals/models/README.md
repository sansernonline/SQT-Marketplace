# scripts/evals/models — เทียบ model ต่อขั้นของทีม agent

อยากรู้ว่าขั้นไหนใช้ model ถูกลงได้โดยคุณภาพไม่ตก ขั้นไหนต้องใช้ตัวแรง → รันงานเดิมที่มีอยู่แล้วกับหลาย model แล้วเทียบ คะแนน เวลา รอบคุย token ค่าใช้จ่าย และความคุ้ม (คะแนน ÷ ดอลลาร์)
ไม่เขียนตัวรันใหม่ซ้ำ: เรียกงานและตัวให้คะแนนของ `speed/` · `coding/` · `review-recall/` ที่มีอยู่

## วัดอะไร

| ขั้น | งาน | คะแนน (เต็ม 10) |
|---|---|---|
| `code` | `speed/tasks/t1` แก้บั๊กวันที่ไทย | test ที่ซ่อนผ่านกี่ข้อ ÷ ทั้งหมด |
| `code-quality` | `coding/tasks/c5-csv-import` | `run-coding.mjs --score --no-judge` (ถูกต้อง · test ของทีม · สะอาด เต็ม 8) ปรับเป็นเต็ม 10 |
| `code-hard` | `coding/tasks/c4-subscription-leak` (ตัวให้คะแนนเดียวกับ code-quality) | เหมือน `code-quality` |
| `review` | `review-recall` เคส r1–r8 (เลือกด้วย `--review-cases`) | ข้อผิดที่ฝังไว้ที่ reviewer เจอ ÷ ทั้งหมด (เทียบข้อความ ไม่ใช้ผู้ตัดสิน) |
| `plan` | spec สั้นให้แตกงาน ([`plan-task.mjs`](plan-task.mjs)) | checklist 5 ข้อ ข้อละ 2: 3–6 ขั้น · ทุกขั้นมี "เสร็จเมื่อ" · ทุกขั้นระบุไฟล์ · ครอบคลุม csv เกณฑ์ รายงาน test README · ไม่เกิน 60 บรรทัด |

model: `claude-haiku-5-5` · `claude-sonnet-5-5` · `claude-opus-5-5` · `claude-fable-5-1` (ราคาจาก `plugins/superuser/skills/model-scorecard/references/prices.json`) · ทุกรอบส่ง `--model` และ `--effort` (ค่าเริ่ม `medium`) ไม่โหลด plugin จึงวัดตัว model ไม่ใช่ทีม · **ข้อยกเว้น: ขั้น `review`** รันผ่าน `run-review-recall.mjs` ซึ่งโหลด plugin superuser และเรียก agent `superuser:reviewer` จึงวัดทีมรีวิว ไม่ใช่ model เปล่า

## คำสั่ง

```powershell
node scripts/evals/models/run-models.mjs --verify   # ฟรี: งานและตัวให้คะแนนพร้อมไหม
node scripts/evals/models/run-models.mjs --plan     # ฟรี: ตารางงาน ประมาณค่าใช้จ่าย ชุดที่อยู่ในงบ
node scripts/evals/models/run-models.mjs --run      # เสียเงิน: ต้องใส่ --run เอง
```

| ตัวเลือก | ค่าเริ่ม | ความหมาย |
|---|---|---|
| `--models` | ทั้ง 4 | เลือก model คั่นด้วย `,` |
| `--steps` | ทั้ง 5 | เลือกขั้น |
| `--runs` | 1 | รันซ้ำกี่รอบต่อช่อง · แนะนำ 3 |
| `--review-cases` | `r1`–`r8` | เคสของขั้น `review` |
| `--skip` | — | ตัดบางช่อง เช่น `claude-fable-5-1:code-quality` (`--plan` พิมพ์ชุดแนะนำให้) |
| `--effort` | `medium` | ส่งเข้า `claude --effort` · `none` = ไม่ส่ง |
| `--budget-total` | 20 | เพดานรวมทั้งรอบ (ดอลลาร์) · ใช้ถึงเท่านี้แล้วข้ามช่องที่เหลือ |

## ค่าใช้จ่าย

- เพดานต่อช่อง = max(ประมาณของ model นั้น × 2, $0.50) · ต่อครั้งเรียก (`--max-budget-usd`) = เพดานช่อง ÷ จำนวนครั้ง (ทุกรอบเรียกซ้ำตาม `--runs` · review หารด้วยจำนวนเคส) · `--plan` แสดงทั้งยอดประมาณและเพดาน
- ยอดใช้สะสมไม่ต่ำกว่าเงินที่อาจเสียจริง: ถ้า claude ล้ม · JSON ไม่ครบ · ไม่มี `total_cost_usd` นับ $ เท่าเพดานของครั้งนั้น · review ที่บางเคสไม่มีไฟล์ผลนับเพดานต่อเคสของเคสนั้น
- รันจากถูกไปแพง (haiku → fable) ช่องที่แพงสุดจึงถูกตัดก่อนเมื่อถึงงบ · ก่อนเริ่มทุกช่องเช็กว่ายอดใช้ + เพดานช่องนั้น ไม่เกินงบ
- ชุดแนะนำของ `--plan` คิดจากยอดประมาณไม่เกิน 80% ของงบ · ตัวกันจริงคือเช็ก ใช้แล้ว + เพดานช่อง ไม่เกินงบ ก่อนเริ่มทุกช่อง
- `--plan` ประมาณจาก $ ต่อครั้งบน sonnet ในผลเก่า (`speed/RESULTS.md` t1 · `coding/RESULTS.md` c5) × อัตราราคาเฉลี่ยถ่วงของ model ÷ sonnet · ผลเก่าไม่เก็บ token จึงสมมุติสัดส่วน token (cache อ่าน 85%) · `review` กับ `plan` ยังไม่เคยวัด ใช้ค่าสมมุติ · ตัวเลขผิดได้เป็นเท่าตัว
- ประมาณรอบแรก (2026-10-27) ทั้ง 16 ช่อง $24 เกินงบ $20 → ชุดแนะนำตัด fable ที่ code-quality กับ review เหลือ ≈ $12 (80% ของงบ = $16) · เพดานช่อง = max(ประมาณ × 2, $0.50) · ตัวรันข้ามช่องที่ใช้แล้ว + เพดานเกินงบ จึงไม่เกินงบรวม

## ผล

`RESULTS.md` ต่อท้ายทุกครั้งที่รัน: ตารางรายขั้น (model × คะแนนรายรอบ · ผ่านกี่รอบ · ขอบล่าง Wilson · เวลา · $ เฉลี่ย · $ ต่องานที่ผ่าน) แล้วสรุปว่าแต่ละขั้นควรใช้ model ไหน · ไฟล์รายรอบอยู่ `_to_delete/models/`

## วิธีเลือก model ต่อขั้น

ตัวคำนวณอยู่ใน [`summary.mjs`](summary.mjs) (test: `node --test scripts/evals/models/summary.test.mjs`)

1. ผ่าน = คะแนนรอบนั้น ≥ 8 → อัตราผ่าน = รอบที่ผ่าน ÷ รอบที่รัน (รอบที่ถูกตัดที่เพดานหรือโควตาหมดไม่นับ)
2. เลือกตัวถูกที่สุดที่ขอบล่าง Wilson 95% ของอัตราผ่าน ≥ 0.6 · ผ่านครบทุกรอบต้องรันอย่างน้อย 6 รอบ (5/5 ได้ขอบล่าง 0.57) ถึงจะถึงเกณฑ์ ดังนั้น `--runs 3` เลือกตัวไม่ได้เสมอ ได้แค่เห็นว่าตัวไหนตกบ่อย
3. $ ต่องานที่ผ่าน = $ เฉลี่ยต่อครั้ง ÷ อัตราผ่าน
4. ทุก model ผ่านหมดทุกรอบ → เขียน "แยกไม่ออก (ชนเพดาน)"

เกณฑ์ 8 กับ 0.6 เป็นค่าตั้งต้น ยังไม่ได้วัดว่าเหมาะกับงานชุดนี้

## ขั้น code-hard: ทำไมเลือก c4

ดู `coding/RESULTS.md` มีผลเก่าแค่ c5 (10/10 ทั้งคู่) จึงไม่มีคะแนนต่ำสุดให้เทียบ เลือกจาก `--verify` กับจำนวน test ซ่อน: c4 โค้ดตั้งต้นผ่านแค่ 2/8 (c5 ตั้งต้นต้องตกเหมือนกัน) มี test ซ่อน 8 ข้อและต้องวัด subscription ค้างจริงจากการสร้าง-ปิด 100 รอบ ไม่ใช่แค่เดาจากโค้ด · stack เป็น Node/TypeScript ไม่ต้องลง .NET หรือ Python เพิ่ม (c1 c2 ต้องใช้ .NET) · ยังไม่เคยรันจริง ว่ายากกว่า c5 จริงหรือไม่ต้องรอผล

## ข้อจำกัด

- ค่าเริ่ม `--runs 1` ดูแนวโน้มเท่านั้น · ตัดสินเปลี่ยน model ของ agent ต้องรันหลายรอบและดูหลายงานต่อขั้น
- งานละ 1 ชิ้น (review 8 เคส) ตัวแทนของขั้นได้แค่หยาบ ๆ
- `code-quality` ไม่มีผู้ตัดสิน (ไม่นับ "ตามแบบแผน" กับ "รายงานจริง") · `review` ไม่มีเลข token เพราะตัวรันเดิมไม่เก็บ
- `review` เรียก `run-review-recall.mjs --run` จึงต่อท้าย `review-recall/RESULTS.md` ด้วย (label `models-<model>`) · reviewer อาจใช้ model ตามที่ `reviewer.md` กำหนดแทน `--model` ตัวรันเดิมเตือนไว้ในผล
- ยังไม่เคยรันจริง ไม่รู้ว่า CLI รับ `--effort` กับทุก model หรือไม่ · `--verify` ไม่เรียก model จึงตรวจไม่ได้ (รันช่อง haiku plan ราว $0.00 ก่อนเป็นการลอง)
