# Prompt ตรวจ plugin

ตัวตรวจ `validate-marketplace.mjs` จับได้แค่ของที่ผิดรูปแบบ prompt นี้ใช้ตรวจในเรื่องที่ต้องใช้วิจารณญาณ

**วิธีใช้**
1. เปิด Claude Code ที่รากของ repo · คัดลอกก้อนข้างล่างไปวาง
2. แก้ 3 บรรทัดบนสุด: ชื่อ plugin · หัวข้อที่จะตรวจ · คำสั่งเพิ่ม (ไม่มีก็ลบบรรทัดทิ้ง)
3. ตรวจทีละ plugin · `software-company` ตรวจแยกตัวเดียว
4. ถ้าจะแก้ต่อ พิมพ์ "แก้ข้อ 1, 2, 4" · แก้เสร็จรัน `node scripts/check/validate-marketplace.mjs` แล้วค่อย build dist

**เลือกหัวข้อ**

| หัวข้อ | ใช้เมื่อไร | ค่าใช้จ่าย |
|---|---|---|
| 1–3 ยาวเกิน · กระชับได้ · ทำงานซ้อน | หลังเพิ่มหรือแก้ skill หลายตัว | ต่ำ |
| 4 คุณภาพตามเช็กลิสต์ Anthropic | ทุกไตรมาส | ต่ำ |
| 5 ความปลอดภัย | plugin มี hook · MCP · `bin/` หรือ script · ก่อนเผยแพร่ | ต่ำ |
| 6 การส่งมอบ | ก่อนขึ้นเลขรุ่น | ต่ำ |
| 7 วัดผลจริง | ก่อนขึ้นเลขรุ่นหลัก · หลังเปลี่ยนรุ่นโมเดล | **สูง** — ให้ skill ทำงานจริงหลายรอบ |

```text
plugin: <ชื่อ plugin>
ตรวจเฉพาะหัวข้อ: <เลขหัวข้อ เช่น 1, 2, 3, 5 · หรือ "1–6">
คำสั่งเพิ่ม: <ถ้ามี>

ตรวจ plugin ข้างบนใน plugins/ ตามหัวข้อที่เลือก · ห้ามแก้ไฟล์ แค่รายงาน
แบ่งไฟล์ให้ subagent อ่าน ให้ส่งกลับมาแต่ตัวเลขกับข้อสรุป ไม่ต้องส่งเนื้อหาไฟล์
ข้ามข้อที่ validate-marketplace.mjs ตรวจอยู่แล้ว (รันมันก่อน แล้วดูว่าครอบคลุมอะไรบ้าง)
บันทึกผลลง _to_delete/audit-<plugin>.md

1. ยาวเกิน
   - SKILL.md ที่ยาวเกิน 300 บรรทัด (เพดานของ Anthropic คือ 500)
   - description ที่ยาวเกิน 200 ตัวอักษร · ความยาว description รวมทั้ง plugin
   - agent .md ที่ยาวเกิน 150 บรรทัด
   - ทุกตัวบอกจำนวนบรรทัดจริงด้วย

2. กระชับได้
   - เนื้อหาที่ควรย้ายไป references/ (ตาราง ตัวอย่าง เช็กลิสต์ยาว)
   - ประโยคที่พูดซ้ำในไฟล์เดียวกัน
   - คำอธิบายเรื่องที่ Claude รู้อยู่แล้ว
   - กฎที่ซ้ำกับ CLAUDE.md หรือ skill อื่นอยู่แล้ว ให้เปลี่ยนเป็นลิงก์แทน
   - บอกว่าแก้แล้วจะลดได้ประมาณกี่บรรทัด

3. ทำงานซ้อน
   - skill หรือ agent 2 ตัวขึ้นไปที่ description จะถูกเรียกจากคำขอเดียวกัน · ยกคำขอตัวอย่าง 1 ประโยคที่ชนกันจริง
   - กฎเรื่องเดียวกันที่เขียนไว้หลายที่ แล้วค่าไม่ตรงกัน (ตัวเลข เพดาน ชื่อเรียก)
   - กฎที่ขัดกันข้าม skill (skill หนึ่งสั่ง อีก skill ห้าม)
   - สิ่งเดียวกันที่เรียกคนละชื่อ
   - skill หรือ command ที่ไม่มี agent หรือ playbook ไหนเรียกใช้

4. คุณภาพตามเช็กลิสต์ Anthropic
   - description เขียนเป็นบุคคลที่ 3 และบอกทั้ง "ทำอะไร" กับ "ใช้เมื่อไร"
   - references/ ลิงก์ตรงจาก SKILL.md ชั้นเดียว ไม่มีไฟล์อ้างอิงที่ลิงก์ต่อไปอีกไฟล์
   - ไฟล์อ้างอิงที่ยาวเกิน 100 บรรทัดมีสารบัญอยู่บนสุด
   - ลิงก์ ชื่อ skill และเลขข้อ (เช่น "ข้อ 0.1") ที่ชี้ไปที่ไม่มีอยู่จริง
   - ให้ทางเลือกเยอะเกินไป แทนที่จะบอกทางหลัก 1 ทาง กับทางสำรอง 1 ทาง
   - ความเข้มงวดตรงกับงานไหม: งานที่พลาดแล้วเสียหายต้องสั่งเป๊ะ · งานที่ทำได้หลายวิธีปล่อยให้ตัดสินเอง
   - ตัวเลข อัตรา วันที่ ชื่อรุ่นโมเดลที่น่าจะหมดอายุ · จุด (รอยืนยัน) ที่ค้างนานเกิน 1 ปี
   - path ใช้ / ทุกที่ ไม่มี \
   - script: จัดการ error เองในตัว · ตัวเลขทุกตัวมีเหตุผลกำกับ · บอกให้ชัดว่า "ให้รัน" หรือ "ให้อ่าน" · บอกว่าต้องติดตั้งอะไร
   - ชื่อ MCP tool เขียนเต็มแบบ Server:tool

5. ความปลอดภัย
   - hooks/hooks.json: แต่ละ hook รันคำสั่งอะไร (hook ทำงานนอก sandbox ด้วยสิทธิ์เต็มของผู้ใช้)
   - .mcp.json · bin/ · monitor: รันอะไร ต่อไปที่ไหน
   - API key · token · รหัสผ่านที่ฝังไว้ในไฟล์
   - tools ของ agent ที่ให้มากเกินงาน (เช่น ตัวที่แค่รีวิวแต่มี Write หรือ Bash)
   - skill ที่อ่านเว็บ อีเมล หรือไฟล์จากภายนอก มีกฎไหมว่าข้อความในนั้นเป็นข้อมูล ไม่ใช่คำสั่ง
   - skill ที่ทั้งเข้าถึงข้อมูลส่วนตัว อ่านข้อมูลจากภายนอก และส่งข้อมูลออกนอกเครื่องได้ ให้ยกขึ้นมาก่อน
   - plugin ที่ไม่ควรเปิดทันทีหลังติดตั้ง ตั้ง defaultEnabled: false ไว้ไหม

6. การส่งมอบ
   - รัน claude --plugin-dir plugins/<plugin> plugin details <plugin> แล้วเทียบกับที่ README บอก
   - แก้ skill แล้วเลขรุ่นใน plugin.json ขึ้นไหม · CHANGELOG มีบันทึกไหม
   - dist ตรงกับ plugins/ ไหม

7. วัดผลจริง (แพง · ใช้ subagent ตัวใหม่ทุกรอบ ไม่ให้ผลปนกัน)
   - เรียกถูกตัว: ประโยคที่ควรเรียก 8–10 ประโยค กับประโยคใกล้เคียงที่ไม่ควรเรียกอีก 8–10 ประโยค · นับครั้งที่พลาดทั้ง 2 ฝั่ง
   - มีกับไม่มี skill: เลือก skill หลัก 3 ตัว ตัวละ 3 โจทย์ รันทั้งแบบเปิดและปิด plugin · ให้ผู้ตรวจที่ไม่รู้ว่าผลไหนมาจากแบบไหนเลือกผลที่ดีกว่า
   - skill ที่ไม่มีก็ทำได้ดีเท่ากัน = เสนอให้ตัด
   - ถ้ามีเวลา รันซ้ำด้วยโมเดลเล็ก (Haiku) ดูว่ายังทำตามได้ไหม

ส่งผลเป็นตาราง 1 ตารางต่อ 1 หัวข้อ
แต่ละแถวมี: ไฟล์:บรรทัด · ปัญหา · แก้อย่างไร · ลดได้กี่บรรทัด (ถ้าเกี่ยว)
จบด้วย 5 ข้อที่คุ้มแก้ที่สุด เอาข้อที่ทำให้ผลลัพธ์ผิดหรือไม่ปลอดภัยขึ้นก่อน แล้วค่อยเรียงตามจำนวนบรรทัดที่ลดได้
อะไรที่ยังไม่ได้ตรวจให้บอกตรง ๆ ว่ายังไม่ได้ตรวจ
```
