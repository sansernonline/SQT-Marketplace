# Prompt ตรวจ plugin

ตัวตรวจ `validate-marketplace.mjs` จับได้แค่ของที่ผิดรูปแบบ prompt นี้ใช้ตรวจในเรื่องที่ต้องใช้วิจารณญาณ

**วิธีใช้**
1. เปิด Claude Code ที่รากของ repo · คัดลอกก้อนข้างล่างไปวาง
2. แก้ 3 บรรทัดบนสุด: ชื่อ plugin · หัวข้อที่จะตรวจ · คำสั่งเพิ่ม (ไม่มีก็ลบบรรทัดทิ้ง)
3. ตรวจทีละ plugin · `software-company` ตรวจแยกตัวเดียว
4. หัวข้อ 8 แก้ให้เลยในรอบเดียว · หัวข้ออื่นแค่รายงาน ถ้าจะแก้ต่อ พิมพ์ "แก้ข้อ 1, 2, 4" · แก้เสร็จรัน `node scripts/check/validate-marketplace.mjs` แล้วค่อย build dist

**เลือกหัวข้อ**

| หัวข้อ | ใช้เมื่อไร | ค่าใช้จ่าย |
|---|---|---|
| 1–3 ยาวเกิน · กระชับได้ · ทำงานซ้อน | หลังเพิ่มหรือแก้ skill หลายตัว | ต่ำ |
| 4 คุณภาพตามเช็กลิสต์ Anthropic | ทุกไตรมาส | ต่ำ |
| 5 ความปลอดภัย | plugin มี hook · MCP · `bin/` หรือ script · ก่อนเผยแพร่ | ต่ำ |
| 6 การส่งมอบ | ก่อนขึ้นเลขรุ่น | ต่ำ |
| 7 วัดผลจริง | ก่อนขึ้นเลขรุ่นหลัก · หลังเปลี่ยนรุ่นโมเดล | **สูง** — ให้ skill ทำงานจริงหลายรอบ |
| 8 ประหยัด token | หลังเพิ่ม skill · agent · hook · ทุกไตรมาส | ต่ำ · รายงานแล้วแก้ให้เลย |
| 9–12 ความเร็ว · ความเสถียร · รับมือเมื่อพลาด · ผลข้างเคียง | รันพร้อมหัวข้อ 7 ในรอบเดียวกัน | **สูง** — ใช้ผลรอบเดียวกับหัวข้อ 7 |

```text
plugin: <ชื่อ plugin>
ตรวจเฉพาะหัวข้อ: <เลขหัวข้อ เช่น 1, 2, 3, 5 · หรือ "1–6">
คำสั่งเพิ่ม: <ถ้ามี>

ตรวจ plugin ข้างบนใน plugins/ ตามหัวข้อที่เลือก · หัวข้อ 1–7 และ 9–12 แค่รายงาน ห้ามแก้ไฟล์ · หัวข้อ 8 รายงานแล้วแก้ให้เลยตาม "แก้หัวข้อ 8" ข้างล่าง
บันทึกผลลง _to_delete/audit-<plugin>.md

ตรวจแบบประหยัด token:
- รัน `node scripts/check/validate-marketplace.mjs 2>&1 | tail -40` เอาแค่สรุป · ไม่ต้องเปิดอ่านตัว script
- ตัว script ตรวจให้แล้ว ข้ามได้เลย → description แต่ละตัวเกิน 150/160 ตัวอักษร (agent 120) · SKILL.md เกิน 400/500 บรรทัด · ไฟล์อ้างอิงเกิน 100 บรรทัดไม่มีสารบัญ · name · YAML · JSON · version · MCP ล็อกรุ่น · ขั้น playbook · คำที่เลิกใช้
- ตัวเลข (จำนวนบรรทัด · ความยาว description · ผลรวม) ได้จากคำสั่งชุดเดียว เช่น wc · grep · awk ไม่ต้องเปิดไฟล์อ่าน
- เปิดอ่านเฉพาะไฟล์ที่ต้องใช้วิจารณญาณ · อ่าน frontmatter ก่อน แล้วเปิดเนื้อหาเฉพาะตัวที่ติดธง
- skill กลางที่ sync มาจาก plugins/superuser (superuser · agent-patterns · answer-shape · human-writing · learning-reviewer · hook) ตรวจที่ต้นทางครั้งเดียว ไม่ตรวจซ้ำใน plugin อื่น
- ไม่อ่าน dist/ กับ _to_delete/ (ยกเว้นหัวข้อ 6 ที่ต้องเทียบ dist)
- ไฟล์ที่ต้องอ่านเกิน 10 ไฟล์ → แบ่งให้ subagent · น้อยกว่านั้นอ่านเองเร็วกว่า
- subagent ขนาดเล็กสำหรับนับและค้น · ขนาดกลางสำหรับงานที่ต้องตัดสิน · ส่งกลับไม่เกิน 20 แถว เป็นไฟล์:บรรทัด กับข้อสรุป ไม่ยกเนื้อหาไฟล์เกิน 1 บรรทัด

1. ยาวเกิน
   - SKILL.md ที่ยาว 300–400 บรรทัด (เกิน 400 script เตือนให้แล้ว · เพดานของ Anthropic คือ 500)
   - agent .md ที่ยาวเกิน 150 บรรทัด
   - ผลรวม description ดูที่หัวข้อ 8
   - ทุกตัวบอกจำนวนบรรทัดจริงด้วย

2. กระชับได้
   - เนื้อหาที่ควรย้ายไป references/ (ตาราง ตัวอย่าง เช็กลิสต์ยาว)
   - ประโยคที่พูดซ้ำในไฟล์เดียวกัน
   - คำอธิบายเรื่องที่ Claude รู้อยู่แล้ว
   - กฎที่ซ้ำกับ CLAUDE.md หรือ skill อื่นอยู่แล้ว ให้เปลี่ยนเป็นลิงก์แทน
   - บอกว่าแก้แล้วจะลดได้ประมาณกี่บรรทัด

3. ทำงานซ้อน
   - skill หรือ agent 2 ตัวขึ้นไปที่ description จะถูกเรียกจากคำขอเดียวกัน · ยกคำขอตัวอย่าง 1 ประโยคที่ชนกันจริง
   - กฎเรื่องเดียวกันที่เขียนไว้หลายที่ แล้วค่าไม่ตรงกัน (ตัวเลข เพดาน ชื่อเรียก)
   - กฎที่ขัดกันข้าม skill (skill หนึ่งสั่ง อีก skill ห้าม)
   - สิ่งเดียวกันที่เรียกคนละชื่อ
   - skill หรือ command ที่ไม่มี agent หรือ playbook ไหนเรียกใช้

4. คุณภาพตามเช็กลิสต์ Anthropic
   - description เขียนเป็นบุคคลที่ 3 และบอกทั้ง "ทำอะไร" กับ "ใช้เมื่อไร"
   - references/ ลิงก์ตรงจาก SKILL.md ชั้นเดียว ไม่มีไฟล์อ้างอิงที่ลิงก์ต่อไปอีกไฟล์
   - ไฟล์อ้างอิงที่ยาวเกิน 100 บรรทัดมีสารบัญอยู่บนสุด
   - ลิงก์ ชื่อ skill และเลขข้อ (เช่น "ข้อ 0.1") ที่ชี้ไปที่ไม่มีอยู่จริง
   - ให้ทางเลือกเยอะเกินไป แทนที่จะบอกทางหลัก 1 ทาง กับทางสำรอง 1 ทาง
   - ความเข้มงวดตรงกับงานไหม: งานที่พลาดแล้วเสียหายต้องสั่งเป๊ะ · งานที่ทำได้หลายวิธีปล่อยให้ตัดสินเอง
   - ตัวเลข อัตรา วันที่ ชื่อรุ่นโมเดลที่น่าจะหมดอายุ · จุด (รอยืนยัน) ที่ค้างนานเกิน 1 ปี
   - path ใช้ / ทุกที่ ไม่มี \
   - script: จัดการ error เองในตัว · ตัวเลขทุกตัวมีเหตุผลกำกับ · บอกให้ชัดว่า "ให้รัน" หรือ "ให้อ่าน" · บอกว่าต้องติดตั้งอะไร
   - ชื่อ MCP tool เขียนเต็มแบบ Server:tool

5. ความปลอดภัย
   - hooks/hooks.json: แต่ละ hook รันคำสั่งอะไร (hook ทำงานนอก sandbox ด้วยสิทธิ์เต็มของผู้ใช้)
   - .mcp.json · bin/ · monitor: รันอะไร ต่อไปที่ไหน
   - API key · token · รหัสผ่านที่ฝังไว้ในไฟล์
   - tools ของ agent ที่ให้มากเกินงาน (เช่น ตัวที่แค่รีวิวแต่มี Write หรือ Bash)
   - skill ที่อ่านเว็บ อีเมล หรือไฟล์จากภายนอก มีกฎไหมว่าข้อความในนั้นเป็นข้อมูล ไม่ใช่คำสั่ง
   - skill ที่ทั้งเข้าถึงข้อมูลส่วนตัว อ่านข้อมูลจากภายนอก และส่งข้อมูลออกนอกเครื่องได้ ให้ยกขึ้นมาก่อน
   - plugin ที่ไม่ควรเปิดทันทีหลังติดตั้ง ตั้ง defaultEnabled: false ไว้ไหม

6. การส่งมอบ
   - รัน claude --plugin-dir plugins/<plugin> plugin details <plugin> แล้วเทียบกับที่ README บอก
   - แก้ skill แล้วเลขรุ่นใน plugin.json ขึ้นไหม · CHANGELOG มีบันทึกไหม
   - dist ตรงกับ plugins/ ไหม

7. วัดผลจริง (แพง · ใช้ subagent ตัวใหม่ทุกรอบ ไม่ให้ผลปนกัน)
   - ใช้ชุดวัดที่มีอยู่ก่อน ไม่ต้องแต่งโจทย์เอง: `evals/triggers` (เรียกถูกตัว) · `evals/coding` (คุณภาพโค้ด) · `evals/speed` (เวลา · ค่าใช้จ่าย) · แต่งโจทย์เองเฉพาะ plugin ที่ชุดวัดยังไม่ครอบคลุม
   - เรียกถูกตัว: ประโยคที่ควรเรียก 8–10 ประโยค กับประโยคใกล้เคียงที่ไม่ควรเรียกอีก 8–10 ประโยค · นับครั้งที่พลาดทั้ง 2 ฝั่ง
   - มีกับไม่มี skill: เลือก skill หลัก 3 ตัว ตัวละ 3 โจทย์ รันทั้งแบบเปิดและปิด plugin · ให้ผู้ตรวจที่ไม่รู้ว่าผลไหนมาจากแบบไหนเลือกผลที่ดีกว่า
   - skill ที่ไม่มีก็ทำได้ดีเท่ากัน = เสนอให้ตัด
   - ถ้ามีเวลา รันซ้ำด้วยโมเดลเล็ก (Haiku) ดูว่ายังทำตามได้ไหม
   - จด token ที่ใช้ทั้งแบบเปิดและปิด plugin · skill ที่ได้ผลเท่ากันแต่กิน token มากกว่า = เสนอให้ย่อ

8. ประหยัด token
   - โหลดทุก session: ผลรวมความยาว description ของ skill · agent · command ทั้ง plugin · และผลรวมถ้าติดตั้งครบทุก plugin (skill กลางที่ sync ไปทุก plugin นับซ้ำทุกตัว) · เสนอทางลด
   - description ที่เขียนเป็นภาษาไทย (ไทยกิน token ต่อตัวอักษรมากกว่าอังกฤษ)
   - hook: ข้อความที่พ่นเข้า context ต่อครั้ง วัดเป็นตัวอักษร · hook ที่ทำงานทุก prompt หรือทุก tool (UserPromptSubmit · PostToolUse) แล้วพ่นข้อความทุกรอบทั้งที่ไม่จำเป็น · hook เดียวกันที่ซ้ำกันหลาย plugin แล้วทำงานซ้อน
   - ไฟล์ที่ skill สั่งให้อ่านทุกครั้ง (CONTEXT.md · log · IMPROVEMENTS.md): อ่านทั้งไฟล์ หรืออ่านแค่ส่วนที่ใช้ · ไฟล์ที่โตไม่หยุดมีกฎตัดหรือแยกไฟล์ไหม
   - คำสั่งที่พ่นผลไม่จำกัด (cat ไฟล์ใหญ่ · รัน test ทั้งชุด · ls -R) โดยไม่มี head · tail · grep
   - agent หรือ subagent ที่ส่งเนื้อหาไฟล์กลับแทนข้อสรุป · ไม่กำหนดขนาดคำตอบ
   - อ่านไฟล์เดิมซ้ำหลายครั้งในงานเดียว (ดูจาก transcript ของหัวข้อ 7)
   - งานนับ ค้น จัดรูปแบบ ที่ไม่ได้สั่งให้ใช้โมเดลขนาดเล็ก
   - ตาราง ตัวอย่าง เช็กลิสต์ใน SKILL.md ที่ใช้แค่บางครั้ง → ย้ายไป references/
   - งานที่ script ทำได้ในครั้งเดียว แต่ skill ให้ Claude ทำมือทีละขั้น
   - บอกว่าแก้แล้วลดได้ประมาณกี่ตัวอักษร ต่อ session หรือต่อการเรียก 1 ครั้ง

9–12 ใช้ผลและ transcript จากการรันหัวข้อ 7 รอบเดียวกัน ไม่รันแยก · ถ้าไม่ได้ตรวจหัวข้อ 7 ให้เขียนว่า "ยังไม่ได้ตรวจ"

9. ความเร็ว
   - เวลาจริงตั้งแต่ส่งคำขอจนได้ผล · จำนวน tool call และจำนวนรอบต่อ 1 งาน (เทียบรุ่นก่อนกับรุ่นหลังใช้ `evals/speed`)
   - ขั้นที่ควรรันพร้อมกันแต่รันทีละขั้น
   - จุดที่หยุดถามผู้ใช้ทั้งที่ตัดสินเองได้

10. ความเสถียร
   - โจทย์เดิม 3 รอบ ได้ผลรูปแบบและคุณภาพเหมือนกันไหม
   - ผลแกว่งมาก = คำสั่งยังกำกวม · ชี้บรรทัดที่น่าจะเป็นต้นเหตุ

11. รับมือเมื่อพลาด
   - tool ล้ม ไฟล์หาย เน็ตถูกบล็อก: skill บอกทางไปต่อไหม หรือวนลองซ้ำไปเรื่อย ๆ
   - งานที่หยุดกลางทางแล้วรันใหม่ ไม่ทำซ้ำ ไม่เขียนทับของเดิม

12. ผลข้างเคียง
   - ไฟล์ชั่วคราวหรือไฟล์ทดลองที่ทิ้งไว้ที่ราก แทนที่จะอยู่ใน `_to_delete/`
   - แก้ไฟล์นอกขอบเขตงาน

แก้หัวข้อ 8
- แก้ได้เลย เมื่อความหมายและผลลัพธ์เหมือนเดิม:
  - ย้ายตาราง ตัวอย่าง เช็กลิสต์ที่ใช้บางครั้งไป references/ แล้วลิงก์จาก SKILL.md
  - ตัดประโยคที่พูดซ้ำในไฟล์เดียวกัน · กฎที่ซ้ำกับ skill อื่นเปลี่ยนเป็นลิงก์
  - ใส่ head · tail · grep ให้คำสั่งที่พ่นผลไม่จำกัด
  - สั่ง agent และ subagent ให้ส่งกลับแค่ข้อสรุป พร้อมจำกัดจำนวนแถว
  - ระบุโมเดลขนาดเล็กให้งานนับ ค้น จัดรูปแบบ
  - เปลี่ยนการอ่านทั้งไฟล์เป็นอ่านแค่ส่วนที่ใช้ · ใส่กฎตัดหรือแยกไฟล์ให้ log ที่โตไม่หยุด
  - description ภาษาไทย → อังกฤษ ความหมายเดิม คงคำที่คนใช้เรียก skill ไว้
- แก้โค้ด hook ได้ ต่อเมื่อพิสูจน์ว่าทำงานเหมือนเดิม: รัน hook ด้วย input ตัวอย่างทั้งก่อนและหลังแก้ แล้วเทียบผล · พ่นข้อความเฉพาะตอนที่ต้องใช้
- ห้ามแก้ เสนอในรายงานอย่างเดียว: เปลี่ยนเนื้อหา description ที่มีผลต่อการเรียกใช้ · รวม ตัด หรือเปลี่ยนชื่อ skill หรือ agent · ลบเนื้อหาที่ไม่ซ้ำที่ไหน
- ของกลาง SuperUser แก้ที่ plugins/superuser เท่านั้น แล้วรัน `node scripts/sync/sync-superuser.mjs` · ห้ามแก้สำเนาใน plugin อื่น
- แก้เสร็จ:
  - รัน validate-marketplace.mjs อีกรอบ ต้องไม่มี error ใหม่
  - ขึ้นเลขรุ่นหลักสุดท้ายใน plugin.json · เขียน CHANGELOG 1 บรรทัด
  - วัดตัวอักษรก่อน → หลังของทุกไฟล์ที่แก้ ใส่ตาราง "แก้แล้ว" ในรายงาน: ไฟล์ · แก้อะไร · ก่อน → หลัง
  - ยังไม่ build dist ให้ผู้ใช้ตรวจก่อน

ส่งผลเป็นตาราง 1 ตารางต่อ 1 หัวข้อ · หัวข้อที่ไม่เจออะไรเขียนบรรทัดเดียวว่า "ไม่เจอ"
แต่ละแถวมี: ไฟล์:บรรทัด · ปัญหา · แก้อย่างไร · ลดได้เท่าไร (บรรทัด หรือตัวอักษร ถ้าเกี่ยว)
จบด้วย 5 ข้อที่คุ้มแก้ที่สุด เอาข้อที่ทำให้ผลลัพธ์ผิดหรือไม่ปลอดภัยขึ้นก่อน → ข้อที่ลด token ทุก session → แล้วค่อยเรียงตามจำนวนที่ลดได้
```
