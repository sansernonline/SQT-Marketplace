# evals/speed — เทียบความเร็ว plugin 2 รุ่น

แก้ skill แล้วอยากรู้ว่าทีมเร็วขึ้นจริงไหม → รันงานชุดเดิมกับรุ่นก่อนและรุ่นหลัง แล้วเทียบตัวเลข
ตัววัดคุณภาพคือ test ที่ซ่อนไว้ (agent มองไม่เห็น) เร็วขึ้นแต่ test ตก ไม่นับว่าดีขึ้น

## วิธีรัน

```powershell
# เทียบ commit ล่าสุด (รุ่นก่อน) กับไฟล์ที่แก้อยู่ตอนนี้ (รุ่นหลัง) · งาน t1 กับ t4 · รุ่นละ 2 รอบ
node evals/speed/run-bench.mjs --old HEAD --tasks t1,t4 --runs 2

# เทียบ 2 commit · ทุกงาน · รุ่นละ 3 รอบ · จำกัดรอบละ $5
node evals/speed/run-bench.mjs --old f105afc --new HEAD --tasks t1,t2,t3,t4 --runs 3 --budget 5
```

| ตัวเลือก | ค่าเริ่ม | ความหมาย |
|---|---|---|
| `--old` | (ต้องใส่) | รุ่นก่อน เป็น git ref |
| `--new` | ไฟล์ในโฟลเดอร์ตอนนี้ | รุ่นหลัง ใส่ git ref ก็ได้ |
| `--tasks` | `t1,t4` (งานใหญ่ใช้ `t5`) | งานที่รัน คั่นด้วย `,` |
| `--runs` | `2` | รันกี่รอบต่อรุ่น · ผลแกว่งมาก ตัดสินจริงใช้ 5 รอบขึ้นไป |
| `--plugin` | `software-company` | plugin ที่เทียบ |
| `--budget` | `8` | เพดานค่าใช้จ่ายต่อรอบ (ดอลลาร์) |
| `--parallel` | `4` | รันพร้อมกันกี่รอบ |

- ใช้ `claude` ที่ล็อกอินอยู่ในเครื่อง · ค่าใช้จ่ายตัดจากบัญชีนั้น (รอบหนึ่งของ t4 ราว $0.5–1.2)
- ต้องมี Node 22 · Python + `pytest` (สำหรับ t2 · t4)
- ทุกรุ่นโหลด plugin ที่เทียบพร้อม `superuser` และ `sqt-toolkit` จาก repo รุ่นเดียวกัน (`--plugin-dir` ไม่ติดตั้ง dependencies ให้) · รุ่นเก่าที่ยังไม่มี 2 plugin นี้โหลดเท่าที่มี
- ทุกรอบรันในโฟลเดอร์ใหม่ใต้ `_to_delete/bench/runs/` · โหลดเฉพาะ plugin ที่เทียบ ไม่โหลด plugin ที่ติดตั้งในเครื่อง
- agent ได้สิทธิ์แค่อ่าน · แก้ไฟล์ · รัน test · git ในโฟลเดอร์ทดสอบ
- ผลรายรอบอยู่ใน `_to_delete/bench/runs/<งาน>-<รุ่น>-<รอบ>.json` · ตารางสรุปต่อท้าย `RESULTS.md`

## งาน

| งาน | ขนาด | วัดอะไร | test ที่ซ่อนไว้ |
|---|---|---|---|
| `t1` | เล็ก · แก้บั๊กวันที่ไทย | งานเล็กต้องไม่ช้าลง | 7 |
| `t2` | กลาง · คำนวณใบเสร็จ ส่งลูกค้า | ต้องมีรอบ `reviewer` | 15 |
| `t3` | กลาง · 4 โมดูลที่ไม่ขึ้นต่อกัน | การแบ่งงานขนาน | 24 |
| `t4` | ใหญ่ · t2 + t3 รวม 5 ชิ้น ส่งลูกค้า | ขนาน + รีวิว + เพดานรอบ | 39 |
| `t5` | ใหญ่ · 6 โมดูลชิ้นใหญ่ (CSV · จองคิว · cron · semver · router · LRU) ส่งลูกค้า | แตกงานขนานคุ้มจริงไหม | 32 |

**ช่องโหว่ที่ตั้งใจใส่ไว้:** `SPEC.md` ของ t2 · t4 ไม่ได้บอกชนิดของ `discount_pct` แต่ test ที่ซ่อนไว้ส่งทศนิยม (`12.5`) → ทีมที่ดีต้องรับค่ากว้างไว้ หรืออย่างน้อย `reviewer` ต้องทักว่าข้อกำหนดเปิดไว้ (กฎ "Spec gaps" ใน agent `reviewer`)

## อ่านผล

| คอลัมน์ | ความหมาย |
|---|---|
| เวลาเฉลี่ย | วินาทีตั้งแต่เริ่มจนจบ |
| รอบคุยเฉลี่ย | จำนวนรอบที่หัวหน้าทีมคุยกับโมเดล (`num_turns`) |
| ลูกทีมเฉลี่ย | จำนวน subagent ที่เปิด |
| ส่งพร้อมกัน | กี่รอบที่มีการเปิดลูกทีมหลายตัวในข้อความเดียว |
| test ที่ซ่อนไว้ | ผ่าน/ทั้งหมด ของแต่ละรอบ |

ตัดสินใจ: เวลาลดลง ≥ 20% และ test ที่ซ่อนไว้ไม่ตก → เก็บรุ่นใหม่ · test ตก → ย้อนข้อที่เป็นต้นเหตุ · ต่างกันน้อยกว่าที่ผลแกว่ง → รันเพิ่มก่อนสรุป

## เพิ่มงาน

สร้าง `tasks/<ชื่อ>/` มี `TASK.md` (คำสั่งที่ส่งให้ทีม) · `repo/` (โค้ดตั้งต้น) · `hidden/` (`*.test.js` รันด้วย `node --test` หรือ `test_*.py` รันด้วย `pytest`) · ก่อนใช้ ตรวจว่า test ที่ซ่อนไว้ผ่านกับคำตอบอ้างอิง และตกกับโค้ดตั้งต้น
