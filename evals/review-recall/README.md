# evals/review-recall — reviewer เจอข้อผิดที่ฝังไว้ไหม

`reviewer` ของ superuser ([`reviewer.md`](../../plugins/superuser/agents/reviewer.md)) เป็นด่านสุดท้ายก่อนงานถึงผู้ใช้ ถ้ามันพลาด ผู้ใช้จะเป็นคนเจอเอง
ชุดนี้วัด **recall** (ข้อผิดที่ reviewer ชี้ได้ ÷ ข้อผิดที่ฝังไว้ทั้งหมด) บนงาน 8 ชิ้นแบบที่บริษัทซอฟต์แวร์ไทยส่งลูกค้าจริง ฝังข้อผิดไว้ 12 ข้อ ทุกข้อมาจากรายการตรวจใน `reviewer.md` และพิสูจน์ได้จากไฟล์ในเคสเท่านั้น

## ทำไมไม่ใช้ผู้ตัดสิน

เรารู้คำเฉลยก่อนรัน (ไฟล์ บรรทัด ข้อความ) จึงให้คะแนนด้วยการเทียบข้อความธรรมดา ไม่ต้องให้ Claude อีกตัวอ่านรายงานแล้วตัดสิน

- รายงานเดิมได้คะแนนเดิมทุกครั้ง ผลที่แกว่งจึงมาจาก reviewer อย่างเดียว
- ไม่มีค่าผู้ตัดสิน และไม่มีปัญหาผู้ตัดสินคล้อยตามรายงานที่เขียนมั่นใจ
- แนวคิดมาจาก recall test ของ kien-thai (ข้อเสนอ C9 ในผลค้น kien-thai ของรอบ 3.0)

## วิธีรัน

```powershell
# 1. ตรวจชุดเคส ฟรี ไม่เรียก claude
node evals/review-recall/run-review-recall.mjs --verify

# 2. รันจริง เสียเงิน: ทุกเคส เคสละ 1 รอบ โมเดลและ effort ตาม reviewer.md
node evals/review-recall/run-review-recall.mjs --run

# 3. ก่อนตัดสินว่าแก้ reviewer แล้วดีขึ้น: 2 รอบ ติดชื่อชุดผล
node evals/review-recall/run-review-recall.mjs --run --runs 2 --label reviewer-v2
```

| ตัวเลือก | ค่าเริ่ม | ความหมาย |
|---|---|---|
| `--verify` | — | ตรวจชุดเคสอย่างเดียว |
| `--run` | — | รันจริง · ไม่ใส่ตัวรันจะไม่เรียก claude เลย กันเผลอเสียเงิน |
| `--cases` | ทุกเคส | id หรือแค่ส่วนหน้า เช่น `r1,r5` |
| `--runs` | `1` | รอบต่อเคส · ผลแกว่ง ตัดสินจริงใช้ 2 รอบขึ้นไป |
| `--model` | `model:` ใน `reviewer.md` (ตอนนี้ `sonnet`) | โมเดลของ reviewer |
| `--effort` | `effort:` ใน `reviewer.md` (ตอนนี้ `medium`) | ระดับการคิดของ reviewer |
| `--budget` | `1` | เพดานดอลลาร์ต่อการเรียก 1 ครั้ง (`--max-budget-usd`) |
| `--parallel` | `4` | รันพร้อมกันกี่ครั้ง |
| `--label` | `current` | ชื่อชุดผล · ผลรายรอบอยู่ใน `_to_delete/review-recall/<label>/` |
| `--plugins` | `superuser` | plugin ที่โหลด คั่นด้วย `,` · ใส่ `superuser,software-company` ถ้าอยากให้ reviewer ใช้ `code-review-checklist` กับเคสโค้ดด้วย |

`--verify` ตรวจ: `case.json` ครบทุกช่อง · ไฟล์งานรวมไม่เกิน 60 บรรทัด · ข้อความที่ฝังอยู่บรรทัดที่บอกจริงและมีบรรทัดเดียว · prompt ไม่มีข้อความที่ฝังหรือคำอธิบายข้อผิด · ตัวให้คะแนนนับแถวที่อ้างถูก ไม่นับหัวข้อ "ตรวจแล้วไม่เจอปัญหา" ไม่นับแถวกลาง ๆ และแถวของข้อหนึ่งไม่ทำให้อีกข้อในเคสเดียวกันนับว่าเจอ · ครบทั้ง 8 ชนิด · แล้วพิมพ์ prompt ของเคสแรกกับคำสั่งที่จะรัน `--run` ตรวจชุดเดียวกันก่อนเรียก claude ไม่ผ่านก็ไม่รัน

## ทำงานอย่างไร

- 1 เคส 1 รอบ = เรียก `claude -p --agent superuser:reviewer` ใหม่ 1 ครั้ง ได้ reviewer ตัวใหม่ที่ไม่เคยเห็นงาน ทำงานในโฟลเดอร์ชั่วคราวนอก repo ที่มีแค่ไฟล์งาน ไม่มี `case.json`
- reviewer ได้สิ่งที่หัวหน้าทีมส่งจริงตามหัวข้อ "What you get" ใน `reviewer.md`: คำขอของผู้ใช้ · จบเมื่อ · รายชื่อไฟล์ · skill ที่งานต้องทำตาม และไม่ได้รายการข้อผิด
- โหลด plugin จาก repo นี้ด้วย `--plugin-dir` · `--setting-sources project` จึงไม่โหลด plugin ที่ติดตั้งในเครื่อง · `--add-dir` เปิดให้อ่าน references และสคริปต์ของ skill ได้เหมือนตอนใช้จริง เฉพาะโฟลเดอร์ plugin ไม่รวม `evals/`
- reviewer เห็น path ของ plugin ใน repo จึงเดินไปหาคำเฉลยได้ในทางทฤษฎี · ถ้าเครื่องมือของมันแตะ `evals/review-recall` หรือ `case.json` ตัวรันขึ้นคำเตือนและจดในบล็อกผลว่ารอบนั้นใช้ไม่ได้
- ปิด WebSearch และ WebFetch เพราะข้อผิดทุกข้อตรวจได้จากไฟล์ในเคส · Bash ใช้ได้เฉพาะคำสั่งอ่าน คำนวณ และรัน test (`node` `python` `grep` `sed` `cp` ฯลฯ)
- รายงานยาวที่ reviewer เขียนลง `_to_delete/` ของโฟลเดอร์งานตามกติกาของมัน ตัวรันเก็บมารวมกับคำตอบสุดท้ายก่อนให้คะแนน (เฉพาะไฟล์ที่ขึ้นหัว `ผล:`)
- ตัวรันขึ้นคำเตือนเมื่อ claude ไม่ได้รันเป็น reviewer จริง (มีเครื่องมือ Write หรือ Edit) · โมเดลที่ได้ไม่ตรงที่ขอ · หรือรายงานไม่ได้เขียนตามแบบ

## ให้คะแนนอย่างไร

นับเฉพาะแถวปัญหาในรายงาน คือแถวตารางหรือรายการที่มีระดับ สูง กลาง หรือต่ำ · ไม่นับหัวข้อ "ตรวจแล้วไม่เจอปัญหา" และบรรทัด "งานนี้" · ระดับที่ reviewer ให้ไม่มีผลกับคะแนน
ข้อผิด 1 ข้อนับว่า **เจอ** เมื่อแถวใดแถวหนึ่งเข้าทางใดทางหนึ่ง:

| ทาง | ตัวอย่างที่นับ |
|---|---|
| ที่อยู่ | `quotation.md:17` · `shipping.test.mjs:10-12` · `faq.md บรรทัด 10` · เคสที่มีไฟล์เดียว เขียนแค่ `บรรทัด 17` ก็นับ |
| ข้อความตรงตัว | ยกข้อความที่ฝังไว้มาตรง ๆ เช่น `[ใส่ชื่อ]` |
| คำสำคัญ | มีคำใน `keywords` ของข้อนั้นตั้งแต่ 2 คำขึ้นไปในแถวเดียวกัน |

ก่อนเทียบ ตัวรันทำทุกอย่างเป็นตัวเล็ก ตัด `` ` `` `*` และเครื่องหมายคำพูด และตัดจุลภาคหลักพัน (`1,500` นับเท่ากับ `1500`)

## ค่าใช้จ่าย

- สมมุติฐาน: 1 รอบ = 8 เคส × reviewer 1 ครั้ง = เรียก claude 8 ครั้ง · `--runs 2` = 16 ครั้ง · ไม่มีผู้ตัดสิน
- ทุกครั้งหยุดที่เพดาน `--budget` (ค่าเริ่ม $1) จึงไม่เกิน $8 ต่อรอบ · ตัวเลขนี้คือเพดาน ไม่ใช่ราคาประเมิน
- ราคาจริงขึ้นกับโมเดลและจำนวน token ที่ reviewer อ่านและเขียน ดูราคาต่อ token ที่หน้า [Pricing ของ Claude](https://platform.claude.com/docs/en/about-claude/pricing) (ตรวจลิงก์ 2026-10-23) · ตัวรันจด `total_cost_usd` ที่ claude รายงานไว้ในหัวบล็อกของ `RESULTS.md` ใช้ประเมินรอบถัดไปได้

## อ่านผล

- หัวบล็อกใน `RESULTS.md` เช่น `เจอ 10/12 (83%)` คือ recall รวม · ตาราง 1 แถวต่อเคสบอกข้อที่พลาด
- บรรทัด "แยกตามชนิด" บอกว่าข้อตรวจไหนใน `reviewer.md` อ่อน ดูคอลัมน์ขวาสุดของตารางเคสด้านล่าง
- คอลัมน์ "แถวปัญหาที่รายงาน" ใช้ดูว่า recall มาจากการรายงานทุกอย่างหรือเปล่า · recall ขึ้นพร้อมแถวพุ่ง แปลว่า reviewer หว่าน ไม่ได้ตรวจเก่งขึ้น
- รอบเดียวใช้ดูแนวโน้ม · จะตัดสินว่าแก้ `reviewer.md` แล้วดีขึ้น ให้รัน `--runs 2` ขึ้นไปทั้งก่อนและหลังแก้ แยกด้วย `--label` แล้วเทียบ
- ข้อที่พลาด เปิด `_to_delete/review-recall/<label>/<เคส>-<รอบ>.json` ดูรายงานเต็มก่อน แล้วแยกว่า reviewer ไม่ได้ตรวจ หรือตรวจแล้วแต่ไม่ได้ลงแถว · 2 แบบนี้แก้คนละที่ใน `reviewer.md`

## เพิ่มเคส

เคสที่ดีที่สุดมาจากของจริง: งานที่ reviewer ให้ผ่านแล้วผู้ใช้ยังเจอข้อผิด ตัดข้อมูลลูกค้าออก แล้วทำเป็นเคสใหม่ ตามขั้น "พิสูจน์ว่ามันจับได้จริง" ของ [`repeated-mistakes-to-checks`](../../plugins/superuser/skills/repeated-mistakes-to-checks/SKILL.md) · เคสนั้นควรพลาดบน reviewer รุ่นที่ปล่อยข้อผิดออกไป และเจอบนรุ่นที่แก้แล้ว

1. สร้าง `cases/r<เลข>-<ชื่อ>/` วางไฟล์งานให้เหมือนงานจริง รวมทุกไฟล์ไม่เกิน 60 บรรทัด และบรรทัดที่ฝังต้องไม่มีปัญหาอื่น (ไม่งั้นแถวที่ชี้ปัญหาอื่นจะนับว่าเจอ)
2. เขียน `case.json` ตามแบบในเคสที่มีอยู่ ช่องที่ต้องมี: `id` (ตรงชื่อโฟลเดอร์) · `kind` · `request` · `done_when` · `planted`
3. รัน `--verify` ให้ขึ้น "ใช้ได้ทุกเคส" ก่อนรันจริง

กติกาของช่องใน `case.json`:

- `request` เขียนแบบที่ผู้ใช้พิมพ์จริง ให้ข้อมูลที่งานต้องใช้ครบ ตัวเลขในงานที่มาจากคำขอจะได้ไม่ถูกนับเป็นตัวเลขไม่มีแหล่ง
- `done_when` เขียนแบบที่ playbook เขียน "จบเมื่อ" ห้ามใบ้ข้อผิด
- `skills` ไม่ใส่ = `human-writing`
- `planted` 1–2 ข้อต่อเคส · `type` เป็น 1 ใน 8 ชนิด: `wrong-total` · `no-source` · `placeholder` · `old-term` · `weak-test` · `thai-connectives` · `broken-link` · `era-mix` · ชนิดใหม่ให้เพิ่มใน `TYPES` ของตัวรัน
- `where.line` เป็นเลขเดียวหรือช่วง `[10, 12]` · `where.quote` ต้องอยู่ในช่วงนั้น มีบรรทัดเดียวในทุกไฟล์ของเคส และไม่อยู่ในคำขอหรือจบเมื่อ
- `keywords` เลือกคำที่โผล่เฉพาะในแถวที่พูดถึงข้อนี้ เช่น ตัวเลขที่ถูก รหัสกฎ คำเดิม · เลี่ยงคำกลาง ๆ 2 คำที่มักมาคู่กัน เช่น "ไม่มีแหล่ง" กับ "ที่มา"
